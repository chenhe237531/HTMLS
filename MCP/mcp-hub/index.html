01

四种形态

大家口中的「MCP Hub」其实混了四件事。先分清形态，再谈哪个网站好用。

1 · 注册表 Registry

存元数据与来源，是「这条记录是否真实存在」的权威口径。官方 Registry 只收元数据，不负责安装体验。

2 · 目录 Directory

以浏览和搜索为主，靠抓取或投稿聚合，通常带分类、评分、使用量。规模最大，质量最参差。

3 · 市场 Marketplace

在目录之上加交易与分发：一键安装、托管运行、OAuth 代管、容器镜像。省事，但把信任交给了平台。

4 · 网关 Gateway

把多个 Server 聚合成一个端点，做鉴权、路由、审计、限流。装很多时才值得，代价是多一个单点。

一个容易踩的坑 「目录里有」不等于「可信」。大多数注册表和目录只收录元数据，不做安全审查；真正跑起来的风险，取决于你给它的权限和它返回的内容。第 05 节给了一份最小检查清单。
02

怎么选：按问题找入口

你的问题先去哪里为什么
「有没有某个能力的 Server？」Glama / PulseMCP / mcp.so索引量大，支持按分类与关键词搜，Glama 还带质量分级
「这条记录是不是官方的？」官方 MCP Registry / GitHub MCP Registry元数据源头，发布者与仓库信息可核对
「我要安全隔离地跑」Docker MCP Catalog容器化、签名、带 SBOM 与来源信息
「我就在 Trae 里，想一键装」Trae 内置 MCP 市场集成度最高，装完即可挂到智能体
「我不想自己管 OAuth / 部署」Smithery 等托管型市场代管连接与凭证（注意其服务调整公告）
「我装了十几个，上下文炸了」MetaMCP / 企业网关聚合端点、按命名空间裁剪工具、统一鉴权审计
「国内网络与合规」火山引擎 / 腾讯云 MCP 市场云厂商托管，网络与计费体系更匹配
推荐路径 用 目录 发现 → 用 官方 Registry 核对来源 → 用 Docker / 客户端市场 安装 → 超过 3 个再用 网关 收口。不要从「排行榜第一」直接装。

05

安全与治理

MCP 的风险不在「协议」，而在「你给了它什么权限、它把什么内容带回了上下文」。目录只负责告诉你它存在。

五步流程

  1. 发现

    用 Glama / PulseMCP / mcp.so 按能力搜索，先收集 3–5 个候选，不要只看第一名。

    产出：候选清单（名称 + 仓库 + 传输方式）
  2. 核对

    到官方 Registry 或 GitHub 确认发布者、仓库、最近更新；找不到源码的直接淘汰。

    产出：来源可信度判断
  3. 评估

    看它暴露多少 tool、需要什么凭证、是否可只读、会不会把外部文本直接喂回模型。

    产出：权限最小化方案
  4. 安装

    优先客户端内置市场或容器化安装；本地 stdio 的，先确认命令与参数来源。

    产出：可回滚的配置（记下原始 JSON）
  5. 治理

    超过 3 个 Server 就考虑网关；定期看日志、清理不用的、升级有安全公告的。

    产出：季度盘点记录

最小检查清单

不要把「目录收录」当安全背书 大多数目录是自动化抓取，不做代码审计；有公开扫描指出大量公共 Server 存在 SSRF 一类问题。默认假设它可能被攻破，按最小权限接。

Trae 项目级配置示例

放在项目根的 .trae/mcp.json。包名与参数以各 Server 官方说明为准；示例只演示结构，不含任何密钥。

.trae/mcp.json
{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp"]
    },
    "playwright": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    }
  }
}

三条使用原则

一次只加一个

加完立刻用真实任务验证；一次装五个，出问题不知道是谁。

默认只读

数据库、文件、云资源都先给只读账号；需要写时再单独开一个。

三个以上就收口

用网关聚合，按任务切换命名空间，避免工具列表长期膨胀。

一句话建议 先用 Trae 内置市场装 2–3 个高频 Server（浏览器、文档、代码托管），用 Glama 做候选发现、官方 Registry 做来源核对；等你开始觉得「工具太多、权限太散」，再上 MetaMCP。
