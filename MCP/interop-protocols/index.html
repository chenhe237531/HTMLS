MCP 之外的协议栈

MCP 解决的是「Agent 怎么用工具」。但 Agent 还要互相对话、被编辑器驱动、把界面推给用户、收钱、被发现。这些是不同层的问题，也就长出了不同的协议。

01

为什么不止 MCP

把 MCP 当成「AI 的 USB-C」是对的，但 USB-C 只解决插头。Agent 生态还需要「谁和谁说话」「界面怎么变」「钱怎么付」「怎么被找到」。

MCP 管什么

Agent ↔ 工具 / 数据 / 提示模板。一次请求、一次返回，通常无状态。

MCP 不管什么

长任务协商、Agent 间委派、多轮人工确认、流式 UI、支付授权、能力发现。

于是长出了什么

A2A 管横向协作，ACP 管编辑器驱动，AG-UI 管前端，A2UI 管界面生成，AP2/UCP 管交易。

先记住一件事：同名不同物 现在有三个「ACP」：Agent Client Protocol（Zed/JetBrains，编辑器驱动 Agent）、Agent Communication Protocol（IBM，已并入 A2A）、Agentic Commerce Protocol（OpenAI/Stripe，代理结账）。看到缩写先问「哪个 ACP」。
本页的取舍 只收录 2026-10 仍有公开规范、实现或明确治理归属的协议。已归档的 IBM ACP 仍然收录，因为它是理解 A2A 合并史的关键；纯企业内部私有协议不展开。
02

03

协议卡片

每个协议只回答一个问题。先看它属于哪一层，再看优缺点，最后看 2026-10 的成熟度。

显示 14 / 14 个协议

MCP
Model Context Protocol
生产可用

Agent 连接工具、数据与提示模板的标准。stdio 与 Streamable HTTP 两种传输，工具 / 资源 / 提示三类原语。

优点
  • 事实标准，客户端与服务端生态最大
  • 服务端实现简单，权限边界清晰
局限
  • 以无状态调用为主，长任务协商弱
  • UI、支付、发现需其它协议补位
AAIF / LFAnthropic 起源规范 →
A2A
Agent2Agent Protocol
生产可用

让独立 Agent 发现彼此并委派任务：Agent Card 声明能力，Task 有生命周期，支持 SSE 与异步回调。

优点
  • 跨厂商协作，v1.0 已被云厂商原生支持
  • 「不透明执行」保护 Agent 内部实现
局限
  • 复杂多轮协商与双向流仍在路线图
  • 发现质量取决于目录与 Agent Card
AAIF / LFGoogle 起源规范 →
ACP（Agent Client）
Agent Client Protocol
生产可用

编辑器 / 客户端驱动编码 Agent 的 JSON-RPC 协议：以 Session 为单位，返回结构化事件而非终端文本。

优点
  • 一次实现接入多个编辑器（Zed / JetBrains / Neovim）
  • 结构化 diff、工具调用，替代 PTY 抓屏
局限
  • 以本地 stdio 为主，远程支持仍在开发
  • 名字与另外两个 ACP 冲突，沟通成本高
Zed + JetBrains编码场景规范 →
AG-UI
Agent–User Interaction Protocol
生产可用

Agent 与用户前端之间的双向事件协议：流式文本、共享状态、前端工具调用、人工介入。

优点
  • 前端集成成熟（CopilotKit），支持 HITL
  • 可与 MCP / A2A 握手，作为统一入口
局限
  • 需要改造前端，事件模型有学习成本
  • 它是交互通道，不是 UI 描述规范
CopilotKit事件流规范 →
A2UI
Agent to UI Protocol
候选 / 早期

Google 的声明式生成式 UI 规范：Agent 用 JSONL 流式描述组件与数据模型，客户端用原生组件渲染。

优点
  • 平台无关、渐进渲染，不依赖 WebView
  • 可绑定 AG-UI / A2A / MCP 传输
局限
  • v1.0 仍为候选，规范仍在演进
  • 需要 renderer 与组件目录，生态未定
Google生成式 UI规范 →
MCP-UI
MCP 的 UI 扩展
早期

Microsoft + Shopify 推动的生成式 UI 标准，用 iframe 承载可交互界面，作为 MCP 的扩展。

优点
  • 复用现有 Web 技术与组件
  • 交互能力强，适合复杂表单
局限
  • iframe 的信任与安全边界需额外设计
  • 与 A2UI / Open-JSON-UI 形成竞争
Microsoft + Shopifyiframe规范 →
AP2
Agent Payments Protocol
早期 / 标准化中

用可验证数字凭证（Checkout / Payment Mandate）表达「用户授权 Agent 买什么、花多少」，覆盖人在与人不在。

优点
  • 授权可验证、可举证，适合争议处理
  • 与 UCP / A2A 组合，支付方式无关
局限
  • 概念与角色多，接入复杂
  • 商户与支付机构改造成本高
FIDO 标准化Google 起源规范 →
UCP
Universal Commerce Protocol
早期 / 早期访问

Google 与 Shopify 推动的商业协议：产品发现、能力协商与结账，站点通过 /.well-known/ucp 声明能力。

优点
  • 覆盖「发现 → 结账」全链路
  • 与 AP2 组成信任层，职责清晰
局限
  • 结账仍在早期访问，覆盖有限
  • 商户需要改造商品与结账接口
Google + Shopify商业规范 →
ACP（Commerce）
Agentic Commerce Protocol
路线不确定

OpenAI 与 Stripe 的代理结账协议：商家提供产品 feed，Agent 在对话内完成下单；规范仍在，产品入口有收缩。

优点
  • 与 ChatGPT / Stripe 支付链路结合紧
  • 产品 feed 规范具体，落地路径清楚
局限
  • Instant Checkout 据报 2026-03 结束，前景待观察
  • 强依赖单一平台流量
OpenAI + Stripe结账文档 →
x402
HTTP 402 支付协议
早期 / 场景明确

复用 HTTP 402 状态码，让 Agent 在请求资源时直接完成支付，结算可在链上。

优点
  • 对机器友好：无需账号、按次付费
  • 适合 API、内容与微支付
局限
  • 链上结算带来合规与波动问题
  • 企业采购与退款流程不成熟
x402 Foundation微支付规范 →
AGNTCY
Internet of Agents 基础设施
早期 / 组件完整

Cisco 捐给 Linux Foundation 的 Agent 互联网栈：OASF 能力描述、Agent Directory、SLIM 消息与可观测。

优点
  • 补齐「发现 + 身份 + 传输 + 观测」
  • 开放治理，适合跨组织场景
局限
  • 组件多、集成与运维成本高
  • 采用仍在早期，工具链不如 A2A 成熟
Linux FoundationCisco 起源官网 →
ANP
Agent Network Protocol
实验 / 社区

面向开放网络的去中心化 Agent 协议，用 DID 与 W3C 标准做身份、发现与点对点协作。

优点
  • 身份自主、无需中心目录
  • 适合开放网络与跨组织协作
局限
  • 规范与实现资料有限，生态小
  • 企业治理与合规路径不清晰
社区DID官网 →
Agent Protocol
Agent 服务化 REST 规范
局部采用

LangChain 提出的 Agent 服务器接口：用 runs / threads 把 Agent 暴露成标准 REST API，便于部署与托管。

优点
  • 部署即 API，客户端无需理解内部框架
  • 与 LangGraph 生态衔接自然
局限
  • 跨厂商影响力有限，平台各自扩展
  • 解决的是部署接口，不是协作语义
LangChainREST仓库 →
FIPA ACL / KQML
经典 Agent 通信语言
历史

上世纪末的多 Agent 通信标准，基于「言语行为」定义 inform、request、propose 等消息类型与语义。

优点
  • 语义理论完整，适合形式化研究
  • 对后来协议的消息设计有影响
局限
  • 非 LLM 时代设计，实现重
  • 生态基本消失，不适合新产品
历史学术资料 →

05

如何组合

真实系统不会只用一个协议。下面是三种最常见的组合，按「谁发起、谁执行、钱在哪」来拆。

场景 A · 编辑器里的编码 Agent

[Zed / JetBrains] │ ACP（Session + 结构化事件） ▼ [Coding Agent] │ MCP（工具 / 数据） ▼ [Repo · Shell · Browser] 旁路：Agent 自身可通过 A2A 调用远端 Agent。

为什么是这套：编辑器只关心「驱动一个 Agent」；工具接入交给 MCP；跨 Agent 再用 A2A。三者正交。

场景 B · 面向用户的产品

[Web / App] │ AG-UI（流式文本、状态、前端工具） ▼ [Agent Backend] │ MCP │ A2A ▼ ▼ [Tools / Data] [Specialist Agents] 界面内容：A2UI / MCP-UI（可选）

为什么是这套：AG-UI 管交互通道，A2UI 管「Agent 生成界面」；后者不是前者的替代。

场景 C · 代理购物 / 交易

[User] │ 授权（AP2 Mandate） ▼ [Shopping Agent] ── A2A ──▶ [Merchant Agent] │ │ UCP：目录 / 结账 │ ▼ │ [Merchant Backend] └── x402（按次资源付费，可选）

为什么是这套：UCP 管购物流程，AP2 管支付授权，x402 管机器微支付；三者不是互斥。

80% 场景的最小组合 MCP + A2A + AG-UI 已经覆盖「工具、协作、界面」三件事。只有当你开始收钱，才需要 AP2 / UCP / x402。

07

趋势判断

2026 年的主线不是「更多协议」，而是「分层 + 合并 + 治理归位」。下面六条，按确定性从高到低。

时间线：两年内发生了什么

  1. MCP 发布2024-11

    Anthropic 把「工具接入」标准化，迅速成为事实标准。

  2. A2A 发布2025-04

    Google 提出 Agent 间发现与委派，随后捐赠给 Linux Foundation。

  3. IBM ACP 并入 A2A2025-08

    Agent Communication Protocol 停止独立发展，社区向 A2A 收敛。

  4. Zed 发布 ACP（Agent Client）2025-08

    编辑器与编码 Agent 之间的标准接口，JetBrains 于 2026-02 加入共同维护。

  5. AP2 发布2025-09

    代理支付授权协议，后续捐给 FIDO Alliance 做标准化。

  6. A2UI 发布2025-11

    生成式 UI 的声明式规范，2026-06 进入 v1.0 候选。

  7. ACP Registry 上线2026-01

    Agent 一次注册，所有 ACP 客户端可见，补上分发层。

  8. A2A v1.02026-03

    首个稳定版，云厂商原生支持，进入生产使用。

  9. A2A 加入 AAIF2026-08

    与 MCP、goose、AGENTS.md 同属一个基金会，两层治理统一。

  10. A2A CLI2026-10

    让 shell / CI 也能直接发现与调用 A2A Agent。

六条判断

1 · 分层已经稳定

工具（MCP）、Agent（A2A）、用户（AG-UI）、交易（AP2/UCP）四层各有赢家，短期不会再出现「一个协议包打天下」。

2 · 治理向基金会集中

MCP 与 A2A 同属 AAIF，AP2 进入 FIDO，AGNTCY 在 LF。中立治理成为采购的硬指标。

3 · 协议与产品解耦

ACP 注册表、A2A CLI 让「Agent 实现一次、到处可调」变成现实，客户端不再绑定单一 Agent。

4 · 生成式 UI 仍在混战

A2UI、MCP-UI、Open-JSON-UI 三种路线并存，AG-UI 做传输层。2026 年内很难收敛。

5 · 支付协议分层

UCP 管购物流程，AP2 管授权与举证，x402 管机器微支付。商业入口收缩（ChatGPT Instant Checkout）提醒：协议不等于需求。

6 · 发现与安全是短板

Agent Card、Directory、DID 三套发现机制未统一；身份、权限、审计将决定企业能否规模上线。

风险与反模式 同名混淆（三个 ACP）：文档必须写全称；过度设计：单 Agent 场景不需要 A2A；把协议当需求：先有交易场景，再谈 AP2；忽略安全：跨 Agent 调用会放大 prompt injection 与越权。
接下来最值得观察的三件事 ① A2A 的多轮协商与双向流能否在 v1.1 落地；② Agent 目录/身份是否会出现事实标准；③ 生成式 UI 是否会像 MCP 一样出现「赢家通吃」。
