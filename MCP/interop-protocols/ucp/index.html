Universal Commerce Protocol2026-10-31

UCP：让 Agent 学会买东西

UCP 是一套面向代理商业的开放协议：商家发布能力，Agent 读取并协商，然后建购物车、结账、付款。它把「AI 能不能在你店里下单」从定制集成变成标准动作。

01

它是什么

一句话：UCP 是商家与 Agent 之间的「商业能力协商协议」。它定义商家如何声明能力、Agent 如何发现、双方如何用一个共同的交集完成购物车、结账、订单与支付。

对商家

在 /.well-known/ucp 发布一份 profile，声明支持的能力、版本、端点与支付方式，不必为每个 Agent 做定制集成。

对 Agent

读 profile、算能力交集、按版本调用；结账与支付走标准原语，而不是抓页面。

对生态

开放、可扩展、传输无关；商家始终是 merchant of record。

时间线（不到一年）

  1. 2026-01-11 · 在 NRF 发布

    Google 与 Shopify 共同发起，Etsy、Wayfair、Target、Walmart 等参与；20+ 公司背书。

  2. 2026-01 → 08 · 四个规范版本

    2026-01-11、2026-01-23、2026-04-08、2026-08-25，迭代速度很快。

  3. 2026-05 · Universal Cart

    Google I/O 推出跨商家购物车，结账由 UCP 驱动；在 AI Mode 与 Gemini 中落地。

  4. 2026-09 · Shopify 开放浏览器内结账

    通过 WebMCP 把 UCP 能力暴露给运行在买家浏览器里的 Agent。

容易混淆 UCP 不是 ACP（OpenAI/Stripe 的 Agentic Commerce Protocol），也不是 AP2。UCP 管「怎么买」，AP2 管「谁授权」，x402 管「怎么付」。
02

为什么需要

让 Agent 在电商里下单，要同时解决五件事。过去每一件都靠定制对接，UCP 试图把它们标准化。

问题定制集成时代UCP 的做法
发现Agent 不知道这家店支持什么/.well-known/ucp 声明能力与端点
协商版本与字段对不上就失败能力交集 + 日期版本，双方取共同支持
购物车每家接口不同Cart 能力：创建、读取、更新、取消
结账抓页面或私有 APICheckout 能力：会话、金额、税费、履约
支付写死某一种支付方式Payment Handler 协商（Google Pay / Shop Pay / PSP）
人工接管Agent 卡住就失败动态 handoff，把控制权交回用户或商家页面
它不解决的事 商品质量、价格竞争力、履约能力、退款政策——这些仍是商家自己的事。UCP 只让「接入」变便宜，不保证「卖得好」。
03

架构：一份 profile 解决发现

UCP 的核心设计是「profile 驱动」：商家把支持的能力、服务端点、支付方式写在一个公开 JSON 里，Agent 读它，而不是读文档或猜接口。

https://shop.example.com/.well-known/ucp（示意）
{
  "ucp": {
    "version": "2026-08-25",
    "services": {
      "dev.ucp.shopping": [{
        "version": "2026-08-25",
        "transport": "rest",
        "endpoint": "https://shop.example.com/ucp",
        "schema": "https://ucp.dev/2026-08-25/services/shopping/rest.openapi.json"
      }]
    },
    "capabilities": {
      "dev.ucp.shopping.checkout": [{ "version": "2026-08-25" }],
      "dev.ucp.shopping.cart":     [{ "version": "2026-08-25" }],
      "dev.ucp.shopping.catalog":  [{ "version": "2026-08-25" }]
    },
    "payment_handlers": {
      "com.google.pay":       [{ "version": "2026-08-25" }],
      "com.shopify.shop_pay": [{ "version": "2026-08-25" }]
    }
  }
}

四个关键概念

概念作用例子
Profile商家能力与端点的公开声明/.well-known/ucp
Service一组能力的承载端点与传输dev.ucp.shopping
Capability反向域名 + 日期版本的原子能力dev.ucp.shopping.checkout
Payment Handler可被协商的支付方式Google Pay、Shop Pay、PSP

协商：服务端选择

Agent 通过 UCP-Agent 头带上自己的 profile 地址；商家取双方能力的交集，选版本与能力，并在每个响应里再次声明当前生效的版本。这样 Agent 永远知道这次会话到底支持什么。

四种传输

  • REST：最通用，HTTP + JSON
  • MCP：Agent 工具式调用
  • A2A：Agent 间委派
  • Embedded：iframe 内嵌结账

版本策略

日期版本（YYYY-MM-DD），按精确版本协商；破坏性变更要求新版本，避免静默漂移。

04

一次结账的流程

STEP 1发现 profile STEP 2协商能力 STEP 3购物车 STEP 4结账会话 STEP 5支付与订单
Agent (Platform) Business (Merchant) │── GET /.well-known/ucp ──────────────▶│ │◀─ profile: services / caps / pay ─────│ │ │ │── POST cart（UCP-Agent: profile） ───▶│ │── POST checkout-sessions ────────────▶│ │◀─ totals / fulfillment / status ──────│ │ │ │ [payment handler 协商] │ │── complete（凭证 / Mandate） ────────▶│ │◀─ order + receipt ────────────────────│

Step 1 · 发现

Agent 读取商家 profile；如果商家已在 Google 等平台注册，平台也可能缓存能力信息，但 profile 仍是事实源。

Step 2 · 协商

双方取能力交集：版本、能力、支付方式。没有交集就不发起结账，避免「调到一半才发现不支持」。

Step 3 · 购物车

通过 Cart 能力创建/更新购物车。商品可以来自 Catalog 搜索，也可以由用户指定 SKU。

Step 4 · 结账会话

Checkout 能力创建会话，返回金额明细（商品、折扣、运费、税费）、履约选项、必须的链接（隐私政策、服务条款）与状态。需要用户介入时，返回 handoff。

Step 5 · 支付与订单

选择协商通过的 payment handler，提交支付凭证（或 AP2 Mandate），完成结账；随后通过 Order 能力查询状态、取消或售后。

关键：商家仍是 merchant of record UCP 不让平台变成卖家。资金通过商家的 PSP 结算，退货、客服、税务仍归商家。

06

支付与 AP2

Payment Handler

支付方式也是协商出来的：Google Pay、Shop Pay、各 PSP。商家声明支持哪些，Agent 选一个可用的，避免写死。

AP2 扩展

UCP 的 checkout 可挂 AP2 Mandates 扩展：用 Checkout / Payment Mandate 证明用户授权，尤其适合人不在场的代理购买。

两种结账形态

  • Native checkout：在 Agent / 平台界面内完成，使用商家的 checkout 会话与支付 handler。
  • Embedded checkout：把商家结账页以 iframe 嵌入（Embedded Commerce Protocol），适合品牌定制强的商家。
安全边界 支付凭证只在协商通过的 handler 与商家/PSP 之间流转；平台不应长期保存卡号。AP2 的 Mandate 只证明授权，不携带卡号。
07

生态与状态

谁在推动

UCP 由 Google 与 Shopify 共同发起，早期参与方包括 Etsy、Wayfair、Target、Walmart；背书名单覆盖 Adyen、American Express、Stripe、Visa、Mastercard、Best Buy、Home Depot 等 20+ 公司。ucp.dev 的协作方名单还在扩展。

Google 侧

  • AI Mode 与 Gemini 内的直接结账（部分商家）
  • Universal Cart：跨商家购物车
  • 从美国扩展到加拿大、澳大利亚、英国
  • 后续进入 YouTube、酒店与本地外卖

Shopify 侧

  • UCP 兼容的 MCP Server
  • 2026-09 开放 WebMCP 结账，支持浏览器内 Agent
  • Universal Cart API 早期访问
  • 商家仍是 merchant of record

成熟度判断

维度状态（2026-10）
规范公开、Apache 2.0、四个日期版本；最新 2026-08-25
实现Google 与 Shopify 有生产路径；大量商家仍在早期访问 / 等待名单
覆盖美国优先，逐步扩到加、澳、英；品类从零售扩到酒店、外卖
生态支付、云、零售多方参与，但实际可用性取决于具体商家
风险版本迭代快，字段与能力可能变化
“支持 UCP”含金量不同 发布 profile 只是声明能力；是否真的能完成结账，要看 checkout 端点、支付 handler 与履约是否打通。接入前请用真实商品跑通一次。
08

优势与局限

优势

  • 发现与协商标准化，接入成本从「每家定制」变成「读 profile」
  • 传输无关：REST / MCP / A2A / Embedded 可换
  • 能力可组合，垂直需求用扩展，不污染核心
  • 商家保持 merchant of record，平台不夺走客户关系
  • 与 AP2 集成，支持人不在场的授权购买
  • 开放许可与多方共建，降低单一厂商锁定

局限

  • 仍处早期访问，覆盖商家有限
  • 8 个月四个版本，规范仍在快速变化
  • 商家要改商品、库存、结账、支付与履约，工程量大
  • 支付 handler 碎片化，跨 PSP 体验不一致
  • Google / Shopify 的事实主导，可能形成新的依赖
  • 协议只解决「怎么买」，不解决信任、比价与售后
别把「协议」当「渠道」 接上 UCP 不等于自动获得流量。它只是让 Agent 能买；用户会不会来，取决于商品、价格与平台分发。

与其它协议

协议解决什么与 UCP 的关系
UCP商品发现、购物车、结账、订单本页主角，商业流程层
AP2用户授权与支付凭证UCP 的支付扩展；UCP 流程 + AP2 授权
x402按请求付款可作为支付轨道；与 UCP 结账并行，不替代流程
ACP（Commerce）OpenAI/Stripe 的产品 feed 与对话内结账同层竞争，目标相似，生态不同
MCP工具与数据接入UCP 的一种传输绑定；Shopify 用 MCP 暴露商店能力
WebMCP浏览器内 Agent 调用页面工具Shopify 用它把 UCP 能力暴露给买家浏览器里的 Agent
用户意图 │ ▼ UCP：发现 → 协商 → 购物车 → 结账 │ ├── AP2：授权（Mandate） │ └── Payment Handler：Google Pay / Shop Pay / PSP / x402 │ ▼ 商家订单（merchant of record）
一句话 UCP 负责「把商品放进购物车并完成结账」，AP2 负责「证明用户允许这笔钱」，支付 handler 负责「钱怎么走」。
