01 · 概览

它解决的是什么问题

按仓库 README / CHANGELOG / Issue 整理

聊天记录是很多人真正的工作知识库，但它锁在客户端里：搜索弱、导出难、AI 也读不到。 im-mcp 的做法是把「解密 → 建索引 → 暴露成 MCP 工具」这一段全部放在本机完成， 让 Claude Desktop、Cursor、Cline、Pi 这类客户端像调用普通工具一样查询历史消息。

本地

不上传、不依赖云服务；MCP 服务通过 stdio 与客户端通信，没有开放端口。

只读

不发送消息、不改原库；同步类工具只重建本地快照与索引。

快

SQLite + FTS5 倒排索引，README 自述「毫秒级响应」（未附独立基准测试）。

一个容易忽略的细节：检索读的是解密快照目录（~/.wechat_mcp/decrypted/ 等）， 而不是微信/钉钉的原库。原库因此不会被写坏，但磁盘上会多出一份明文副本 —— 这是后面安全一节的核心。

02 · 项目定位

定位：给 Agent 用的「聊天档案检索层」

它是

  • 一个 MCP Server，向 AI 客户端暴露 34 个只读工具
  • 一套本地 ETL：解密 → 解析消息格式 → 建 FTS5 索引
  • 一套交换式 CLI：wechat-init / dingtalk-init / im-clean
  • 一份面向 Agent 的运维规范（skills/im-mcp/SKILL.md）

它不是

  • 不是聊天记录导出器 / 备份工具（没有批量导出 UI）
  • 不是爬虫，也不调用任何官方 API 或云端接口
  • 不是多用户服务，没有鉴权、审计、租户隔离
  • 不是「装上就永远能用」—— 客户端升级可能打断解密

名字里的 im 指 instant messaging。仓库 README 里把微信写作「绿泡泡」、钉钉写作「DuangDuang」， 代码、CLI 与工具名仍然使用 wechat / dingtalk。推测是规避关键词检索的写法， 不影响功能，但读文档时需要对上号。

03 · 工作原理

从加密数据库到一次 AI 回答

  1. STEP 1读取加密库微信 WCDB / 钉钉 128 分表，原始文件保持不动SQLite + WAL
  2. STEP 2取得密钥并解密内存扫描或 passphrase 派生，离线校验后落盘~/.wechat_mcp/
  3. STEP 3解析与 ETL压缩消息体解压、XML/卡片解析、会话与联系人归一app.db
  4. STEP 4建 FTS5 索引倒排索引支撑全文检索与 snippet 命中上下文FTS5
  5. STEP 5MCP 工具调用stdio 上的 JSON-RPC，Agent 拿到结构化结果再总结wechat-mcp / dingtalk-mcp

两条解密路径，复杂度差别很大

微信 需要密钥，Windows 要管理员权限
Windows
运行时扫描 Weixin.exe 的 Config.Cipher，动态提取 Salt 密钥；终端需管理员身份，且微信已登录
macOS
系统原生 CommonCrypto（CCCrypt）零额外依赖解密；微信 4.1+ 可传 --passphrase（64 位 hex），走 256,000 轮 PBKDF2
校验
离线 HMAC 校验，失败即判定密钥不对，不会产出坏库
钉钉 纯 Python，普通权限即可
密钥
读取用户目录下的 user_config，PBKDF2-HMAC-SHA1 + MD5 推导 AES-128 密钥
解密
V2 / V3 的 AES-ECB，并合并 WAL 事务，避免读到半提交状态
查询
消息分散在 tbmsg_000 ~ tbmsg_127 共 128 张分表，查询时跨表聚合，并把联系人映射成实名

步骤描述取自 README 与 CHANGELOG 的公开说明；具体实现细节以仓库代码为准。钉钉 V2/V3 与 WAL 合并的修复记录见 commit「fix(dingtalk): fix WAL decrypted checksum mismatch…」。

格式解析覆盖到哪一层

内容类型微信钉钉
文本 / 引用消息支持支持
富文本卡片 / Markdown 卡片支持支持
小程序、协同日程通知小程序支持日程通知支持
文件（PDF / Excel / Word 等）支持，返回磁盘路径支持附件提取
图片三代格式：旧 XOR / V1 固定密钥 / V2 账号级密钥不在公开工具表内
表情包需要 prepare_emoticons 生成明文库，wxgf 按需转码—
合并转发的「聊天记录」get_chat_record 展开为结构化条目—
收藏 / 头像收藏列表；头像只返回本地路径不返回 base64—

图片的 V2 密钥是个特例：它不落盘，只在账号查看图片时临时驻留 Weixin.exe 内存。 所以 extract_image_key 的正确用法是「先在客户端点开 1–2 张图，再立刻调用」；未命中时工具返回 ok=false 与原因，不会谎报成功。这也说明这类解密方案天生依赖客户端内部实现，版本一变就可能失效。

04 · 工具能力

34 个 MCP 工具 微信 29 + 钉钉 5

全部只读；同步类工具只重建本地快照

工具面是这个项目最实在的部分：不是只有一个 search，而是把「找消息、找群、找人、找文件、 做统计、出日报、同步」都拆成了独立能力。下表可按关键词与类别筛选。

媒体文件		 列出表情包与表情，含官方文字说明。 「那个『偷听』表情在哪个包里」

分析同步		 分析某联系人的沟通风格：画像 + 高频用语 + 典型语句。 「模仿一下这个人的说话风格」

这 34 个工具里，哪几个最值得先试

做日报 / 周报：get_group_digest 或 get_chat_activity_stats 一次拿到聚合数据，比让模型自己数消息可靠得多。

找东西：search_wechat_messages（带命中片段）+ search_shared_files（文件）+ get_chat_record（合并转发）。

06 · 安装与接入

三步：装 CLI → 初始化 → 客户端接入

仓库遵循 PEP 517 / 621 打包，支持 uv / uvx / pip，无需手动建虚拟环境。

1. 安装 CLI 工具链

bash · 推荐：uv tool 全局隔离安装
# 一次安装，注册 wechat-init / dingtalk-init / wechat-mcp / dingtalk-mcp / im-clean
uv tool install "git+https://github.com/stkoecn/im-mcp.git" --with "im-mcp[all]"

# 国内网络可换 Gitee 镜像
uv tool install "git+https://gitee.com/ws4m/im-mcp.git" --with "im-mcp[all]"

# 之后升级
uv tool upgrade im-mcp

2. 初始化本地数据库（各跑一次）

bash · 初始化
# 微信：Windows 需管理员终端，且微信已登录
wechat-init

# 微信：macOS 4.1+ 传 64 位 hex passphrase
wechat-init --passphrase <64位十六进制>

# 钉钉：普通权限即可
dingtalk-init

# 常用开关
wechat-init --only-extract      # 只提取密钥，不立即解密
wechat-init --etl-only          # 只重建 FTS5 索引，不重复解密
wechat-init --output <dir>      # 指定解密库输出目录

3. 客户端接入配置

json · claude_desktop_config.json / mcp.json
{
  "mcpServers": {
    "wechat": {
      "command": "uvx",
      "args": ["--from", "git+https://github.com/stkoecn/im-mcp.git[all]", "wechat-mcp"],
      "env": { "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1" }
    },
    "dingtalk": {
      "command": "uvx",
      "args": ["--from", "git+https://github.com/stkoecn/im-mcp.git[all]", "dingtalk-mcp"],
      "env": { "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1" }
    }
  }
}

已用 uv tool install 安装的话，可把 command 直接写成 wechat-mcp / dingtalk-mcp， 冷启动更快。若 uv 提示命令不在 PATH 中，执行 uv tool update-shell 或改用绝对路径。

让 Agent 自己完成配置（仓库提供的提示词）

项目同时提供了一份面向 Agent 的运维规范 skills/im-mcp/SKILL.md，内容包括依赖策略、初始化前置检查、 工具调用 SOP 与异常处置禁令。把技能文件复制到对应目录后，可直接把下面这段发给客户端：

text · 复制给 AI 客户端
请阅读并遵循开源项目 https://github.com/stkoecn/im-mcp 中的 README.md 与 skills/im-mcp/SKILL.md，帮我配置并启用本机的微信与钉钉 MCP 服务。
bash · 安装技能文件
# 通用 Agent（Pi / Codex 等）
mkdir -p ~/.agents/skills/im-mcp && cp skills/im-mcp/SKILL.md ~/.agents/skills/im-mcp/

# Claude Code / Desktop
mkdir -p ~/.claude/skills/im-mcp && cp skills/im-mcp/SKILL.md ~/.claude/skills/im-mcp/
卸载与彻底清理的顺序

顺序很重要，否则 SQLite 句柄会锁住文件删不掉：

  1. 完全退出 AI 客户端（或结束 wechat-mcp / dingtalk-mcp 进程）；
  2. im-clean -y（可先 im-clean --dry-run 预览；残留句柄用 --force，也可只清 --scope wechat / --scope dingtalk）；
  3. uv tool uninstall im-mcp（或 pip uninstall im-mcp；uvx 用户可 uv cache clean）；
  4. 手动删除各客户端的 MCP 配置与技能文件（程序无法跨权限改其他软件配置）。
07 · 安全与隐私

「只读」不等于「没有痕迹」

README 反复强调本地、只读、不上云，这些在代码层面对应的是：MCP 走 stdio、没有网络出口、不调用发送接口、 写入只落在自己的数据目录。但同样要看清它在磁盘上留下了什么。

设计上收敛的部分

  • 不修改微信/钉钉原库，读取的是解密快照
  • 无监听端口，stdio 通信，攻击面局限在本机进程
  • 工具全部只读语义，同步只重建本地索引
  • 提供 im-clean 做生命周期收尾，支持 dry-run 预览
  • 密钥提取失败时返回原因，不谎报成功

必须自己承担的部分

  • 明文 SQLite 副本会长期留在 ~/.wechat_mcp/、~/.dingtalk_mcp/
  • 密钥文件（all_keys.json、image_aes_key）与明文表情库同目录
  • Windows 下以管理员权限扫描进程内存，权限很宽
  • 任何能调用该 MCP 的 Agent 都能读到全部历史消息与通讯录
  • 从 Git 源安装，更新即换代码，无版本签名与发布包

最实际的风险不是「上云」，而是「本机上的明文」。Prompt 注入同样成立： 群聊里的消息内容会进入模型上下文，一条被精心构造的消息就可能诱导 Agent 去查别的会话、把通讯录或文件路径带出来。 只读限制的是写入，不限制读取范围。

实践建议

  • 先 dry-run 再决定：安装后立即跑一次 im-clean --dry-run，亲眼看看会生成哪些路径、占多少磁盘。
  • 按需安装：只需要微信就装 im-mcp[wechat]，少一套依赖也少一份数据。
  • 用完即清：临时借用他人设备分析时，任务结束就 im-clean -y，不要留着 decrypted/。
  • 控制客户端权限：只在你信任的宿主里启用，避免把 MCP 暴露给会自行规划多步任务的自动化 Agent。
  • 固定版本：从 Git 安装的话，记录下用到的 commit，出问题能回退。
  • 合规前提：只处理自己账号的数据。读取他人设备、公司设备上的聊天记录涉及法律与公司制度，与本项目是否开源无关。

09 · 适用建议

什么情况下值得用

适合

  • 个人把群聊当资料库：找文件、找结论、找谁说过什么
  • 需要 AI 帮忙写日报 / 周报 / 群聊纪要，且数据只在本机
  • 想接自己的看板：增量游标、头像路径、头像与文件都返回本地路径
  • 愿意按需清理明文数据、能接受偶发的版本兼容问题

不适合

  • 多人共享的检索服务：没有鉴权、审计与租户隔离
  • 合规审计、法律取证：正确性缺陷未关闭，且无版本锚点
  • 需要实时消息推送：这是检索工具，不是消息网关
  • 处理非本人账号的数据，或公司明确禁止的设备

如果决定上手，建议的顺序

  1. 先在非主力机器或虚拟机里跑通 wechat-init，确认密钥提取在你当前的客户端版本上能成功 —— 这是最大的不确定性。
  2. 只接微信或只接钉钉，减少变量；确认基础检索与文件路径可用。
  3. 用 get_group_digest 做一次周报，和人工印象对照，感受一下统计口径是否符合预期。
  4. 再开定时同步，并注意不要与手动同步同时触发。
  5. 把 im-clean --dry-run 记在心里，出差、换机、借用设备前跑一次 im-clean -y。

总评：架构选择是对的 —— 本地解密快照 + FTS5 + 只读 MCP，比让模型直接啃导出文件靠谱得多； 工具划分也明显来自真实使用场景，而不是 API 包装。短板同样清楚：正确性缺陷还开着、没有发布版本、 强度依赖客户端内部实现，以及明文数据需要用户自己收拾。
