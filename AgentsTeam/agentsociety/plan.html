把 AgentSociety
跑在自己手里

三个问题，按“先算账、再自动化、最后育人”的顺序回答。所有数字都是工程估算，公式和可调参数都放在页面里，你可以按自己的预算改。

Q1 · VPS
1 → 3 → 6台

POC 1 台；千级 agent 3 台；万级 agent 6–8 台。瓶颈不是 CPU，是 LLM 并发配额。

Q2 · 自动化
3 个脚本+ 1 份配置

bootstrap、preflight、run。用 agentsociety check/run 串起来，systemd 托管，run 粒度可重放。

Q3 · 对接与培训
4 周4 个角色

先接 LLM 与地图，再接存储与 UI；培训分运维、实验设计、Agent 开发、数据分析四条线。

01先定范围，再谈机器

“复刻 AgentSociety”有两种做法，硬件和人力差一个量级。先选一个，别同时上。

目标：复现“1 万个 agent 在一座城市里生活”的仿真能力，能配置实验、施加干预、导出数据分析。

  • 安装：pip install agentsociety
  • 依赖：Python 3.11+、Ray；v1.5 起已移除 Redis / MLflow 依赖，数据库默认 SQLite，可换 PostgreSQL
  • 必需资产：MOSS 城市地图 .pb 文件（官方提供部分城市）
  • 入口：agentsociety check / run / ui
  • 适合：政策预演、舆情传播、城市演化；也是本方案第 2–7 节的默认假设

目标：复现“AI 社会科学家 + 硅基被试”的端到端研究流水线，重点是可重放与可审计。

  • 安装：pip install agentsociety2
  • 依赖：Python 3.11+、Ray Task；组件更多（PersonAgent、workspace、ServiceProxy、JSONL replay + DuckDB）
  • 额外需要：对象存储（轨迹）、DuckDB 查询层、MCP 工具链
  • 适合：研究流程自动化、实验复现、论文级产物；工程量约为 A 的 1.5–2 倍

建议：先用 A 把“仿真跑通、数据能出”，再决定要不要上 B。

02要买多少台 VPS

先给结论，再给算法，最后给一个你可以自己改数字的估算器。

三档配置

档位规模节点单机规格用途
POC≤ 200 agent · 1 天1 台8 vCPU / 32 GB / 200 GB NVMe跑通链路、验证地图与模型；SQLite 足够
试点1,000 agent · 3–7 天3 台1×8C/32G（head + UI）＋ 2×8C/32G（worker）一个完整实验；建议 PostgreSQL
生产10,000 agent · 多轮6–8 台1 head、3–4 worker、1 DB、1 网关/监控多实验并行、结果共享、可复盘

官方给的最低配置是 4 核 / 16 GB，但那是“能启动”，不是“能跑万级”。上表是工程建议，需用你的 agent 记忆大小与模型并发实测校准。

真正的瓶颈通常不是 VPS

单进程的 LLM 并发（官方示例里 concurrency: 200）和供应商的 RPM / TPM 配额，才是决定“能不能跑起来”的东西。VPS 加得再多，配额不够也只是多几台机器一起排队。

估算器

改数字，下面会实时更新。默认：1,000 个 agent、目标并发 200、每进程并发上限 200、每 worker 承载 2,500 个 agent。

worker 数—
VPS 总数—
合计 vCPU / 内存—
基础设施 / 月—
单次实验 token—
单次实验模型费—

worker 数 = max(⌈目标并发 ÷ 每进程并发⌉, ⌈agent 数 ÷ 每 worker 承载⌉)；总数再加 1 台 head，以及你勾选的 DB / 网关。没算：失败重试、缓存未命中、对象存储、带宽、人工。默认值下，模型费通常是基础设施月费的数倍——所以先控模型，再谈加机器。

买机器时的四个硬要求

  • 不要用突发性能实例：长时间仿真会把 CPU 积分耗光，后半程直接降速。
  • 磁盘要 NVMe：SQLite/PostgreSQL 写入与轨迹落盘是持续小 IO，网络盘会拖死 tick。
  • 出网要稳定：每步都在调模型 API，NAT 抖动会表现为“agent 随机卡住”。
  • 同区域部署：head 与 worker 跨区会放大 Ray 的调度延迟；模型 API 也尽量选近的区域。

03自动化：从裸机到一次实验

原则：机器可重建、配置可版本化、实验可重放。不要在生产机上手工 pip install。

仓库结构

as-ops/
├─ configs/
│  ├─ base.yaml            # 通用：模型、数据库、路径
│  ├─ exp-ubi.yaml         # 单个实验：agent 数、天数、干预
│  └─ secrets.example.env
├─ scripts/
│  ├─ bootstrap.sh         # 装 Python/Ray/agentsociety
│  ├─ preflight.py         # 跑前检查：配置/配额/磁盘/地图
│  └─ run.sh               # 加锁、建 run 目录、执行、归档
├─ deploy/
│  ├─ ray-head.service     # systemd
│  ├─ ray-worker.service
│  └─ nginx.conf           # UI 反代 + 鉴权
└─ runs/                   # 每次实验一个目录（gitignore）

1）机器初始化

#!/usr/bin/env bash
# bootstrap.sh — Ubuntu 22.04 / 24.04
set -euo pipefail

apt-get update && apt-get install -y python3.11 python3.11-venv build-essential curl
curl -LsSf https://astral.sh/uv/install.sh | sh

uv venv --python 3.11 /opt/as/.venv
source /opt/as/.venv/bin/activate
uv pip install agentsociety==1.5.* agentsociety-community

# Ray 版本必须全集群一致，锁死
uv pip install "ray[default]==2.4x.*"

agentsociety --help   # 确认 check / run / ui 三个子命令

2）Ray 集群

# head 节点
ray start --head --port=6379 --dashboard-host=0.0.0.0 --num-cpus=8

# worker 节点（改 IP）
ray start --address=10.0.0.10:6379 --num-cpus=8 --memory=30000000000

# 任意节点检查
ray status

Ray 的 GCS 仍用 6379 端口，但它不是 Redis 依赖——v1.5 移除的是业务层的 Redis。别把两件事混在一起。

3）实验配置（最小可用）

# configs/exp-ubi.yaml
llm:
  - model: qwen2.5-14b-instruct
    api_key: "${AS_LLM_KEY}"
    base_url: "https://your-endpoint/v1"
    provider: vllm
    concurrency: 200
    timeout: 60

env:
  db:
    enabled: true
    db_type: sqlite        # 多人协作换 postgresql
  home_dir: ./agentsociety_data

map:
  file_path: ./agentsociety_data/beijing.pb

agents:
  citizens:
    - agent_class: SocietyAgent
      number: 1000

exp:
  name: ubi-pilot
  workflow:
    - type: run
      days: 1
      ticks_per_step: 300
  environment:
    start_tick: 28800      # 08:00

4）跑前检查 + 执行

# preflight：先便宜地失败
agentsociety check -c configs/exp-ubi.yaml

# 再花 30 秒验一次模型连通性
curl -sS "$AS_LLM_BASE/chat/completions" \
  -H "Authorization: Bearer $AS_LLM_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen2.5-14b-instruct","messages":[{"role":"user","content":"ping"}],"max_tokens":4}'

# 正式跑：一个 run 一个目录，避免互相覆盖
RUN_ID=$(date +%Y%m%d-%H%M%S)
mkdir -p runs/$RUN_ID
agentsociety run -c configs/exp-ubi.yaml 2>&1 | tee runs/$RUN_ID/run.log
run.sh 里必须有的五件事
  • 文件锁：同一 DB/home_dir 不允许两个实验同时写
  • run 目录：日志、配置快照、git commit 一起存
  • 成本闸：环境变量里写死本次预算，超了就 kill
  • 超时：整轮墙钟上限，防止“卡住但没报错”
  • 归档：DB 快照或导出文件，移动到对象存储

5）常驻与开机自启

# /etc/systemd/system/ray-head.service
[Unit]
Description=Ray head
After=network-online.target

[Service]
Type=simple
User=as
ExecStart=/opt/as/.venv/bin/ray start --head --port=6379 --dashboard-host=0.0.0.0 --num-cpus=8 --block
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
systemctl daemon-reload
systemctl enable --now ray-head
journalctl -u ray-head -f

# Web UI 不要直接暴露：nginx 反代 + Basic Auth / SSO
agentsociety ui

6）CI 与回归

把“10 个 agent × 1 天”做成冒烟测试，每次改配置或升级版本都跑一遍。它验证的是链路（配置解析、地图、DB、模型、UI），不是科研结论。冒烟通过再放量，能挡掉八成低级错误。

04对接：五个接口

按“先通、再稳、再治理”的顺序接。每一项都给出验收标准，避免“看起来接上了”。

接口怎么接验收标准
模型 任意 OpenAI 兼容端点：DeepSeek / Qwen / 智谱 / 火山 / SiliconFlow / 自建 vLLM。配置里写 base_url + api_key + provider，并设 concurrency 与 timeout。 10 agent × 1 天跑通；P95 延迟与失败率有记录；配额够目标并发的 1.5 倍
地图 MOSS 城市地图 .pb，官方站可下载部分城市；自定义地图按其格式生成。 agentsociety check 的 Map 项通过；agent 能按路网移动
存储 默认 SQLite；多人/多实验换 PostgreSQL。轨迹与导出文件放对象存储（S3 兼容）。 两个实验并发写不冲突；能用 SQL 直接查 agent 状态与对话
界面 agentsociety ui + nginx 反代；接公司 SSO 或至少 Basic Auth；只在内网/白名单开放。 未登录不可访问；实验列表与问卷能打开
下游系统 用 Web API 或直接读库，把实验结果送进 BI / Notebook；v2 可走 MCP 接工具。 一条 SQL / 一个 API 能拿到“实验 → agent → 行为”三层数据

密钥与配额

  • 不要把 key 写进 YAML：用环境变量或 secret manager，配置文件只留 ${AS_LLM_KEY}。
  • 按实验发子 key：每个实验一个额度，烧穿只影响自己。
  • 模型分层：规划/反思用强模型，日常动作与格式化用便宜模型；先跑小规模对比再定比例。
  • 限流要主动：客户端并发 ≤ 供应商配额的 80%，把 429 当常态处理。

合规与数据

如果 agent profile 来自真实问卷或用户数据，先做脱敏与授权；地图数据注意来源许可；仿真结论对外发布时，必须标注“模拟结果，非预测”。这三条在“复刻”里最容易漏，也最容易出事。

05培训：四个人，四周

这里的“培训”指人和agent 调优，不是训练基础模型。别把两件事混在一个预算里。

角色与职责

角色要会什么交付物
平台运维Ray 集群、systemd、监控、备份、升级与回滚Runbook、故障演练记录
实验设计把研究问题翻译成配置：agent 数、天数、干预、指标实验模板、变量清单
Agent 开发Block 组合、自定义 agent、消息拦截器、prompt 校准自定义 Block/Agent + 测试
数据分析读库、指标提取、可视化、显著性判断分析 Notebook、报告模板

四周课表

  • W1 · 概念跑通一次。装环境、跑官方最小配置、看懂 check 的三项输出、用 UI 观察 agent。作业：10 个 agent 跑 1 天，导出一次对话。
  • W2 · 配置改一个变量。只改 agent 数或 ticks_per_step，观察运行时间与 token 变化；学会用 run 目录对比两次实验。作业：一份变量对照表。
  • W3 · 干预加一个干预。用消息拦截器做一次信息注入，或改一个 Block 的行为；写清楚“预期变什么、怎么判定”。作业：一个可重放的干预实验。
  • W4 · 闭环出一份报告。从问题到配置到数据到结论，全程留痕；做一次失败复盘（限流、地图、DB 各一次）。作业：可复制的实验包。

    • 三道认证闸

    • 能独立跑：给一份没见过的配置，能 check 通过并跑完，出问题能定位到是配置、地图还是模型。
    • 能改行为：不碰核心代码，只加一个 Block 或一条拦截规则，让某个指标发生可解释的变化。
    • 能出结论：拿到一份结果，能说清“这个差异是实验设计造成的，还是噪声”。
    培训的长期机制

    每周一次实验复盘（只看看翻转的指标，不看平均分）；每月一次版本升级演练（在影子环境跑冒烟）；每次事故写一页纸：现象、根因、闸门。人和系统一起长。

    0690 天路线图

    1. D0–14POC。1 台 VPS，200 agent，1 天；目标只有一个：链路通、数据能查。产出：bootstrap.sh、最小配置、一次完整日志。
    2. D15–45试点。3 台，1,000 agent，跑 2–3 个场景；接 PostgreSQL 与 UI 鉴权；建立 run 目录与成本台账。产出：runbook、实验模板。
    3. D46–75放量。6–8 台，10,000 agent；做一次限流演练与一次失败重放；把冒烟测试接进 CI。产出：容量报告、故障演练记录。
    4. D76–90交接。四个人各过一道认证；把“怎么跑、怎么改、怎么判”写成三份文档；决定是否上 v2。
    预算提醒

    6–8 台 8C/32G 的月费通常在几百美元量级；而一次 1 万 agent × 50 步的实验，模型费可能是它的数倍。预算表要把“基础设施”和“模型调用”分开列，否则第一个月就会超。

    07七个会咬人的地方

    • 配额先于机器耗尽：供应商 429 会让 agent 表现为“随机不动”；先压测配额，再谈扩容。
    • SQLite 并发写：多实验共用一份库会锁；超过一个人用就换 PostgreSQL。
    • Ray 版本漂移：head 与 worker 版本不一致时，报错通常很难懂；锁死版本。
    • 地图不匹配：换城市不是换文件那么简单，路网与 POI 会影响行为分布。
    • 模型升级改变结论：换模型等于换“人性”；升级后必须重跑基线。
    • 把模拟当预测：对外输出必须标注边界，否则一次误读就毁掉项目信誉。
    • 许可例外：Apache-2.0，但 commercial 目录另有条款；商用前读 LICENSE。
