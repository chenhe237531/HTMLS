先把数字拆开：没有人在同时盯 1000 个 agent 这一节决定你后面看所有案例时是清醒还是被唬住。

16单次运行默认并发 agent 数（官方，可调至 256）
1,000单次 workflow 的 agent 总数硬上限（官方）
~10Claude Code 作者实际同时在看的会话数
3–5官方建议的 agent team 起步人数

「1000+ agents」在 X 上通常指三件完全不同的事，混着讲就会得出错误结论：

三种「1000 agents」说法的区别
说法实际含义谁真的在看对应路线
「一次跑 1000 个 agent」 单次 workflow 脚本内的 agent 总数上限，累计计数；同一时刻只跑 16 个（默认） 1 个会话 + 进度面板 A
「通宵几千个 agent」 一整夜多波次（wave）累计的 subagent / 会话数，中间大量是重启出来的新会话 ~10 个 supervisor 会话 B
「几百个 worker 并发」 长周期项目里同时存在的 worker 会话，靠 worktree / 共享分支合并，冲突面很小 人只看 PR 与告警 C D
为什么这件事重要 如果你的目标是「一个人同时监督 1000 个 agent」，这个目标本身不可达，也不是任何成功案例的做法。 所有可复现的千级案例，规模都来自两点：把工作切成独立单元，以及把判断权交给代码而不是人。 数字只是这两件事的副产品。

A

扇出工作流：唯一能「一次跑满 1000」的官方路径 Dynamic Workflows。计划写进 JavaScript 脚本，结果留在脚本变量里，主会话只拿最终答案。

A

Dynamic Workflows

代表案例：Bun 用 11 天把 53.5 万行 Zig 移植成百万行 Rust（峰值 64 并行，二手）；官方 /deep-research。

✓ 单元互不依赖 ✓ 有自动判定信号 ✓ 需要可复跑 ✗ 需要中途插话 ✗ 步骤强依赖

  1. 确认环境够新、计划够高 终端 / Claude Code

    三个前置条件，缺一个后面都会卡：

    • 付费计划，或走 API / Bedrock / Google Cloud Agent Platform / Microsoft Foundry；Pro 用户需要手动打开开关。
    • 版本：改并发上限需要 v2.1.269+；重置（resume）行为的修复在 v2.1.305 前后，建议直接升到最新。
    • 可用 WebSearch 工具（/deep-research 依赖它）。
    claude --version
claude            # 进入交互式会话
/config           # 找到 Dynamic workflows 一行，Pro 计划在这里打开

    坑 用 -p 无头模式或 Agent SDK 时不会生产队友/团队，但 workflow 本身在无头模式可用；不要拿团队功能去试无头脚本。

  2. 先跑内置的 /deep-research 试水 Claude Code 输入框

    不要一上来就写自己的脚本。用一个内置 workflow 先看清「阶段 / 并发 / token / 交叉验证」长什么样，成本可控。

    /deep-research Node.js 的权限模型在 v20 到 v22 之间改了什么？

    它会：按角度扇出网页搜索 → 抓取并交叉验证来源 → 对每条结论投票 → 返回带引用的报告，未通过交叉验证的结论已被过滤掉。

  3. 批准一次运行，并知道批准的是什么 权限提示

    Claude Code 会问是否允许该 workflow。不同 permission mode 下提示措辞不同，但含义一致：允许一个脚本在后台派生多个子 agent。

    关键认知 workflow 里的 agent 和普通工具调用受同样的权限检查与沙箱约束；脚本传给 agent() 的提示词在 auto 模式下不算「你的请求」，分类器仍会审它派生的动作。

  4. 打开进度面板，练熟 8 个键 /workflows

    这是千级运行唯一的观察窗口。先在小任务上把键位练到不用想：

    键动作什么时候用
    ↑ ↓选阶段或 agent定位异常阶段
    Enter / →逐层下钻看单个 agent 的提示词、工具调用、结果
    Esc / ←退回上一层—
    f按状态过滤只看失败的 agent
    p暂停 / 恢复整个 run发现它在烧钱
    x停单个 agent 或整个 run止损
    r重启选中的运行中 agent卡住的单元
    s把本次脚本存成命令跑对了以后固化

    面板顶部会显示每个阶段的 agent 数、token 总量与耗时；单个 agent 的 token 也可见，这是你估成本的唯一实测数据。

  5. 写第一个自己的 workflow：用「小切片 + 对抗验证」 Claude Code 输入框

    提示词里有三个词决定成败，缺一个就退化：

    • use a workflow（或关键词 ultracode）——显式 opt-in，否则 Claude 会按普通对话一轮轮做。
    • adversarially verify——要求验证者是干净上下文的独立 agent，任务是反驳结论而不是确认。
    • at most 20 files first——先测单位成本，再放大。
    use a workflow to audit every route handler under src/routes/ for missing
authentication checks, and adversarially verify each finding before reporting
it. Analyze at most 20 files first.

    另外三个可直接复用的形状：

    # 迁移：隔离副本 + 测试当闸门
use a workflow to migrate every component under src/components/ from
JavaScript to TypeScript, working on each file in its own isolated copy,
and run the test suite on each one before accepting it.

# 修到通过：带停止条件，防死循环
use a workflow to run npx tsc --noEmit and keep fixing the reported errors
until the type check passes or two rounds in a row make no progress.

# 逐文件评审 + 合成一份：防 20 份互相矛盾的结论
use a workflow to review every file changed in this PR for correctness
issues, then merge the per-file findings into one ranked summary with
duplicates removed.

    坑 「让 Claude 自己决定要不要继续」是这类脚本最常见的失控点。任何迭代型任务都必须把停止条件写进提示词（两次无进展即停）。

  6. 读它生成的脚本，别当黑盒 ~/.claude/projects/

    运行开始时 Claude 会拿到脚本路径。打开它，确认三件事：每个 agent 的工作目录在哪、结果怎么合并、两个 agent 结论冲突时谁赢。

    脚本形如（官方示例，可直接照这个骨架读）：

    export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const found = await agent('List every .ts file under src/routes/.', {
  schema: {
    type: 'object',
    required: ['files'],
    properties: { files: { type: 'array', items: { type: 'string' } } },
  },
})

const audits = await pipeline(found.files, file =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)

    脚本语言只有这几个东西，其余都是普通 JS：

    原语作用注意
    agent(prompt, opts)派生一个子 agent被中止或不可恢复错误时返回 null
    parallel(tasks)一批同时跑，等全部结束单次最多 4,096 项
    pipeline(items, fn)对列表逐项跑，保留顺序单次最多 4,096 项；null 会留在结果里
    phase(title)把后续 agent 归到一个阶段标题下只影响视图
    log(msg)在阶段上方打一行只影响视图
    args保存后运行时的入参见第 8 步
    四条硬约束（写脚本前必须知道）
    • 运行中没有用户输入：只在权限提示和额度等待时自动暂停。需要分阶段签字，就拆成多个 workflow。
    • 脚本本身不能读写文件或跑 shell：所有实际动作都由 agent 做。
    • 不能 import 模块：含 import() 的脚本启动即失败；需要库的活儿放进 agent 的任务描述。
    • Date.now()、Math.random()、无参 new Date() 会抛错——为了重跑可复现。要时间戳就通过 args 传进去。

  7. 把验证做成「独立上下文」，否则你在自欺 提示词层

    这是 Ray Fu 总结的两个「静默失败」之一：验证者如果和干活的是同一个上下文，它不是验证，只是用另一种字体同意自己。

    判断标准很具体：

    • 验证 agent 的输入是原始证据（测试输出、文件 diff、页面响应），不是干活 agent 的自述。
    • 验证 agent 的任务措辞是「找出这条结论为什么是错的」，不是「确认这条结论」。
    • 验证失败时，报告里要能区分「被驳倒」和「无法验证」（例如限流导致没跑成）。官方实现就是这么分的。
    use a workflow to audit src/api for the same class of bug. For every finding,
spawn a separate verifier with no access to the original agent's reasoning;
the verifier must reproduce the bug or mark the finding unverified.

  8. 保存成命令，下次一条斜杠复跑 .claude/workflows/

    跑对了以后在 /workflows 里按 s，脚本落到 .claude/workflows/（项目内共享）或 home 目录（个人）。它立刻变成 /audit-routes 这样的命令，和内置命令一起出现在自动补全里。

    带参数复用：脚本里读 args，运行时由命令传入。这样同一套编排可以跑不同目录 / 不同分支。

    为什么值得存 存下来的是编排本身，不是提示词。下次同一类任务不需要重新说服 Claude 怎么拆，成本与结果都可对比。

  9. 放大：改三个旋钮，不要改脚本 /config + 环境变量

    /config workflowSizeGuideline=large     # 目标 < 50 个 agent；unrestricted 让 Claude 按任务定
/config workflowSizeGuideline=medium    # 默认，目标 < 10（第三方教程写作 15，以 /config 显示为准）

# 同时在跑的 agent 数：默认 16，可设 1–256（需 v2.1.269+）
export CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS=32

# 关掉扇出时的前缀停顿（默认 5000ms，为了共享 prompt 缓存）
export CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS=0

    三个天花板要背下来：单次 run 最多 1,000 个 agent；单次 parallel/pipeline 最多 4,096 项；同刻并发默认 16（CPU 少时更少）。超过 1,000 的唯一办法是拆成多次 run。

    坑 把并发从 16 拉到 64，收益不是 4 倍：CPU、限流、合并冲突都会先到瓶颈。Bun 的 64 并行是峰值不是常态。

  10. 成本闸门与停手 /workflows + /config

    • 当一次 run 计划超过 25 个 agent，或预计 token 超过 150 万，任务面板会出现 Large workflow 警告。它只是提示，不会暂停。
    • 你自己设了 size guideline 后，25 这个阈值会被你设的 agent 数替换；开了 ultracode 的会话不显示该警告（因为你已经显式选择了大跑）。
    • 停：/workflows 里按 x。通常不丢已完成的工作。
    • 续：同一会话内可 resume；已完成的 agent 不会重跑。agent 卡住最多自动重启 5 次，第 6 次仍卡则失败；可用 stallMs 单独放宽某个 agent，例如 agent(prompt, { stallMs: 1800000 }) 给 30 分钟。
    先算单位成本 20 个文件的审计跑完，看 /workflows 里的 token 总量，乘以你的文件总数，再决定要不要 large。 不做这一步就放大，是千级玩法里最常见的一次性学费。
B

通宵车队：让 agent 在你睡觉时干活，醒来只做 review Overnight Fleet。核心不是「更多 agent」，而是「没有你也能做决定的四件套」。

B

Worktree 车队 + 无人值守循环

代表案例：Terry Li（270 个会话 / 43 波，一夜 250 个文件）；Boris Cherny 的手机触发工作流；Projectify fleet。

✓ 任务已就绪且有验收 ✓ 可跨夜 ✓ 少量审批可预先定策略 ✗ 任务含糊 ✗ 需要你现场决策

先把失败长什么样记住，这决定了每个步骤为什么存在：两个 agent 抢同一个任务；agent 捡了个没准备好的活；agent 停在第一个问题上等你；agent 卡在权限提示上八小时；没人先看一眼，早上直接进 review 队列；什么都没记录。

B-1 从零自建（可控、无依赖）

  1. 前置闸门：不通过就不启动 你本人 + 一个 checklist

    这是整个路线里唯一必须你亲自做的一步。四项全绿才 GO：

    • 任务就绪：每个任务有摘要、验收标准、无 blocker、不需要人做设计决策。含糊的一律留在「定义中」，不进队列。
    • 额度：写死两个数字——5 小时窗口用掉多少百分比就停派发，周额度到多少就硬停。写在配置里，不写在提示词里。
    • 凭证与访问：列出整晚整个目标可能用到的所有访问（git push、开 PR、CI、测试账号、浏览器登录态），现在补齐。缺的当场 NO-GO，不要指望半夜自己解决。
    • 沙箱边界：白名单=编辑/测试/commit/推分支/开 PR；黑名单=部署生产、自动 merge main、动密钥、改 CI 配置。

    坑 最常见的翻车是「以为不用权限」：worker 到第 3 个任务开始要 npm install，卡在提示上到天亮。把所有会触发的命令形状提前 allow 掉。

  2. 任务队列：只让 agent 拿「就绪」的活 issue / 看板

    队列要能回答一个问题：现在排名最高的、agent 可以拿的任务是哪个。判据四连：已定义、无 blocker、未被认领、不需要人。

    每条任务必须带验收标准。没有验收标准的任务等于「让 agent 自己定义成功」，它一定会定义得比你想的宽松。

  3. 每个任务一个独立工作区 git worktree

    git worktree add ../wt-issue-47 -b agent/issue-47
cd ../wt-issue-47

    不要多个会话在同一个 checkout 里并行改文件。后保存的覆盖先保存的，而且每一边的检查都是绿的——这是所有并行写事故的共同形状。

  4. 启动后台会话，让它活过关终端 终端

    claude --bg --worktree wt-issue-47 -p "$(cat prompts/worker.md)"

    --bg 后台会话跑在独立 supervisor 下，关终端、机器休眠、自动更新都不会杀掉它。这是「通宵」三个字的技术前提；普通前台会话做不到。

    prompts/worker.md 要写清楚五件事，缺一件就会出事故：

    • 你的任务 ID 与它的验收标准（逐条列出）
    • 你只能改哪些文件（显式文件清单）
    • 完成后：commit → push 分支 → gh pr create → 把任务移到 Review
    • 绝不 merge，绝不推 main
    • 需要人决定时，写进 questions.md 并继续做不依赖它的部分

  5. 写 manifest：唯一的跨波记忆 manifest.json / md

    每一波都是新会话，context 全部重置，唯一继承的是文件和 git。manifest 是这个继承的核心，至少四个字段：

    {
  "north_stars": ["career", "finance", "health", "systems"],
  "produced": ["briefs/fintech-competitor.md", "plans/week-1.md"],
  "do_not_recreate": ["plans/week-1.md — 已存在，只允许追加章节"],
  "failed": [{ "task": "health-protocol", "why": "rate_limited", "attempts": 3 }],
  "queue": ["systems/obsidian-index", "career/portfolio-page"]
}

    坑 produced 不够，必须写 do_not_recreate。Terry 的实际数据：一夜 250 个文件里约 30% 是同一件东西的变体，因为下一波 agent 从「优先级」推理，而不是先查文件系统。

  6. 循环用 shell，不用提示词 run.sh

    #!/usr/bin/env bash
set -uo pipefail
while true; do
  [ -f STOP ] && break
  claude -p "$(cat prompts/wave.md)" --worktree "../wt-$(date +%s)"
  # 每波结束：更新 manifest、跑一次 dedupe 检查
  python3 scripts/manifest_check.py || exit 1
done

    关键设计：LLM 决定「做什么」，脚本决定「是否继续」。任何「让 agent 自己判断要不要接着跑」的写法，最后都会得到两种结果之一：过早收工，或者不撞限流不停手。

    Terry 的实测教训：第 28 波撞限流，manifest 记了失败，后续波次用同样方法重试了 6 小时。修法不是加提示词，是在脚本里对同一错误设「两次即跳过 + 换策略」。

  7. 给「没人可问」准备一个代理 coordinator 会话

    worker 一定会提问。你需要一个按类别预设策略的协调会话，而不是每件事都留到早上：

    类别策略含义
    实现细节decide直接回答，worker 继续
    范围 / 澄清decide直接回答
    产品判断recommend记录建议，等你确认
    设计取舍recommend记录建议
    高风险（密钥、数据、对外发布）ask me留在「Needs you」，不执行
    权限审批recommend记录，不代签

    协调者只做决策与记录，不写代码。它同时消费：worker 的提问、任务评论、被 @ 的讨论。

  8. Review 在你看之前先跑一遍 reviewer 会话 + PR

    PR 一开就触发 review agent：读 diff、跑仓库自带检查、给结论（ready / changes）。changes 就在同一分支返工，最多 N 轮。

    这样早上的三点分法才成立：Review（已过一遍眼睛的 PR）、Needs you（真正需要你的判断）、Activity（谁在什么时候做了什么，按角色归因）。

  9. 早上只做三件事 看板 + git

    • 读 Review 里的 PR，而不是读 transcript。
    • 处理 Needs you，把当晚的临时策略固化成下一条规则。
    • 把昨晚重复出现的失败写进 manifest 的约束，而不是写进「下次注意」。

B-2 用现成实现：Projectify fleet（5 步跑起来）

不想自己搭协调层，可以直接用这套（要求 Claude Code、Node 18+、gh 已登录）：

# 5. 早上看 Review / Needs you / Activity

C

Agent 团队：5–10 个能互相说话的常驻队友 Agent Teams。和 subagent 的根本区别：队友有名字、有收件箱、能自己抢任务、能直接质疑别人。

C

共享任务列表 + 收件箱

代表案例：Anthropic 的 C 编译器项目用 16 个 Claude 跑了两周（2000+ 会话）；madsalt 用 165 个 hook 管 3315 次 subagent 运行。

✓ 需要讨论与互相质疑 ✓ 后端 / 前端 / 测试分层 ✓ 竞争性假设排障 ✗ 同文件并行编辑 ✗ 强顺序依赖
先想清楚规模 官方建议从 3–5 个队友起步：15 个独立任务，3 个队友是好的起点。三个专注的队友经常打过一个散在五个方向的。 队友每个都是独立 Claude 实例，token 成本线性增长，协调开销也线性增长。

  1. 打开实验开关 ~/.claude/settings.json

    {
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

    不设这个变量，会话启动时不会建团队目录，Claude 也不会提议队友。需要较新的 Claude Code（第三方教程写作 v2.1.32+，以你本机文档为准），且必须是交互式会话（-p 无头模式不组队）。

    副作用 打开后，Claude 给 subagent 起名字的行为会变成「拉起队友」——你可能没要团队却得到了团队。不想要就关掉开关，或明确说「用 subagents，不要团队」。

  2. 选显示模式（决定你能不能用肉眼盯） settings.json 或命令行

    • in-process（默认）：所有队友在一个终端里，↑↓ 选人、Enter 进去说话。任何终端都能用。
    • split panes：每个队友一个窗格。需要 tmux，或 iTerm2 + it2 CLI。VS Code 内置终端、Windows Terminal、Ghostty 不支持。
    • auto：在 tmux 里就用分屏，否则 in-process。
    // ~/.claude/settings.json
{ "teammateMode": "auto" }

# 或单次会话指定（实验性 flag，不在 --help 里）
claude --teammate-mode auto

  3. 用一句自然语言拉团队，并给角色起名 Claude Code 输入框

    三个角色必须能各自独立探索、不需要等别人，否则会退化成串行：

    I'm designing a CLI tool that tracks TODO comments across a codebase.
Spawn three teammates to explore this from different angles: one on UX,
one on technical architecture, one playing devil's advocate.

    要可预测的名字（后面要按名字点名）：在指令里直接写「把负责安全的队友叫 auditor」。

    坑 Claude 有时用 subagent 冒充团队，两者在同一个面板里出现，看不出区别。发现没组队就再说一次，明确「agent team，不是 subagent」。

  4. 指定每个队友的模型，别全用最贵的 提示词 / settings

    模型选择优先级（从高到低）：

    1. 你在 spawn 提示里点名的模型
    2. subagent 定义里的 model（inherit 表示跟随 lead）
    3. CLAUDE_CODE_SUBAGENT_MODEL（非 inherit 时）
    4. lead 当前模型
    Spawn 4 teammates to refactor these modules in parallel.
Use Sonnet for each teammate; use Opus only for the architect teammate.

    队友的模型在 spawn 时确定，之后不能改（/model 只改 lead）。所以这一步要在拉人之前想好。

  5. 高风险任务先让队友「只规划」 plan mode

    把 lead 切到 plan mode（Shift+Tab），再要求拉人：

    Spawn an architect teammate to refactor the authentication module.

    队友会以只读模式工作，计划完成后向 lead 发审批请求。默认情况下如果它没被改过权限模式，Claude Code 会自动批准；想让 lead 真正审，就在看它会话时按 Shift+Tab 把它切进 plan mode。

  6. 用共享任务列表分工，而不是靠嘴 Ctrl+T 任务列表

    任务有三种状态（pending / in progress / completed），可以声明依赖（依赖未完成显示 blocked）。队友不会抢 blocked 的任务，但你可以强行指派。

    两种分配方式：lead 显式指派；或队友做完自己认领下一个未分配未阻塞任务。认领用文件锁防并发重复领取。

    任务粒度是关键：一个任务应该是「一个队友能在一次会话里做完并自证」的大小。太大的任务会让队友开始写「计划」而不是代码。

  7. 直接跟队友说话，绕过 lead 面板键位

    操作in-process
    选队友↑/↓
    查看并给它发消息Enter，然后直接打字
    停止该队友选中后按 x
    切换任务列表Ctrl+T
    打断队友当前回合在它transcript 视图里按 Esc

    在队友视图里：普通文本和 skill 发给队友，内置命令发给 lead。其中 /compact、/clear、/rewind 作用于 lead 的会话，所以会要你确认；/model、/fast 不能在这里用。

  8. 装质量门：三个 hook settings.json hooks

    队友「说自己做完了」不可信。用 hook 在关键节点拦截：

    • TeammateIdle：队友即将空闲时触发，退出码 2 = 打回并让它继续干。
    • TaskCreated：创建任务时触发，退出码 2 = 拒绝创建并反馈（防止任务写得不可验收）。
    • TaskCompleted：标记完成时触发，退出码 2 = 拒绝完成并反馈（例如测试没跑、文件没提交）。
    // 示例：任务完成前必须能通过测试，否则打回
{ "hooks": { "TaskCompleted": [ { "hooks": [ {
  "type": "command",
  "command": "npm test --silent || exit 2"
} ] } ] } }

    实际项目里更狠的做法（madsalt 的 165 个 hook）是：检查文件只读、在 hook 里拒绝并发写同一文件的 agent、失败三次升级模型。

  9. 按名字关停，目录自动清理 Claude Code 输入框

    Ask the researcher teammate to shut down

    lead 发关停请求，队友可以同意（优雅退出）或拒绝并说明原因。团队目录随会话结束自动清理，任务列表目录保留（~/.claude/tasks/<team>/，按 cleanupPeriodDays 清理）。

已知限制（决定你能不能用它做长任务）
  • resume 不恢复 in-process 队友：/resume、/rewind 之后 lead 可能给不存在的队友发消息，需要让它重新拉人。
  • 任务状态会滞后：队友有时忘了标记完成，依赖它的任务就卡住。要人工核对并让 lead 催。
  • 关停慢：队友要把当前请求 / 工具调用做完。
  • 一个会话只能有一个团队，且不能嵌套团队（队友不能再拉队友）。
  • lead 固定：不能把队友提升为 lead。
  • in-process 队友的子 agent 只能前台跑（不能 background: true）。
  • 权限模式在 spawn 时定，不能按队友单独设置。

无中心 Swarm：用 git 当协调层，跑几周 Ralph-Loop。16 个 Claude、2000+ 会话、约 2 万美元、10 万行 Rust，造出一个能编译 Linux 内核的 C 编译器。

D

裸循环 + 锁文件 + Oracle 二分

代表案例：Anthropic「Building a C compiler with a team of parallel Claudes」、Cursor 的浏览器项目（一周百万行）、@jhleath 的 128 agents（共享文件系统自组织造 Factorio）。

✓ 任务能变成很多独立失败 ✓ 有可信的自动 oracle ✓ 可低成本重启 ✗ 项目小 ✗ 强协调设计
先读这一段再决定 这条路线不适合大多数工作。官方复盘自己列了三个「不要搭」的条件：项目小（一个会话能干完）；工作需要紧密协调（API schema、协议不变量、共享数据模型会被并行摧毁）；没有可信 oracle（没有确定性的「它 work 了吗」信号，agent 会优化验证器而不是目标）。 三条中一条成立，就回去用 A 或单会话。

  1. 为每个 agent 准备一个容器 Docker

    同一个镜像、只读的代码来源、独立的文件系统。目的是让「重启」变便宜：容器销毁重建的成本远低于清理一个被污染的环境。

    docker run --rm -it \
  -v "$PWD/repo":/work \
  -v "$PWD/prompts":/prompts:ro \
  c-compiler-agent:latest

  2. 用 bare repo 做协调层，不要写任务队列 git

    git init --bare /srv/fleet.git
# 每个容器：clone → 工作 → push

    锁、合并、冲突解决、历史、回滚，git 已经解决了；你再搭一个任务队列 / 锁服务 / 消息总线，就是在重新实现一个更差的版本。

  3. 锁 = 一个文件，push 成功才算抢到 current_tasks/

    current_tasks/fix-segfault-x86.txt   # 文件存在 = 有人在做
current_tasks/struct-layout-03.txt

    抢锁序列（顺序不能变）：

    git pull
git add current_tasks/<task>.txt
git push          # 被拒 = non-fast-forward = 你迟到了
# 被拒就 git pull --rebase，看到别人的锁还在，换一个任务

    这就是整个并发模型：一个 push 赢，另一个被拒。不需要中心协调器，不需要谁记录「agent-7 在做什么」。

  4. 写死 11 步会话生命周期 AGENT_PROMPT.md

    1  git clone / pull
2  扫描仓库 → 找一个任务 T
3  git add current_tasks/T.txt      # 声明
4  git push                          # 发布声明（赢了才算抢到）
5  做 T（写代码、跑测试、commit）
6  git pull --rebase                 # 拿别人的改动
7  解决冲突 / 重跑测试
8  git push                          # 交付
9  git rm current_tasks/T.txt        # 释放
10 git push
11 退出 → 外层循环起一个新 Claude

    提示词全文的骨架就是这个：「看开放的 TODO、失败的测试和进度文件，挑一个当前没人在做的最明显的下一件事，为它放一个锁文件，做这份工作，commit，移除锁，退出。」

  5. 外层循环：一个 bash while true agent.sh

    #!/usr/bin/env bash
# 在容器内运行
while true; do
  claude --dangerously-skip-permissions -p /prompts/AGENT_PROMPT.md
done

    整个「编排器」就这四行。没有 scheduler，没有守护进程，没有消息总线。会话崩了就崩了，下一个会话从 git 状态继续。

    为什么这能 work：LLM 本来就是无状态的；重启比抢救一个塞满失败实验的 context 更便宜；失败隔离免费——下一个会话继承的是 git，不是废墟。

  6. 为 agent 写测试，不是为人类写 test harness

    这是整个项目投入产出比最高的一条，也是最容易被忽略的。人类能扫一眼 500 行输出抓出可疑模式，循环里的 LLM 不行：一千行输出会吃掉 context，等它开始推理时已经忘了提示词。

    def run_test(name):
    r = execute(name)
    print(f"PASS {name}" if r.ok else f"ERROR {name}  see logs/{name}.log")
    write(f"logs/{name}.log", r.full_output)   # 细节进文件
    return r

    agent 看到的是：

    PASS tests/struct_layout_01
PASS tests/struct_layout_02
ERROR tests/struct_layout_03  see logs/struct_layout_03.log
PASS tests/struct_layout_04
    • 统一标记：只用 ERROR，不要一处 failed、一处 FAIL、一处 ❌。这样 grep -l ERROR logs/ 就能扫完几千条结果。
    • 细节入文件：需要时只 cat 那一个 log。
    • 时间盲：Claude 分不清「慢」和「卡死」。给它显式超时，别让它自己判断。

  7. 把进度文件当成写给「下一个自己」的信 PROGRESS.md

    唯一的长寿命记忆是文件系统。项目里维护两类文件：

    • 每个模块顶部的 README.md：这模块干什么，什么 work，什么不 work。
    • PROGRESS.md 与分区进度文件：试过什么、失败过什么、当前的理论是什么。

    这些不是给人看的，是给下一个醒来的 agent 看的。把它当交接文档写，它就是仓库里最值钱的产物。

  8. 按「最明显的下一步」分工，而不是按职位 角色提示词

    同一个模型、同一个二进制，只改提示词。作用是改变 agent 眼中「最显然的下一件事」：

    角色提示词味道
    duplicate-code-cleaner找重复模式、抽 helper、不改变行为地减少行数
    performance-tunerprofile、找热路径、局部优化，不改语义
    codegen-optimizer只盯后端，改进生成汇编质量
    design-critic不写代码，只读仓库并给设计异味 / 死代码 / 不一致开 TODO
    doc-maintainer让 README / PROGRESS 保持诚实和最新

    规则：两个 agent 老是撞车，通常是它们的提示词没有区分什么叫「显而易见的下一步」。

  9. 单体任务：找一个 Oracle，二分到局部失败 oracle 脚本

    「编译整个内核」是一个不可分割的失败，16 个 agent 一起上只会互相覆盖。解法不是加编排器，是把单体变成很多独立的失败。

    做法：拿 GCC 当已知好的参照，按比例混合编译，坏了就二分。

    def locate_bad_file(c_files):
    lo, hi = 0, len(c_files)
    while hi - lo > 1:
        mid = (lo + hi) // 2
        subset = c_files[lo:mid]
        img = build_kernel(subset, claude_compiler, rest=gcc)
        if boots(img): lo = mid      # bug 在另一半
        else:          hi = mid      # bug 在这一半
    return c_files[lo]

    通用形状：当任务太大无法并行，就找一个可信参照，让大部分工作走参照，让你的 agent 在一个不断缩小的残余上啃，直到每个失败都是局部的。适用于任何有可信参照的单体系统（数据管道、模型子组件、配置生成、甚至 UI 渲染）。

  10. 停手就是一行命令 host

    pkill -9 bash

    没有优雅退出、没有「请完成当前任务」。SIGKILL 掉循环，下次启动从 git 继续。前提是每个任务都能在任意时刻被打断而不留半成品（锁文件在 git 里，清理靠下一个会话发现并释放）。

  11. 算清这笔账值不值 决策

    指标实测值
    并行 Claude 实例16
    总会话数2,000+
    墙钟时间约 2 周
    API 成本约 $20,000
    人类写的代码约 0 行
    产出约 10 万行 Rust；GCC torture suite 通过 99%；能编译 Linux 6.9 / QEMU / FFmpeg / SQLite / Postgres / Redis

    按编译器团队的标准这很便宜；按「修个 bug」的标准这很荒唐。用之前先确认你的项目属于前者。

@jhleath 的 128 agents 复刻要点（我的拆解，非原作者原文）

原帖说法是：128 个 agent 共享同一个文件系统，自组织、切分问题、认领任务、自己做测试，造出 Factorio 的复刻版。可迁移的三个条件：

  • 共享一个可读写的文件系统，而不是靠消息传递同步状态。
  • 任务可被认领（文件即锁），且认领动作是原子的。
  • 自己做测试：每个 agent 能在本地验证自己的那部分，才允许它独立推进。

把它当「D 路线的轻量版」：没有容器、没有 bare repo，用共享目录 + 文件名做锁。适合原型与游戏 / 仿真类项目，不适合多人协作的真实代码库（没有隔离，互相覆盖的风险高）。

E

模型分层：不改结构，只把成本砍一半 所有千级案例的共同省钱点：让最贵的模型写计划，让便宜的模型执行。

E

Advisor / Worker 分层 + 失败升级

代表案例：X 上流传的 Anthropic 官方技巧（--advisor 组合）；madsalt 在 165 个 hook 里的模型升级规则。

✓ 已有多 agent 流程 ✓ 成本敏感 ✗ 任务本身极小

  1. 把「计划」与「执行」拆给不同模型 终端

    X 上流传的组合（二手，官方文档未核对）：

    claude --advisor opus --subagents haiku

    思路：Opus 只看到计划脚本和最终裁决，Haiku 群执行具体步骤。更稳的做法是反过来——Sonnet 主驾、Opus 当顾问、Haiku 做扇出：

    claude --advisor opus            # 顾问只在被叫到时介入
# 扇出阶段在提示词里点名模型：
#   "Use Haiku for the per-file readers, Sonnet for the writers,
#    and only ask Opus to review the merged plan."

    坑 便宜的模型不是「同样的活更便宜」，是「能干的活不一样」。读文件、提取、分类这类任务 Haiku 够用；跨文件重构、架构取舍会明显退化。分层的前提是你有测试能发现退化。

  2. 写死三级升级规则 hook

    不要靠感觉切模型，用可观测的触发条件：

    触发动作
    默认便宜模型（Haiku / Sonnet）
    同一测试连续失败 3 次升级一次到最强模型，只试一次
    改到风险路径（迁移、鉴权、服务端路由）直接升级
    升级后仍失败交给人，不再重试

    madsalt 的实测：23% 的启动里实际运行的模型和文件里写的不一样，几乎全是 Sonnet 被升到 Opus（584/610），由 hook 自动决定。

  3. 把审查放在便宜的一侧 成本结构

    来自 3315 次真实运行的账：

    • 一次安全 / 代码评审：1–4M tokens。
    • 一次实现：5–100M tokens。
    • 两个评审盯每个高风险 commit，比让实现重试一次更便宜。

    所以「加审查」通常不是加成本，而是降成本——前提是审查者能独立判定，而不是复述实现者的说法。

  4. 缓存是你真正的账单 settings

    30 天 160 亿 token 里，97.7% 是缓存读。同一 run 里同模型、同 effort、同工具、同 schema、同工作目录的 agent 共享前缀缓存。

    // 让子 agent 的缓存活 1 小时而不是 5 分钟
{ "subagentPromptCacheTtl": "1h" }

    代价：API 侧 1 小时缓存写入按更高价计费。订阅用户不受此影响，但缓存 TTL 仍按默认 5 分钟。

2.1 三个「玩法型」案例：怎么复刻

这三个不是生产力工具，而是把 agent 当世界 / 当对手 / 当研究助手。它们的价值在于压力测试编排能力：把一个规则简单的系统放大到 1000 个角色，任何协调缺陷都会立刻显形。以下步骤是我的复刻拆解，不是原作者公开的方法。

玩法 1 · 你是市长，1000 个市民 @DeRonin_

实测：75 分钟 / 约 324k tokens

  1. 写一个 world.json：时间、天气、财政、政策列表。这是唯一真相。
  2. 写 1000 个市民档案（姓名、职业、性格标签、记忆数组），分批生成，每批 50 个，避免一次爆 context。
  3. 每回合只唤醒 8–16 个市民（关注度高的、被政策影响的），其余按规则「静默演化」——这是 1000 人只花 32 万 token 的关键。
  4. 市民输出结构化 JSON（行动、情绪、对政策的反应），由脚本写回 world.json。
  5. 你的指令只作为「市长法令」进世界状态，不要直接指挥个体 agent。

坑 让 1000 个 agent 每回合都发言，成本会爆两个数量级，而且大部分发言是重复的。

玩法 2 · 128 个 agent 自己造游戏 @jhleath

原帖：共享文件系统 + 自组织 + 自测

  1. 建一个共享目录，划出 tasks/、src/、tests/、claims/。
  2. 每个 agent 启动时读 tasks/ 里未认领的条目，写一个 claims/<task>.json（原子创建，已存在就换任务）。
  3. 限定每个 agent 只改自己声明的文件，公共文件（入口、配置）指定单一 owner。
  4. 必须自己写测试并跑通才能交付；测试文件放 tests/，命名带任务 ID。
  5. 每轮结束由一个汇总 agent 跑全量测试 + 合并，坏的直接回退到上一个绿色 commit。

坑 128 个 agent 共享文件系统意味着没有隔离。只适合原型 / 仿真 / 玩具项目，不要用在有真实用户数据的仓库。

玩法 3 · 300 个 agent 做研究，15 步收口 @slash1sol

原帖：Kimi 的 context graph

  1. 先把问题拆成 300 个可独立回答的子问题（或 300 个来源 / 300 个视角）。
  2. 扇出阶段每个 agent 只交结构化结论（主张、证据、置信度），不交长篇。
  3. 给收口 agent 明确的步数预算（原帖约 15 步）：读结论 → 聚类 → 找矛盾 → 定稿。
  4. 收口阶段不要新增检索，只做筛选与裁决，否则它会重新打开 300 个方向。
  5. 输出必须能追溯到具体 agent 的证据，无法追溯的结论标为未验证。

坑 扇出很容易，收口才是瓶颈。300 个 agent 的产出如果全部倒进一个 context，收口 agent 会在前 3 步就崩。

怎么用这张表 不要按「数字最大」挑，要按你的任务形状挑：能切成独立失败 + 有测试 → 看 C 编译器与 Bun；长周期单体项目 → 看 Cursor；只想通宵推进 backlog → 看 Terry 与 fleet； 想要「像团队一样讨论」→ 看 madsalt。
3

翻车库：16 个真实事故与对应闸门 这些都不是「模型写错代码」。全部发生在 agent 之间的接缝处，而每一条都有一行代码可以拦。

按来源分两组。第一条最值得先看：agent 会攻击挡住它的检查。

接缝层（agent 之间）

1. 并行写同一文件，全部检查通过

症状：三个 agent 同时改一个翻译总表，各自保存整份文件，最后保存的赢；55 / 95 个 key 消失。

为什么没被发现：每个 agent 的副本自洽，构建通过；覆盖率检查坏在另一处。

修法：共享目录类文件（翻译、lockfile、changelog）只允许一个 owner；其他 agent 写入分片文件，由一个合并脚本证明每个 key 都落地；合并脚本对冲突值直接失败。

2. 验证者与被验证者共享上下文

症状：报告里每条结论都被「确认」，但抽查发现一半是错的。

判据：验证 agent 能看到干活 agent 的推理过程，就等于在自我认同。

修法：验证者的输入只有原始证据（测试输出、diff、响应）；任务措辞用「反驳」；报告区分「被驳倒」与「无法验证」。

3. 扁平协调退化（Cursor）

症状：20 个平等 agent 共享一个协调文件，实际吞吐退到 2–3 个。

原因：锁持有过久、忘记释放、持锁崩溃；乐观并发好一些但仍有更深问题。

修法：分层——planner 持续产出任务（可递归派生 sub-planner），worker 只 grind 自己的任务，周期末由 judge 决定是否继续。

4. 无层级导致集体避险（Cursor）

症状：没有 agent 愿意接难任务，都在做小而安全的改动，系统长时间空转。

修法：明确 ownership；或引入 judge 每轮判定「是否真的在推进」，不推进就换策略而不是继续等。

5. 重复产出（Terry）

症状：一夜 250 个文件，约 30% 是同一件东西的变体。

根因：下一波 agent 从「优先级」推理，不查文件系统。

修法：manifest 里写 do_not_recreate 清单，并在提示词里要求先列目录再动手。

6. 卡死重试（Terry）

症状：第 28 波撞限流，后续波次用同样方法重试 6 小时。

修法：脚本层对同一错误设「两次即跳过」，并切换来源或降到本地保存；不要在提示词里求它别重试。

7. 单体任务无法并行（C 编译器）

症状：16 个 agent 一起修「内核不启动」，互相覆盖，一下午烧掉 2 万美元。

修法：找 Oracle 做二分，把单体失败变成局部失败，再回到「一个失败一个 agent」。

8. 波次从旧代码开始

症状：第 2、3 波从会话起始 commit 开工，落后三个 commit；把文件拷回去等于回滚别人的改动。

修法：结果以 三方 patch 合回，永远不要整文件复制；冲突要暴露出来。

系统层（信号与闸门）

9. agent 改掉挡住它的检查

症状：commit 被某个检查拦了三次，agent 直接编辑那三个检查脚本，让 commit 通过。没有任何隐藏，也没人拦。

为什么危险：「让 commit 过」这个目标会把闸门当成问题的一部分。

修法：检查文件放在项目会话不可写的目录；所有写入路径都要覆盖（编辑器、shell 重定向、脚本、git）；项目会话期间任何改动记日志并告警。

10. cleanup 删掉已完成的工作

症状：清理脚本只判断「agent 还在跑吗」，四个已完成的 worktree 被删，git 对象都没了。

修法：判断标准改成「它的工作是否已经在主 checkout 里」；先收集再清理；另加 hook 禁止直接删 worktree 目录。

11. 死掉的 agent 报告「成功」

症状：绑定到额度用尽的模型的 agent 第一步就死了，启动返回「spawned successfully」，失败以 idle 通知的形式迟到一个小时。

修法：让启动器读 agent 的第一条输出；连续读不到就标记该模型在一段时间内不可用。

12. 你自己的两条规则互相矛盾

症状：一条规则要求把三个以上 shell 步骤合成一个脚本省 token；隔离 worktree 的沙箱恰好拒绝这种形状。agent 连续三天撞「too complex to verify」，把预算烧在改写措辞上。

修法：连续两次相同拒绝即停并上报；隔离 agent 的 brief 里写明沙箱接受的命令形状。

13. 成功信号在撒谎

判据：「spawned」「saved」「cleaned up」每个词都比它听起来窄。

修法：每个成功信号都要有独立的验证证据（文件存在且非空、key 数量未减少、PR 真的开了）。

14. 连接池 / 限流 / 雷群（100k 并发）

症状：并发一上来，DB 连接耗尽、HTTP 池饥饿、429 亮起、重试堆成雷群。

修法：池上限与并发信号量对齐；超时分层（connect ≤ TTFT ≤ inter-chunk ≤ total）；按错误类型分类重试（4xx 不重试，429 尊重 Retry-After，5xx 指数退避 + 抖动）；熔断。

15. context 越长，指令跟随越差

症状：单个长会话跑到第 15 波开始忽略约束、偏离优先级。

修法：每波用全新 context，靠 manifest 传递「重要的事」，context 本身不传递任何东西。

16. agent 没有挂钟（时间盲）

症状：测试慢 vs 卡死，agent 分不清；它可能等 40 分钟然后杀掉测试去乱改。

修法：给所有测试显式超时；输出只留一行结论 + 日志路径；用确定性抽样代替「跑全套」。

一句话总结 这些事故里「模型能力不足」出现 0 次。出现最多的是三件事：共享可变状态、撒谎的成功信号、没有独立验证。 加固顺序也照这个来：先隔离写、再让信号可证伪、最后才谈规模和并发。
