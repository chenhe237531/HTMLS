01先分清三种“上千”

这三个数字经常被放在同一句话里，但它们的技术栈、成本结构和失败模式完全不同。混着谈，就会得出“编码也能轻松上千”的错误结论。

仿真型10³–10⁶

成百上千万个轻量 agent 各走各的步，彼此只通过环境或消息层耦合。没有“交付物”，只有统计结果。规模来自“便宜的单步 + 异步调度”，不是来自“聪明的个体”。

OASIS · AgentSociety · AgentScope
评测型10²–10³

每个 trial 是一个完全隔离的沙箱，跑同一道题的不同实例或不同模型。agent 之间不通信，所以规模只受沙箱配额和预算限制。

Harbor · Terminal-Bench
生产编码型10¹–10²

多个 coding agent 改同一个仓库。真正的瓶颈不是生成，是合并、验证和人工 review；开源工具的现实并发是几十，不是上千。

vibe-kanban · claude-flow
这份报告要纠正的一点

“调用上千个 agent 跑一个应用”在公开仓库里几乎没有可复现案例。能到千级的是仿真和评测；编码场景到百级就已经撞上人的审查带宽。把三类数字混用，是这类内容最常见的失真方式。

Harbor 是 Terminal-Bench 团队的评测框架：每个 trial 起一个隔离环境（Docker / Daytona / Modal / Vercel 等），跑 agent、打分、回收。README 直接写“在数千个环境中并行实验”。

04为什么编码场景到不了 1000

不是模型不够快，是下游有三个串行环节。把这三个算清楚，任何“千个 agent 写一个 App”的说法都会露馅。

4.1 审查带宽

假设每个 agent 产出一个可评审的 PR，一个熟练工程师一小时能认真看完 8–10 个中小 PR。1000 个 PR 就是 100–125 小时的纯 review；10,000 个就是 1000 小时以上，约等于一个人半年的工作量。生成可以并行，审查不能。

4.2 合并与验证

worktree 能隔离写入，但合并是串行的。N 个分支同时改同一模块，冲突数随耦合度上升；每合并一次，其他分支的测试基线就变了。所以“并行生成 1000 个分支”之后，你还得串行地跑 1000 次集成验证。

4.3 规格与验收

真正决定成败的是需求有多清楚。给 1000 个 agent 同一份模糊需求，会得到 1000 种合理解释；把它们合并，比从零写一遍更贵。这也是为什么生产编码工具的现实形态是几十个并行任务 + 人在环，而不是无人值守的千级。

反过来，什么场景适合上千

只要满足两条——agent 之间不需要达成一致、结果可以被自动打分——规模就能上去。评测与仿真正好满足，业务交付不满足。

06三档可复刻方案

按“你手上有什么”选，不要按“听起来多大”选。

十级：把并行用起来

10
  • worktree + 每个任务一个 agent（vibe-kanban 模式，或自己写 tmux 脚本）
  • 以 PR 为单位交付，人做 review
  • 预算：一顿饭钱；时间：小时级

百级：把验证自动化

100
  • Harbor + 云沙箱，先跑 oracle 校验环境，再跑 agent
  • 每个 trial 独立、可重放，结果落文件
  • 预算：几百到几千美元；时间：小时到一天

千级：先有调度器，再谈 agent

1,000+
  • AgentScope / AgentSociety 的 actor 或 Ray 路径，或自建队列
  • 必须有：并发配额、失败重放、去重、指标看板
  • 只做“不需要达成一致”的任务；否则回退到百级

07开跑前先过这九条

  • 任务可独立评分：没有自动判定标准，规模越大越像在制造噪声。
  • agent 之间不需要达成一致：需要共识就留在小规模，共识成本随 N 上升。
  • 一 trial 一隔离：容器或 VM，不要共用一个工作目录。
  • 结果可重放：输入、配置、模型版本、随机种子都要落盘。
  • 有并发闸：provider 配额、沙箱配额、token 预算三处都要限。
  • 失败不吞：超时、限流、空输出分别计数，别混成一个“失败”。
  • 成本可归因：按项目 / 数据集 / 模型分开记账。
  • 人工出口明确：哪些结果必须人看，看多少条，谁看。
  • 先跑 10 个再放大：小规模跑不通，放大只会更贵。
