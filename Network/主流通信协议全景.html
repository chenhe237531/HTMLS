01先建立坐标系

“主流通信协议”横跨很多层：既有 TCP、UDP 这种传输底座，也有 HTTP、DNS 这种基础设施，还有 MQTT、gRPC、WebRTC 这种面向具体场景的协议。把它们放在同一个列表里比较“快慢”没有意义，因为解决的问题不同。

判断一个协议是否适合，先回答四个问题：

  1. 谁发起、谁响应？客户端主动请求，还是服务端主动推送，还是双方对等？
  2. 一次交互要几条消息？一问一答、连续事件流、双向帧、还是大块数据传输？
  3. 网络有多差？公网稳定、移动弱网、受限专网、还是设备局域网？
  4. 失败时能接受什么？可以丢、必须到达、必须有序、还是必须可重放？
四个维度比“协议排名”更有用
维度选项它会排除什么
传输语义可靠字节流 / 数据报 / 消息 / 帧 / 媒体包需要严格有序却选了 UDP；只需要小消息却背了 TCP 的队头阻塞
交互模式请求-响应 / 发布-订阅 / 双向流 / 单向流 / 广播用轮询模拟推送；用消息队列做同步调用
拓扑客户端-服务器 / 代理 / 对等 / 联邦 / 总线没有公网入口却要求外部直连；多租户却用点对点
运行环境浏览器 / 移动端 / 服务端 / 嵌入式 / 工业设备浏览器不支持原生 gRPC；MCU 跑不动完整 HTTP/2 栈
一句话原则

不要问“最好的协议是哪个”，要问“在这个约束下，哪种协议的错误模式最容易接受”。协议选型的本质是选择代价，而不是选择优点。

还有一点容易被忽略：协议和 API 风格不是一回事。REST 是一种架构风格，通常跑在 HTTP 上；gRPC 是 RPC 框架与协议组合；GraphQL 是查询语言与运行时约定。把它们并列时，要分清“传输协议”“接口风格”“消息模型”三个概念。

02分层地图

现实中的协议栈并不严格对应 OSI 七层。QUIC 把传输与加密揉在一起，WebSocket 借 HTTP 升级后自己管帧，WebRTC 则是一整套协议组合。下面这张图按“数据被谁负责”来分层，比背课本更有用。

每一层解决什么问题，以及常见的错配
层代表协议解决什么常见错配
应用层HTTP、DNS、MQTT、gRPC、SIP业务语义：方法、主题、资源、邮件、会话把应用协议当传输协议用，重复造可靠性
安全 / 会话TLS、DTLS、SSH、WebSocket加密、身份、会话状态、双向帧以为“上了 TLS”就自动有授权与审计

网络层IPv4/IPv6、ICMP、IPsec寻址、路由、分片、网络层加密用应用层方案解决本该由网络层解决的路由问题
链路 / 物理Ethernet、Wi-Fi、蜂窝相邻节点之间的帧传输在应用层处理链路抖动与丢包细节
边界提醒

BGP、OSPF 这类路由协议当然也是“通信协议”，但它们属于网络控制平面，选型对象是网络设备与运营商，不是应用开发者。本文聚焦应用与传输层，以及直接服务于应用的实时、消息与设备协议。

下面按“主要用途”分组，而不是按 OSI 层分组，因为开发者通常先有场景再找协议。一个协议可能同时属于多个模式，筛选结果会按主要标签归类。

HTTP/1.1

Web & API

最普遍的 Web 协议，文本报文、请求-响应、缓存与内容协商完备。

承载
TCP，通常 80 / 443
适合
兼容性优先的 API、静态资源、遗留系统
注意
连接级串行，管道化基本不用；并发靠多连接

HTTP/2

Web & API

二进制分帧，一条 TCP 连接上多路复用请求，头部用 HPACK 压缩。

承载
TLS + TCP（浏览器要求 ALPN）
适合
多资源页面、常规 Web API、gRPC 底层
注意
仍有 TCP 队头阻塞；服务器推送实践有限

HTTP/3

Web & API

HTTP 语义跑在 QUIC 上，每个流独立，丢包不再阻塞整条连接。

承载
QUIC + UDP，通常 443
适合
移动弱网、跨地域、连接迁移场景
注意
部分网络封 UDP；需保留 HTTP/2 回退

WebSocket

Web & API

借 HTTP 升级建立全双工帧通道，浏览器与服务端可持续双向通信。

承载
TCP + TLS（也可跑在 HTTP/2 上）
适合
聊天、协作、行情、游戏、双向控制
注意
重连、心跳、鉴权、背压都要自己做

SSE

Web & API

服务器单向推送 text/event-stream，浏览器自动重连并支持断点续传。

承载
HTTP/1.1 或 HTTP/2
适合
通知、进度、日志、AI 流式输出
注意
只能服务端到客户端；文本为主

WebRTC

Web & API

浏览器原生的实时音视频与数据通道，负责采集、编码、NAT 穿透与拥塞控制。

承载
UDP（SRTP / SCTP over DTLS），失败回退 TURN/TCP
适合
视频会议、通话、低延迟互动、远程控制
注意
信令不在标准内；多人需 SFU；对称 NAT 要中继

WebTransport

Web & API

基于 HTTP/3 的多流与数据报 API，目标是把 QUIC 的低延迟能力暴露给浏览器。

承载
HTTP/3 + QUIC + UDP
适合
云游戏、实时协作、低延迟消息

浏览器支持范围需按目标平台确认

REST

架构风格

用资源与统一接口组织 HTTP API，强调无状态、可缓存与分层。

承载
通常是 HTTP/1.1、HTTP/2 或 HTTP/3
适合
公开 API、CRUD、CDN 友好、易调试
注意
不是协议；复杂聚合易产生多次往返

GraphQL

接口风格

客户端声明所需字段，服务端按 schema 返回，减少过度获取与聚合往返。

承载
HTTP POST；订阅常走 WebSocket
适合
前端驱动的数据聚合、多端复用
注意
缓存与 N+1 需专门设计；查询复杂度要限制

gRPC

RPC

Protobuf 定义契约，HTTP/2 承载，支持一元、服务端流、客户端流与双向流。

承载
HTTP/2 + TLS + TCP
适合
服务间高频调用、强类型契约、流式传输
注意
浏览器需 gRPC-Web 代理；调试与网关要额外投入

JSON-RPC

RPC

用 JSON 描述方法名与参数的最小 RPC 约定，规范简单、实现成本低。

承载
HTTP、WebSocket、stdio 等皆可
适合
工具集成、以太坊节点、MCP、内部轻量调用
注意
无标准 IDL；错误码与版本要自行约束

SOAP

RPC

基于 XML 信封与 WSDL 契约的企业级调用协议，WS-* 扩展覆盖安全与事务。

承载
HTTP（也可 SMTP 等）

MQTT

轻量发布-订阅协议，主题寻址，支持 QoS、保留消息、遗嘱与会话。

承载

适合
海量设备上报、远程控制、移动弱网

AMQP 1.0

ISO 标准的消息协议，定义会话、链路、流控与投递确认，强调跨厂商互操作。

消息

NATS

消息

极简的文本协议，主题寻址，核心模式为至多一次；JetStream 补齐持久化。

承载
TCP + TLS

微服务事件、服务发现式请求、边缘消息

核心模式不保证送达；持久化要显式启用 JetStream

RESP

消息 / 数据

Redis 的序列化协议，简单可读、支持管道化；Streams 可做轻量消息流。

承载
TCP + TLS
适合
缓存、会话、排行榜、轻量事件
注意
不是通用 broker 标准；持久化与投递语义有限

TCP

传输

面向连接的可靠字节流，负责重传、排序、流控与拥塞控制。

语义
字节流，不保留消息边界
适合
HTTP、数据库、文件、需要可靠有序的通道
注意
应用要自己做帧；丢包会阻塞同连接上的所有流

UDP

传输

无连接数据报，保留消息边界，不保证送达、顺序或拥塞控制。

语义
独立数据报
适合
DNS、音视频、游戏、QUIC 等自带机制的协议
注意
网络拥塞时要有自己的退让策略，否则容易伤害其他流量

QUIC

传输

基于 UDP 的通用传输，内建 TLS 1.3、独立流、0-RTT 与连接迁移。

语义
可靠流 + 可选数据报扩展
适合
HTTP/3、移动网络、需要低握手延迟的场景
注意
用户态实现带来 CPU 成本；UDP 可能被网络策略拦截

CoAP

IoT

面向受限设备的类 REST 协议，报文极小，支持 Observe 与块传输。

承载
UDP + DTLS；常与 LwM2M 搭配
适合
低功耗传感器、NB-IoT、局域网设备
注意
与 HTTP 生态之间通常需要代理转换

Modbus

工业

工业现场最常见的寄存器读写协议，主从模型，简单到几乎任何设备都能实现。

承载
串口（RTU/ASCII）或 TCP
适合
PLC、仪表、传感器、SCADA 采集
注意
原生无认证与加密；应限制在受控 OT 网络

OPC UA

工业

带信息模型与安全模型的工业互操作标准，支持浏览、订阅与历史访问。

承载

适合
产线集成、跨厂商设备、需要语义建模的系统

CAN

多主总线，按优先级仲裁，广泛用于汽车与工业控制，CAN FD 提升带宽。

RTP / RTCP

04重点协议详解

目录给你候选，这一节解释候选之间的真正差异。读的时候抓住一条主线：可靠性、顺序、延迟、状态这四件事分别由谁负责。

详解默认折叠，打印时会自动展开

4.1 传输底座：TCP、UDP、QUIC

应用层协议的性能差异，很多时候来自它选了哪个传输底座。TCP 把“可靠有序”做成默认，UDP 把它交还给应用，QUIC 则在 UDP 之上重新实现了可靠流，但把“流”拆开，避免彼此阻塞。

三种传输底座的关键差异
特性TCPUDPQUIC
连接建立三次握手（可 TCP Fast Open）无连接1-RTT；会话恢复可 0-RTT
可靠性重传、确认、排序不提供每条流独立重传
顺序全局字节流有序不保证流内有序，流间独立
队头阻塞有：一个丢包阻塞整条连接无无跨流阻塞；单流内仍有
加密外挂 TLS外挂 DTLS 或自定义内建 TLS 1.3
连接迁移依赖四元组，换网即断无连接概念Connection ID 支持换网续连
部署现实内核实现，几乎无处不在内核实现，但常被策略限制用户态实现，需 UDP 可达
为什么“TCP 粘包”其实是应用层没有定义帧

TCP 只保证字节按序到达，不保留发送方 write() 的边界。一次读取可能拿到半个消息，也可能拿到两个半消息。解决办法不是“换协议”，而是在应用层定义长度字段、分隔符或固定头。

HTTP/1.1 用 Content-Length 或 chunked 编码，HTTP/2 用帧长度，WebSocket 用帧头，都是同一件事：在字节流上重建消息边界。

QUIC 快在哪里，又慢在哪里

快在握手与恢复：传输参数和 TLS 1.3 合并协商，常见场景 1-RTT 建立；恢复会话可以 0-RTT 发送早期数据。流之间互不阻塞，移动网络切换 Wi-Fi/蜂窝时连接可以继续。

慢在实现与网络策略：QUIC 在用户态处理，包处理开销高于内核 TCP；部分企业网络、老防火墙会丢弃或限速 UDP。因此生产上通常同时保留 HTTP/2，通过 Alt-Svc 或 DNS HTTPS 记录协商升级。

4.2 Web 与 API：HTTP 的三次进化

HTTP 的语义（方法、状态码、缓存、内容协商）在三个版本之间基本不变，变的是“如何在连接上传输”。这也是为什么升级 HTTP/3 通常不需要改业务代码。

HTTP/1.1文本每连接一个请求；靠多连接并发连接数、队头阻塞、头部重复兼容性兜底；静态资源可继续用
HTTP/2二进制帧单连接多路复用TCP 层丢包阻塞所有流常规 Web 与 API 的默认选择

只需要“服务端推、客户端收”，SSE 往往比 WebSocket 更省事：它复用 HTTP 基础设施，自带重连与事件 ID。需要双向、二进制或复杂会话时，再上 WebSocket。

4.3 RPC：gRPC、Thrift、Dubbo、JSON-RPC

RPC 的目标是“像调用本地函数一样调用远程服务”。代价是隐藏了网络：超时、重试、序列化、连接复用、错误语义都需要框架补齐。选 RPC 框架，实际是在选契约方式与生态。

常见 RPC 方案对比

gRPCProtobuf IDLHTTP/2四种模式需 gRPC-Web + 代理云原生、多语言、服务网格
ThriftThrift IDL自定义二进制 / 框架传输有限不直接大数据、跨语言内部服务

别把 gRPC 用错地方

gRPC 很适合内部高频调用与强类型契约，但不适合直接暴露给浏览器或第三方：需要代理转换、调试不如 curl 直观、部分网关对 HTTP/2 支持不完整。公开 API 往往仍是 REST/JSON 更稳妥。

gRPC 的四种调用模式分别解决什么
  • 一元（Unary）：一请求一响应，对应普通 RPC。
  • 服务端流：客户端发一次请求，服务端持续推送，适合订阅、下载、进度。
  • 客户端流：客户端连续上传，服务端最后汇总，适合采集、批量写入。
  • 双向流：双方独立收发，适合实时协作、长会话。

流式并不自动带来低延迟；它只是省掉重复建连与请求头。背压、超时、取消仍要按框架语义正确处理。

4.4 消息与事件：MQTT、AMQP、Kafka、NATS

“消息队列”常被当成一个东西，实际上有三种不同模型：设备消息总线（MQTT）、企业队列/路由（AMQP）、可重放日志（Kafka）。它们的投递语义与运维方式差别很大。

消息系统的语义差异
系统模型投递语义顺序历史重放典型规模
MQTT主题发布-订阅QoS 0/1/2（到 broker）不跨主题保证仅保留消息，非完整历史海量连接、小消息
AMQP 1.0队列 + 链路未确认 / 已确认，支持事务按链路取决于 broker 持久化企业应用、可靠队列
Kafka分区追加日志至少一次；事务可做精确一次分区内有序按 offset 重放高吞吐日志与流处理
NATS主题 + JetStream核心至多一次；JetStream 至少一次主题内近似有序JetStream 可持久化微服务事件、低延迟
Redis Streams日志 + 消费组至少一次流内有序可重放，受内存限制轻量事件、会话内消息
MQTT 的 QoS 2 为什么不是“端到端精确一次”

MQTT 的 QoS 描述的是客户端与 broker 之间的投递保证。QoS 2 通过四次握手避免重复，但当消息经过桥接、规则引擎、多个 broker，或最终写入业务数据库时，端到端仍可能重复或丢失。

真正的“恰好一次”需要业务侧幂等键、去重表或事务性写入。把 QoS 2 当成业务幂等，是物联网系统里很常见的误解。

Kafka 为什么不能当普通任务队列用

Kafka 的消费进度是 offset，不是逐条 ACK。一条消息处理失败，通常不会只重投那一条，而是回退 offset 或进入重试主题；分区数决定并行度，扩容分区还会影响键的顺序。

它擅长“高吞吐、可重放、按分区有序”的流，不擅长“每条任务独立确认、延迟重试、优先级队列”。后者更适合 RabbitMQ、SQS 或数据库队列。

AMQP 1.0 与 RabbitMQ 常见的 AMQP 0-9-1 不是一回事

AMQP 1.0 是 ISO/IEC 19464 标准，定义了会话、链路、流控与投递状态，强调跨厂商互操作。RabbitMQ 长期默认使用的是 AMQP 0-9-1，它的 exchange/queue/binding 模型更广为人知，但线协议与 1.0 不同。

选型时要确认客户端库、broker 插件与网关支持的是哪一版，不要只看“支持 AMQP”这句话。

4.5 IoT 与工业：从 CoAP 到 OPC UA

物联网协议的分水岭通常是“设备有没有稳定的 TCP/IP 与足够内存”。有，就走 MQTT/HTTP；没有，就看 CoAP、MQTT-SN 或现场总线。工业场景还多一层：语义建模与安全边界。

设备与工业协议对照
协议承载模型安全适合
CoAPUDP + DTLS类 REST，支持 ObserveDTLS / OSCORE低功耗传感、局域网设备
MQTT-SNUDP 等非 TCP 链路MQTT 的主题发布-订阅依赖底层或网关传感器网络、需要网关汇聚
LwM2M通常跑在 CoAP 上设备管理与对象模型DTLS远程固件、配置、设备生命周期
Modbus串口 / TCP主从寄存器读写原生无PLC、仪表、SCADA 采集
OPC UA二进制 TCP / HTTPS / WS信息模型 + 订阅证书、签名、加密跨厂商产线、语义化集成
CAN差分总线帧与优先级仲裁原生无车载、电机、实时控制
CoAP 还是 MQTT

需要 UDP、极低功耗、请求-响应语义时选 CoAP；需要 broker 汇聚、主题分发、海量连接与 QoS 时选 MQTT。两者都能对接平台，差别主要在“谁维护连接与状态”。

LoRaWAN、NB-IoT、Zigbee 更偏链路/网络接入，不是应用消息协议；设备上仍然可以用 CoAP、MQTT-SN 或自定义二进制载荷。选型时要把“接入方式”和“应用协议”分开看。

工业网络还有一条硬规则：不要为了远程访问把 Modbus、CAN 直接暴露到公网。合理做法是边缘网关做协议转换与白名单，OT 与 IT 之间加隔离，运维通道走 VPN 或跳板。

4.6 实时音视频：WebRTC、RTMP、HLS/DASH、SRT

音视频没有“一个协议通吃”。通常是一条链路：采集 → 上行/贡献 → 服务端处理 → 分发 → 播放，每一段的最优协议不同。

按链路位置理解媒体协议
协议链路位置承载延迟量级典型用途
WebRTC端到端 / 分发UDP（SRTP），TURN 回退通常亚秒级会议、通话、互动直播
RTSP + RTP控制 + 局域网媒体TCP 控制 + UDP 媒体低IP 摄像头、监控
RTMP采集上行TCP较低OBS 推流、平台 ingest
SRT跨公网贡献UDP + ARQ低赛事回传、远程制作
HLS / DASH大规模分发HTTP数秒到数十秒直播、点播、CDN
WebRTC 到底包含哪些协议

WebRTC 是一套组合：信令（通常由业务自己用 HTTPS/WebSocket 实现）、ICE 选路、STUN 发现公网映射、TURN 中继、DTLS 握手、SRTP 传输媒体、SCTP 承载数据通道，再加拥塞控制与抖动缓冲。

一对一可以走 P2P；多人会议通常用 SFU（选择性转发），因为每个端只需上行一路、下行多路，比 MCU 混流更灵活。SFU 的带宽与地理分布会直接决定体验。

RTMP、SRT、HLS 不是替代关系

RTMP 生态成熟、兼容性好，但基于 TCP，弱网下容易累积延迟；SRT 用 UDP + ARQ，在不稳定链路上更低延迟、更能抗丢包，适合“把现场信号送回机房”；HLS/DASH 把内容切片走 HTTP，靠 CDN 大规模分发，代价是延迟较高。

常见组合是：SRT 或 RTMP 上行 → 转码 → HLS/DASH 分发；互动场景则直接 WebRTC。

4.7 基础设施：DNS、SSH、邮件、监控与时间

这些协议不直接承载业务功能，但几乎每个系统都依赖它们。它们出问题时，表现往往像“应用故障”，排查却要从基础设施开始。

几个容易混淆的点：SFTP 不是 FTP over TLS，它只是 SSH 的一个子系统；FTPS 才是 FTP 加 TLS。FTP 的控制连接与数据连接分离，主动/被动模式还涉及防火墙与 NAT，新系统通常直接用 SFTP 或 HTTP 对象存储。

局域网文件共享还常见 SMB、NFS 与 WebDAV：SMB 在 Windows 生态最普遍，NFS 在 Linux/Unix 环境常用，WebDAV 则借 HTTP 做跨平台文件访问。它们更偏存储协议，选型时重点看客户端支持、权限模型与跨网段访问，而不是“传输快不快”。

4.8 安全与隧道：TLS、IPsec、WireGuard

安全协议解决的是“机密性、完整性、身份”，不自动解决“这个人能不能做这件事”。认证之后的授权、最小权限与审计，仍然要在应用层设计。

三种常见加密通道的边界
方案作用层典型用途密钥 / 身份注意

IPsec网络层站点到站点 VPN、远程接入IKEv2、证书或预共享密钥配置复杂；NAT 场景要 NAT-T
WireGuard网络层（UDP 隧道）站点互联、远程接入、覆盖网络Curve25519 公钥不带 NAT 穿透与密钥分发，需要上层补齐
SSH应用层会话运维、端口转发、SFTP主机密钥 + 用户密钥转发要限制，避免变成万能内网入口

TLS 1.3 把握手压缩到 1-RTT，并用 AEAD 与前向安全作为默认。会话恢复的 0-RTT 能省一次往返，但早期数据可能被重放，只应承载幂等请求。mTLS（双向证书）常用于服务网格与设备身份，但证书轮换与吊销必须有自动化，否则会变成新的故障源。

WireGuard 的优势是“小到可以读懂”，代价是把组网、发现、密钥分发留给上层产品；IPsec 的优势是标准化程度高、设备支持广，代价是配置与排错复杂。两者都不是“开了就安全”，访问控制仍要单独做。

“首选”是默认情况下最省事的答案，不是唯一答案。如果你的团队对某个协议更熟、可观测性更完整，那个协议往往就是更好的选择——运维能力也是选型约束的一部分。

06选型向导

选三个条件，得到一个默认组合。它不替你做最终决定，但能快速排除明显不合适的方案。

默认组合：HTTP/2（或 HTTP/3）+ JSON；保留 HTTP/1.1 作为兼容兜底。

使用边界

向导只覆盖“协议与组合”层面，不替代容量评估、安全评审与合规判断。生产选型还应做一次真实网络下的压测与故障演练。

07典型组合栈

真实系统很少只用一个协议。下面这些组合可以直接作为方案讨论的起点，再按团队能力与基础设施调整。

现代 Web 应用

优先 HTTP/3，失败回退 HTTP/2；静态资源走 CDN。

HTTP/3→ QUIC→ UDP→ IP
回退：HTTP/2 → TLS 1.3 → TCP

微服务同步调用

强类型契约 + 多路复用；异步事件另走消息系统。

gRPC→ Protobuf→ HTTP/2→ TLS→ TCP

IoT 设备上云

设备只连 broker；平台侧再桥接到流处理与存储。

MQTT→ TLS→ TCP→ Broker
后端：MQTT → Kafka → 流处理 / 数据库

实时协作 / 聊天

HTTP 负责登录与历史，WebSocket 负责在线增量。

HTTPS 鉴权→ WebSocket→ TLS→ TCP

视频会议

信令走 HTTPS/WS；媒体优先 P2P，多人经 SFU 转发。

WebRTC→ SRTP→ UDP
信令：HTTPS / WebSocket 回退：TURN over TLS/TCP

大规模直播

上行重稳定，下行重覆盖；CDN 是分发核心。

SRT / RTMP 上行→ 转码→ HLS / DASH→ CDN

工业数据采集

现场协议不出 OT 区，由网关统一成平台可消费的协议。

Modbus / CAN→ 边缘网关→ OPC UA / MQTT→ 平台

远程接入与运维

管理面与业务面分开；默认不暴露任何入站端口。

WireGuard→ UDP + SSH（仅运维网）
审计：跳板机 + 会话记录 + 最小权限

08常见误区

下面这些说法在方案评审里经常出现。它们不是完全错误，而是省略了关键前提。

“UDP 不可靠，所以生产不能用”

UDP 本身不提供可靠性，但 QUIC、SRTP、SRT 都在它之上实现了各自需要的重传、拥塞控制或纠错。选 UDP 不是“放弃可靠”，而是“把可靠性交给更懂业务的层”。真正危险的是裸用 UDP 却没有拥塞控制。

“WebSocket 一定比 HTTP 快”

WebSocket 省掉了重复请求头与建连，但代价是长连接状态、心跳、重连、代理兼容与横向扩展。低频、简单的请求用普通 HTTP 往往更快也更稳；只有持续双向交互才值得长连接。

“gRPC 会全面取代 REST”

gRPC 在内部服务、强类型契约与流式场景优势明显；但浏览器直连、公开 API、第三方集成、简单调试仍然偏向 REST/JSON。很多系统是“内部 gRPC，边缘 REST”，而不是二选一。

“MQTT 可以承担所有消息场景”

MQTT 擅长海量连接、小消息与设备控制，但不提供完整历史重放、复杂路由、批量吞吐与流处理语义。日志管道、事件溯源、任务队列应分别交给 Kafka、AMQP 或专用队列。

“HTTP/3 一定比 HTTP/2 快”

HTTP/3 的优势在丢包、移动网络与连接迁移；在稳定低延迟的内网，差异可能很小，甚至因用户态 QUIC 的 CPU 开销而略慢。它也不是“打开开关就生效”，需要客户端、服务端、CDN 与网络策略一起支持。

“上了 TLS 就安全了”

TLS 保护传输中的机密性与完整性，并验证服务端身份；它不阻止越权访问、注入、密钥泄露或错误配置。认证、授权、输入校验、密钥管理、审计，一个都不能少。

“协议越新越好”

新协议通常解决了旧问题，也带来新的运维成本：可观测性、团队熟悉度、中间件支持、故障排查工具。选型要算总成本，而不是只看协议版本号。

“MQTT QoS 2 就是端到端恰好一次”

QoS 2 只保证客户端与 broker 之间的单跳语义。经过桥接、规则引擎、多 broker 或写入数据库后，仍可能重复或丢失。端到端幂等必须由业务键与去重机制保证。

“长连接一定比轮询省资源”

长连接要占文件描述符、内存与心跳流量，还要处理断线重连与广播扇出。事件非常稀疏时，带缓存的轮询可能更简单、更省资源。关键看连接数、事件频率与运维能力。

“TCP 粘包是 TCP 的缺陷”

TCP 是字节流，本来就不保留消息边界。所谓“粘包/拆包”是应用层没有定义帧。长度前缀、分隔符、固定长度或自描述格式，任选一种都能解决。

09术语与标准

术语表

RPC
远程过程调用。把网络请求包装成函数调用，需要框架处理序列化、超时、重试与错误。
发布-订阅
发送者把消息发到主题，多个订阅者按规则接收，双方不直接寻址。
QoS
服务质量等级。MQTT 中表示消息在客户端与 broker 之间的投递保证，不等同于端到端业务保证。
队头阻塞
前一个数据单元未完成，后面的数据即使已到达也不能被处理。TCP 丢包会阻塞整条连接。
多路复用
在一条连接上并发承载多个逻辑流，减少建连与端口开销。
背压
消费者处理不过来时，让生产者降速的机制。没有背压的推送最终会耗尽内存或拖垮服务。
幂等
同一操作执行多次与执行一次的结果相同。重试、消息重复、0-RTT 重放都依赖它。
0-RTT
会话恢复时在握手完成前发送早期数据，省一次往返；代价是可能被重放。
NAT 穿透
让位于 NAT 后的双方建立直接连接，常用 STUN 发现映射、ICE 选路、TURN 中继兜底。
SFU / MCU
多人音视频的两种服务端模式：SFU 选择性转发多路流，MCU 混流后分发。
ABR
自适应码率。客户端根据带宽与缓冲切换不同清晰度的分片。
Broker
消息中间节点。负责接收、路由、存储与投递消息，MQTT、AMQP、NATS 都依赖它。
Partition / Offset
Kafka 的分区与消费位点。分区决定并行度与顺序范围，offset 用于记录消费进度与重放。
mTLS
双向 TLS。客户端与服务端都出示证书，常用于服务网格与设备身份认证。
DTLS
面向数据报的 TLS，为 UDP 提供加密与握手，WebRTC 与 CoAP 会用到。
拥塞控制
根据网络反馈调整发送速率，避免把链路打满。TCP、QUIC、WebRTC 都有各自实现。
