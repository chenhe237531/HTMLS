01

结论先行

先看这一段，决定要不要继续。

“现成开源方案直接拼”这条路已经断了。 2025-10-20，chatlog（9.2k star）和 PyWxDump（9.6k star）在同一天因腾讯法务函删除全部代码； 2026-07-10，WeChatFerry（6.8k star）被作者归档为只读；chatlog-bot 已返回 451。 依赖这些仓库的教程和脚本，现在大多已经跑不起来。
可行的路线是“锁定版本 + 自建解密/导出 + 自建 MCP Hub”。 核心逻辑不复杂：取密钥 → 解密 SQLite → 解析消息表 → 建全文索引 → 暴露 MCP 工具。 代码量约 500–1500 行，好处是完全可控、不会被删库、不依赖第三方二进制。

最关键约束

4.0.3.80 / macOS 取密钥上限

再高的版本，密钥不再常驻内存，内存扫描直接失效。

方案 D 的问题

Windows only

wcferry 注入的是 Windows 的 WeChatWin.dll，macOS 没有对应实现。

建议节奏

先读 后写

先做“导出 + AI 读取”，实时自动回复放到第二阶段。

03

版本矩阵：三种“低版本”不是一回事

选错版本是这类项目最常见的返工原因。

只做导出 → 锁 4.0.3.x

Windows 上限
4.0.3.36
macOS 上限
4.0.3.80
原因
再高的版本密钥不再长时间驻留内存，内存扫描拿不到。
优点
不需要绕“低版本登录限制”，不修改微信二进制，风险最低。
代价
不能实时收发；只能读已有数据。
这是本项目第一阶段应采用的口径。

要实时收发 → 需要 Hook，但平台受限

WeChatFerry
仅 Windows，最后适配 3.9.12.51，已归档。

Windows，覆盖 3.6 → 4.2.0.9，活跃。
macOS
没有等价的 DLL Hook 实现。

在 macOS 上，“Hook 实时收发”这条路实际上不成立。可行的替代是 数据库监听 + Accessibility 发送，属于“伪实时”，维护成本更高。

04

推荐架构：本地 Hub，不上云

数据只在本机流转；AI 通过 MCP 读取，而不是把聊天记录上传。

受版本约束 自建核心 可替换

四条设计原则

  1. 数据层只读。永远不写回微信数据库——写回没有技术必要，风险却最高。
  2. MCP 是接入 AI 的标准答案。比自建聊天 UI 省一个数量级的工作量，而且 Claude/Cursor/Cherry Studio 都能直接用。
  3. 先 FTS5，后向量。几 GB 数据用 SQLite 全文索引足够；embedding 是加分项，不是前置条件。
  4. 一份数据三种出口。JSONL 保留原始、CSV 供分析、静态 HTML 供存档与人工核对。
05

macOS 落地路径

按顺序执行；前四步做完就能导出，第五步之后才是 AI。

  1. 锁定版本并禁止自动更新安装 macOS 微信 ≤ 4.0.3.80；设置里关闭自动更新；hosts 阻断 dldir1.qq.com 与 dldir1v6.qq.com。
  2. 手机 → 电脑迁移历史手机微信：我 → 设置 → 通用 → 聊天记录迁移与备份 → 迁移到电脑。PC 端默认只有本机收发的消息，这一步不能省。
  3. 提取密钥用 lldb attach 微信进程（需临时 csrutil disable），或重签微信后走 task_for_pid。取完密钥可以立刻把 SIP 开回去。
  4. 批量解密SQLCipher 4：AES-256-CBC + HMAC-SHA512，page 4096，reserve 80，KDF 64000/SHA512；微信 4.x 每个库独立 key。几 GB 建议按库分批，避免一次性占满内存。
  5. 解析与索引消息表按 Msg_<md5(wxid)> 分表；处理 type=49 的 XML、zstd 压缩内容、.dat 图片（XOR/V1/V2 三代）。写入 SQLite 并建 FTS5。
  6. 导出三件套JSONL（原始）+ CSV（分析）+ 单文件 HTML（人工核对）。先做小样本，确认字段对齐再全量跑。
  7. 挂 MCP暴露 search_messages / get_session / get_contact 三个工具，接入 Claude Desktop、Cursor 或 Cherry Studio。
几 GB 的注意点：不要在浏览器里一次性渲染全部消息；导出 HTML 要按会话/时间分片。 解密和索引都做成可断点续跑，避免中途失败重来。
06

方案 D 在 macOS 上的修正

你选了 D（实时 AI 助手）。原方案是 Windows + wcferry，在 macOS 上必须换实现。

原方案 D

Windows 3.9.12.51 + wcferry

DLL 注入 → 消息回调 → LLM → 直接发送。功能最全，后台可跑。

macOS 不可用

macOS 等价物

DB 监听 + Accessibility 发送

fsnotify 发现新消息 → Hub → LLM → AppleScript/AX 发送。没有真正的消息回调，靠文件变化与轮询。

伪实时 · 需维护

建议拆成两个阶段

阶段能力技术风险建议
第一阶段 导出 + AI 读取（问答、总结、检索） DB 解密 + FTS5 + MCP 低 先做，能覆盖 80% 需求
第二阶段 新消息监听 + AI 自动回复 fsnotify + Accessibility 中 确认第一阶段稳定后再加
为什么这样拆：“读”只需要数据库，失败也不影响微信本身； “写”要操作微信 UI，一旦版本更新就可能失效，而且更容易触发风控。 先读后写，出问题时损失最小。
07

风险与合规

这一节不是免责声明，是选型依据。

已有明确先例：腾讯对 chatlog、PyWxDump 发出法务函，并公开了针对“违规获取及利用微信终端用户数据行为”的打击公告。 公开分发、SaaS 化、代运营，是风险最高的三种用法。
路线封号风险法律风险说明
数据库只读解密最低中只读内存取密钥，不改微信逻辑；但仍属非官方手段。
UI 自动化中中行为层接近真人；4.0 后维护成本高。
Hook 注入中高中高修改进程内存，可被完整性校验/模块扫描发现。
协议模拟（PadLocal）最高高服务端可识别；社区多起封号。

必须遵守的边界

  • 只处理本人账号、本人数据，不碰他人聊天记录。
  • 本地运行、不公开分发、不提供服务；代码不进公开仓库。
  • 导出数据全盘加密（FileVault / VeraCrypt），不进网盘、不进 Git。
  • 先用小号验证链路，确认稳定后再考虑主号。
  • 不做“老板监控”、代运营、群发营销——这是打击重点。
