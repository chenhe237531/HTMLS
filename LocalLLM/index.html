01

速览与结论

这不是「谁更强」，而是「谁更适合你的负载」。原文的结论是：当本地 AI 从“偶尔跑一下”变成“持续交付”，硬件需求从「能装下模型」转向「能稳定地同时服务多个任务」。

Mac Studio 路线

统一内存、低功耗、安静、生态成熟。适合单人写作、编码、图像与日常对话。

双 Thor 路线

算力与并发更强、可长时间满载。适合多 Agent、长上下文、团队共享。

真正的分水岭

不是 tok/s，而是并发、TTFT、长上下文与持续稳定性。单人体验和多任务吞吐是两种指标。

一句话结论 个人创作者优先 Mac Studio；小型团队 / 重度 Agent 工作流优先双 Thor（或同类算力舱）。介于两者之间的人，先问「你需要同时服务几个任务」，而不是「谁跑分高」。
读之前：原文数据的边界 文中型号与数字（M5 Ultra、DeepSeek V4.1 Flash 1017、1M 上下文、8 并发等）部分无法从公开产品页直接核验。本报告把「原文数据」「公开规格」「推断」分开标注，避免把一张概念图当成评测结论。

03

决定体验的六个变量

同样叫“跑本地大模型”，单人对话和多人 Agent 工作流看的根本不是同一组指标。

1 · 容量：能不能装下

模型权重 + KV cache + 运行时开销。低比特量化能省容量，但会牺牲质量；长上下文会让 KV cache 迅速膨胀。

2 · 带宽：单路快不快

自回归解码通常受内存带宽限制。Mac 的统一内存带宽是它的核心优势；Thor 的单机带宽是公开规格，但双机不会自动合并带宽。

3 · 算力：prefill 与批处理

TOPS/TFLOPS 更影响长 prompt 的 prefill、批处理与多模态；对单路逐 token 解码的帮助没有想象中大。

4 · 并发：总吞吐

单人只看 TTFT 与 tok/s；团队看并发下的总吞吐与尾延迟。并发上去，单路速度通常下降。

5 · 软件：能不能跑好

MLX 与 CUDA/Jetson 的量化、算子、推理引擎成熟度不同。同一个模型，换框架可能差一倍。

6 · 持续运行：能不能一直跑

功耗、散热、噪音、稳定性决定它能不能当“生产力”，而不是周末玩具。

原文最容易被误读的一句 “总吞吐 200 tok/s”不是“每条都 200 tok/s”。它通常意味着多路并发下的合计吞吐；单路速度仍由带宽与模型决定。

06

场景与决策

选 Mac Studio

  • 单人使用：写作、编码、图像、日常问答
  • 上下文大多在 4K–32K，偶尔更长
  • 需要安静、低功耗、开箱即用
  • 不想维护集群与驱动
  • 预算优先，且能接受低比特量化的质量取舍

选双 Thor 算力舱

  • 小型团队共享，或 4–8 个 Agent 并发
  • 长上下文、长文档、持续批处理
  • 需要长时间满载运行与稳定散热
  • 有人能维护 CUDA/Jetson 栈与集群
  • 更看重总吞吐与尾延迟，而不是单机安静

07

被忽略的瓶颈

带宽 vs 算力

逐 token 解码吃带宽，长 prompt 的 prefill 吃算力。只堆 TOPS 不一定让聊天更快；只堆带宽也不一定扛得住并发。

KV cache 会吃掉容量

上下文越长、并发越多，KV cache 越大。百万上下文不是“免费”的，需要算清每路的内存占用。

双机不是双倍

两台设备做模型分片会引入跨机通信开销；单路速度不一定提升，更多是容量与并发收益。

量化质量

2/3-bit 与 NVFP4 都能省内存，但对代码、数学、长文连贯性的影响要用自己的任务测。

软件成熟度

同一模型在不同引擎上的吞吐差异，可能大于两台硬件的差距。

散热与降频

短跑分不等于长稳。连续几小时满载后的频率、噪音与稳定性才是生产力指标。
