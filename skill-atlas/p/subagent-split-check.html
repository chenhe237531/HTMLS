要不要拆 Subagent

Subagent 是管 context 的工具，不是分地盘的工具。默认一个主循环，只有明确条件成立才拆。

第 01 / 17 篇 stack ronny 规划与拆分 工程笔记 01

01它治什么病

多 agent 被当成组织架构来用：A 负责前端、B 负责后端、C 负责测试。结果是每个 agent 只握着一块局部信息，真正的状态在交接处丢掉，主循环并没有因为拆分而变好，反而多出几段无法核对的转述。

02机制

  1. 先问有没有 context 理由：单循环因为上下文膨胀而实测变差、任务可并行且用完即弃、工具或指令互相冲突——三条至少成立一条。
  2. 再问决定性问题：后面还需要原始中间输出，还是只要一个结论？只有“只要结论”的工作适合拆。
  3. 要拆就沿 context 边界切：子任务几乎不依赖系统其余部分，返回压缩结果（判定、清单、小结构对象）。
  4. 拆之前先找更便宜的解法：合并工具、把流程写成 skill、把状态落到文件。
  5. 已有的一堆 subagent 要合并回去：先建小 eval，从最常调用、最耦合的开始，一次合并一个。

03规则要点

默认值
一个主循环 + 按需加载 skill。拆是例外，不是默认架构。
不算理由
“这块归另一个团队”“这是另一类问题”都不是拆分理由，那只会制造有损交接。
暴露方式
把 subagent 暴露成主 agent 的一个工具，保住用户对话；只有真的需要直接对话时才整体移交。
合并顺序
最常调用、读写同一份数据、互相喂输入的优先合并。prompt 变 skill，API 调用变工具。
保留条件
只有合并后的版本实测更差才保留原 subagent。不要因为“当初就是这么设计的”保留。
原文关键句（English）
Subagents are a tool for managing context, not for dividing up territory. Default to one main loop with skills loaded on demand. Split only when one of the conditions below is clearly met.

04落到你的场景

可以直接用

你的 HTML 交付流程里，真正值得拆的只有两处：独立审查（干净 context、只回结论）和素材调研（可并行、用完即弃）。把“写 HTML”“调样式”“补文案”拆给三个 agent 只会让它们互相猜。

05边界与反例

别用过头

没有 eval 就没有“实测退化”这回事，此时任何拆分都是猜测。单文件、单人维护的项目通常先优化 context 更划算。

06关联

independent-review独立审查只给 reviewer 三样东西：diff、需求、测试结果。作者的推理过程一律不给。 harness-experiment把改动当实验先测量，一次只改一处，只保留通过测试的。看翻转任务，不只看平均分。 tool-budget-audit审计工具占用的 Context工具定义常驻、工具结果回灌，还顺带让模型选错工具。先量，再做减法。
