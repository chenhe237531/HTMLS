01先选一条路径

新手路径

先解决三件最痛的事：自审不可靠、跨会话丢状态、长会话跑偏。

  1. 独立审查
  2. 写交接文档
  3. 长会话自查

质量路径

从拆 PR 到回评论，一条完整的评审链路。

  1. 把大改动切成小 PR
  2. 代码评审的标准与流程
  3. 怎么写评审意见
  4. 作为作者回应评审

省钱路径

工具和注入项都在吃 context，先把账算清再动手。

  1. 审计工具占用的 Context
  2. 审计每轮的上下文税
  3. 长命令与后台任务

subagent-split-check01要不要拆 Subagent

Subagent 是管 context 的工具，不是分地盘的工具。默认一个主循环，只有明确条件成立才拆。

规划与拆分 · ronny engineering-small-prs02把大改动切成小 PR

“小”指的是概念聚焦、自包含，不是行数少。审得完、退得回、方向变了不白干。

规划与拆分 · ronny engineering-change-descriptions03写清改了什么、为什么

变更描述是永久的工程史：现在让 reviewer 看懂，以后让维护者找得到。

规划与拆分 · ronny tool-budget-audit04审计工具占用的 Context

工具定义常驻、工具结果回灌，还顺带让模型选错工具。先量，再做减法。

Context 与工具 · ronny context-tax-audit05审计每轮的上下文税

缓存按前缀匹配，一个字节变了，后面全部作废。稳定在前，易变在后。

Context 与工具 · ronny long-session-check06长会话自查

Context window 是工作台，不是仓库。压缩和 memory 都有损，重要状态要早点写进文件。

长会话与长命令 · ronny handoff-doc07写交接文档

重要状态不该只活在 context window 里。一页纸让人（或新会话）接着干。

长会话与长命令 · ronny long-command-check08长命令与后台任务

前台等一条长命令，用户干等；更隐蔽的代价是等过缓存寿命，下一次请求重算整个前缀。

长会话与长命令 · ronny independent-review09独立审查

只给 reviewer 三样东西：diff、需求、测试结果。作者的推理过程一律不给。

代码审查 · ronny engineering-code-review10代码评审的标准与流程

标准不是完美，是“让系统变好，且不引入不可接受的风险”。

代码审查 · ronny engineering-review-comments11怎么写评审意见

三段式：级别 + 观察，为什么重要，要作者做什么。不带级别的评论会被当成必须改。

代码审查 · ronny engineering-review-feedback12作为作者回应评审

优先改产物，而不是在评论区解释。回复只写：改了什么、为什么、怎么验的。

代码审查 · ronny harness-experiment13把改动当实验

先测量，一次只改一处，只保留通过测试的。看翻转任务，不只看平均分。

实验与紧急修复 · ronny trajectory-review14回看 Agent 的轨迹

通过的结果可能藏着脆弱的过程。看它怎么走到那儿，不只看它到没到。

实验与紧急修复 · ronny engineering-emergency-changes15紧急改动怎么审

紧急不是跳过判断，而是缩小改动、改变评审重点、事后补审。

实验与紧急修复 · ronny lifting-loops16把自己从循环里捞出来

找出你一直在给 agent 当人工环节的那些循环，每条落成一个具体改动：删规则、改 skill、加脚本、加定时任务。

个人工作流 · jiachen making-content17去 AI 味的内容生产
