01

速览

这不是再造一个 Agent，而是给 Agent 建一座「索引 + 说明书 + 装配台」。核心价值在于：让「该派谁上」和「怎么派」在 10 秒内被回答。

它是什么

一个本地优先的 Agent 目录：每张卡片写清角色、适用场景、权限边界、推荐模型与两个工具下的落地方式。

它解决什么

「我知道有个审查 Agent，但忘了叫什么、放哪、怎么配」；「这条技巧上次用得很顺，想不起来原话」。

本期做到哪

内容模型定稿 + 单文件原型（搜索、筛选、收藏、自定义）+ 双工具配置模板；同步脚本列为下一阶段。

一句话架构 内容层（Markdown / JSON，进 Git）→ 视图层（离线单文件 HTML，可搜索可筛选）→ 使用层（收藏、复制配置、导出清单、后续与本地目录同步）。三层解耦，任何一层都能单独替换。

三个关键决策

决策选择理由
交付形态先做单文件 HTML，不做后端零依赖、可离线、可进 Git、双击即用；先验证内容结构，再谈工程化。
Agent 定义载体Markdown + frontmatter 为唯一事实源OpenCode 与 Pi 都吃 Markdown；同一份角色卡可双向生成配置片段。
「我的 Agent」浏览器本地存储 + 可导出 JSON不引入账号体系；收藏是个人偏好，导出后可跨设备迁移或进仓库。
02

背景与目标

现状盘点

你当前的 Agent 资产分散在两个运行时、两种目录层级、两种 frontmatter 方言里。它们本身都够用，问题出在「跨工具的心智模型」没有被统一。

资产OpenCode 里的位置Pi 里的位置现状痛点
Agent 定义~/.config/opencode/agents/*.md
.opencode/agents/*.md		~/.pi/agent/agents/*.md
.pi/agents/*.md（依赖子代理扩展）		同名不同义，字段不通用，容易写两份且逐渐漂移
项目指令AGENTS.mdAGENTS.md / SYSTEM.md / APPEND_SYSTEM.md约束写在项目里，跨项目不可见
可复用流程commands/*.md（/cmd）prompts/*.md（slash 命令）流程与 Agent 混在一起，缺少统一索引
技巧散落在会话、笔记、聊天记录同左不可检索，复用全靠记忆

五个具体问题

1 · 找不到

知道「有个专门做审查的角色」，但名字、文件、触发方式记不全，于是每次重新写 prompt。

2 · 对不齐

OpenCode 用 mode / permission，Pi 用 name / tools，同一角色维护两份，改一处忘一处。

3 · 记不住

「先侦察后施工」「审查要用另一个模型」这类经验，没有沉淀成可检索的条目。

4 · 不敢加

想试新 Agent，但不清楚权限边界与风险，索性只用默认那几个。

目标与非目标

本期目标

  • 统一 Agent 卡片模型，覆盖 OpenCode 与 Pi
  • 可搜索、可筛选、可比较的角色目录
  • 按场景组织的技巧库（可检索）
  • 「我的 Agent」：手动添加、删除、导出
  • 每条角色卡都能一键复制为两个工具可用的配置

明确不做

  • 不做 Agent 运行时 / 不做模型网关
  • 不做账号、云同步、团队协作后台
  • 不自动修改你的 OpenCode / Pi 配置（同步脚本需显式确认）
  • 不做 Agent 市场与评分体系（先解决自用）
成功判断 两周后回看：新增一个 Agent 的时间从「翻文档 + 试错 20 分钟」降到「复制模板 + 改 3 行」；不再出现「这个角色我是不是写过」的疑问。
03

产品定位

一句话：Agent 的图书馆 + 你的工具箱。图书馆负责「有什么、怎么用」，工具箱负责「我常用哪几个、怎么一键带走」。

三个使用瞬间

  1. 开工前：搜「审查」，30 秒内拿到角色卡与配置片段。
  2. 卡住时：翻「技巧库 → 上下文」，找到「先侦察后施工」的具体做法。
  3. 沉淀时：把这次调好的 Agent 加进「我的」，下次直接复用。

设计原则

  1. 内容先于交互：关掉 JavaScript 也能读完所有角色与技巧。
  2. 一屏一问题：每个模块只回答一个疑问，不堆仪表盘。
  3. 权限显性化：只读 / 可写、开箱 / 需配置，一眼可见。
  4. 本地优先：不依赖网络、不依赖账号、数据可导出。
维度常见做法本方案选择
组织方式按工具分类（OpenCode 区 / Pi 区）按职责分类，工具作为标签；同一角色跨工具只维护一份说明
内容粒度长文教程卡片 + 折叠细节：先给结论，再给配置
个性化登录后云端收藏本地收藏 + JSON 导出，零账号
演进一次性文档目录结构固定，内容可增量；后续接目录扫描

06

技巧库

技巧不是「更好的 prompt」，而是「更稳的工作方式」。按你遇到问题的时刻分组，而不是按工具分组。

上下文与成本 任务与验收 权限与安全 工程化

显示 14 / 14 条技巧

上下文与成本›

先侦察，后施工

让只读 Agent 先摸清入口、约定与影响面，再让实现 Agent 带着结论动手。省下的不是 token，是返工。

落地：探索 → 计划 → 实现，三段式；第一段强制只读。

子代理只回传结论

子代理的价值是把噪音留在它自己的上下文里。要求它输出「文件:行号 + 一句话结论 + 未确认项」，不要整段粘贴源码。

落地：在子代理 prompt 里写死「≤ 15 行摘要，禁止粘贴超过 5 行的代码」。

便宜模型做广度，贵模型做判断

枚举文件、扫文档、跑格式化交给快模型；架构取舍、审查、难 bug 交给强模型。把预算花在分歧点上。

落地：角色卡上的「推荐档位」就是给这件事用的。

长会话及时收口

一个会话只服务一个目标。话题切换时开新会话，把结论带走；不要在旧上下文里「顺便再问一个」。

落地：任务完成先让 Agent 输出「交接摘要」，再新开会话粘贴。
任务与验收›

一个 Agent 一个职责

「顺便把文档也写了、测试也补了」是多角色任务，应该拆给三个角色。职责越单一，输出越可预测。

落地：若一个角色卡需要写两个「何时用」且互不相关，就该拆。

先写验收标准

在 prompt 里先列出「怎样算完成」：命令、预期输出、不能动的文件。没有验收标准的任务，Agent 只能猜。

落地：模板：目标 / 约束 / 验收命令 / 不允许做的事。

小步提交，每步可回滚

一次只改一个可解释的单元；每步跑最小验证。失败时先回滚到上一个绿点，而不是在红树上继续叠补丁。

落地：要求 Agent 在每步结束时报告「改了哪些文件、跑了什么命令、结果如何」。

审查者与实现者分离

让同一个 Agent 审查自己的改动，等于让它给自己打分。审查应使用独立会话、最好独立模型与只读权限。

落地：实现结束后另起 reviewer，输入只有 diff 与需求，不带实现过程。
权限与安全›

只读角色默认 deny

审查、调研、分析类角色，默认关闭 edit 与 shell。权限是边界，不是建议；能写就会写。

落地：OpenCode 用 permission 规则；Pi 通过 tools 白名单限定。

项目指令是契约

AGENTS.md 不是装饰。把「不许 commit」「测试命令是哪个」「目录约定」写进去，比每次在对话里重复有效。

落地：两工具都读 AGENTS.md；Pi 还支持 SYSTEM.md / APPEND_SYSTEM.md 做全局注入。

密钥永不进 Agent 文件

角色文件会进 Git、会被分享。任何 key、token、内部地址都不该出现在 prompt 或示例里。

落地：用环境变量引用；导出/分享前跑一次关键词扫描。
工程化›

Agent 文件纳入版本库

角色是资产。放进项目 .opencode/agents/ 或 .pi/agents/，随代码一起 review 与回滚。

落地：团队共用就进项目；个人通用放全局目录并单独备份。

命名即接口

用「动词-对象」或稳定职责名：review、scout、test-writer。避免 my-agent-2 这种一次性命名。

落地：文件名 = 角色 ID；中文名只出现在卡片展示层。

定期清理，变更留痕

每季度用 opencode agent list / Pi 的 /agents 盘点一次：删掉三个月没用的，合并重复的。重要 prompt 改动写一句原因。

落地：在角色卡 YAML 里保留 version 与 updated 字段。

五个反模式

反模式为什么会坏替代做法
万能 Agent职责漂移，输出不可预测，prompt 越写越长按「侦察 / 规划 / 实现 / 审查」拆开
让实现者自审自洽偏差，问题被自己的假设掩盖独立 reviewer + 只读权限
无边界并行子代理互相改同一批文件，冲突难追只并行只读任务；写任务串行或限定文件集
把长文档塞进 prompt上下文被占满，关键约束被稀释先摘要 / 检索，再按需引用原文
只靠记忆复用技巧不可检索，经验随时间丢失沉淀进技巧库与角色卡，定期回看
07

我的 Agent

这是整个工作台里唯一「会长大」的部分：内置目录负责通用知识，我的清单负责你的个人习惯。

三种录入方式

  1. 手动添加：名称 + 用途 + 偏好工具，30 秒完成。
  2. 从目录收藏：点角色卡上的「加入我的」，保留原始字段。
  3. 导入 Markdown：粘贴已有 frontmatter，自动解析 name / description / tools。

存储与导出

  • 默认存浏览器 localStorage，不上传。
  • 导出 mine.json，可进 Git 或换机恢复。
  • 「生成配置」把条目渲染成 OpenCode / Pi 的 Markdown 片段。
  • 冲突时以本地为准，导入前展示差异预览。

model: anthropic/claude-sonnet-4-5
temperature: 0.1
permission:
  edit: deny
  bash: deny

你是独立的代码审查员。

输入：需求描述 + diff（或文件清单）。
输出：按「阻断 / 建议 / 疑问」三档排序的问题，每条必须包含
      文件路径:行号、问题、为什么是问题、最小修复方向。

约束：
- 不修改任何文件。
- 不运行命令。
- 不确定的地方标为「疑问」，不要猜。
- 不超过 15 条；超过就说明主要风险集中在哪里。

    三阶段技术路径

    阶段做法收益代价 / 风险
    A · 单文件原型
    本期    		内容直接写在 HTML；搜索 / 筛选 / 收藏用原生 JS + localStorage零依赖、可离线、可进 Git，验证信息架构最快数据与视图耦合，条目多后维护成本上升
    B · 数据驱动内容抽到 data/*.json；构建时内联进 HTML，仍是单文件产物改内容不碰视图；可校验、可复用需要一个很轻的构建脚本（Node，无框架也可）
    C · 本地同步sync.mjs 扫描两个 agents 目录，生成清单与冲突报告；写入需显式确认真实资产与工作台不再脱节要处理 frontmatter 方言、路径差异与误覆盖
    D · 可选扩展CLI（agent list/search）或 OpenCode / Pi 内的快捷入口不离开终端也能查维护两套界面；非必要不优先
    同步脚本的安全底线 默认只读、只生成报告；任何写入（覆盖用户 agents 目录）都必须 --write 显式开启，并在写入前输出 diff 预览与备份路径。

    路线图

    按「能独立验收」切片。前三阶段一周内可以完成；阶段 4 只有在内容确实开始膨胀时才值得做。

    1. Phase 0 · 内容定稿0.5–1 天

      锁定字段字典，写满 12 张角色卡与 14 条技巧，确认每条的适用边界与权限标注。

      产出：data/agents.json 草案、schema/agent.schema.json、本报告
    2. Phase 1 · 目录与筛选1–2 天

      把角色卡做成可搜索、可筛选的网格；补齐空态、计数、键盘操作与窄屏布局。

      验收：任意角色在 2 次交互内被找到；360px 宽度无横向滚动
    3. Phase 2 · 我的 Agent1–2 天

      添加、收藏、删除、导出；本地持久化与恢复路径跑通。

      验收：刷新不丢；导出 JSON 可重新导入并还原清单
    4. Phase 3 · 双工具模板1 天

      为每个角色生成 OpenCode / Pi 两份 Markdown，附检查清单，实机各建一个角色验证。

      验收：opencode agent list 与 Pi 的 /agents 都能看到新角色
    5. Phase 4 · 数据抽离与同步2–3 天 · 可选

      内容搬到 JSON，构建时内联；sync.mjs 只读扫描两个 agents 目录并输出冲突报告。

      验收：冲突报告能准确指出「同名不同内容」与「只在一边存在」
    建议的推进方式 先交付 Phase 0 + 1 的可点版本（本报告已经覆盖大部分），用一周真实使用来验证字段是否够用；再决定要不要投入同步脚本。不要先写脚本，后补内容。

    逐项勾选。全部通过才算「可用」，而不是「做完」。

    风险与取舍

    风险影响对策
    两个工具迭代快，配置字段会变模板过时，复制后不生效每条记录 updated 与核验来源；季度复核；模板只保留稳定字段
    Pi 的子代理依赖第三方扩展角色文件放了却不加载卡片明确标注「需扩展」；提供无扩展时的 prompt 降级用法
    同步脚本误改用户配置破坏现有 Agent默认只读；--write 才写；写前 diff + 备份
    localStorage 被清理个人清单丢失一键导出 JSON；建议把 mine.json 纳入版本库
    内容膨胀变成文档垃圾场搜索变差，维护成本上升每类角色设上限；季度合并；卡片只保留决策信息
    投入产出比下降花时间建设，使用频率低以「两周内是否减少重复配置」为继续投入的判断线
    一个明确的取舍 不做「自动读取你所有会话并推荐 Agent」。那需要侵入式权限与长期维护，收益不确定；本方案只做静态知识 + 手动清单，先把确定性价值拿到。

    附录

    A · 字段字典

    字段类型说明
    idstring稳定标识，小写连字符，与文件名一致
    displaystring中文展示名，仅用于界面
    roleenumexplore / plan / build / review / test / debug / refactor / research / orchestrate / document / security / analyze
    summarystring一句话职责，不超过 60 字
    toolsarray支持该角色的运行时：opencode / pi
    modeenumprimary / subagent / all（Pi 端由扩展映射）
    permissionsobjectedit / shell 的 allow / deny / ask 摘要
    modelTierenumfast / balanced / strong，用于选择模型而不绑定具体型号
    triggersarray「何时用」，2–4 条
    avoidWhenarray「别用它」，至少 1 条，防止滥用
    riskenumlow / medium / high，按写权限与影响面评估
    tagsarray≤ 5 个，用于检索
    filesobject两个运行时的 Markdown 路径
    updateddate最近核验日期（ISO）

    B · 命名规范

    • ID：职责优先，review、test-writer、log-triage；避免 my-agent-2。
    • 文件：<id>.md；同一角色在两个工具下保持同名，减少心智负担。
    • 版本：version 用语义化版本，updated 用 ISO 日期；两者都进 card。
    • 标签：只放能力与边界（只读 / 可写 / 联网 / 高成本），不放情绪词。

    D · 术语

    主代理 / 子代理

    主代理直接面向你；子代理由主代理按任务派发，拥有独立上下文。

    开箱 / 需配置

    开箱指当前运行时已有等价能力；需配置指需要自建 Markdown 或安装扩展。

    只读 / 可写

    只读角色禁用编辑与执行写入命令；可写角色需明确影响面与回滚方式。

    事实源

    本方案中唯一可编辑的数据文件；界面与模板都由它派生，避免多份真相。
