Goose

MCP 原生、可扩展的本地通用 agent：桌面 + CLI + API，用 recipes 固化工作流。

类型通用本地 Agent / MCP界面桌面 / CLI / API（macOS、Windows、Linux）许可证Apache-2.0最新v1.57.0 · 2026-10-28调研2026-10-31

适合

  • 想用 MCP 组合工具、并把流程固化成 recipe 的人
  • 需要桌面/CLI 双形态、复用现有模型订阅的人
  • 重视厂商中立与 Linux Foundation 治理的人

不适合

  • 只做仓库内编码、追求极简的人
  • 不愿维护扩展和配置的人
  • 要求默认强隔离的人

01

定位与事实

一句话：Goose 把能力拆成 MCP extension，用 YAML recipe 把步骤固定下来；适合“把工具串成流程”，不只是写代码。

Goose 最初由 Block 发起，现在由 Linux Foundation 下的 Agentic AI Foundation（AAIF）治理。它用 Rust 写了一个本地 agent 内核，桌面、CLI 和 API 共用；扩展几乎都通过 MCP 接入。

  • Apache-2.0；v1.57.0（2026-10-28）；GitHub 56,057 stars；仓库已从 block/goose 迁到 aaif-goose/goose。[2][5]
  • Rust 编写；桌面 macOS/Windows/Linux + CLI + API。[1][2]
  • 15+ provider；可用 API key，也可通过 ACP 复用 Claude/ChatGPT/Gemini 订阅。[1]
  • MCP 原生，官方目录 70+ extensions；MCP Apps 可在桌面内渲染交互 UI。[1]
  • recipes 是 YAML，可带 instructions、extensions、parameters、subrecipes，适合团队共享与 CI。[1]
  • v1.25 起 Goose Desktop 在 macOS 沙箱中运行（官方 release note）。[5]
02

核心能力

MCP extensions

能力主要来自 MCP server；官方目录 70+，也能接任意自定义 MCP。

Recipes

把模型、扩展、参数和步骤写成 YAML；可版本化、共享、在 CI 里跑。

三形态

桌面 GUI、CLI、API 共用内核；桌面支持 MCP Apps 交互 UI。

模型自由

15+ provider，含 Anthropic/OpenAI/Google/Ollama/OpenRouter/Bedrock；可复用订阅。

本地执行

默认在你自己机器上跑；Desktop 在 macOS 上使用系统沙箱。

治理中立

AAIF / Linux Foundation 治理，不绑定单一模型厂商。

03

工作方式

  1. 安装
    桌面下载，或运行官方 CLI 安装脚本；确认 goose --version。
  2. 配置 provider
    goose configure 选模型与 key；可跳过 keyring，改用环境变量。
  3. 加扩展
    从目录安装 MCP extension，或 --with-extension 临时加载。
  4. 写 recipe
    把稳定流程固化成 YAML，参数化后给团队/CI 复用。
  5. 在项目里跑
    goose session 在项目目录启动；需要时开 Desktop 看 MCP Apps。
04

安装与首次运行

CLI · 官方脚本
curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh | bash

仓库迁移后旧 block/goose 链接可能重定向；以 goose-docs.ai 的当前命令为准。

配置
goose configure

首次配置 provider；Windows 若 keyring 报错，可选择不存 keyring。

启动会话
goose session

在项目目录启动；也可 goose session --with-builtin developer 只启用需要的扩展。

常用命令与路径

goose configure

首次配置 provider/model/key；可跳过 keyring，改用环境变量。

goose session

在项目目录启动交互会话。

goose session --with-builtin developer

只启用需要的扩展，避免一次挂满导致上下文膨胀。

goose session --with-extension "uvx mcp-server-fetch"

临时加载一个 MCP server，不写入长期配置。

goose run --recipe recipe.yaml

按 recipe 跑固定流程；适合 CI/定时任务。

goose serve

以 ACP/server 形态暴露 agent，供桌面、编辑器或其他客户端连接。

05

模型与成本

软件

Apache-2.0，软件免费；无 seat fee。

使用

按 provider 计费；复用已有订阅不额外收费；本地 Ollama 只消耗本机算力。

Goose 本身不卖模型。扩展越多，工具 schema 进入上下文越多，token 成本会上升；按需启用，不要一次挂满。

06

优势

  • MCP 集成最深之一：扩展生态和 MCP Apps 让“工具编排”是核心能力，不是附加项。
  • recipes 把一次性对话变成可复用资产，适合团队和 CI。
  • 桌面 + CLI + API 三形态，同一套配置；非编码任务也能做。
  • 模型自由，且能复用已有订阅。
  • AAIF 治理，厂商中立性比单一公司项目更稳。
07

限制与风险

  • 扩展挂太多会让上下文和 token 成本膨胀；需要纪律。
  • 代码库感知不如 OpenCode 专精；大型 repo 的定点编辑要自己加约束。
  • recipes 和 extension 配置需要维护，团队落地有学习成本。
  • 工具权限与 MCP server 的信任边界要自己把关。
  • macOS 沙箱目前主要覆盖 Desktop；CLI 的隔离取决于你的环境。
  • 仓库迁移后，旧教程/旧链接可能失效，安装命令要核对。
08

与同类差异

对照关键差异
Hermes两者都是通用本地 agent；Hermes 强在消息网关、记忆、cron，Goose 强在 MCP 扩展与 recipes。
OrcaGoose 是 agent 本身；Orca 是启动多个 agent 的控制台。可把 Goose 放进 Orca 跑。
OpenHandsOpenHands 面向沙箱内自治软件工程；Goose 更像可编排的通用工具代理。
09

适用判断

建议安装

  • 你想用 MCP 把本地工具、API、脚本串成固定流程。
  • 你需要桌面 + CLI 两种入口，且希望复用已有模型订阅。
  • 你想把工作流固化成 YAML，交给团队或 CI。

建议跳过

  • 你只想要一个极简的终端编码 agent。
  • 你不愿维护 extension/recipe 配置。
  • 你需要开箱即用的强沙箱和审计。
10

衍生项目：GUI / Web / 手机

官方入口

  • Goose Desktop官方

    macOS/Windows/Linux 原生桌面应用；v1.25 起在 macOS 沙箱中运行。

  • Goose CLI官方

    终端会话、recipe、扩展加载；与桌面共用内核。

  • GDK / API官方

    把 goose 运行时嵌进自己的应用/服务；GDK 提供跨端 agent 能力。

  • MCP Apps官方

    扩展可在 Desktop 里渲染按钮、表单、可视化，而不只是返回文本。

Web / 远程

  • goose serve官方

    ACP server：桌面、编辑器、机器人或其他客户端通过协议连接同一 agent。

  • goose-mobile官方

    PWA/p2p 移动访问的早期实现；维护者称仍是 early working state。

  • ACP 客户端第三方

    Zed、JetBrains 等 ACP 客户端可驱动 goose；不需要单独的 goose Web UI。

  • 旧 goose web官方

    维护者已从仓库移除；不要再照旧教程部署（见仓库历史）。

手机 / 移动

  • goose-mobile（PWA）官方

    浏览器即可打开，通过配对/卡片建立 p2p 连接；适合尝鲜，不是成熟成品。

  • 原生 App官方

    截至调研没有成熟的官方原生 iOS/Android 应用；旧 Swift app 已被 p2p/PWA 路线替代。

扩展与配方

  • MCP 扩展目录官方

    70+ 文档化扩展；也能接任意 MCP server。

  • Recipes Cookbook社区

    社区 recipe 归档；公开提交计划已结束，但仍可参考和自建。

  • MCP servers 官方仓库第三方

    官方 MCP server 集合；也可把任意 MCP server 作为 goose 扩展。

Goose 的“官方 UI”是 Desktop，CLI/API 是另外两种入口；旧的 goose web 已移除，移动/远程改走 ACP + goose-mobile。后者仍是早期实现，别把它当稳定生产客户端。
11

社区与玩友生态

扩展生态

  • 70+ MCP extensions官方

    数据库、API、浏览器、GitHub、Google Drive 等；按需启用。

  • MCP Apps官方

    扩展可渲染交互 UI，适合做内部工具/仪表盘。

  • Recipes官方

    YAML 固化 instructions、extensions、parameters、subrecipes；可进 CI。

社区与治理

  • Discord官方

    官方社区，扩展/recipe 交流主阵地；入口见官网。

  • GitHub官方

    源码、issue、release；仓库已迁到 aaif-goose/goose。

  • AAIF / Linux Foundation官方

    厂商中立的基金会治理，降低单一公司控制风险。

经典玩法

  • Recipe 进 CI官方

    把重复的代码审查/发布/数据整理固化成 recipe，定时或事件触发。

  • 扩展按需加载官方

    用 --with-builtin / --with-extension 控制上下文，不要把所有 MCP 都常驻。

  • MCP Apps 仪表盘官方

    把内部工具做成扩展 UI，在 Desktop 里直接操作。

  • 本地模型官方

    Ollama/LM Studio 等本地端点，数据不出机器。

扩展、MCP server 和 recipe 都可能执行命令或访问外部系统；启用前看权限。扩展挂得越多，工具 schema 越占上下文，token 成本也越高。
