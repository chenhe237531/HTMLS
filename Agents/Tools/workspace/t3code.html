TOOL REPORT/控制面 / 远程/2026-11

T3 Code
给已有的编码 Agent 装一个远程驾驶舱

它不生产 Agent，也不替换 Claude Code 或 Codex。它把「跑在你机器上的 Agent」变成一个有服务器、有事件日志、能在手机和浏览器里安全接管的工作区。真正的卖点是远程与多端，而不是模型能力。

MIT TypeScript 3.87 万 star macOS / Windows / Linux 服务器 iOS / Android / Web / 桌面

适合

  • 已经装好 Claude Code、Codex、Cursor 等 CLI，想要统一入口
  • 人离开工位后，仍想用手机查看进度、审 diff、处理审批
  • 需要把一个仓库的线程、检查点与 PR 关联起来

不适合

  • 没有安装任何 Agent CLI，希望开箱即用
  • 不愿让一台机器长期在线做服务器
  • 对默认 Full access 权限模式敏感、又不想配策略

01

它是什么，不是什么

先划清边界：T3 Code 是「Agent 的宿主与控制面」，不是新的编码模型。

T3 Code 官方把自己称为 agent harness control surface。它接管你机器上已经安装并登录的 Agent 进程，通过一个本地服务器持有终端、Git、项目文件和 provider 凭据，再把「线程」投射到 Web、桌面和手机客户端。

它负责

  • 启动、恢复、切换多个 Agent 线程
  • 保存事件日志、检查点、PR 关联
  • 把同一环境暴露给手机、浏览器、另一台电脑
  • 统一权限模式与审批请求

它不负责

  • 模型推理（用你订阅的 Claude / Codex / Cursor 等）
  • 替代 Agent 自己的工具与提示词
  • 替你托管代码（默认代码留在服务器所在机器）
  • 保证 Agent 一定做对（它只提供控制与审计面）
一句话

如果你只在本机终端里写代码，T3 Code 的复杂度不值得；它的价值在「离开键盘之后」。

02

它解决的具体问题

不是「让 Agent 更聪明」，而是「让 Agent 可被远程监督」。

  • 多 provider 割裂：Claude Code、Codex、Cursor、Grok Build、OpenCode、Antigravity、fx 各有自己的会话与登录，T3 Code 用统一线程模型接住它们。
  • 远程不可用：Agent 在桌面跑，人在地铁上。T3 Code 的服务器把环境暴露给手机与浏览器，而不是把代码同步到手机。
  • 审批碎片化：不同 Agent 的权限模型不同，T3 Code 用 Supervised / Auto-accept edits / Auto / Full access 四档统一表达。
  • PR 与线程脱节：一个任务改了什么、对应哪个 PR、CI 是否过了，T3 Code 把 PR 链接与 diff 放回线程。
  • 长任务不可恢复：事件日志 + 隐藏 Git ref 检查点，让「回滚到某一轮之前」有据可依。
03

运作方式

服务端拥有环境，客户端只是视图；这条边界决定了它的安全模型。

官方架构文档写得很明确：provider 进程、终端、Git、项目文件都属于服务器，客户端不能用自己的文件系统或凭据替代。桌面端内置服务器，但渲染进程仍然遵守同一条边界。

  1. 服务器：运行 Agent CLI、持有登录态与 Git 凭据、执行工具、写事件日志。
  2. RPC 契约：客户端通过认证 RPC 订阅线程状态；只订阅当前线程，不拉全量历史。
  3. 事件日志：命令先落库、再产生副作用；重试幂等，投影不会跑到日志前面。
  4. 检查点：用隐藏 Git ref 捕获工作区，不往你的分支加提交；回滚要与 Agent 会话状态一起处理。
  5. PR 同步：合并、关闭、CI 状态变化会触发重新读取；外部 gh pr merge 也能被后续同步捕获。
这意味着

服务器所在机器必须保持运行且可达。手机只是遥控器，不是执行环境；关机后任务不会继续。

04

上手

先装 Agent、登录，再装 T3 Code；顺序反了会发现「没有 provider 可用」。

至少安装并登录一个 provider：Codex（codex login）、Claude Code（claude auth login）、Cursor CLI（agent login）、Grok Build（grok login）、OpenCode（opencode auth login）等。

# 安装 CLI 并启动本地服务器
curl -fsSL https://t3.codes/install.sh | sh
t3

# 常驻后台
t3 service install

# 不安装，先试
npx t3@latest

桌面端可从 GitHub Releases、Homebrew（brew install --cask t3-code）、winget、scoop、deb、AUR、Nix 安装。远程访问有三种：T3 Connect 中继、局域网直连、Tailscale/SSH 等既有网络。

# 让其他设备连进来
t3 up                 # 选择 T3 Connect / LAN
t3 pair               # 生成一次性配对链接
t3 status --json      # 查看当前连接方式
05

日常流程

一个线程 = 一个任务，不是一个终端窗口。

  1. 建线程：选 provider、模型、权限模式；权限可以按线程覆盖。
  2. 跑任务：Agent 在服务器上执行；客户端看到流式消息、工具调用与 diff。
  3. 审改动：Diff 面板按轮次或提交查看；合并/变基带进来的文件不会混进「本轮改动」。
  4. 连 PR：支持 GitHub、GitLab、Forgejo、Gitea、Bitbucket、Azure DevOps、GitCafe；可关联多个 PR、查看栈。
  5. 远程接管：手机审批、追问、看 PR；桌面端继续同一线程。
  6. 收尾：线程结算可由 PR 状态与空闲时间驱动；合并后缓存失效并重新检查。
多账号与多环境

provider 支持多个账号；设置分为「客户端偏好」与「服务器/项目默认值」，客户端不能把偏好写回别的环境。T3 Connect 免费账号可连 3 台机器，Pro 10 台，Premier 100 台；手机与浏览器不计入机器数。

06

强项

它强在工程边界，而不是功能列表。

  • 远程优先的架构：不是把桌面 UI 投屏，而是服务器持有环境、客户端按 RPC 订阅。
  • 多 provider 统一：7 种 Agent 共用线程、权限、diff、PR 模型，迁移成本低。
  • 事件日志 + 幂等命令：长任务、断线重连、重复提交都有明确语义。
  • 隐藏 Git ref 检查点：能回到某一轮之前，又不污染分支历史。
  • 移动端不是阉割版：iOS/Android 可审批、看 diff、连 PR，适合「离开工位」场景。
  • 多 forge：GitHub 之外还支持 GitLab、Forgejo、Gitea、Bitbucket、Azure DevOps、GitCafe。
07

边界与代价

官方自己说「非常非常早期」；这决定了它能用在什么场合。

  • 服务器必须在线：关机、休眠、断网，手机就连不上；任务也不会在云端继续。
  • 默认权限是 Full access：新线程默认不询问命令与文件修改。官方支持管理员用 managed policy 限制，但默认值不适合不可信仓库。
  • provider 差异：Auto 模式并非所有 provider 都支持；OpenCode、Antigravity 会退回询问；fx 不支持 Auto-accept / Full access。
  • 早期项目：README 明确「expect bugs」，且基本不接受大功能贡献。
  • 远程依赖：T3 Connect 是托管中继；不用它就自己要解决 LAN/VPN/SSH 的可达性与证书。
  • 机器数限制：免费 3 台，更多要 T3 Chat 付费档。
适合的部署：一台常开的 Mac mini 或 Linux 工作站做服务器，代码与凭据留在上面，手机只做审批与查看。
08

安全与权限

默认值、配对、密钥存储，是三个必须检查的点。

权限模式
Supervised（命令与改动都问）、Auto-accept edits（自动改文件）、Auto（provider 自动审查）、Full access（全放行）。新线程初始默认 Full access。
管理员上限
可用 managed policy 限制单机可用的最高模式；超过上限的模式会显示管理者。
凭据
GitHub token 存在服务器的 secret store；也支持 GH_TOKEN 或已登录的 gh。远端客户端不会带来自己的凭据。
配对
一次性配对链接；t3 pair 可刷新。LAN 模式接受局域网与 tailnet 连接，配对码是唯一门槛。
中继
T3 Connect 负责跨网可达；不开启时可走 LAN、Tailscale、SSH 或自己的 URL。
最需要改的默认

把新线程默认改成 Supervised，至少对包含生产凭据或不可信依赖的仓库如此。Full access 适合你完全信任的 Agent 与代码库，不适合「先跑起来再说」。

和谁比

同样解决「多 Agent」，切入点不同。

工具核心抽象最强场景主要代价
T3 Code服务器 + 线程 + 远程客户端离开工位后继续审阅与审批服务器常开；早期；默认 Full access

herdr终端运行时 + 会话保活SSH/断线后不丢 Agent机器重启仍会丢进程
Paseo本地 daemon + 全端客户端手机为中心的跨设备监督daemon 常开；生态较新

T3 Code 的差异点是「服务器拥有环境 + RPC 视图 + 事件日志」，不是「终端分屏」。

10

结论

推荐路径

把 T3 Code 装在一台常开的工作站上，先只接 Claude Code 或 Codex 其中一个；把默认权限改成 Supervised；用手机完成一次「审批 + 看 diff + 连 PR」的闭环。跑通后再加第二个 provider。

它不适合作为「第一个 Agent 工具」：没有 provider、没有 Git 凭据、没有常开机器，体验会很差。它适合已经有一套 CLI Agent 工作流、现在需要远程与多端的人。
