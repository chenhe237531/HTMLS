CLI-Anything
给每个软件生成一层 Agent 能读的 CLI

它不是又一个 GUI Agent，而是把「读源码/接口 → 设计命令 → 生成 Click CLI + REPL + JSON + 测试 + SKILL.md」做成 7 阶段流水线。听起来像万能钥匙，实际成败取决于目标软件有没有可调的 backend/API，以及你愿不愿意维护生成出来的代码。

Apache-2.0 Python ≥ 3.10 58,070 star v0.4.0 18 个应用案例 2,461 tests（徽章）

适合

  • 目标软件有源码或稳定 API，需要把 GUI 能力变成可批量调用的 CLI
  • 想让 Agent 用结构化命令而不是截图/点击来操作真实软件
  • 愿意审查生成的代码、测试与权限范围，并承担维护

不适合

  • 闭源、无 API、只能靠人工点击或授权弹窗的软件
  • 要求零维护、开箱即用、长期稳定不变的自动化
  • 把生成的 CLI 当成安全沙箱，或直接跑在敏感主机上

01

它是什么

HKUDS 的 CLI 生成器 + CLI-Hub 分发层 + 面向 Agent 的 SKILL.md。

官方口号是「Making ALL Software Agent-Native」。它把「把专业软件变成 Agent 可调用工具」拆成一条自动流水线：分析目标代码库，设计命令组与状态模型，生成基于 Click 的 CLI（带 REPL、JSON 输出、undo/redo），再生成测试、文档与 SKILL.md。

58,070GitHub star
5,221fork
236open issues
v0.4.02026-06-25

它不是一个运行时框架，也不是模型；产出物是每个软件一个 Python 包：cli-anything-gimp、cli-anything-blender、cli-anything-libreoffice 等。CLI-Hub 负责发现、安装、更新与 matrix 编排。

它负责

  • 从源码/仓库分析出可自动化的能力
  • 生成命令组、状态、JSON 输出与 REPL
  • 生成单元/E2E 测试与 SKILL.md
  • 通过 CLI-Hub 分发、安装、更新
  • 为 Claude Code、Codex、Cursor 等提供调用入口

它不负责

  • 给闭源软件凭空造 API
  • 保证生成代码的生产质量
  • 提供安全沙箱或权限隔离
  • 替代你对上游软件/许可证的合规判断
  • 保证「所有软件」都能同等自动化
先纠正一个常见误解

「把 GUI 程序转换成命令行」并不是录屏或像素点击。README 的流程是分析源码与 GUI 动作，映射到底层 API/命令，生成直接调用真实 backend 的 CLI。对没有可编程接口的软件，它只能做到有限封装，甚至做不了。

02

它解决的具体问题

Agent 会用终端，但大多数专业软件只给了人用的 GUI。

  • GUI 自动化脆弱：截图、坐标点击、等待弹窗，界面一变就坏；token 与延迟也高。
  • API 缺口：很多桌面软件有完整 backend，却没有稳定 CLI/API 给 Agent 用。
  • 能力被砍：为了「让 Agent 能用」，团队常重写一个简化版，丢掉 90% 专业功能。
  • 集成成本：每个软件单独写包装、测试、文档，重复劳动。
  • 结构化输出：Agent 需要 JSON，而 GUI 只给人看。
  • 可复现性：点击流程难以版本化、回放、写测试；命令可以。
它的核心主张

把「软件能力」变成「命令 + 状态 + JSON + 测试 + 技能说明」，让 Agent 通过终端调用真实软件，而不是通过屏幕猜。

03

运作方式

7 阶段流水线 + SKILL.md 生成 + CLI-Hub 分发。

Analyze → Design → Implement → Plan Tests → Write Tests
   → Document → Publish
                 ↘ Phase 6.5: SKILL.md
   ↺ Refine（gap analysis，可多次增量执行）
阶段产出关键点
1 Analyze源码/仓库能力地图扫描代码、GUI 动作、API/命令、状态与文件格式
2 Design命令组、状态模型、输出格式把能力组织成可组合命令，而不是 1:1 包装每个按钮
3 ImplementClick CLI + REPL + JSON + undo/redo直接调用真实 backend，保留专业能力
4 Plan TestsTEST.md单元 + E2E 测试计划，含真实文件/软件
5 Write Tests测试套件子进程验证安装后的命令
6 DocumentREADME + 结果命令组、示例、错误处理
6.5 SKILL.mdAgent 技能定义YAML frontmatter、命令组、JSON/错误用法
7 Publish可安装包setup.py、PATH 上的 cli-anything-*

生成物长什么样

  • 命令：cli-anything-gimp project new --width 1920 --height 1080 -o poster.json；--json 给 Agent，默认给人读。
  • 状态：持久项目状态、REPL、undo/redo；复杂软件不是「一条命令一次执行」。
  • 预览/轨迹：FreeCAD/Blender 等创意软件支持 preview、live preview、trajectory，把命令与视觉状态对应起来。
  • 技能：每个 harness 带 SKILL.md，Agent 可先读技能再调用；CLI-Hub 还提供 meta-skill 让 Agent 自己发现/安装。

CLI-Hub 与矩阵

  • cli-hub list/search/info/install/update/uninstall/launch 管理已发布的 harness 与公共 CLI。
  • v0.4.0 引入 cli-hub matrix：把多个 CLI 组成的任务流做成一次安装、能力预检与断点续装。
  • 支持 pip/npm/brew/系统工具等多种安装源；具体包仍要装上游软件（GIMP、Blender、LibreOffice 等）。
04

上手

先逛 Hub 装现成的，再决定是否为缺失的软件生成新 harness。

A. 使用已有 CLI

pip install cli-anything-hub

cli-hub list
cli-hub search image
cli-hub info gimp
cli-hub install gimp
cli-hub launch gimp

装完后也可以直接走 PATH：

cd gimp/agent-harness
pip install -e .
cli-anything-gimp --help
cli-anything-gimp

B. 让 Agent 生成新 CLI

以 Claude Code 为例：

/plugin marketplace add HKUDS/CLI-Anything
/plugin install cli-anything

/cli-anything ./gimp
/cli-anything https://github.com/blender/blender

# 定向补齐能力
/cli-anything:refine ./gimp "batch processing and filters"

也提供 OpenCode、Pi、Cursor、Codex、OpenClaw、Hermes、Reasonix、Qodercli、GitHub Copilot CLI 的插件或 skill 安装方式；不同平台的命令名略有差异。

前置条件：Python 3.10+、目标软件或源码、一个支持的编码 Agent。很多 harness 需要本机已安装上游应用；例如 GIMP/Blender/LibreOffice 的 CLI 不是自带渲染引擎。
05

日常流程

「先发现，后生成，再精修」比一上来就 /cli-anything 更稳。

  1. 先查 Hub：已有 harness 优先，省掉生成与测试；确认版本、上游依赖与维护状态。
  2. 装上游软件：很多 CLI 只是控制层，真实渲染/转换由 GIMP、Blender、LibreOffice 等完成。
  3. 生成缺失 harness：给 Agent 源码路径或仓库，跑完 7 阶段；先看它设计的命令组是否覆盖关键能力。
  4. 跑测试：单测之外，用真实文件做 E2E；检查 JSON 输出、错误码、退出码与幂等性。
  5. 定向 refine：哪里缺命令就补哪里，不要一次要求「全部功能」；每次增量验证。
  6. 交给 Agent：让它读 SKILL.md，用 --json 调用；把权限与工作目录限制在项目内。
  7. 版本化：把生成的 harness 与测试纳入仓库；上游软件升级后重新跑 validate。
06

强项

它把「为每个软件写包装」从一次性工程变成了可重复流程。

  • 真实 backend：不是 toy 重写，直接调用 GIMP/Blender/LibreOffice 等真实软件的能力。
  • 结构化：默认人类可读、--json 给 Agent；命令组 + 状态 + REPL + undo/redo。
  • 覆盖案例多：README 展示 18 个应用、2,461 个测试（徽章口径），含 FreeCAD、Blender、Draw.io、VideoCaptioner、Slay the Spire II 等。
  • 面向 Agent 生态：Claude Code、Codex、Cursor、OpenCode、Pi、OpenClaw、Hermes 等都有入口。
  • 分发层：CLI-Hub 让发现/安装/更新/矩阵编排有统一入口。
  • 可复现：7 阶段与 SKILL.md 生成把「怎么包装」文档化；refine 可增量补齐。
  • 许可证宽松：Apache-2.0；技术报告公开在 arXiv。
07

边界与代价

星标很高，但「所有软件」是愿景，不是当前覆盖率。

  • 依赖源码/API：闭源、无稳定 backend、强交互/授权弹窗的软件，生成质量会明显下降，甚至不可行。
  • 质量不均：18 个案例是经过挑选与打磨的；社区提交的 harness 覆盖度、测试与错误处理差异很大。
  • 上游依赖：很多 CLI 需要安装专业软件与插件；CI/容器里部署并不轻。
  • 测试口径：「2,461 tests」是 README 徽章；不同 harness 的测试深度不同，不能等同于生产验证。
  • 维护成本：生成不是一次性的；上游软件、API、许可证变化都要回归。
  • 发布节奏：最新 Release v0.4.0 在 2026-06-25，最后一次 push 2026-09-22；58k star 与发布频率并不同步，选型要看具体 harness。
  • 宣传与边界：「ALL Software」是愿景；商业化/许可受限软件是否允许自动化，需要单独确认。
  • 不是沙箱：生成的 CLI 能真实写文件、调网络、操作软件；权限隔离要自己加。
最容易被高估的地方：把「能生成 CLI」当成「生成出来就能生产用」。命令组设计、错误处理、并发/锁、回滚、权限与测试，仍要逐项验收。
08

安全与权限

它把 Agent 的权限直接接到真实软件的 backend，信任边界更大。

执行面
生成的 CLI 可读写项目文件、调用本机软件、访问网络；能力越完整，误操作面越大。
凭据
部分 harness 需要 token（Zoom、Sketch、Exa 等）；v0.4.0 做了 owner-only 权限、token 文件路径限制与 path traversal 修复。
解析
对 XML/SVG/ODF/MLT/MusicXML/CSL 等不可信输入，v0.4.0 改用 defusedxml；这是必要但不充分。
上游软件
CLI 调用的是真实 GIMP/Blender/LibreOffice；上游的宏、脚本、插件与文件解析漏洞仍会影响你。
Agent 技能
SKILL.md 与 CLI-Hub 安装链是供应链的一部分；固定版本、校验来源，不要盲目自动安装。
沙箱
项目本身不提供强隔离；在容器/低权限账号/只读挂载里跑，给最小目录与网络权限。
合规
商业软件、云服务、内容平台的自动化条款可能限制批量操作；先确认许可证与 ToS。
最容易被忽略

一个「生成出来的 CLI」仍然是你机器上的可执行程序，带着你的账号与文件权限。它不会因为「是 Agent 生成的」就自动安全。

09

和谁比

都能让 Agent 操作软件，但控制点与可靠性不同。

方案控制点最强场景主要代价
CLI-Anything生成 CLI，直接调真实 backend有源码/API 的专业软件批量自动化需生成/测试/维护；依赖上游
MCP Server厂商或社区提供的工具协议已有稳定 API 的服务/工具需要有人写 server；覆盖有限
Computer Use / 浏览器 Agent截图 + 鼠标键盘 / DOM没有 API 的 GUI、一次性任务脆弱、慢、token 高、难测试
RPA录制好的点击/流程固定界面、固定步骤界面一变就坏，难泛化
手写脚本直接调 API/SDK少量核心软件、长期维护每个软件重复开发
Dify / n8n可视化工作流节点非工程同学编排服务桌面软件能力弱
10

结论

推荐路径

先在 CLI-Hub 里找现成 harness；没有再用 /cli-anything 生成。选一个非关键、可回滚的任务跑通 7 阶段，重点验收命令组、JSON、错误码、E2E 与权限。确认稳定后再接 Agent；把生成代码与测试纳入仓库，固定上游版本。

它最适合「有源码/API、但缺 CLI」的专业软件，尤其是创意、办公、工程与数据工具。对闭源、强交互或高频变化的软件，GUI Agent 或人工流程可能反而更省事。把它当加速器，不要当万能钥匙。
