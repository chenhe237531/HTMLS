TOOL REPORT/自托管 Harness/2026-11

Mainplane
把旧电脑变成 Agent 的常开主机

Mainplane 把 Agent 基础设施拆成三块：一台常开的 harness server、若干台被 Agent 控制的 worker、以及消息 connector。它最值得读的不是功能，而是安全模型——worker 是信任边界，Agent 对它有一切权限，且没有逐次审批。

MIT Go 657 star macOS / Windows / Linux 自托管

适合

  • 有一台常开的旧电脑/NUC/服务器，想变成 Agent 主机
  • 需要 Agent 操作多台设备、真实浏览器与共享文件
  • 接受「整机授权」而不是逐命令审批

不适合

  • 需要每条命令人工确认
  • 不愿维护自托管服务、反向代理与网络
  • 计划把主力工作机直接交给 Agent 全权控制

01

它是什么

一个自托管的 Agent harness：server + workers + connectors。

官方定义：open-source agent harness。它不是单个 Agent，而是让 Agent 长期运行、连接多台设备、共享文件、接收消息的基础设施。

三个组件

  • Server：常开主机，持有会话、provider 密钥、控制面、观测与文件服务
  • Worker：交给 Agent 控制的电脑，执行代码、开浏览器、读写文件
  • Connector：让你从消息渠道（如聊天）给 Agent 发任务

关键取舍

  • 模型无关：Anthropic、OpenAI、Google、Bedrock、OpenRouter 等
  • 自托管：代码与会话留在你的机器
  • Worker 是信任边界：整机授权，无逐命令审批
  • 不是 SaaS；你要自己运维
02

它解决的具体问题

Agent 需要一个「一直在」的家，而不是一台合盖就睡的笔记本。

  • 常开：Agent 要持续接消息、跑定时任务、处理长任务；主力笔记本会休眠。
  • 多设备：Agent 需要同时操作 Mac、Windows、Linux 上的浏览器与文件。
  • 环境真实：云沙箱没有你的登录态、本地软件与内网访问。
  • 安全边界：逐命令审批在长任务里不可持续；需要一个清晰的「这台机器可以全权，那台不行」的边界。
  • 共享文件：多台 worker 之间需要并发安全的工作区，而不是手工 scp。
它的主张

与其用规则去约束一个拥有 shell 的 Agent，不如用「机器」划边界：给它的机器全权，不给的机器完全隔离。

03

运作方式

harness 不开入站端口；cloudflared + pointer 负责寻址；worker 之间走 WireGuard。

  1. Server 启动：harness 在本机 loopback 监听，自己拉起 cloudflared 子进程，获得一个公开 HTTPS URL。
  2. 寻址：设备只知道网络名与设备码；pointer.mainplane.ai 把网络名映射到 harness 公钥，再映射到当前 URL。
  3. Worker 加入：在目标机器运行安装命令，输入网络名 + 设备码；worker 通过指针找到 harness，建立连接。
  4. 网络：worker 之间走 WireGuard；只有 harness 配置里显式命名的 link 才互通。
  5. 会话：一个 session 指定模型、工具集、context 上限与 worker 列表；Agent 只在给定 worker 上执行。
Quick tunnel 限制：官方说最多约 200 个并发请求，每个 worker 占 2 个、每个 chat 占 1 个，约 95 个 worker；无 SLA。更多要用自己的域名/反向代理。
04

上手

在常开机器上装 server，再把 worker 加进来。

# 在常开机器上（Linux / macOS）
curl -fsSL https://mainplane.ai/install | sh -s -- server quickstart

# Windows
& ([scriptblock]::Create((irm https://mainplane.ai/install.ps1))) server quickstart

quickstart 会引导你加 provider、worker 与 connector，并打印网络名、设备码与 API key。之后在每台 worker 上：

curl -fsSL https://mainplane.ai/install | sh -s -- YOUR-NETWORK XXXX-XXXX

# 加 provider key
mainplane key openai sk-...

# 新建会话并进入聊天
mainplane new
mainplane chat
注意

quickstart 默认把 harness 机器也变成名为 admin 的 worker。Agent 因此能读到 harness 配置与 provider key。若不想这样，用 server --no-admin，代价是失去会话文件盘、自动更新与「Agent 管理 Mainplane」等能力。

05

日常用法

会话是「模型 + 工具 + worker 列表」的组合。

  • 会话：指定模型、工具集（如 patch）、context 上限、可用 worker；Agent 只在列表内的机器执行。
  • Worker：可以是旧电脑、Mac mini、云 VM；每台机器以连接它的用户身份执行代码。
  • Connector：从消息渠道发任务；只发消息的机器不需要 worker。
  • 共享文件盘：多 worker 并发读写不丢同步；需要一台 Linux worker 提供文件服务。
  • 浏览器/computer use：驱动真实浏览器与应用，而不是无头沙箱。
  • 订阅复用：支持 Claude Code / ChatGPT 订阅的用量（按各自条款），也支持 API key。
06

强项

它把「自托管 Agent 主机」做成了一个清晰的产品边界。

  • 模型无关：Anthropic、OpenAI、Google、Bedrock、OpenRouter、ChatGPT/Claude 订阅等。
  • 真正自托管：server 可在 macOS/Windows/Linux；代码、会话、密钥在自己手里。
  • 多设备：worker 覆盖 Mac/Windows/Linux，共享文件盘与浏览器。
  • 网络简单：不需要 Tailscale；harness 不开入站端口，worker 通过指针连接。
  • 安全模型清晰：worker 是边界，整机授权；不做「看似安全」的逐命令规则。
  • MIT：可审计、可改；社区小但代码开放。
07

边界与代价

「整机授权」是特性，也是最大的风险。

  • 无逐命令审批：Agent 对给定 worker 有完全控制；它读到的网页/邮件/AGENTS.md 都可能注入指令。
  • admin worker 暴露密钥：quickstart 默认让 Agent 能读 provider key；生产应改用 --no-admin。
  • Cloudflare 可见：quick tunnel 在 Cloudflare 终止 TLS，能看到 connector 与 harness 之间的流量；worker 之间的 WireGuard 不可见。
  • 常开硬件：「旧电脑」要真的常开、稳定、能散热；休眠/断网就失去 24/7。
  • 共享文件要求 Linux：托管共享文件盘需要兼容的 Linux worker。
  • 社区规模：约 657 star，生态与排障资料远少于头部项目。
24/7 的真实条件

Server 常开只保证「能接任务」；真正执行任务的 worker 也要在线。把主力笔记本当 worker，合盖后任务一样会停。

08

安全与隐私

先读这一节，再决定把哪台机器接进来。

边界
Agent 对 session 指定的 worker 有完全控制；对未指定的机器没有访问。没有逐命令确认。
Harness 机器
quickstart 的 admin worker 能读配置与 provider key；用 --no-admin 把 Agent 挡在 harness 之外。
传输
connector → harness 经 Cloudflare（可见）；worker ↔ worker 走 WireGuard（Cloudflare 不可见）。用自己的反向代理可避开 Cloudflare。
Provider
模型提供方能看到整个会话上下文：消息、工具调用、命令输出、读到的文件与图片。
提示注入
Agent 会读消息、网页、AGENTS.md；这些文本都可能试图操控它。只把「愿意交给会读一切的 Agent」的内容放进 worker。
部署建议

harness 放独立小主机，开 --no-admin；worker 用专门的 VM/旧电脑，不放密码、钱包、个人照片；共享文件盘单独挂载；对外只暴露 Cloudflare 或自己的反代。

09

和谁比

同样是「远程用电脑」，Tie 逐次审批，Mainplane 整机授权。

方案执行边界审批最适合
Mainplaneworker 整机无逐次自托管、多设备、长期运行
CoreSpeed Tie单台机器的工具组逐次（读除外）云端 Agent 借本地登录态
云 VM + Tailscale云主机取决于你隔离、可重建
T3/Paseo开发环境Agent 自己的权限模式编码任务与远程监督
10

结论

推荐路径

找一台旧机器装 harness，先用 --no-admin；把一台独立 VM 作为 worker，只放测试仓库与测试账号；跑通「消息 → 会话 → worker 执行 → 共享文件」。确认边界后再接真实设备。

它适合愿意运维、且能接受「整机授权」的人；如果你需要每条命令审批，选 Tie 或 Agent 自身的权限模式。
