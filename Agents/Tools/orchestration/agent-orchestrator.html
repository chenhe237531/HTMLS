TOOL REPORT/多 Agent / PR 流水线/2026-11

Orchestrator.inc
把 Agent 舰队管到 PR 合并

它不是「再开一个 Agent」，而是把「主 Agent 拆任务 → 多个 Worker 在独立 worktree 里并行 → CI/评审失败回灌 → 推进到可合并」串成一条可监督的流水线。代价是：它替你做了更多决策，也看到了更多数据。

Apache-2.0 Go 1.40 万 star macOS / Windows / Linux iOS / Android

适合

  • 一个需求要拆成多个并行子任务，且不想手工管分支
  • 希望 CI 失败、评审意见自动回到「拥有这个分支的 Agent」
  • 需要从手机看板审批与查看 PR

不适合

  • 只做单文件小改动，拆舰队反而更慢
  • 不能接受桌面应用/本地 daemon 的资源占用
  • 对遥测或云端执行代码有硬性限制

仓库已从 AgentWrapper 迁到 OrchestratorInc，产品名也改为 Orchestrator.inc。
01

它是什么

本地桌面工作台 + 常驻 daemon + 主从 Agent 流水线。

官方定位是「run a fleet of coding agents while keeping branches, reviews, and CI failures manageable」。核心抽象只有三个：主 Agent（规划与拆解）、Worker（一个任务一个 worktree 一个 Agent）、看板（按状态自动分栏）。

它负责

  • 把需求拆成子任务并派给不同 Agent
  • 每个 Worker 独立 Git worktree，避免互相覆盖
  • 观察 PR、CI、评审，把失败路由回原 Worker
  • 桌面 + 手机看板；可选云端 Worker

它不负责

  • 模型本身（用 Claude Code、Codex 等）
  • 替你做产品决策；主 Agent 仍可能拆错
  • 保证自动合并安全（合并策略要自己定）
  • 托管你的私有代码（除非选 Cloud Agents）
02

它解决的具体问题

多 Agent 的难点不是「启动」，而是「收尾」。

  • 分支冲突：多个 Agent 在同一目录改文件，最后互相覆盖。
  • 上下文切换：每个 Agent 一个终端，谁在跑、谁卡住、谁等审批，全靠人记。
  • CI/评审回灌：测试挂了，要把日志贴回给正确的 Agent；人工转述会丢信息。
  • 合并前黑洞：PR 开了之后没人跟进，分支逐渐过期。
  • 离开工位：审批请求在桌面上，人在外面。
它的核心主张

把「Agent 的产出」当成「PR」来管理：状态由 PR/CI/评审事实推导，而不是靠 Agent 自报。

03

运作方式

Go daemon + SQLite + PTY/ACP host + worktree；显示状态是算出来的。

  1. 主 Agent 规划：读需求，拆成可并行的子任务，为每个子任务选 Agent 与模型。
  2. Worker 隔离：每个任务一个 Git worktree；TUI 模式跑在 PTY/ConPTY（tmux 作为兼容/回退），Chat 模式走原生协议控制器。
  3. 持久事实：SQLite 保存 session、活动状态、PR/CI/评审事实；展示状态（working / needs_input / ci_failed / mergeable）在读取时计算，不落库。
  4. 观察循环：轮询 SCM 与 CI；失败、冲突、评审意见回到拥有该分支的 Worker，直到 PR 通过。
  5. 休眠：Chat 会话在「已完成且无人查看」时可休眠，下次有工作时恢复原生会话；TUI 保持原生命周期。
架构取舍：把「展示状态」做成派生值，避免状态表与事实表不一致；代价是每次读取都要计算，且观察循环的延迟会影响看板新鲜度。
04

上手

桌面应用自带 daemon，不需要先装 CLI；但要先把 Agent CLI 配好。

# 从官网或 GitHub Releases 下载
# macOS (Apple silicon / Intel)、Windows、Linux AppImage/deb/rpm
# https://orchestrator.inc/download/

# 打开应用，指向一个仓库
# 应用会自动启动本地 daemon；无需单独运行 CLI

首次使用建议：

  1. 至少安装并登录 Claude Code、Codex 或 Cursor 中的一个；其它 Agent 按需装。
  2. 在设置里确认每个 Agent 的 worker / chat / reviewer 支持矩阵（不同 Agent 能力不同）。
  3. 先用一个小仓库跑「一个主 Agent + 两个 Worker」，确认 worktree 与 PR 流程。
  4. 需要手机时，在 Settings → Connect Mobile 扫码配对。
05

日常流程

看板不是装饰，它是「谁需要你」的队列。

  1. 描述目标：对项目主 Agent 说要做什么；它给出计划与 Worker 划分。
  2. Worker 执行：每个 Worker 在自己的 worktree 里写码、跑测试、开 PR；可以选结构化聊天或 Agent 自己的终端 UI。
  3. 看板分栏：Working / Needs you / In review / Ready to merge；状态由 Agent、PR、CI、评审共同推导。
  4. 失败回灌：CI 挂了、评审有意见、合并冲突，自动回到原 Worker，而不是让人转述。
  5. 审阅：Reviewer Agent 可以先读每个 PR；人再做最终判断。
  6. 合并：推进到可合并状态；是否自动合并取决于你的仓库策略与设置，不要假设它会替你按下按钮。
Cloud Agents

选择「Clone to the cloud」后，Worker 跑在托管工作区，代码、worktree、Agent 都在云端；笔记本合盖也能继续。代价是私有代码离开本机，需要评估合规与凭据范围。

06

强项

它把「多 Agent」做成了有状态、可观察的系统。

  • 35+ Agent 支持：Claude Code、Codex、Cursor、OpenCode、Aider、Copilot、Grok、Kimi、Pi、Amp、Devin、Goose 等，按任务挑。
  • worktree 隔离：并行任务不共享工作区，冲突在合并阶段才暴露。
  • CI/评审闭环：失败自动回灌给原 Worker，减少人工转述。
  • 状态派生：看板基于 PR/CI/评审事实，不靠 Agent 自报「我做完了」。
  • 移动端：推送、审批、开新 Worker、看 PR。
  • 可选云端：需要 24/7 时把 Worker 放到托管环境。
07

边界与代价

能力越大，默认收集与默认执行的范围也越大。

  • 遥测：收集有限使用与可靠性数据，含安装 ID、GitHub 用户名；登录 AO Cloud 还会含用户 ID 与邮箱。官方称不含代码、prompt、对话或凭据，可在设置中关闭。
  • 云端执行：Cloud Agents 会把代码与 worktree 放到托管环境；不是默认本地。
  • 资源占用：Electron 桌面 + Go daemon + 多个 Agent + worktree，内存与磁盘高于单 CLI。
  • 主 Agent 拆错：计划质量决定并行收益；拆得过细会增加协调成本。
  • 合并风险：多 Worker 并行会放大「各自测试通过、合并后失败」的概率；需要合并队列与回归。
  • Agent 能力矩阵不均：Worker / Chat / Reviewer 的支持因 Agent 而异，不是所有组合都等价。
部署建议

先把「自动合并」关掉，用 Reviewer Agent 做第一道，人做第二道；等 CI 稳定后再讨论自动化。

08

安全与权限

三个边界：本机、云端、遥测。

代码位置
默认在本机 worktree；Cloud Agents 会克隆到托管工作区。
凭据
沿用各 Agent CLI 的登录态；Worker 能读到你账号能读的仓库与文件。
遥测
安装 ID、GitHub 用户名；AO Cloud 登录后含账号 ID 与邮箱；可在 Settings → General → Privacy 关闭。
评审
Reviewer Agent 是「另一个模型」，不是安全边界；它也会漏。
合并
默认应保留人工批准；分支保护与 required checks 仍然要配。
最容易被忽略

Worktree 隔离的是「文件」，不是「凭据」。一个 Worker 仍然能用你的 SSH key、云 token、浏览器登录态；并行越多，暴露面越大。

10

结论

推荐路径

用一个中等仓库跑两周：主 Agent 拆 2–3 个 Worker，观察「CI 失败回灌」是否真的减少你的转述工作。若收益明显，再开手机与云端；否则退回单 Agent + 手工 worktree 更省心。

它适合「已经把 Agent 当团队用」的人；如果还在验证单个 Agent 是否靠谱，先别上舰队。
