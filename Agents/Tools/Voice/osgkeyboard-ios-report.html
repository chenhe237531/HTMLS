01

结论先行

它不是“另一个语音输入 App”，而是把输入法当成 AI 入口。

一句话判断：如果你用 iPhone/iPad、系统在 iOS 26+，并且想要“键盘里直接听写 + 润色 + 中文打字 + 剪贴板处理”，OSGKeyboard 是目前功能最完整的一类方案。端侧路径值得先用；但“开源”“完全免费”这两个说法都不准确，商用/二次分发会被许可挡住。

它适合

  • iPhone/iPad 重度输入者：微信、邮件、文档、搜索都在键盘里完成。
  • 想要“说完就能发”的人：听写、润色、翻译、剪贴板技能在同一个界面。
  • 接受 BYOK 的人：愿意自己填 DeepSeek/其他服务商的 Key。
  • 需要中文打字兜底的人：全拼、双拼、模糊音、英文补全都在。

它不适合

  • 要求开源合规、可自由分发/二开/商用。
  • 系统低于 iOS 26，或主要用 Android/Windows。
  • 不愿开启键盘“完全访问”，也不愿配置 API Key。
  • 需要完全免费且没有任何内购/积分。
  • 需要企业统一部署、SLA、发票与长期支持。
采用建议：先用“端侧听写”跑一周，确认键盘稳定性与中文打字是否替代你的主输入法；再决定是否开 BYOK 润色。不要一上来就买积分。
02

事实边界与三个纠偏

这个项目的一手信息很完整，但简报里有三处需要改口径。

先纠正三处常见说法

  1. “完全免费”不准确。端侧听写与 BYOK 路径没有订阅费；但 iOS/iPadOS 的“OSG 托管积分”是付费能力，App 本体是否收费、积分单价多少，仓库没有给出，需看 App Store 内购页。
  2. “开源”不准确。仓库使用 OSGKeyboard Source Available License 1.0，LICENSE 原文明确写着 “This is NOT an open-source license.”，只允许个人、非商业的本地学习/评估/修改，禁止再分发、公开衍生与商业使用。
  3. “输入法平替”要限定。它是第三方自定义键盘，不是系统级替换；需要手动添加键盘、开启“完全访问”，并受键盘扩展的内存与生命周期限制。

为什么键盘扩展不直接拿账号令牌

键盘扩展是第三方键盘的一部分，权限与攻击面都比主 App 大。README 说托管服务只给键盘扩展短时、按 scope 限权的 grant，主 App 账号令牌不下发。这是一个正确的隔离方向；但具体实现仍需代码审计才能确认。

为什么键盘扩展会“被回收”

iOS 给键盘扩展的内存预算远小于普通 App。项目在 40 MiB / 48 MiB 主动释放中文引擎、英文词库和在飞任务，并接入 MetricKit 记录内存回收。这说明“功能多”与“键盘稳定”之间有真实取舍：低内存设备上，重功能可能被系统优先牺牲。

端侧、BYOK、托管三条路线的区别

端侧：Apple 本地听写，不联网，不用 Key，AI 润色不可用或需另行触发。BYOK：音频仍端侧识别，转写文本直达你选的服务商，Key 存 Keychain。托管：用 OSG 的积分换语音/AI 服务，省去配置，但数据经 OSG 服务，且需要付费。

做得好的地方

  • 默认端侧识别，原始录音不上传；云端是显式选择。
  • BYOK 请求直达服务商，不经 OSG 中转（README 口径）。
  • API Key 存 Keychain；托管 grant 短时、限权，不下发主账号令牌。
  • 剪贴板历史默认关闭、最多 15 条、仅本机。
  • 不集成第三方广告/追踪 SDK；产品分析不采集输入内容。

仍需警惕

  • “完全访问”是键盘工作的前提，权限叙事容易被用户忽略。
  • BYOK 润色会把输入框上下文发给第三方；服务商保留策略不由 OSG 控制。
  • 托管路径经 account.osglab.com，具体日志/保留期限需读隐私政策。
  • iCloud 同步是可选，但开启后数据进入苹果云；敏感词库/历史要按需关闭。

优势与局限

工程质量是加分项；许可与平台门槛是硬约束。

优势

  • 键盘内完成听写、润色、中文打字、剪贴板技能，切换成本低。 文档
  • 端侧优先，默认不上传录音；云端是显式选择。 文档
  • BYOK 路径透明，Keychain 存凭证，请求直达服务商。 文档
  • 中文打字能力强：全拼、5 种双拼、模糊音、英文补全。 文档
  • 剪贴板技能与原生 EventKit 写入，减少跨 App 操作。 文档
  • 工程细节扎实：内存阈值、MetricKit、App Group/Keychain CI 校验。 文档

局限

  • iOS 26+ 门槛很高，老设备/旧系统直接排除。 文档
  • 源码可见但非开源：不能自由分发、公开衍生或商用。 LICENSE
  • 键盘扩展内存受限，功能多反而更容易被系统回收。 文档
  • 托管积分是付费能力，价格与套餐未在仓库中公开。 待核实
  • 功能面很宽，设置、权限、服务商配置的学习成本不低。 推断
  • macOS 公开 DMG 落后，最新源码需自行构建。 文档
08

适合谁，不适合谁

它的核心价值是“少切 App”，不是“识别最准”。

适合

  • iPhone 重度输入者：每天大量微信、邮件、文档、搜索，切键盘很烦。
  • 想要键盘内 AI：说完直接润色/翻译/总结，不想复制到聊天窗口。
  • 接受 BYOK：有 DeepSeek 或其他服务商 Key，愿意自己管理。
  • iOS 26+ 设备：能用到 Apple 最新的端侧听写能力。
  • 需要中文打字兜底：语音不方便时仍要全拼/双拼。

不适合

  • 开源合规要求：需要 OSI 许可、自由分发、商用或二次开发。
  • 旧系统：iOS 25 及以下无法使用。
  • 不想配 Key：只想要“装完就能用”的纯端侧体验。
  • 完全免费预期：不想碰任何内购/积分。
  • 企业统一部署：许可限制 + 无企业支持。
  • 追求极致稳定：键盘扩展被回收的风险始终存在。
一个务实的判断：先用端侧路径替代系统听写一周。如果键盘稳定性、中文候选、语音识别都过关，再考虑 BYOK 润色；否则功能再多也不值得。

采用建议

先端侧、后 BYOK、最后才考虑托管。

推荐路径

  • 第 1 周：只用端侧听写，替代系统听写；观察键盘稳定性与中文候选。
  • 第 2 周：开 BYOK，只配一个 LLM（如 DeepSeek），对比润色前后修改量。
  • 第 3 周：如果确实省时间，再评估托管积分；否则保持端侧+BYOK。
  • 团队使用：先拿商业授权，再谈部署。

不建议的做法

  • 一上来买积分，结果发现键盘被系统频繁回收。
  • 把公司代码/客户资料粘进剪贴板，再让键盘技能处理。
  • 把“源码可见”当成“可以随便改一改发给同事”。
  • 在 iOS 25 设备上折腾安装，浪费时间。
底线建议：把 OSGKeyboard 当“个人效率工具”没问题；把它当“可自由分发的开源组件”会踩许可红线。
