01

结论先行

它不是“转写工具”，而是“把口述整理成能直接发出去的句子”。

一句话判断：如果你在 macOS 上、在意隐私、愿意装 Ollama 并接受约 1.5–3 GB 内存占用，voiceType 是这四个工具里“数据边界最干净”的一个：识别、整理、上屏都在本机。代价是热键固定、没有流式识别、安装要绕 Gatekeeper。

它适合

  • 隐私敏感：会议、客户、内部资料不想离开 Mac。
  • 经常离线：飞机、内网、弱网环境仍要输入。
  • 中文口述为主：邮件、笔记、文档、聊天。
  • 能接受本地模型：愿意占内存、接受 0.5–1 秒延迟。
  • 愿意手工安装：能处理自签名/未公证 App。

它不适合

  • 要开箱即用、已公证、无 Gatekeeper 警告。
  • 需要流式识别：边说边出字。
  • 需要多语言会议、长音频、说话人分离。
  • 内存紧张（8GB 且同时开很多应用）。
  • 需要商用支持、SLA、统一部署。
采用建议：先用默认 0.6B + 整理模式跑一周；如果内存吃紧，把整理切成“插入原文”或换 0.6B；如果你经常说术语/人名，再试 1.7B。
02

事实边界

简报与仓库基本一致；需要补充的是三个“边界条件”。

简报核对结果：“macOS 14+”“全流程本机”“静默后台输入”“中文 CER 7.57%”“35 秒语音约 0.57 秒”“不消耗 API 额度”都能在 README 中找到对应描述。它们成立，但有三个边界：首次要联网下载模型；整理依赖本机 Ollama；热键固定且没有流式识别。

  • 常驻内存：0.6B 约 1.5 GB；1.7B 约 3.1 GB；Ollama 约 1.4 GB。README，M5 Pro / 48GB

  • 限制：热键固定 Option+Command、主要面向中文、无流式识别、自签名未公证、依赖 Ollama。README

  • 全流程本机离线 → 日常使用成立；首次下载模型除外。
  • 静默后台输入、不抢焦点 → README 明确“不抢焦点、不进 Dock”。

日常使用不产生云端请求；只有首次下载模型需要网络。
为什么用 CGEvent 而不是剪贴板

剪贴板方案会覆盖你原来的剪贴板，还要处理恢复与权限；CGEvent 直接投递 Unicode 键盘事件，等价于真实键入，不切应用、不碰剪贴板。代价是某些安全输入框会静默丢弃事件，所以项目保留了剪贴板兜底。

事实校验为什么重要

口语整理最容易犯的错不是“没删口头禅”，而是“把三点改成两点”“把人名改错”。voiceType 在整理后比较数字、时间等事实；一旦对不上，就丢弃整理结果、用原文。这个取舍比“更顺滑”更重要。

为什么没有流式识别

流式需要边录边解码、处理分段与上下文，复杂度和资源占用都更高。voiceType 选择“说完再识别”，换来更简单的链路和更稳定的注入；代价是说完要等 0.5–1 秒。

做得好的地方

  • 语音、识别结果、整理请求都不离开本机；整理发往 127.0.0.1。
  • 唯一网络访问是首次下载模型；之后断网可用。
  • 没有账号、API Key、第三方 SDK、遥测。
  • MIT 许可，代码可审计、可自行构建。
  • 事实校验 + 剪贴板兜底，减少“改错”和“丢字”。

仍需注意

  • 录音留档在 ~/Library/Application Support/voicetype/Recordings/，不会自动清理。
  • 自签名、未公证；首次安装要手动去隔离属性。
  • 辅助功能权限很大；注入事件可被安全输入框丢弃。
  • 模型下载走第三方（Hugging Face / hf-mirror），首次仍需信任下载源。

优势与局限

优势是“数据边界”和“事实校验”；局限是“安装门槛”和“热键固定”。

优势

  • 真全本地：语音、转写、整理都不出设备。 文档
  • MIT 开源，可审计、可自行构建。 LICENSE
  • 中文 CER 7.57%，默认 0.6B 在精度/内存间平衡好。 基准
  • 事实校验兜底：数字/时间对不上就退回原文。 文档
  • 注入失败退化为剪贴板，不会“既没插进去又没后路”。 文档
  • 不抢焦点、不进 Dock；后台静默输入。 文档
  • 成本只有电费；没有 API Key/账号/订阅。 文档

局限

  • 热键固定 Option+Command，可能和窗口切换等快捷键冲突。 文档
  • 主要面向中文；中英混说 + 不规则数字串是已知弱项。 文档
  • 没有流式识别，说完要等 0.5–1 秒。 文档
  • 自签名未公证，安装要绕 Gatekeeper。 文档
  • 依赖 Ollama；整理常驻约 1.4 GB 内存。 文档
  • 录音留档不自动清理，需要手动管理。 文档
  • 社区很小（1★），维护风险高；Intel 支持未明确。 文档
08

适合谁，不适合谁

它是“隐私优先”的答案，不是“最省事”的答案。

适合

  • 隐私敏感的专业人士：律师、医生、研究员、财务，内容不能上云。
  • 经常离线的人：飞机、内网、弱网环境。
  • 中文口述为主：写邮件、笔记、文档、聊天。
  • 愿意折腾：能处理 Gatekeeper、权限、Ollama。
  • 内存够用：16 GB 及以上更舒服；8 GB 可用但紧张。

不适合

  • 要开箱即用：不想看 Gatekeeper/权限设置。
  • 需要流式：边说边出字。
  • 多语言会议/长音频：不是它的目标。
  • 低内存设备：0.6B+Ollama 约 2.9 GB，容易和别的 App 抢内存。
  • 需要正式支持：没有企业版、SLA、发票。
试用判据：用它写 10 段真实内容，统计“改字数”和“事实错误”。如果事实校验经常触发，说明整理模型不适合你的口述风格；先切“插入原文”或换 1.7B。

采用建议

先 0.6B + 整理，再按内存和准确率调。

推荐路径

  • 第 1 天：装 v0.2.0，授权三项权限并重启；先用 0.6B + clean。
  • 第 2–3 天：用 10 条真实口述对比原文/整理；记录事实校验触发次数。
  • 第 1 周：如果术语/人名错得多，切 1.7B；如果内存紧张，切“插入原文”。
  • 长期：定期清理 Recordings；关注仓库更新与签名变化。

不建议的做法

  • 在共享 Mac 上留着录音不清理。
  • 不看签名/来源，直接绕过 Gatekeeper。
  • 8 GB 内存还同时开 1.7B + Ollama + 大型 IDE。
  • 把它当会议转写/多语言工具。
底线建议：voiceType 适合“把隐私放在第一位、愿意承担本地资源成本”的人。它不是最省事的，但它是这四个里数据边界最清楚的。
