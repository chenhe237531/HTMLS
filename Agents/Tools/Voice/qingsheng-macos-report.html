01

结论先行

它解决的是“我说的话要和屏幕上的东西对上”，不是“我要一个便宜的听写”。

一句话判断：如果你经常一边看资料一边口述，且能接受把转写文本（可能还有屏幕文字）发给 DeepSeek，轻声输入值得小范围试用；如果你要的是可审计、全本地、开箱即用，它现在都不满足。

它可能适合你

  • macOS 上长期用语音写邮件、周报、客服回复、会议纪要。
  • 经常需要把屏幕上的文件名、数字、专有名词准确说出来。
  • 接受“本地识别 + 云端润色”的混合隐私模型。
  • 愿意自己看网络请求、签名和权限，而不是只看宣传。

它大概率不适合你

  • 处理客户资料、合同、医疗、财务等敏感内容。
  • 组织要求开源可审计、可统一部署、可开票支持。
  • 不愿授予“屏幕录制/辅助功能”这类高权限。
  • 需要 Windows/Linux，或需要稳定的长期维护承诺。
采用建议：把它当“待验证的候选”，不要当“已确认的成品”。先用隔离环境、断网、网络监控和 10 条真实口述做一次小验证，再决定是否日常使用。

跨越边界的内容取决于设置：最理想是只发转写；最差是连屏幕 OCR 一起发。
为什么“读屏幕”是这类工具的关键差异

普通听写只知道你说了什么；读屏幕的工具还知道你正在看什么。它可以把屏幕上的产品名、文件名、数字、英文术语作为识别提示或润色上下文，从而减少“同音词”和“专有名词”错误。代价是权限更高、数据面更大：屏幕里可能有密码、聊天记录、客户名单。

为什么“本地 ASR + 云端润色”是常见折中

音频体积大、上传慢、隐私敏感，放本地最划算；文本体积小、云端大模型整理质量高，按 token 计费也便宜。所以很多产品选择“音频不出门，文本出门”。这不是全本地，也不是全云端，隐私叙事要按混合模型来评估。

“约 ¥10/月”是怎么来的（推断）

如果识别完全本地，成本只剩 DeepSeek 的输入/输出 token。按每次 15 秒、上下文 600–1200 字、每天 50–100 次估算，月成本大致落在几元到十几元；把屏幕上下文调大、次数调多，就会逼近或超过 ¥10。具体价格随 DeepSeek 调价和上下文长度变化。

相对好的做法

  • 优先找“仅输入框”或“不读屏幕”的开关；没有就按最坏情况评估。
  • 用 Little Snitch / LuLu 观察它到底连了哪些域名。

  • 把“本地识别”宣传成“全本地”，却不提云端润色。

  • 把屏幕 OCR 文本和转写一起发给第三方，却不说明保留多久。
  • 用“评论区更新”作为唯一发布渠道，无法核对版本与签名。

优势与局限

优势大多来自产品思路；局限大多来自“不透明”。

可能的优势

  • 上下文感知是真正的差异化：屏幕上的词能反过来提升识别/润色。 待核实
  • 本地 ASR 至少让原始音频不必上传，比全云端听写少一层风险。 待核实
  • 文本 token 成本低，重度使用也通常只是“几元到十几元/月”。 估算
  • 对中文口述、专有名词、屏幕资料场景可能明显省修改时间。 推断

明确的局限

  • 没有公开仓库、版本号、构建说明，无法独立验证二进制行为。 已核实
  • “读屏幕”通常意味着屏幕录制/辅助功能权限，权限面很大。 待核实
  • 云端润色意味着文本（可能还有屏幕内容）离开设备。 待核实
  • 分发依赖作者个人渠道，更新、回滚、漏洞修复都不可预期。 待核实
  • 没有公开的延迟、内存、准确率数据，无法做容量规划。 未知
  • 单人维护的项目，长期可用性风险高于成熟产品。 推断
08

适合谁，不适合谁

按场景判断，不要按“功能列表”判断。

适合

  • macOS 文字工作者：每天要写大量邮件、文档、回复，且经常参考屏幕上的资料。
  • 能接受混合隐私模型的人：知道文本会去 DeepSeek，但音频留在本机。
  • 愿意做验证的人：会看网络请求、签名、权限，不把“作者说”当结论。
  • 把它当效率实验的人：先用一周，和 Apple 听写/voiceType 对比修改成本。

不适合

  • 机密/合规场景：合同、病历、财务、客户名单、源代码。
  • 要求开源可审计：需要看源码、自己构建、做安全评审。
  • 不愿给屏幕权限：屏幕里经常有密码、私信、未公开材料。
  • 需要稳定支持：组织采购、SLA、发票、长期维护承诺。
  • 非 macOS：Windows/Linux 用户直接看 Saydra 或其他方案。
一个简单的试用判据：用同一段 30 秒的口述，分别走 Apple 听写、voiceType、轻声输入，统计你“改了多少个字/改了几次”。如果轻声输入不能把修改时间至少减少三分之一，上下文优势就不值得它的隐私代价。

采用建议

按你的约束选，不要按“别人说好用”选。

如果你…

  • 最看重屏幕上下文，且能接受云端润色 → 小范围试用轻声输入，先做安全验证。
  • 最看重全本地、零 API → 选 voiceType。
  • 在 Windows 上，想要免费开源 → 选 Saydra，并接受“整理要联网”。
  • 在 iPhone 上，想少装一个 App → 选 OSGKeyboard 的端侧路径。
  • 处理机密内容 → 不要用云端润色；选全本地并做审计，或继续用键盘。

30 分钟试用脚本

  • 第 0–5 分钟：在隔离用户/虚拟机安装，记录版本与来源。
  • 第 5–10 分钟：断网，测试识别是否可用、润色失败如何提示。
  • 第 10–15 分钟：开 LuLu，记录所有出站域名。
  • 第 15–20 分钟：关闭屏幕权限，比较识别/润色质量差异。
  • 第 20–30 分钟：用 10 条真实口述，统计修改字数与事实错误。
底线建议：在它能给出公开仓库、签名信息和明确的“发送内容清单”之前，不要把它放进你的主工作流，更不要用于客户数据。
