01它到底是什么

一句话：把“资深工程师的流程与约束”产品化成可安装的 harness 配置，而不是再写一个 agent 框架。

ECC 的自我定位是 agent harness performance optimization system。拆开看是四件事：

  • 流程：TDD、规划、评审、安全审查、研究，写成可被 agent 按需加载的 skill 和 agent。
  • 约束：rules 与 hooks 把“必须这样做”从提示词里拿出来，放到模型上下文之外执行。
  • 记忆：跨会话的 instinct / memory 层，让下一次会话不必从零解释项目。
  • 安全：AgentShield 扫描 hooks、MCP 配置、技能与凭据泄漏，自带 1,282 条测试。
和“配置包”的区别

普通 dotfiles 是复制文件；ECC 有安装器、插件市场、跨工具适配层、版本化发布和付费的 GitHub App。它把“个人经验”做成了有分发渠道的产品。

02架构：一份源，多套适配

根目录是唯一事实来源，平台目录只做映射。这是它能同时维护七个 harness 的关键。

读法：上面是内容，中间是适配，下面是执行。内容只写一份，平台差异由适配层吃掉——这也是它和“给每个工具各维护一套配置”最大的区别。

五个组件，各自的职责

组件是什么什么时候进上下文典型用途
Skills可复用的工作流与领域知识（SKILL.md + 可选脚本）任务需要时按需加载TDD、深度研究、安全评审、写作
Agents有独立上下文与工具权限的子代理被委派时启动规划、实现、评审、构建修复
Rules项目或语言的持久标准常驻编码规范；所以要选择性安装
Hooks由 harness 事件触发的脚本不进模型上下文提交前检查、权限拦截、记忆写入
Commands斜杠命令 shim调用时展开把常用流程做成一个入口

03跨工具支持：主参考只有一个

官方自己的措辞是“parity: partial”。别把“支持七个工具”理解成“七个工具体验一样”。

Harness状态安装方式关键限制
Claude CodeStable · 主参考插件或选择性安装插件会把整个目录暴露给模型；上下文敏感时要手动裁剪

GitHub CopilotInstruction-only / Beta CLI指令文件；或 --target copilotChat 不适配 hooks；CLI 不装命令 shim
Gemini、Zed、Kimi 等Experimental各 harness 的选择性 target只验证了文件放置与指令可移植性
平台限制是真实的

README 自己列了：macOS 上独立的 GAN shell 路径与系统 Bash 3.2 不兼容；Windows 原生下 continuous-learning 的守护进程与 memory-vault 写入有未修问题。跨平台团队要按能力表验收，不要按宣传语验收。

04怎么装：三条路，只选一条

官方明确要求“Pick one path only”。叠加安装是社区里最常见的故障来源。

适合：第一次装、想一次配好多个 harness、之后还要改 hook profile。

# 需要 Node 18+、Git、Claude Code 2.1+
npx ecc-universal@2.2.3 setup

# 一次配多个 harness（Codex / Kimi Code 等）
npx ecc-universal@2.2.3 install --guided

# 验证
claude --version
# 然后在 Claude Code 里
/plugin list

同一个命令也用于更新、改作用域、改 hook profile。

适合：只想用 Claude Code，且习惯用官方插件市场。

# 在 Claude Code 会话里
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc

插件装不了 rules。需要规则时，单独复制 rules/common 加一个语言包，别再把完整手动安装叠上去。

适合：上下文预算紧、只想要几个 agent / 规则、或要审查每一行配置。

git clone https://github.com/affaan-m/ECC.git
cd ECC

# 只要 agent
cp agents/*.md ~/.claude/agents/

# 只要规则：先装 common，再加一个语言包
mkdir -p ~/.claude/rules/ecc
cp -R rules/common ~/.claude/rules/ecc/
cp -R rules/typescript ~/.claude/rules/ecc/

手动路径不会自动更新；把版本号记在安装记录里，升级时重新对照。

只从官方渠道装

README 明确警告：第三方转存与镜像未经审核，可能含恶意代码。官方渠道只有 GitHub 仓库、npm 的 ecc-universal / ecc-agentshield、GitHub App、插件 slug ecc@ecc 和 ecc.tools。版本号固定不等于安全审计，装之前仍要看 release 与 registry integrity。

05五个值得抄的设计

1. 选择性加载，而不是全量灌入

314 个技能不可能全进上下文。ECC 用 SKILL.md 的描述做发现、按任务加载；agent 是独立上下文；hooks 干脆不进模型。这套分层是它能“很大但不炸”的前提。

2. 约束放到 hooks，而不是提示词

“提交前必须跑测试”“写文件前检查权限”这类要求，写在 prompt 里会被忽略，写成 hook 就是硬约束。代价是平台适配复杂——所以它才需要一层 adapter。

3. 一份源，多套适配

根目录是唯一事实来源，各平台只做映射。这让新增一个 harness 的成本落在“写适配”而不是“复制维护七份内容”。

4. 把安全做成可执行的扫描

AgentShield 面向的是 agent 配置本身：hooks、MCP、技能、凭据泄漏。官方给的数字是 1,282 条测试、98% 覆盖、102 条静态规则。对“agent 会执行命令”的场景，这比再多 prompt 都实在。

5. 用 GitHub App 做商业化，而不是把仓库关掉

MIT 永久免费；Pro 是托管 GitHub App：私有仓库分析、PR 审计、团队用量。开源做分发，托管做收入——这是这类“配置型项目”少见的可持续路径。

07边界与风险

  • 上下文税：314 个技能 + 71 个 agent 的目录会进模型视野；插件模式尤其明显。上下文敏感时要走选择性安装。
  • 跨平台不齐：Cursor / OpenCode 是 Beta，Copilot 只到指令层，其余是实验适配。
  • 质量不是均质的：几百个技能由不同阶段沉淀而来，命名、边界、脚本质量会有差异；别默认“装了就等于会”。
  • 供应链风险：项目自己警告第三方镜像可能含恶意代码；hooks 与脚本会以你的权限执行。
  • 快速演进：v2.0.0 到 v2.2.3 几个月内多次改动目录与安装方式；照着旧博客装很容易踩坑。
  • 数字口径会变：71 agents / 314 skills / 98 commands 是当前 main 的 README 数字；v2.0.0 时是 67 / 281 / 94。引用时带版本。

它适合谁

场景建议理由
同时用 Claude Code / Codex / Cursor 的个人值得试一份流程多端复用，省去重复配置
想把 TDD、安全评审固化成团队标准值得试hooks + rules + 选择性安装可以裁剪成团队版
上下文预算极紧、只用单一 agent谨慎优先手动装几个 skill / rule，别上全量插件
要求供应链可审计、禁止外部 hooks不适配需要逐个 review 脚本，成本高于收益
我的判断

ECC 的真正价值不是“295K stars 的配置包”，而是它示范了一件事：把个人工作方式做成有安装器、有适配层、有安全边界、有商业闭环的产品。你可以不装它，但如果你在做团队级 agent 规范，这五层（内容 / 适配 / 执行 / 审计 / 分发）值得照抄。
