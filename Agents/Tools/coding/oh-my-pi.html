TOOL REPORT/终端编码 Agent / Harness/2026-11

oh-my-pi / OMP Studio
把 IDE 的能力塞进终端 Agent

官方 oh-my-pi 是一个终端编码 Agent，真正的卖点不是聊天，而是把 LSP、DAP、原生 grep/glob、子 Agent、advisor 与多 provider 路由做成 harness。OMP Studio 不是官方产品，而是多个社区桌面壳共用的名字；两者要分开评估。

MIT TypeScript + Rust 37,470 star v18.15.0 60+ provider macOS / Linux / Windows

适合

  • 以终端为主、希望 Agent 能直接做 LSP 重命名、DAP 调试与结构化编辑
  • 需要多 provider / 订阅混搭、子 Agent 并行、第二模型审查
  • 愿意接受高频升级、较大二进制与项目级扩展信任

不适合

  • 只想要一个稳定、轻量、长期不变的 CLI
  • 不愿让项目内的扩展、hooks、MCP 配置自动进入信任边界
  • 把「OMP Studio」当成官方桌面客户端来采购

01

它是什么

Pi 的重型分支：终端编码 Agent + 原生工具 + IDE 协议 + 多入口 SDK。

oh-my-pi（命令 omp）是 Pi 的分支，由 Stencil Labs 维护，定位是「a coding agent with the IDE wired in」。它不是通用 Agent 框架，而是把「在真实仓库里读写、搜索、重构、调试、审查、提交」做成一整套 harness。

README 给出的硬指标：60+ provider、31 个内置工具、14 个 LSP 操作、28 个 DAP 操作、约 8 万行 Rust core。它同时提供 TUI、单次执行、Node SDK、RPC、ACP 四种入口。

OMP Studio 不是官方产品

官方仓库里没有名为 OMP Studio 的一等桌面应用。官方提供的是 TUI、Agent Hub（Alt+A）、本地统计包 @oh-my-pi/omp-stats 与 collab 浏览器观看。OMP Studio 是社区桌面壳的名字，目前至少有两个不同仓库：DawnJson/omp-studio 与 dylanmccavitt/omp-studio。详见第 09 节。

它负责

  • 在仓库里读、搜、改、重构、跑命令
  • LSP 诊断/重命名与 DAP 断点调试
  • 子 Agent 并行、结果聚合、第二模型审查
  • 多 provider/订阅路由、记忆、技能、MCP

它不负责

  • 替你做产品决策或保证合并安全
  • 提供官方 GUI（社区 Studio 另计）
  • 默认给你一个安全沙箱
  • 保证第三方 benchmark 在你的仓库复现
02

它解决的具体问题

它赌的是「harness 决定模型发挥」，而不是「换更大的模型」。

  • 编辑格式拖累模型：str_replace 一类格式容易让模型在空白、上下文、stale file 上反复失败；omp 用 hashline（内容哈希锚点）减少重试。
  • 工具延迟：很多 Agent 每次 grep/glob 都 fork-exec 系统二进制；omp 把 ripgrep、glob、find、shell 内建进进程。
  • 缺少 IDE 上下文：普通 Agent 看不见类型错误、重命名影响面、调试器栈帧；omp 把 LSP/DAP 接进工具面。
  • 子 Agent 协调：并行任务需要隔离 worktree、结构化返回、可中断/复活；omp 的 task/Agent Hub 针对这个。
  • 模型锁定：不同任务适合不同模型；omp 用 9 个角色与 fallback chain 路由。
  • 上下文与记忆：会话压缩、持久记忆、技能沉淀，避免每次从零开始。
它的核心主张

模型能力不是唯一变量；读、搜、改、验证的工具质量与提示适配，会把同一个模型的表现拉开数倍。README 的数字是厂商自测，方向值得看，绝对值要自己复现。

03

运作方式

TypeScript 外壳 + Rust 原生层 + 多入口协议；重活在进程内完成。

原生层

  • 六个 Rust crate：pi-natives、pi-shell、pi-ast、pi-iso、pi-voice、pi-walker；通过 N-API addon 暴露给 TypeScript。
  • 内建工具：grep/glob/find、bash（内建数十个 coreutils/常用工具；README 不同段落写 58 与 46 两个口径）、AST、语法高亮、PTY、桌面控制、图片解码、token 计数。
  • 平台：macOS / Linux / Windows，x64 与 arm64；x64 带 AVX2 与 baseline 双二进制；Alpine/musl 需要 libstdc++/libgcc。

模型路由

  • 9 个角色：default、smol、slow、plan、commit、vision、task、advisor、tiny；按意图把请求分给不同模型。
  • 60+ provider：前沿 API、coding plan 订阅、本地 Ollama/LM Studio/vLLM、以及自定义 OpenAI-compatible provider。
  • 可靠性：fallback chains、path-scoped 模型集合、按 provider 轮换 API key、按凭证退避。

工具与编辑

  • read/write/edit：一个路径接口覆盖文件、目录、压缩包、SQLite、PDF、notebook、URL、ssh:// 与内部 scheme。
  • hashline：模型指向内容哈希锚点而不是重抄整行；stale anchor 会在写盘前被拒绝。
  • AST：ast_grep 查询、ast_edit 预览后确认；覆盖 50+ tree-sitter 语法。
  • eval：持久 Python/JS cell，能从 cell 内回调 Agent 工具；适合数据处理与图表。
  • LSP/DAP：诊断、导航、符号、重命名、code action；lldb/dlv/debugpy 断点、步进、栈、变量。
  • 浏览器/桌面：headless Chromium 或接管现有 Chrome；桌面窗口、截图、原生输入、AX 树、剪贴板。

子 Agent 与审查

  1. task 扇出：把任务拆给多个 worker，每个 worker 有独立工具面，必要时在隔离 worktree 中运行。
  2. Agent Hub：Alt+A 查看每个子 Agent 的活动、用量、实时 transcript；可发消息、暂停、复活、终止。
  3. advisor：第二模型读取主 Agent 每一轮，以内联 note 形式提出 concern 或 blocker；不抢主 Agent 的控制权。
  4. review：/review 用并行 reviewer 子 Agent 扫分支/提交/未提交改动，按 P0–P3 排序并给结论。
  5. collab：/collab 生成链接/二维码，队友可只读观看或加入同一会话；帧在客户端加密。

入口与互操作

  • TUI：omp；单次：omp -p；SDK：@oh-my-pi/pi-coding-agent；RPC：omp --mode rpc；编辑器：omp acp（Zed 等）。
  • 规则迁移：读取 .claude、.cursor、.windsurf、.gemini、.codex、.cline、.github/copilot、.vscode 的已有规则/技能/MCP。
  • 内部 scheme：pr://、issue://、agent://、skill://、ssh:// 等 16 种，统一走 FS 形状的工具。
厂商自测数字：README 称 Grok Code Fast 1 在编辑格式修正后从 6.7% 提升到 68.3%，Gemini 3 Flash +5pp，Grok 4 Fast 输出 token 减少 61%，MiniMax pass rate 2.1×。这些是 Stencil Labs 的 harness 对比，不是独立复现；选型时应拿自己的仓库跑回归。
04

上手

安装很快，真正的工作量在模型登录、provider 选择和项目信任配置。

# macOS / Linux
curl -fsSL https://omp.sh/install | sh

# Homebrew
brew install can1357/tap/omp

# Bun（推荐）
bun install -g @oh-my-pi/pi-coding-agent

# Windows PowerShell
irm https://omp.sh/install.ps1 | iex

# Nix
nix run github:can1357/oh-my-pi

首次使用：

  1. omp --version 确认安装；omp setup 走登录/模型选择。
  2. /login 接 OAuth 或 API key；/model 指定 default，Ctrl+P 轮换当前角色的模型。
  3. 在目标仓库里运行 omp；先只用 read/grep/edit 做小改动。
  4. 需要子 Agent 时用 task，用 Alt+A 观察；需要第二意见时配 advisor。
  5. 接入编辑器时运行 omp acp，在 Zed 等客户端里把它当 ACP Agent。

从源码开发：

git clone https://github.com/can1357/oh-my-pi
cd oh-my-pi
bun setup
bun dev

# 改 Rust crate / packages/natives 后
bun run build:native

源码构建需要 Bun 与 Rust 工具链；Nix 用户可以用 nix develop 拿到固定版本。

05

日常流程

把 omp 当成「有 IDE 能力的终端同事」，而不是聊天窗口。

  1. 先读再改：让它用 read/grep/lsp 建立上下文，避免一上来大范围重写。
  2. 小步编辑：hashline 指向锚点；每次改动后跑测试/诊断，坏锚点会在写盘前被拒。
  3. 需要重构时：走 LSP rename/workspace edit，让 re-export、barrel、别名一起更新。
  4. 需要调试时：让它 attach lldb/dlv/debugpy，而不是到处加 print。
  5. 拆并行任务：用 task 扇出到独立 worktree；在 Agent Hub 里看谁卡住、谁花了多少。
  6. 审查与提交：/review 先扫 P0–P3；omp commit 拆原子提交并生成消息。
  7. 沉淀：retain/learn/recall 把仓库事实与可复用经验留给下次会话。
最小工作流

omp → 读三个相关文件 → hashline 改一处 → 跑测试 → /review 看 diff → 提交。先把这个循环跑顺，再开子 Agent 和 advisor。

06

强项

它把「终端 Agent」的上限抬到了接近 IDE 的水平。

  • 原生工具链：grep/glob/find/shell 在进程内，减少 fork-exec 与跨平台差异；Windows 不需要 WSL。
  • IDE 级操作：LSP 重命名/诊断/符号 + DAP 调试，是多数终端 Agent 缺失的能力。
  • 编辑可靠性：hashline 用内容锚点降低 stale file 与空白噪声造成的失败。
  • 子 Agent 可观察：Agent Hub 能看 transcript、用量、暂停/复活，不是「黑盒扇出」。
  • 第二模型审查：advisor 独立上下文、独立模型，能指出主 Agent 的验收偏差。
  • provider 广度：60+ provider、9 个角色、fallback、路径级模型集合。
  • 多入口：TUI、SDK、RPC、ACP，既能人用也能嵌进编辑器/宿主程序。
  • 协议与迁移：读取已有规则、16 种内部 scheme、PR/issue 当路径读。
  • MIT + 高频迭代：v18.15.0 在 2026-11-01 发布，社区非常活跃。
07

边界与代价

能力面越大，升级、磁盘、信任与 triage 成本越高。

  • 体积：v18.15.0 的单个平台二进制约 215–277 MB；安装、更新、备份都更重。
  • 复杂度：60+ provider、9 个角色、扩展/hook/MCP/技能/记忆，配置面很宽；新手容易被选项淹没。
  • 迭代速度：release 频繁、4,437 个 open issues；接口与行为可能快速变化，生产使用要固定版本并读 changelog。
  • 厂商自测：benchmark 数字来自 Stencil Labs 的 harness 对比，不是第三方复现；换仓库可能不成立。
  • 项目信任：打开仓库会加载项目设置、扩展、hooks、工具、命令、技能、规则与 MCP；这不是「只读一个文件」。
  • 无官方 GUI：社区 OMP Studio 质量/维护状态不一，不能按官方 SLA 采购。
  • 平台差异：Windows 优先但仍有平台细节；Alpine/musl 需要额外系统库。
  • 模型质量不均：provider 列表长不等于每个模型都能把工具调用/编辑格式跑好。
高 issue 数不必然等于质量差：对一个每天多次 release 的热门项目，4,000+ open issues 更像 triage 压力；但它确实意味着你要自己判断哪些问题会影响你的工作流。
08

安全与权限

omp 的默认模型是「信任项目」，不是「默认沙箱」。

项目输入
设置、扩展、hooks、tools、commands、skills、rules、项目 MCP 会随仓库加载。对不可信仓库要收紧。
收紧开关
--no-extensions 跳过环境扩展；--trusted-extension /abs/file.ts 白名单；--no-tools 关内置工具（项目工具模块仍是独立发现面）；--config overlay.yml 可关闭项目 MCP。
执行面
bash、eval、browser、computer、github、generate_image 等能触达真实文件、网络、桌面与账号；破坏性操作有审批，但不是全面沙箱。
编辑器
ACP 模式下写入走 session/request_permission；这是编辑器层的人工闸门，不替代仓库级隔离。
隔离
子 Agent 可用 worktree/overlay 隔离文件；这解决并发覆盖，不等于凭据/网络隔离。
第三方 Studio
社区 Studio 运行官方 omp 并共享 ~/.omp；安装前要审查其代码、签名与更新渠道。
凭据
provider key、GitHub token、浏览器登录态都可能被工具间接使用；给最小权限、按项目分 key。
最容易忽略

--no-tools 并不会自动禁用项目里的工具模块；--no-extensions 也不等于「不读项目配置」。在陌生仓库里，先看 --help 与项目文件，再用白名单启动。

09

OMP Studio 与 GUI 生态

官方给的是 TUI/Agent Hub/统计/collab；「Studio」是社区壳的名字。

项目定位与 omp 的关系状态
官方 omp终端 Agent + SDK/RPC/ACPTUI、Agent Hub、advisor、collab、omp-statsv18.15.0；主仓库
DawnJson/omp-studioWindows/macOS/Linux 桌面每个任务在 PTY 里跑官方 omp，渲染 TSP；共享 ~/.omp 登录/设置/会话MIT；10 star；2026-10-25 创建；安装包未签名
dylanmccavitt/omp-studioElectron 桌面 cockpit通过 omp --mode rpc 驱动；仪表盘、实时聊天、子 Agent drill-in、会话/技能/MCP/GitHub/LinearMIT；14 star；2026-06 创建；自我标注 pre-1.0、UI/格式不稳定
其他同名项目OMP Desktop / OMP Studio / OmpCode 等多为社区 GUI/PTY 包装维护状态与完成度差异大，需逐个核验

把你描述里的能力拆开看：

  • 「实时监控子 Agent 对话与花费」：官方 Agent Hub 提供子 Agent transcript/活动/用量；omp-stats 是本地使用统计面板；社区 Studio 把这些做成仪表盘。
  • 「防死循环审查」：官方文档没有把这个作为一等功能。omp 有的是 advisor（第二模型逐轮审查）与 time-traveling stream rules（匹配到规则时中断并注入提醒）；「doom-loop detection」是 PraisonAI 的明确特性。
  • 「多模型混搭调度」：这是官方 omp 的能力：9 个角色、60+ provider、fallback chain、路径级模型集合；Studio 只是把配置暴露出来。
选型建议

先用官方 omp 的 TUI + Agent Hub 两周；确实需要 GUI 时再试社区 Studio。优先选仍在维护、与当前 omp 版本兼容、安装包有签名/校验的仓库；不要因为名字叫「Studio」就假定它是官方。

10

结论

推荐路径

如果你以终端为主、需要 LSP/DAP/结构化编辑，omp 是目前工具面最完整的一类 harness。先用 --no-extensions 或 --trusted-extension 在陌生仓库里试；固定版本、读 changelog；子 Agent 与 advisor 等基础编辑循环稳定后再开。GUI 需求单独评估社区 Studio，不要混为一谈。

它适合「愿意把 Agent 当开发工具链一部分」的人；如果你只想要一个轻量聊天式编码助手，omp 的能力面和升级节奏可能过重。
