怎么写评审意见

三段式：级别 + 观察，为什么重要，要作者做什么。不带级别的评论会被当成必须改。

第 11 / 17 篇 stack ronny 代码审查

01它治什么病

一整屏没有级别的评论，作者不知道哪条是阻塞、哪条只是顺嘴一提；或者批评本身对，但语气让协作变难，最后讨论的是态度不是代码。

02机制

  1. 非琐碎评论用三段式：SEVERITY: 对代码的观察 → Why this matters → Requested action。
  2. 选级别：BLOCKER / IMPORTANT / QUESTION / NIT / OPTIONAL / FYI。
  3. 遵守写作规则：评论代码不评价人；除明显风格外都讲 why；需要 review 线程解释才懂的代码，要求简化。
  4. 遇到 pushback：先重估对方论点 → 对方对就明说并解决 → 仍有分歧就先复述对方观点再讲代码健康理由 → 区分强制与偏好 → 无法推进就换高带宽沟通，把结论写回 review。

03规则要点

级别含义
BLOCKER 必须改；IMPORTANT 应改，除非有书面理由；QUESTION 需回答才能定论；NIT 不得阻塞；OPTIONAL 可拒绝；FYI 不需要动作。
措辞
用“这让 X 更难，因为……”而不是“我不喜欢 X”。
给代码的时机
只有当直接给代码比让作者推断更快或更安全时才给；否则描述问题，让作者选实现。
注释
代码本身表达不了 why 时才加注释；能用代码说清就改代码。
正向反馈
看到好的工程选择就说出来，并说明好在哪。
不要变成设计作业
别把每条评论都写成完整重构方案；教育性注释不是阻塞项。
原文关键句（English）
Review comments should improve the code and the developer's future judgment. They should be clear about severity, grounded in engineering reasoning, and directed at the code rather than the person.

04落到你的场景

可以直接用

让 agent 给你提修改建议时，明确要求“每条带级别”。否则你会把十来个 nit 当成必改项，把一个本来 20 分钟的迭代拖成一下午。

05边界与反例

别用过头

六档级别是团队约定；单人项目砍到三档（阻塞 / 建议 / 知道了）更实用。
