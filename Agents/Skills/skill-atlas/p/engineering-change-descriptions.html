写清改了什么、为什么

变更描述是永久的工程史：现在让 reviewer 看懂，以后让维护者找得到。

第 03 / 17 篇 stack ronny 规划与拆分

01它治什么病

标题写“fix bug”“cleanup”“phase 1”，正文只描述实现。半年后同一个问题再次出现，没人能从历史里判断当时为什么这样选、试过什么。

02机制

  1. 首行：短、具体、祈使句，能单独出现在版本历史里。
  2. 空一行后写正文，回答 what / why / 非显然的约束与取舍 / 怎么测的 / 风险与回滚。
  3. 按变更类型套模板：标准 PR、小改动、重构、机械生成。
  4. 评审改动后重读一遍描述，确认它仍然匹配最终 diff。

03规则要点

首行
避免 fix bug、cleanup、phase 1、misc、add helpers 这类无法检索的词。
正文取舍
只放有用的：要解决的问题、为什么选这个方案、可见行为变化、已知限制、issue/基准/设计文档链接。
链接
关键上下文不要完全依赖外链，链接会失效；给一句自足的说明。
重构
明确写出“结构变了、行为没变”，以及它为哪个后续改动做准备。
机械生成
写清工具、版本、命令，以及手工改了哪些地方。
原文关键句（English）
A change description is permanent engineering history. It should let reviewers understand the change now and help future maintainers find and understand it later.

04落到你的场景

可以直接用

你的 HTML 交付仓库里，commit 就是发布记录。把“为什么这样组织信息架构、排除了哪两种方案”写进 body，比在对话里解释有用得多。

05边界与反例

别用过头

面向用户的 changelog 是另一种文体（讲影响，不讲实现），不要混用。

06关联

engineering-small-prs把大改动切成小 PR“小”指的是概念聚焦、自包含，不是行数少。审得完、退得回、方向变了不白干。 handoff-doc写交接文档重要状态不该只活在 context window 里。一页纸让人（或新会话）接着干。 engineering-code-review代码评审的标准与流程标准不是完美，是“让系统变好，且不引入不可接受的风险”。
