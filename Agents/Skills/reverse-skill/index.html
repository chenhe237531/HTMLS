摘要

一句话：给 AI 装一个“资深逆向工程师的分诊台”

当你说“帮我看看这个 APK 的签名”或“这网站的加密参数怎么来的”，模型缺的不是智力，而是该走哪条路和哪些事不能做。reverse-skill 把这两件事写成了可校验的文件。

它是什么

面向 AI 编码客户端的技能路由包：路由层选 PRIMARY，契约层管授权，技能层给方法论，工具层给真实路径，经验层回收教训。

RULES.md → routing.json → SKILL.md → tool-index

它凭什么值 4 万星

把 AI 三个高频失败模式——“不会选工具”“同一个坑反复踩”“不知不觉越权”——变成文件契约、硬门禁和 178 条路由回归用例。

client-neutral · Windows + Ubuntu CI

它不能给你什么

不是一键逆向平台，不是沙箱，也不是漏洞利用工具集。约束靠指令与文件，不靠技术隔离；真授权与真边界仍由人负责。

dual-use · 合规责任在用户

读这份报告的三个结论

1. 它的核心创新不在“技能多”，而在路由 + 契约 + 回归测试三件套：路由是单一 JSON，契约是硬门禁，测试让改路由这件事可被验证。

2. 真正的差异化是 scope.md 与 Evidence→Finding→Path：先证明你有权打，再要求结论能追溯到证据。这在同类 skill 包里很少见。

3. 它仍然是提示词级治理。43 个模块、42 个 CTF 子技能、几十个 MCP，靠“别预加载、只读 PRIMARY”的自律；没有进程级隔离。

01 · 定位

“Skill 路由包”，不是“红队操作系统”

仓库里有一份很罕见的自我约束文件 skills/ops/IDENTITY.md：明确列出“我们做什么”和“我们故意不做什么”。这决定了它的形态——一堆 Markdown、几个 PowerShell/Bash 脚本、零数据库、零 UI。

“When an AI agent encounters an APK, a binary, frontend JS encryption, a CTF challenge, or a pentesting target, this package routes it to the right methodology, checks available tools, and executes a repeatable workflow instead of guessing commands.”

原文README.md · About

它解决的问题（原文四条，摘译）

  1. AI 不知道该用 jadx、apktool、Frida、IDA 还是 BurpSuite；
  2. APK、ELF、JS、PCAP、CTF 各需要完全不同的打法；
  3. 工具、MCP 服务、脚本散落在不同机器上；
  4. 同样的错误反复出现，因为经验没有被复用。

它刻意不做的事

Z3r0（红队平台）有reverse-skill 的选择
React 作战台、FastAPI 控制面不做。终端 + AI 客户端即可
PostgreSQL 证据库、LightRAG 服务不做。Markdown 文件 + 哈希字段
Docker 主机池 / noVNC 代理不做。最多文档推荐可选沙箱 profile
多 Agent 进程运行时不做。只给“角色 → skill”映射与交接协议

观察这是它能在任何一台装了 Node/Java/Python 的机器上跑起来的原因：部署就是 git clone。

五层结构

层关键文件职责
路由层RULES.md · skills/config/routing.json · master-route.*把任务 hint 映射成一个 PRIMARY 模块；路由表的唯一事实源是 JSON

一个值得注意的设计

它把“越狱（jailbreak）”这类歧义词写进了 exclude 规则：越狱 默认归 iOS 侧，但如果 hint 里同时出现 模型/提示词/LLM/prompt，就排除掉，交给 llm-security。这类小规则是它区别于“关键词表”的地方。

02 · 机制

一次任务要过八道关

RULES.md 把这套流程叫“行为链（behavior chain）”。关键点不是步骤多，而是顺序不可换：先路由、再建案、后动手。

0

激活 + 同意门

“读仓库不等于授权执行”。第一次产生副作用（写文件、下载、起服务、改客户端配置）前，必须披露命令与影响并拿到批准。

1

路由

master-route.ps1 -Hint "..." 或 master-route.sh --hint "..."，从 routing.json 算出 PRIMARY，并写出一份 route-scope.md（含 confidence 与 secondary 列表）。

2

建案 + 授权硬门

case-init 在分析项目里生成 work/<case>/scope.md。只有 auth.status=granted 且 network_profile 合法才允许对目标 ACT；-Force 也绕不过。

3

打开 PRIMARY 的 SKILL.md

先执行文件顶部的 ACTION REQUIRED（读 precedent、核对适用范围、查 tool-index、缺工具走 bootstrap），再进工作流。不允许停在“我已了解”。

4

工具只认索引

tool-index.md 是唯一工具真相源，路径必须是绝对路径；缺工具只能从 manifest 里按能力安装，禁止猜路径、禁止 curl | bash。

5

执行与自检

过程写 timeline.md 与 workitems.md；每 5 次工具调用或卡住时自检；同一方法失败 2–3 次必须换路径（静态↔动态、Java↔Native、IDA↔r2）。

6

结论三段式

Evidence（不可变观察，带 repro_command / hash）→ Finding（结论，带 severity / confidence）→ Path（攻击路径 / 调用链 / 解题步骤）。

7

交付与回收

docs-generator 出报告、diagram-generator 出图、field-journal 脱敏回写、case-review --verify-hashes --strict 审证据图。

为什么要有第 0 步和第 2 步

因为这套包会指挥 AI 执行命令、下载二进制、连 MCP 服务。没有这两道门，一个“帮我看看这个站”就可能变成对生产环境的未授权扫描。作者把这两步写成硬门，而不是“建议”。

真实案例：Flutter APK 去广告

原文field-journal/2026-08-20_apk-flutter-banner-ad-removal.md 记录了一次完整闭环：目标是本地自有 APK（auth_basis：用户自有文件），network_profile 是“纯静态分析 + 本地构建”；先用 apktool / jadx 侦察，确认广告逻辑在 Flutter 的 libapp.so，再用 Blutter 还原类与字符串表，最后等长替换广告键、重打包签名、真机 logcat 验证。

最有价值的是踩坑记录：初版把 API 路径字符串也替换，真机请求 404 导致启动卡死；复盘后明确“只替换 JSON 键/插槽键，保留 API 路径”。这条经验被写进 journal，下一个类似样本可以直接少走两小时。

推断这类“日常小活”才是路由包真正的使用场景，而不是 CTF 或红队大片。它把一次性的手艺变成了可复述、可检索的流程。

03 · 路由核心

44 条规则：先到先得，命中多者胜

路由表全部在 skills/config/routing.json。脚本不硬编码规则，只读取 JSON；MASTER-ROUTING.md 的优先级表由校验脚本比对，防止文档与配置漂移。

算法（读源码确认）

  1. 把 hint 转小写；
  2. 逐条规则逐条 keyword 匹配 must；
  3. 若声明 mustAll，要求全部子正则命中；
  4. 若命中 exclude，本条作废；
  5. 每命中一条 keyword，该规则 +1 分；
  6. 按 priority 数组顺序取分数最高者；并列时靠前的胜出；
  7. 全不中 → 回退 R0（通用逆向）。

置信度

high：只有一条规则命中；medium：多条规则命中，取分最高者；low：回退 R0（空 hint 或没有强关键词）。

这不是语义路由，而是可解释的词典路由：好处是能写回归测试、能手工改；代价是长句、多意图、口语化表达会抢路由。

priority 顺序 ≠ 编号顺序：R4 排第一，R41 排倒数第三。

为什么“命中条目数”而不是“关键词出现次数”

一条规则可以有 1–3 条 keyword 条目（例如 R2 同时收 ipa/objection、越狱、jailbreak+iOS 语境）。因此一句同时提到 “APK 和 Frida” 的话，会优先给只有一条宽规则的 R1，而不是靠多条细分条目加分的其他规则。理解这一点，才能解释它偶尔的“抢路由”。

06 · 契约

真正让它区别于“提示词合集”的，是这四份契约

技能可以抄，流程可以学，但“没有 scope 就不许动手”和“结论必须能追到证据”是这套包最硬的部分。

6.1 scope.md：先证明你有权打

每个 case 在 work/<case>/scope.md 落一份范围契约。字段名保持英文键，方便脚本校验。

字段要点

in_scope / out_of_scope资产、面（web/mobile/binary/network/api）、活动（recon/reverse/exploit_validate/report）分别列清；明确排除 DoS、真实钓鱼、数据外带。

观察role-map.md 定义 9 个角色代号，不启动任何额外进程，只在同一会话里切换“帽子”，输出时加角色前缀便于 timeline 检索。

6.3 Evidence → Finding → Path

三段式把“我说有漏洞”拆成“我观察到了什么、我据此得出什么、这条路径怎么走”。每条 Finding 至少引用 1 条 Evidence；要升级为 validated，建议有 2 条独立证据（最好一静一动），单条证据不得悄悄升级。

对象关键字段
E-nnnobserved_at · source_type（command/screenshot/file/log/memory/network/manual）· repro_command · content_hash · raw_excerpt（脱敏）· linked_workitem
F-nnnseverity · category（vuln/misconfig/design/reverse_algo/bypass）· status（candidate/validated/false_positive/accepted_risk）· evidence_ids · location · confidence
P-nnnpath_type（attack/callflow/solve）· start · goal · 每步 action/evidence/finding · residual_risks

6.4 timeline：只传增量，不复制快照

timeline.md 只追加、不改历史。每次阶段切换写 decision_delta（只列真正改变后续动作的决定）与 carry_forward_refs（引用未变的 scope/evidence）。这解决的是长任务里“上下文越滚越大、AI 反复复述”的问题。

推断这一条比“Evidence 链”更实用：它把“状态”和“变更”分开，读的人先看引用再叠加增量，长会话不容易漂。

供应链防护写进了 manifest

08 · 质量

改路由不是改文档，是改代码

这套包最不像“提示词项目”的地方，是它给路由配了回归测试和一致性校验，并且在 Windows + Ubuntu 双平台跑 CI。

发现一处文档数字漂移

观察README 的 Current status 写 175 个回归用例；Key files 写 173；而 skills/tests/routing-benchmark.json 实际是 178 条（其中 44 条标记 quick）。三个数字互不一致。

这说明文档里的统计还没有纳入自动校验（仓库虽有 verify-doc-facts.ps1）。不影响路由本身，但提醒读者：以 JSON 与脚本为准，别以 README 的统计为准。

路由覆盖长什么样

178 条用例里，命中最多的是 R11 渗透工具（14 条）、R0 通用逆向（11 条）、R1 APK（8 条）、R3 前端 JS（7 条）。这基本对应真实使用频率：渗透、逆向、APK、JS 是四大入口。

为什么这很重要

关键词路由最大的风险是“改一条规则，误伤十条用例”。有了 benchmark，路由变更就从“感觉更准了”变成“跑完 178 条再说”。这是它从 prompt 工程走向工程化的分水岭。

09 · 边界

安全设计：把“别乱来”写成可检查的条款

这是一个双用途工具。它的安全策略不是“我们保证安全”，而是“把该问的问题提前问完，把该留的证据留下”。

四道门

  1. 激活门：只读仓库不等于授权执行；首次副作用需批准。
  2. 范围门：scope.md 的 auth + network_profile 不满足，禁止 ACT。
  3. 工具门：只从 tool-index 取路径，只从 manifest 装能力，固定版本与哈希。
  4. 证据门：Finding 必须引用 Evidence；validated 建议双证据；报告前跑 case-review。

供应链视角（AST10 思路）

仓库专门写了 ops/skill-supply-chain.md，把恶意 skill、权限过度、依赖投毒、MCP 盲信、提示注入、范围漂移、技能堆叠过载逐条对应到控制措施。

其中一条很现实：不 bulk-vendor 社区 skill 库，只维护索引与借鉴规则，避免“投毒面 + 维护成本”。

11 · 评价

值不值得用：看你是不是它的目标用户

我的判断分三块：它做对了什么、它付出了什么代价、什么人应该绕开。

做对的五件事

  • 单一事实源：路由只在 JSON 里改，文档与脚本都被校验，避免“三份路由表互相打架”。
  • 可回归：178 条用例 + 双平台 CI，让“路由更准”可被证明。
  • 先授权后动手：scope 是硬门而不是建议，-Force 也绕不过。
  • 证据化交付：Evidence/Finding/Path + 哈希 + 可复现命令，报告能被别人复核。
  • 经验会沉淀：field-journal 脱敏回写 + INDEX 自动生成，越用越厚。

付出的五个代价

  • 关键词路由的天花板：多意图长句会抢路由；靠 exclude 打补丁，规则会越来越绕。
  • 上下文负担：43 个模块 + 42 个 CTF 子技能 + 大量 ops 文档，必须严格“只读 PRIMARY”，否则注意力被稀释。
  • 流程摩擦：scope、consent、timeline、evidence、case-review，一次小活也要建案。
  • Windows 优先：PowerShell 是主路径，manifest 路径仍是 Windows 形式，跨平台体验不对称。
  • 软约束：所有安全门都是提示词级，挡不住不听话的模型或绕过 AI 的人。

适合 / 不适合

适合不适合
安全研究员、CTF 选手、需要做授权测试的研发；已经把 Claude Code / Codex / Cursor 当主力工具的人；想给团队沉淀“打法 + 证据规范”的负责人。 想要“点一下自动逆向”的人；需要技术隔离的生产环境；没有授权、想拿它打别人系统的人；只做纯源码架构分析的人（REA 类工具或普通仓库分析更合适）。

如果是我，会怎么用

  1. 只挂 PRIMARY：把“不要预加载”当硬规矩，先跑 master-route 再开文件。
  2. 把 scope 当团队资产：每次任务的授权依据、网络档、排除项都留在 work/ 里，报告直接引用。
  3. 改路由前先跑 quick 集：44 条 quick 用例能在几十秒内告诉你有没有误伤。
  4. 把 field-journal 当知识库：只写“下次能复用的一条”，别写流水账；脱敏是底线。
  5. 不神化它：它提高的是“起手正确率”和“交付可复核性”，不是漏洞发现率。
一个容易被忽略的风险

这类包会引导 AI 执行命令、下载二进制、连接本地 MCP。真正的攻击面往往不在目标，而在你给 AI 的这台机器：manifest 之外的安装、来源不明的 MCP、仓库里的 .env 与客户端配置。用之前先确认出站与凭据边界，比读多少 SKILL.md 都重要。
