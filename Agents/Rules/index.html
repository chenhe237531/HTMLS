规则如何
被 Agent 使用

规则不是“更长的提示词”。它是一套文件约定：放在哪、什么时候进上下文、和别的规则冲突时谁赢、哪些事根本不该交给规则。这份指南按“加载机制 → 工具差异 → 写法 → 生命周期”讲清楚。

01先纠正一个误解

规则是“上下文”，不是“配置”，更不是“权限”。

大多数工具把规则文件的内容在会话开始时拼进模型上下文，或者在某类文件被打开时追加进去。模型“看到”它，然后决定是否遵守。它没有执行器，也没有强制力。

因此有三件事不能只靠规则
  • 安全边界：禁止访问某个目录、禁止 push main → 用 permissions / hooks。
  • 确定性动作：每次提交前必须跑测试 → 用 hook 或 CI，不要指望模型记得。
  • 格式规范：缩进、引号、import 顺序 → 用 formatter / linter，规则里只写“跑哪个命令”。

规则真正擅长的是：项目事实（构建命令、目录结构、约定）、偏好（语言、风格、沟通方式）、决策背景（为什么不用某个库）。这些内容模型无法从代码里可靠推断，又每次都需要。

02五种加载机制

不同工具的叫法不同，底层其实就这五种。看懂它们，换工具只需要换文件名。

MECHANISM 1

启动时全量注入

会话开始就把根目录的规则文件塞进上下文。最简单，也最贵：每一轮都在付 token。

AGENTS.md · CLAUDE.md
MECHANISM 2

按目录就近发现

从当前目录向上找，或读子目录里的规则；越靠近工作目录的越晚读、越具体。适合 monorepo。

AGENTS.md 层级 · CLAUDE.md 子目录按需加载
MECHANISM 3

按文件路径匹配

规则声明 glob（如 src/api/**/*.ts），只有打开匹配文件时才加载。省上下文，也减少无关干扰。

.cursor/rules/*.mdc · .claude/rules + paths · Copilot applyTo
MECHANISM 4

按需 / 手动调用

规则平时不进上下文，用户 @ 一下或模型判断相关才读。适合长流程、低频场景。

Cursor 的 @rule · skills · 引用文件让 agent 自己 Read
MECHANISM 5

事件钩子（不是规则）

在工具调用前后跑脚本，能真正阻断动作。规则做不到的事，放这里。

Claude Code hooks · Cursor hook adapter · OpenCode plugins

一次请求里，规则是怎么进去的

读法：上半条是“文本进上下文”，下半条是“脚本拦截动作”。两者都叫“规则”时，最容易混淆；写之前先决定你要的是哪一种。

03八个工具，规则放哪

以各工具 2026-11 的官方文档为准。共同趋势很清楚：AGENTS.md 正在成为跨工具的公共入口。

工具主文件 / 目录作用域路径级关键机制
OpenCode AGENTS.md；兼容 CLAUDE.md 项目、全局（~/.config/opencode/AGENTS.md）、instructions 配置 通过 opencode.json 的 instructions 支持 glob 与远程 URL 就近查找，每类第一个命中；AGENTS.md 优先于 CLAUDE.md；所有 instructions 合并
Claude Code CLAUDE.md；.claude/rules/*.md managed / user / project / local 规则 frontmatter 的 paths glob 启动加载 + 子目录按需；@path 导入最多 4 层；hook 才能强制
Cursor .cursor/rules/*.mdc；AGENTS.md Team / Project / User globs 字段 四种应用方式：alwaysApply、描述匹配、文件匹配、手动 @；Team → Project → User
GitHub Copilot .github/copilot-instructions.md；.github/instructions/*.instructions.md；AGENTS.md 个人 / 仓库 / 组织；最近 AGENTS.md 优先 applyTo glob；可用 excludeAgent 仓库规则 + 路径规则同时生效；cloud agent 与 code review 都读
Codex AGENTS.md 仓库根 + 子目录 靠目录层级 就近的 AGENTS.md 优先，适合 monorepo 分区
Gemini CLI GEMINI.md 项目 / 全局 目录层级 与 AGENTS.md 同一类机制；Copilot 也接受根目录单个 GEMINI.md
Cline .clinerules（文件或目录） 项目 目录组织 规则直接进上下文；自定义指令另有一套设置
Windsurf .windsurf/rules/（旧版 .windsurfrules） 项目 / 全局 规则激活模式 按 always / manual / model / glob 等模式激活；细节随版本变化
跨工具最小方案

把项目事实写在根目录 AGENTS.md；需要路径级时，再为 Cursor 加 .cursor/rules/*.mdc、为 Copilot 加 .github/instructions/*.instructions.md。Claude Code 没有 CLAUDE.md 时会直接读 AGENTS.md；有 CLAUDE.md 时用一行 @AGENTS.md 导入即可共享。

04冲突时谁赢

这是最容易踩坑的部分：大多数工具不是“覆盖”，而是“全部塞进去，冲突时模型自己挑”。

工具顺序冲突行为
OpenCode本地 AGENTS.md / CLAUDE.md → 全局 AGENTS.md → ~/.claude/CLAUDE.md每类第一个命中；不同类合并；instructions 全部追加
Claude Codemanaged → user → project → local；目录由根到当前全部拼接，不覆盖；冲突时可能任选，建议人工清理
CursorTeam → Project → User合并，前面的来源优先；Team 可强制
Copilot个人 → 仓库 → 组织全部提供；个人优先级最高；官方建议避免冲突
AGENTS.md 生态最近的目录优先父级 + 子级合并；越具体越晚读
一条实用规则

同一个行为，只在一个地方定义。要么在根规则，要么在路径规则，不要两处都写；否则模型收到两条略有差异的指令，行为会变得不稳定。

05怎么写一条 Agent 能执行的规则

核心标准只有一个：可验证。模型能判断“做没做到”，规则才会生效。

不要写写成为什么
“注意代码质量”“提交前运行 npm test，失败不得提交”有命令、有判定
“保持文件整洁”“单文件不超过 400 行；超过就拆分”有阈值
“用合适的错误处理”“API 边界返回 {code, message}，禁止抛裸字符串”有结构
“遵循项目架构”“业务逻辑在 src/services/；路由只做参数校验”有位置
“不要动生成文件”“禁止编辑 dist/、build/；它们由 pnpm build 生成”有边界与替代方案

一条规则的六段结构

# 适用范围（越具体越好）
适用：src/api/**/*.ts
不适用：migrations/**

# 必须
- 所有 handler 在入口处校验输入
- 错误返回 { code, message }，不抛裸字符串

# 禁止
- 不在此目录直接访问数据库；走 service 层
- 不修改 dist/ 下的任何文件

# 验证
- `pnpm test src/api` 必须通过
- `pnpm lint` 无新增 warning

# 参考
- 模板：@src/api/handlers/_template.ts
- 规范：docs/api-errors.md

# 维护
- Owner: @backend-team · 最近复核: 2026-10

“参考”部分很关键：不要复制模板内容，给路径，让 agent 自己读。文档会变，复制会过期。

长度与颗粒度

  • 根规则控制在 200 行内（Claude 官方建议）；Cursor 建议单条规则 500 行内。
  • 一个文件一个主题：测试、API、前端、发布，不要混在一起。
  • 能按路径触发就别常驻：只在改 src/api 时才需要的规则，不要每轮都带。
  • 多步流程写成 skill，不要塞进规则；规则是“事实与约束”，skill 是“步骤”。

06三套可直接抄的模板

同一个项目，三种工具的写法。内容一致，机制不同。

# 项目规则

## 构建与验证
- 安装：`pnpm install`
- 开发：`pnpm dev`（端口 3000）
- 测试：`pnpm test`；提交前必须通过
- 类型检查：`pnpm typecheck`

## 目录
- `src/api/` 路由与校验
- `src/services/` 业务逻辑
- `src/db/` schema 与迁移
- `dist/` 生成物，禁止手改

## 约定
- TypeScript strict；禁止 `any`
- 错误统一 `{ code, message }`
- 新增 API 必须带一条集成测试

## 不要做
- 不直接改 `main` 分支
- 不引入新的状态管理库，先讨论
- 不提交 `.env`、密钥、真实用户数据

适合 OpenCode、Codex、Cursor（根目录）、Copilot（AGENTS.md）等。

---
description: API 路由的输入校验与错误格式
globs: src/api/**/*.ts
alwaysApply: false
---

- 每个 handler 在入口校验输入
- 错误返回 `{ code, message }`，禁止抛裸字符串
- 业务逻辑放 `src/services/`，路由只做校验与转发
- 新增或修改接口时，补一条集成测试
- 参考模板：@src/api/handlers/_template.ts

alwaysApply: false + globs：只有打开匹配文件时才自动附加。@ 引用不会内联内容，agent 需要时自己读。

---
applyTo: "src/api/**/*.ts"
---

# API 规则
- 所有 handler 入口校验输入
- 错误统一 `{ code, message }`
- 不在路由层直接访问数据库
- 新接口必须附带集成测试
- 模板见 `src/api/handlers/_template.ts`

仓库级规则放 .github/copilot-instructions.md；路径级规则放 .github/instructions/NAME.instructions.md。

07规则的生命周期

规则不是写完就完了。它和代码一样会腐坏，而且腐坏得更隐蔽。

阶段动作判定标准
提出同一个错误出现第二次，或新人需要同样的解释有具体案例，不是“感觉应该写”
落位判断放根规则、路径规则、skill 还是 hook能按路径触发的不常驻；要强制的不用规则
评审检查是否可验证、是否与现有规则冲突有命令/阈值/结构；无重复定义
度量观察同类错误是否下降；是否增加上下文负担错误率下降，且没有明显拖慢/干扰
退役重构后失效、工具已强制、规则已被代码表达删除或降级为 skill/文档
每季度做一次规则审计

Claude Code 提供 /doctor prompt-audit 检查过期引用与冲突；其他工具没有内置审计时，就人工过一遍：删掉已由 linter/hook 覆盖的条目，合并重复项，把长流程移到 skill。

08七个常见错误

  • 把整个风格指南贴进去：改用 formatter/linter，规则只写“运行哪个命令”。
  • 复制模板代码：引用路径，让 agent 自己读；否则模板一改规则就过期。
  • 根规则过长：超过 200–500 行后，遵循率下降，token 成本上升。
  • 同一行为写两遍：父级与子级、根规则与路径规则各写一条，冲突时行为随机。
  • 把安全边界写成规则：模型可能忽略；用 permissions、hooks、CI 强制。
  • 规则里放密钥或内部 URL：规则会进上下文、进日志、进截图。
  • 只写“要做什么”，不写“怎么算做到”：没有验证标准的规则等于建议。
