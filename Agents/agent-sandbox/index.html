Agent 沙箱：隔离、防护与调度

当 Agent 开始自己写代码、开浏览器、调工具，「一个 Agent 一个容器」就不再是可运营的模型。这份文档拆开 agent-sandbox 这一类编排层：它到底隔离了什么、默认挡住了哪些攻击、资源从哪里省出来，以及哪些数字是真 benchmark、哪些只是营销。

01

先厘清边界：编排层不等于隔离层

这是最容易搞错的一点，也是所有安全评审的第一道题。

agent-sandbox 自己在 README 里写得很直白：它是一个 sandbox orchestrator，把底层隔离委托给 gVisor、Kata Containers 这类 Sandbox Runtime，通过 RuntimeClass 挂到 Pod 上。换句话说：

编排层负责

  • 单例、有状态、稳定身份的生命周期
  • 从预热池领取（claim）与回收
  • Pod / Service / PVC 的创建与收养
  • 暂停、恢复、快照、定时销毁
  • 为租户生成默认拒绝的 NetworkPolicy

运行时负责

  • 系统调用拦截或硬件虚拟化边界
  • 内核攻击面收敛（gVisor 用户态内核 / Kata 独立内核）
  • 文件系统与网络的重定向（Gofer、virtio-fs、netstack）
  • 单沙箱内的资源与设备可见性
结论：只装 agent-sandbox、不配 runtimeClassName，你得到的是一个「生命周期更好管的普通 Pod」，不是安全沙箱。默认值能挡一部分网络与身份问题，但挡不住容器逃逸。

02

隔离技术全景：四种边界，四种代价

隔离强度、启动速度、系统调用兼容性构成一个不可能三角。选型不是选「最安全」，而是选「你的威胁模型能接受哪一种代价」。

2.1 基线：共享内核的容器

普通容器靠 Linux 原语把进程「关起来」，但内核是同一个：

  • namespace：PID、网络、挂载、IPC、UTS、user、cgroup、time。决定「看得见什么」。
  • cgroup v2：CPU、内存、IO、PID 限额。决定「能用多少」。
  • capabilities：把 root 拆成细粒度权限；默认应全部 drop，只留必要项。
  • seccomp-bpf：系统调用白名单/黑名单；RuntimeDefault 是 K8s 的合理下限。
  • LSM：AppArmor / SELinux 做路径与标签级约束。
  • user namespace：容器内 root 映射为非 root，降低部分逃逸收益。

问题在于：内核攻击面完全共享。一个内核提权漏洞、一个错误的 hostPath、一个多余的 CAP_SYS_ADMIN、一个 privileged: true，边界就没了。对「LLM 生成的、会执行任意命令的代码」，这层通常不够。

什么时候够用：代码可信、只是需要资源隔离与生命周期管理；或者沙箱里没有凭据、没有内网访问、节点本身是一次性的。

2.2 gVisor：把系统调用关进用户态内核

gVisor 的 runsc 不让应用直接碰宿主内核，而是把系统调用交给用 Go 实现的 Sentry。Sentry 自己实现了一套 Linux 系统调用语义，文件访问通过 Gofer 进程代理，网络走用户态 netstack。

拦截平台

  • systrap：较新版本的主力路径，用 seccomp 陷入 + 共享内存加速，兼顾性能与可移植性。
  • ptrace：兼容性最好，系统调用密集时开销明显。
  • KVM：把 Sentry 跑在 VM 里，减少陷入成本，但需要 /dev/kvm。

实际取舍

  • 优点：不需要嵌套虚拟化；密度高；单沙箱内存开销小；启动通常在百毫秒级；内核攻击面显著收敛。
  • 代价：不是 100% 系统调用兼容；ioctl、部分设备、GPU、eBPF、嵌套容器等能力受限；IO 与系统调用密集负载有可测开销。
  • 适合：代码解释器、浏览器自动化、不可信脚本、多租户 SaaS。

事实 agent-sandbox 的 gVisor 示例与快照能力都以 RuntimeClass: gvisor 为前提；快照依赖 GKE 的 podsnapshot.gke.io。推断 对 GPU 推理类 Agent，gVisor 往往不是首选，需先验证设备与驱动路径。

2.3 Kata Containers：每个 Pod 一个轻量 VM

Kata 用硬件虚拟化把边界拉到 hypervisor：每个 Pod 有独立 guest 内核，容器进程跑在 VM 里。上层仍是 OCI 镜像与 K8s Pod，下面由 kata-runtime（shim v2）负责启动 VMM。

  • VMM 可选：QEMU、Cloud Hypervisor、Dragonball、Firecracker。不同 VMM 在启动时间、设备模型、GPU 支持上差异很大。
  • 文件与网络：virtio-fs / virtio-9p 共享目录，vsock 做宿主通信，CNI 仍负责 Pod 网络。
  • 优势：兼容完整 Linux 用户态；支持设备直通与 GPU；可叠加机密容器（如 AMD SEV-SNP、Intel TDX）。
  • 代价：需要 VT-x / AMD-V 或云上嵌套虚拟化；每个 Pod 有 guest 内核与 VMM 的内存开销；启动通常比 runc 慢一个量级。

agent-sandbox 在 AKS、GKE 都有 Kata 示例；托管集群要确认节点池支持嵌套虚拟化或裸金属实例。

2.4 Firecracker 与 microVM：更小的设备面

Firecracker 是 Rust 写的极简 VMM，只保留 virtio-net、virtio-block、串口等必要设备，配合 jailer 与 seccomp 收敛攻击面。AWS 对外宣称可在约 125ms 内启动、VMM 内存开销约 5MiB——这也是它适合「每请求一个沙箱」的原因。

在 K8s 里它有两条路：一是作为 Kata 的 VMM 后端；二是像 E2B 那样自建控制面（Firecracker + 调度器 + 网络/存储编排）。后者能力强，但运维成本远高于 helm install。

2.5 更轻的边界：Hyperlight、urunc、WASM

2.7 选型规则

默认从 gVisor 开始：不需要嵌套虚拟化、密度高、对「执行 LLM 代码」这个主场景足够。

需要完整内核能力、GPU、机密计算时换 Kata：代价是节点池必须支持虚拟化，单 Pod 开销更高。

需要每请求一个隔离单元、且能自建控制面时考虑 Firecracker：不要把「能用 Firecracker」误当成「应该自己运维 Firecracker」。

只跑工具/插件时用 WASM 或 Hyperlight：别为了跑一个 20 行的转换函数起一个 VM。

03

威胁模型与防护：默认值能挡什么，挡不住什么

agent-sandbox 的威胁模型把「控制面」视为可信、「Sandbox Pod」视为不可信。所有防护都围绕这条线展开。

3.1 五条信任边界

  1. 用户 → K8s API：必须经过认证与 RBAC，不能靠「不知道名字」当安全。
  2. 控制面 → 工作负载：Controller 与 Router 可信，Pod 不可信。
  3. 租户 ↔ 租户：不同 Sandbox 之间默认不应互通。
  4. 工作负载 → 宿主：不可信代码不能打到节点内核。
  5. 工作负载 → 控制面：默认不允许访问 API Server。

3.2 六类威胁与控制

筛选
  • 容器逃逸逃逸

    恶意代码利用内核漏洞、错误挂载或过高权限打到宿主，进而影响同节点其他租户。

    控制：用 gVisor / Kata 的 RuntimeClass；禁止 privileged、hostPath、hostNetwork、hostPID；drop 全部 capabilities；seccompProfile: RuntimeDefault；只读根文件系统。

  • 工作负载篡改模板元数据逃逸

    租户在 podTemplate.metadata 里伪造 agents.x-k8s.io/* 系统标签，把别人的 Service 流量劫持到自己的 Pod。

    控制：控制器把系统前缀键视为保留字，创建与收养路径都会过滤；Service 选择器标签在合并用户标签之后由控制器写入，无法覆盖。不要自己再绕过控制器直接改 Pod 标签。

  • 跨租户网络攻击网络

    被攻陷的沙箱扫描并攻击同集群其他沙箱、内部服务或云元数据端点。

    控制：使用 SandboxTemplate.networkPolicy 生成托管策略：入站仅允许 Router，出站默认拒绝，只放行公网，阻断 RFC1918 与 169.254.169.254；需要 DNS 时显式放行 53 端口。

  • Router SSRF 与代理滥用网络

    攻击者伪造 X-Sandbox-Pod-IP 让 Router 代理到元数据服务或任意内网地址；或绕过 Router 直连 Pod。

    控制：Router 校验 IP 字面量并拒绝本地/受限网段；但默认 authorizer 是 AllowAll（为了 Python 客户端兼容），生产必须配置自定义 authorizer。用 NetworkPolicy 保证只有 Router 能进 Pod。

  • 滥用 ServiceAccount Token 访问 API身份

    Pod 自动挂载的 token 让沙箱内的代码直接读写集群资源。

    控制：模板路径下 automountServiceAccountToken 默认 false；裸 Sandbox 需用准入策略强制。确实需要时，用最小权限的专用 ServiceAccount + TokenRequest 短时令牌。

  • 凭据进入模型上下文身份

    把云密钥、数据库密码写进环境变量，Agent 在推理或工具调用中把它们带出去。

    控制：沙箱内只放占位符，真实凭据由出网代理注入；按工具拆分凭据；使用工作负载身份而非长期密钥；对出站请求做域名白名单与审计。

  • 资源耗尽资源

    沙箱跑满 CPU/内存/磁盘/PID，拖垮节点上的其他租户；或大量创建沙箱刷爆 API Server。

    控制：requests = limits（不可信负载不要 Burstable）；LimitRange 设默认与上限；ResourceQuota 限制命名空间总量；emptyDir.sizeLimit；PID 上限；对 claim 速率做准入或队列。

  • 未授权创建 / 越权领取控制面

    任意用户创建 Sandbox 消耗容量，或领取不属于自己的预热沙箱。

    控制：RBAC 限定 sandbox、sandboxclaim、sandboxtemplate 的 verbs；按命名空间隔离租户；对 claim 的 label 域做 allowlist（默认 sandbox.users.io）。

  • 控制面被刷爆控制面

    大批量创建导致 watch 饥饿、etcd 膨胀、API Server 排队，正常领取被拖慢。

    控制：APF 隔离（FlowSchema + PriorityLevel）；补充限速；多池分片；独立 watch 连接；关闭非必要 Event；缓存按标签收敛。

  • 镜像与依赖投毒供应链

    使用可变标签、未签名镜像，或镜像内预置后门。

    控制：按 digest 固定；cosign / Sigstore 验签；生成并核对 SBOM；私有仓库 + 准入校验；禁止 :latest；基础镜像最小化。

  • 工具与 MCP 服务器越权供应链

    Agent 通过 MCP 工具拿到超出预期的文件系统或网络权限。

    控制：每个 MCP 服务器独立容器/独立文件系统；工具级 allowlist 与审批；出网策略按工具身份而不是按 Pod 统一放行。

该分类下暂无条目。

3.3 三个最容易被忽略的坑

坑一：只配了 gVisor，没配网络策略

隔离解决的是「打到宿主」，不解决「横向移动」。没有 NetworkPolicy 时，沙箱之间、沙箱到内网、沙箱到云元数据端点都是通的。托管策略是默认拒绝，但它会连 sidecar 端口一起挡掉，健康检查会挂——需要显式放行。

坑二：把 Router 当成认证层

Router 只按 X-Sandbox-ID 拼目标地址，默认 authorizer 为 AllowAll。它能防「拼错地址」，不能防「知道别人 ID 的人」。认证与授权要在前面做：TokenReview、mTLS、网关鉴权，并校验 Claim UID 仍然存活。

坑三：用 ConfigMap/Secret 挂载当凭据隔离

挂进容器的 Secret 对容器内所有进程可读，Agent 执行 cat 就能拿到。真正的隔离是「凭据不进入沙箱」：由代理在出站时附加，沙箱只看到占位符。这需要在网络层做，而不是在文件权限上做。

3.5 身份与凭据

三层身份

  • 调用者身份：谁在创建/领取沙箱（RBAC + OIDC）。
  • 沙箱身份：Pod 的 ServiceAccount 或 x509 证书/mTLS，用于服务间认证。
  • 出网身份：出口代理代表沙箱去取云资源，凭据只在代理侧。

推荐做法

  • 默认不挂载 SA token；需要时用 TokenRequest 申请分钟级令牌。
  • 按工具拆 ServiceAccount，一个工具一个最小权限集。
  • 出网请求带可审计的沙箱 ID，便于追责。
  • 定期轮换，禁止把长期密钥写进镜像或环境变量。

3.6 准入与供应链

  • Pod Security Standards：命名空间至少 baseline，理想是 restricted。
  • ValidatingAdmissionPolicy：强制 runtimeClassName、禁止特权、强制资源上限。项目仓库提供了示例。
  • Gatekeeper / Kyverno：跨命名空间的统一策略，适合已有 OPA 体系的团队。
  • 镜像：digest 固定 + 验签 + SBOM；镜像拉取用私有仓库与 imagePullSecret 的最小权限账号。
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: sandbox-baseline
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["agents.x-k8s.io"]
        apiVersions: ["v1beta1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["sandboxes"]
  validations:
    - expression: >-
        object.spec.podTemplate.spec.runtimeClassName == 'gvisor'
      message: "Sandbox 必须使用 gvisor RuntimeClass"
    - expression: >-
        !has(object.spec.podTemplate.spec.containers.exists(c,
          has(c.securityContext) && has(c.securityContext.privileged) && c.securityContext.privileged))
      message: "禁止 privileged 容器"

CEL 写法随 K8s 版本略有差异，上线前用 kubectl apply --dry-run=server 验证。

3.7 运行时检测

  • OpenTelemetry：Controller 与 SDK 都能出 trace；把 trace context 透传到沙箱，才能把「一次 Agent 行为」与「一次内核拒绝」串起来。
  • eBPF：Tetragon / Falco 观察进程、网络、文件行为；比日志更早发现异常执行。
  • 审计：K8s audit log 记录谁创建了哪个 Sandbox；出口代理记录每次外联。

L1 单团队代码基本可信runc + PSS restricted + 资源限额 + 默认拒绝网络
L2 多团队互相不可信，但同一组织gVisor + 每租户命名空间 + 托管 NetworkPolicy + 准入策略
L3 对外多租户完全不可信，可能恶意Kata / microVM + 节点池隔离 + 出网代理 + 凭据不落地 + 审计与检测
一句话：L1 靠配置，L2 靠运行时，L3 靠「假设已经失陷」的纵深防御。级别越高，越不能只依赖 K8s 的默认行为。
04

资源调度：真正卡住你的往往不是 CPU

Agent 沙箱的调度有两个平面：Kubernetes 调度 Pod，Controller 调度「领取」。后者先成为瓶颈。

4.1 一次领取完整经过什么

  1. 创建 Claim：客户端提交 SandboxClaim，指定 warm pool 与命名空间。
  2. 选择候选：控制器在池中找 Ready 的 Sandbox；新 Sandbox 需要等 Pod IP 上报，默认最多等 2 秒（--sandbox-claim-warm-candidate-grace-period）。
  3. 收养或冷建：能收养就直接改归属；否则按 Template 冷建。注意：Claim 一旦设置 spec.env 或 spec.volumeClaimTemplates，永远走冷建，因为运行中的 Pod 无法安全注入这些配置。
  4. 创建资源：核心控制器建 Pod、headless Service、可选 PVC；写入 Sandbox 状态。
  5. K8s 调度：kube-scheduler 绑定节点；RuntimeClass 的 overhead 会参与资源计算。
  6. 运行时就绪：CNI 分配 IP、镜像拉取、runsc/kata 启动、就绪探针通过；Claim 变为 Ready，Router/SDK 才能连。
性能分水岭：热采用是「改一个对象的归属」；冷启动是「创建 Pod + 调度 + 拉镜像 + 起运行时」。官方实测冷启动 p50 约 42–50 秒，热采用 p50 约 92 毫秒——差两个数量级。

4.2 容量有三种状态

Warm（热）

已存在、已调度、已就绪，等一个 Claim。它占资源但不干活，是「用钱买延迟」。

Cold（冷）

按需创建。省资源，但首请求承担 40 秒级延迟；突发流量下会同时压 API Server、调度器、镜像仓库和 CNI。

Paused / Snapshotted（挂起）

状态落盘，计算资源释放。恢复要重新调度并回放状态，适合「多轮对话之间长时间空闲」。

三种状态不是互斥选项，而是同一条流水线上的三段。成熟部署通常同时存在：小热池兜底延迟、冷建承接长尾、快照回收空闲会话。

4.3 与 Kubernetes 调度器的交互

  • RuntimeClass overhead：gVisor/Kata 的额外内存与 CPU 应计入 overhead，否则节点会被超卖到 OOM。
  • 专用节点池：用 taint/toleration 把沙箱固定到装了 runsc 或支持嵌套虚拟化的节点；不要让普通业务 Pod 混部。
  • 拓扑：topologySpreadConstraints 打散故障域；但热池副本本身要保留局部性，避免全部跨 AZ。
  • 中断预算：长会话沙箱配 PodDisruptionBudget，节点轮转时不要一次清空。
  • 调度门：需要「先建对象、后决定调度」时用 scheduling gates，避免 Pod 在镜像/网络未就绪时被反复驱逐。
默认参数会咬人：kube-scheduler 的 --kube-api-qps 默认是 50。单池持续补充上限 70–85/s 就是被它和每池串行 reconcile 共同卡住的。要更高吞吐，必须同时调调度器与控制器，而不是只加 worker。

05

资源利用：从「一 Agent 一 Pod」到「一池多用」

Agent 的负载曲线和 Web 服务相反：长时间空闲、短时爆发、状态必须保留。按 Web 的方式做容量规划，钱一定花在闲置上。

5.1 三种利用率模型

模型资源占用启动延迟状态保留适用
Pod per Agent最高，空闲也占满已运行时为 0内存 + 磁盘少量长期在线 Agent
Warm Pool + Claim中，池容量是常数成本热采用亚秒级收养后保留交互式、突发领取
Actor 多路复用 + 快照最低，多个 Agent 共享少量 worker从快照恢复，非冷启动快照到对象存储海量低频 Agent

第三行参考 kagent 的 Agent Substrate：WorkerPool + Actor，空闲 Actor 快照到对象存储、按需回填，用少量预热 worker 承载远多于 Pod 数的 Agent。事实 它解决的是「空闲也占 Pod」的浪费，不是隔离强度问题——每个 Actor 仍在 gVisor 沙箱里。

5.2 用 Little's law 算池子

最容易被忽略的公式，却能挡住大部分拍脑袋容量规划：

N = λ × W　　（并发数 = 到达率 × 平均停留时间）

热池还要覆盖「补充延迟」：在冷启动的 T 秒里，新请求仍在到达。

N_warm ≈ ceil( λ_peak × (W + T_cold) × safety )
Pods ≈ N_warm　（agent-sandbox 是单例 Pod）
Nodes = max( ceil(Pods × cpu_req / cpu_alloc), ceil(Pods × mem_req / mem_alloc) )

λ 用峰值而不是均值；W 包含模型思考、工具调用、人工审批的全部挂起时间。若 Agent 会在等审批时挂几小时，W 会被严重低估——这类会话应改用暂停/快照，而不是一直占着热池。

5.3 暂停、恢复与快照

两条路径

  • PVC 挂起/恢复：operatingMode 切到 Suspended，保留 PVC，缩到 0；恢复时重新挂载。只保文件系统。
  • Pod Snapshot：GKE 的 podsnapshot.gke.io，冻结 gVisor 容器状态，保留内存与文件系统；恢复后进程接着跑。

两种用法

  • 按会话快照：同一个 Sandbox 在两次用户提问之间挂起，省掉空闲成本。
  • 黄金快照：预热一个装好依赖的沙箱，把快照共享给整个 WarmPool，新沙箱直接从「已初始化」状态启动。
限制要提前知道：快照能力目前是 Python SDK 提供、依赖 GKE Pod Snapshot；Go SDK 尚未封装。默认按 sandbox-name-hash 分组，一个沙箱只恢复自己的快照；要跨沙箱共享，需要用按模板标签分组的 PodSnapshotPolicy。

5.4 超卖：省钱的边界在哪

06

可观测性与运维：把「沙箱」当生产系统

沙箱的故障很少是「挂了」，更多是「慢」和「悄悄不隔离了」。指标要覆盖生命周期、控制面与安全三类。

6.1 先看状态条件

Sandbox 通过 conditions 暴露生命周期。排障顺序应该是「先看 Ready，再看 reason」，而不是先翻 Pod 日志。

信号含义下一步
Ready=TruePod 就绪，可接收流量正常
Ready=False / MultiplePods控制器发现同一 Sandbox 有多个受控 Pod，安全失败关闭检查是否有外部工具手工建了 Pod；清理后再等 reconcile
Ready=False / InvalidMetadataClaim 的附加标签域不在 allowlist改标签域，或调整 allowed-label-domains
长时间 Pending调度不上去：资源、RuntimeClass、亲和性看 scheduler event 与节点池容量
反复重启OOM、探针失败、入口命令退出先看 limits 与探针，再看运行时日志

6.2 三层指标

生命周期

  • claim → ready 的 p50/p90/p99
  • 热采用 vs 冷建的比例
  • 热池缺口（deficit）与补充速率
  • 挂起/恢复耗时与失败率

控制面

  • reconcile 次数、耗时、错误率
  • workqueue 深度与重试
  • 409 Conflict 速率
  • rest_client_*：API 延迟、重试、限流等待

安全

  • 被拒绝的出站连接与目标域名
  • 提权/异常 exec/eBPF 告警
  • 镜像验签失败与准入拒绝
  • SA token 使用与异常 API 调用

资源

  • 每沙箱 CPU/内存实际使用 vs 请求
  • 节点可分配余量与装箱碎片
  • OOMKilled、驱逐、PDB 阻塞
  • PVC 容量与快照存储增长

控制器指标的具体名称以 /metrics 与项目的 Controller Metrics Reference 为准；指标会随版本增加，别把面板写死在未公开的名字上。

6.3 建议的 SLO

SLO目标（示例）说明
热采用延迟p90 < 500ms超过就说明池子不够或有控制面争用

症状先查动作

这是官方在「持续 30–100 claims/s」场景验证的档位。突发型负载才考虑 --sandbox-write-behind-window=250ms；它会显著抬高持续场景的 p50。--sandbox-warm-pool-replenish-delay 在有过一次创建失败时会导致池子排空，非必要不开。

7.5 上线检查

  1. 随机抽一个沙箱，确认 runtimeClassName 真的是 gVisor/Kata，而不是被模板覆盖。
  2. 从沙箱内访问 169.254.169.254、同命名空间其他 Pod、API Server，三者都应失败。
  3. 确认 /var/run/secrets/kubernetes.io/serviceaccount 不存在。
  4. 在沙箱内尝试 mount、unshare、加载内核模块，应被 seccomp/capabilities 拒绝。
  5. 压测领取：观察 p90、409、池子缺口，确认补充速率 ≥ 到达率。
  6. 杀掉一个节点，确认 PDB 与重调度不会一次清空会话。
08

选型与结论

8.1 和相邻项目怎么分工

项目层次强项你要自己补的
agent-sandbox沙箱编排最小、标准、框架中立；WarmPool/Claim/快照运行时、Agent 逻辑、网关、策略
kagentAgent 控制面Agent/Model/Tool 都是 CRD；MCP/A2A；Agent Substrate 多路复用更细的租户隔离仍需底层运行时
E2B沙箱 API / 托管运行时Firecracker microVM；暂停恢复、fork；SDK 成熟自建时是 Nomad/Consul 级运维
Kata / gVisor 直接上运行时成熟、可单独验证生命周期、领取、池化、策略全要自己做
Firecracker 自建IaaS 级最强控制力与隔离调度、网络、存储、镜像、运维团队

如果目标是「像 K8s 一样管 Agent」，组合通常是：agent-sandbox 做沙箱编排 + gVisor/Kata 做隔离 + 上层 Agent 控制面（kagent 或自研）+ 网关做认证与出网。不要指望单一项目把四层都做满。

8.2 五个结论

  1. 编排与隔离必须分层。Sandbox 不是安全边界，RuntimeClass 才是。评审时先问「runtimeClassName 是什么」。
  2. 默认值只覆盖一半。网络默认拒绝、token 不挂载、系统标签保护是实打实的；但容器逃逸、Router 认证、凭据外泄仍要自己补。
  3. 瓶颈在控制面，不在节点。300/s 的突发能过，70–85/s 的单池持续上限却很容易撞到；解决靠分片、限速、APF，不是加 worker。
  4. 利用率来自生命周期。热池买延迟，快照省空闲，多路复用省 Pod。三者叠加才是「云」的成本结构。
  5. 不要用超卖换密度。对不可信负载，Guaranteed 的稳定性比多塞几个 Pod 更值钱。

8.3 还没解决的事

  • 没有跨厂商的 Agent spec。kagent、agent-sandbox、kars 的 CRD 各成一套，迁移要重写。
  • Token 预算没有调度语义。K8s 不认识「这个 Agent 这次最多花 20 万 token」，只能在外层做配额。
  • 快照不通用。Pod Snapshot 依赖 GKE；跨集群/跨云恢复仍是空白。
  • Router 默认不安全。AllowAll 是为了兼容性，生产必须替换；这点在文档里写了，但很容易被忽略。
  • 多集群编排缺席。单集群的池化已经可用，跨集群的容量调度还没有标准答案。
落地建议：先用 1 个命名空间、1 个 gVisor 节点池、1 个 20 副本的 WarmPool 跑通「领取 → 执行 → 销毁」；把网络策略与准入策略当成第一天的事；等 p90 稳定在亚秒级，再谈池化与快照。

可复现的最小验证

# 1. 安装（版本按 release 固定）
export VERSION=v1.0.8
kubectl apply -f https://github.com/kubernetes-sigs/agent-sandbox/releases/download/${VERSION}/sandbox-with-extensions.yaml

# 2. 确认控制器与 CRD
kubectl -n agent-sandbox-system get deploy,pod
kubectl get crd | grep agents.x-k8s.io

# 3. 应用模板 / 池 / 领取
kubectl apply -f template.yaml -f warmpool.yaml
kubectl apply -f claim.yaml

# 4. 观察
kubectl get sandbox,sandboxclaim,sandboxwarmpool -n agents -w
kubectl get events -n agents --sort-by=.lastTimestamp | tail -20

文档会随项目快速变化；以你锁定版本的 release 与 kubectl explain 为准。本文只覆盖单集群、单控制面的形态，多集群与跨云调度不在范围内。
