ARTICLE ANALYSIS/AGENT AUTOMATION/2026-11

把 Agent 当团队带

数字生命卡兹克用一年搭出的 Agent 自动化系统：事件中台、本地 Agent 集群、CI 流水线与飞书“批奏折”。这不是工具评测，而是一套把人的注意力当稀缺资源的组织设计。

来源微信公众号 作者数字生命卡兹克 发布2026-11-02（UTC+8） 正文约 9,100 字 分析2026-11-01 阅读原文

适合读

  • 独立开发者、小团队，已被多窗口/多任务压垮
  • 想把“人盯 agent”改成“事件驱动 + 人工只做决策”
  • 愿意维护一点服务、CI 和规则，而不只是换一个聊天窗口

不适合

  • 只想要单 agent 提示词技巧的人
  • 不愿维护队列、规则、CI 与权限的人
  • 需要可复现 benchmark 或厂商官方架构文档的人

一句话：不要把 Agent 当“更快的聊天窗口”，要把它当团队：事件负责发起工作，中台负责分派与去重，Agent 负责执行，CI 负责把关，人只处理必须拍板的那一小部分。

原文文章从 DeepSeek《Super-agent 设计探索：迈向更自主的 Agent 系统》开篇那句“一个人通常只能同时跟进 3 到 5 个活跃的会话”出发，提出：单任务上限取决于模型，多任务上限取决于人的注意力。作者把“人的注意力”称为最宝贵、也最大的瓶颈，并用朱元璋废丞相、亲自批奏折的历史类比今天的多 Agent 管理。

“所有事情的起点都是你，你只要不打开那个窗口，什么都不会发生；不管模型有多强，你能同时推进的事，永远就是你盯得过来的那几个窗口。”

原文 · 对聊天式 Agent 的批评

分析这篇文章真正的贡献，不是某个工具或提示词，而是把问题从“如何让 Agent 更强”换成“如何设计一个不需要人持续盯着的组织”。它对应三个转变：

旧模式文章的模式关键变化
人打开窗口 → 给任务 → 看着做事件发生 → 中台分派 → Agent 执行任务起点从人移到环境信号
一个 Agent 串行处理多 Agent 并发 + 规则路由吞吐从“盯得过来”变成“调度得过来”
人检查每一步CI 硬门禁 + 人只批关键决策质量控制从事后检查前移到流水线

作者的样本是“一个人 + 两台 Mac mini + 若干订阅”的独立开发/小团队场景；文中的“百万月活”“9000 star”“5 天公司 AI 化”等均为作者自述，本文未独立核验。

02

系统全貌

重构原文给出了架构图，但没有公开代码与完整配置；下面先用五段流水线把图读薄，再进入各模块。五段流水线是本报告的简化读法，不是作者原图。

01 / TRIGGER

事件源

飞书消息、邮件、GitHub、告警、Cron 定时任务。事件是半结构化的，来源和格式各不相同。

→
02 / ROUTER

自动化中台

统一 schema、rules.json、去重、排队、分派；需要人决策时推飞书卡片。

→
03 / WORKER

本地 Agent 集群

两台 Mac mini 上的 Claude Code / Codex；每类任务配一个 Skill；长轮询接单，不暴露公网。

→
04 / GATE

CI 中台

审查、检查、合并、发布、核实；Agent 不能自己上线，必须过流水线。

→
05 / HUMAN

人 / 上线

绝大多数任务自动结束；只有删数据、停服、花钱等少数决策进入飞书卡片。

关键反转：传统流程是“人 → 提示词 → Agent”；这套系统是“事件 → 中台 → Agent → CI → 人（仅例外）”。人不再负责启动和跟踪，只负责设定规则、处理异常、验收结果。

与 DeepSeek Super-agent 的对照

分析作者不是照搬 DeepSeek Harness，而是用现成 Agent + 自建中台做了一套“同构不同实现”。对照 DeepSeek 原文（来源 [2][3]），能看到他补了什么、漏了什么。

DeepSeek 的设计作者的系统判断
Router / Worker 双层自动化中台 + 本地 Agent 集群部分对应：有路由/执行分离，但没有显式的 Router 会话与 Worker 上下文隔离
Trigger 事件驱动Cron、Webhook、飞书/GitHub/告警对应：事件是入口，规则决定是否叫醒 Agent
Thread 订阅与直通rules.json 的 group / parallel / tell部分：有分组和并发，但原文未说明后续事件如何直接路由给同一 Worker
Inline & Spill / 链式召回未描述缺口：长任务跨天/跨月时，上下文如何按需找回没有展开
异步 ReAct / 全双工依赖 Claude Code / Codex 应用未自建：前台对话与后台命令的阻塞问题交给现成 Agent
投机执行未描述缺口：没有“先后台试做、有价值再交付”的机制
计算 / 状态 / 环境分离中台在轻量服务器，执行在本地 Mac部分对应：环境留在本地，但状态/计算没有完全云化
Watchdog 外部控制回路CI 核实 + 告警 + 定时任务不完整：没有独立的 Watchdog 判断 Worker 是否“假忙/跑偏”
面向人的交互飞书卡片 + 升级清单 + 决策记忆更强：作者把“什么值得打扰人”写成了明确清单和记忆

原文中台是一个“很小的独立服务”，部署在一台轻量服务器上，有自己的网址和数据库；所有事件先到这里，由它决定交给哪个 Agent、统一叫醒、统一收结果。作者强调：“所有消息，只有一个出口”——不管哪个 Agent、哪个任务要找人，都只走飞书里的 AI 助理“小卡”。

分析这个结构像“事件总线 + 规则引擎 + 任务队列 + 通知网关”的组合，而不是一个更聪明的 Agent。真正的复杂度被搬到了中台和 CI，Agent 反而被简化成可替换的执行器。

03

自动化中台：事件、规则、去重

原文中台做的第一件事，是给所有事件定统一格式：从哪来、什么类型、对象是谁、一句话摘要、回到原处的链接。格式统一后，规则才能写成配置，而不是每个来源一套脚本。

事件 schema（按原文示意简化）
{
  "id": "evt_0001",
  "source": "product-hub",
  "type": "feedback.new",
  "subject": "#12",
  "summary": "同事给中台提了一条新意见",
  "link": "https://example.com/f/12",
  "ts": "2026-11-01T12:00:00+08:00"
}

统一字段是整套系统的地基：没有它，去重、路由、审计都无从谈起。

原文规则写在 rules.json 里：匹配来源与类型，指定 Agent、工作目录、Skill、并行数、通知策略。作者给的实际例子（节选）：

rules.json（按原文例子简化）
{
  "name": "中台意见",
  "when": {
    "source": "virxact-hub",
    "types": ["feedback.new", "feedback.followup", "feedback.decided"]
  },
  "to": "m5-claude",
  "cwd": "~/code/work/virxact-hub",
  "skill": "hub-feedback",
  "parallel": 3,
  "tell": "needed"
}

翻译：这类事件交给 M5 上的 Claude Code，在指定目录用 hub-feedback 这个 Skill 处理；同一件事最多 3 条并行；只有需要决策时才通知人。

原文因为两台 Mac 都在内网、外面连不进来，作者反过来做：每台 Mac 跑一个“接单程序”，一直挂在中台上等活，一次最长等 50 秒，有活立刻接走，没活再挂回去。这样机器不用暴露到公网，速度也接近实时推送。

加事件类型

不用写新脚本，在 rules.json 加一条规则即可；作者说改完文件、过检查，几分钟生效。

换 Agent / 模型

哪类事交给谁，是规则里的一行字；今天 Claude，明天换别的模型，不需要改业务代码。

去重

同一件事被重复推送是常态；中台统一去重，避免多个 Agent 同时改同一处。

单一出口

所有需要人的消息只走“小卡”，不刷屏；规则里写清楚什么时候才通知。

数据沉淀

事件何时来、交给谁、结论是什么、是否需留意，全部落库；可回跳到当时 Agent 的会话。

可视化

作者做了一个“自动化小镇”网页，把流水线像游戏一样展示，并与真实时间/天气打通。

分析中台的价值不在“统一”，而在把隐式流程变成可检查的对象：事件有 schema、路由有规则、执行有记录、通知有策略。代价是要维护一个服务、一份规则文件和一套去重键；规则漂移、队列积压、worker 掉线都会变成新的运维问题。

04

Agent 执行与模型分工

原文作者明确说“不是无限 Token”：他开 200 美元 Claude 会员 + 100 美元 GPT 会员，猛用下来 3 天能用掉近 90%。所以他按能力与性价比分工，而不是所有任务都用最贵模型。

角色作者使用的模型负责任务作者评价
主力开发Claude Opus 5.5AIHOT 自动化开发、公司中台意见、复杂且需要主观能动性的活核心项目大部分代码由它写
运维 / 审查GPT-6.1 Sol告警、每日系统日报、到期复查、Codex 代码审查运维与审查效果好，性价比高
浏览器 / 电脑操控GPT-6.1 Terra操控登录好账号的 Chrome，抓没有 API 的数据、做 GEO 检查专门干浏览器与桌面操作

原文执行环境放在两台 Mac mini 上（M5 Pro 日常机、M4 跑自动化），而不是云上。理由很具体：代码仓库、发布权限、飞书身份、登录好各种账号的 Chrome 都在本地；复制到云上既麻烦又不安全；国内服务跨境访问慢/超时；微信等浏览器任务在云虚拟机里容易崩；两台 Mac 本来就是现成的，功耗低。

“做决策和做管理的模型，一定得是智力和主动性最强的；你不能用笨逼来指挥聪明的，这样会乱套了。”

原文 · 为什么用强模型做调度

分析这是典型的“能力路由 + 成本路由”：复杂决策给强模型，重复运维给性价比模型，浏览器/桌面给专用模型。它依赖作者对模型能力的长期体感，不是可移植的规则；模型版本一变，路由表就要重估。文中模型名称属于作者 2026 年的上下文，不应直接当作选型建议。

风险把登录态、发布权限、飞书身份都留在本地 Mac 上，降低了“云端复制凭据”的风险，却把风险集中到了两台机器：一旦其中一台被恶意 Skill、提示词注入或供应链攻击拿下，损失是“代码 + 发布 + 身份 + 浏览器账号”的合集。原文没有展开凭据隔离与最小权限的实现。

05

Skills 与 CI 中台

原文每个自动化任务基本都配一个专属 Skill。作者把 Skill 定义为“沉淀给 Agent 用的 SOP”：规则、参考、脚本都在里面。比如每周日的大扫除任务，Skill 写的是找出这一周合进来的“屎山”：重复代码、为个案打的补丁、停用却没拆干净的代码、变成流水账的文档，能删的直接删掉再上线。

分析这是把“任务逻辑”从 Agent 执行中解耦：改流程改 Skill，不改 Agent；换模型也不用重写流程。代价是 Skill 会成为新的“代码”，需要版本、审查和回归测试。

原文CI 中台是第三块。作者不用 GitHub 自带 CI，原因很直接：量太大。AIHOT 一个项目 10 月合了将近 1000 个 PR，平均一天二三十个，每个还要来回跑几遍；GitHub 会员每月 3000 分钟不够，按他的量每月超额要 50 美元以上。于是他用家里旧的 M4 Mac mini 自建 CI，机器现成、性能更强、在北京跑得更快。

步骤做什么关键约束
1. 审查Codex（GPT-6.1 Sol）只读审查每个 PR只读、不能改、不能联网、读不到密钥；只报真会出错的问题，不报风格；最多审 3 轮
2. 检查类型检查、全部测试、构建、数据库只能加不能改任一条不过就不能合；每个任务开全新虚拟机，跑完连机器带身份一起删
3. 合并GitHub 自动合并“审过 + 检查过”写死在 GitHub 规则里，任何 Agent/工具都不能绕过
4. 发布GitHub 启动发布流程单独开一台发布虚拟机执行
5. 核实等发布完成，再去线上确认版本已包含本次改动结果写回 GitHub，这一轮才结束
298两周四个项目审查的 PR 数
333Codex 报出的问题数
306合并前修掉的问题数
51其中最严重的一档
2–3 分钟从交代码到真正上线的中位数
5–15%一次审查约占该任务 Token

以上数字均为作者自述，未独立核验；样本是作者自己的四个项目与两周窗口。

分析CI 中台是整套系统里最值得抄的部分：把“质量”从提示词移到硬门禁。只读审查、最多 3 轮、临时虚拟机、GitHub 规则、发布后核实，这五件事共同把“Agent 说做完了”变成“系统证明它上线了”。但审查者仍是另一个模型，不是独立人类；3 轮上限也可能放过复杂问题。

06

批奏折：人的位置

原文最后能推到作者面前的，必须是需要他做的决策或大事。他在飞书里让 AI 助理“小卡”弹一张卡片，点一下确认，Agent 收到决策继续干活。卡片交互被作者类比为明朝的“票拟—批红”：Agent 把建议写在票上，人只做红笔批下去的那一下。

“我只做判断，只要点击就行；然后在之前等着我审批的 Agent 就会接着往下干，卡片也会自己改成结论。”

原文 · 飞书决策卡

原文作者踩过“一天推几十条、严重干扰注意力”的坑，所以现在把“必须先问人”的范围收窄到几类：删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限。其余 Agent 自己全权做完上线。

原文为了让 Agent 不重复问，作者在仓库里维护两份“记忆”：

「卡兹克定的事」

只记作者亲口做的决定，带原话和日期；Agent 以后按这个执行。

「定了不做的事」

记录被拒绝的方向；Agent 再遇到类似问题，直接照着回答，不再来烦。

原文唯一完全没有交给 Agent 的是用户反馈：每一条作者都亲自看，觉得能做的就复制粘贴给 Agent 去解决，解决完再给对方邮箱发一封真诚的回信。作者把这称为“最后的一种仪式感”。

分析“批奏折”不是偷懒，而是把人的角色限定在高风险、不可逆、涉及外部承诺的决策上。真正难的不是做卡片，而是定义什么值得打扰人；这份升级清单和两份决策记忆，才是系统能长期运行的关键资产。

08

分析：强在哪

1. 事件驱动

把任务起点从人移到环境信号；人不在窗口前，工作仍可发生。这是全文最核心的架构选择。

2. 统一事件 schema

来源、类型、对象、摘要、链接五个字段，让去重、路由、审计都能复用同一套逻辑。

3. 规则表

rules.json 把“哪类事交给谁、用什么 Skill、并行多少”变成可读、可改、可审查的配置。

4. 去重 / 幂等

重复事件不会叫醒多个 Agent 改同一处；这是多 Agent 系统能否稳定的分水岭。

5. 拉取式 worker

长轮询 50 秒，让内网 Mac 不用暴露公网也能近实时接单；简单、有效、可解释。

6. 模型路由

复杂决策、运维、浏览器操作分给不同模型；按能力和成本分配，而不是一把梭。

7. Skill 即 SOP

流程、规则、脚本沉淀成可版本化的 Skill；改流程不改 Agent，换模型不重写流程。

8. CI 硬门禁

只读审查、测试/构建、GitHub 规则、临时 VM、发布后核实：质量靠系统，不靠 Agent 自觉。

9. 升级清单 + 决策记忆

只把不可逆/高风险/外部承诺交给人类；定过的事不重复问，降低注意力税。

10. 数据沉淀

每个事件可追溯：从哪来、交给谁、结论、是否需留意；为换模型/改规则提供依据。

分析这套系统的本质不是“更强的 Agent”，而是把 Agent 放进一个有输入、有路由、有门禁、有审计、有升级路径的组织。这也是它比“多开几个窗口”更有借鉴价值的地方。

09

边界与风险

证据边界

  • 单一案例：一个人的两台 Mac、几个项目、特定模型组合；没有对照组，也没有公开代码/配置。
  • 数字未核验：PR 数、审查命中率、Token 占比、上线时长均为作者自述，缺少采集口径。
  • “几乎没有 BUG”是强主张：没有失败案例、漏审率、回滚率，无法证明。
  • 模型时效性强：Claude Opus 5.5 / GPT-6.1 的具体表现会变，路由表不可直接复制。

系统风险

  • 凭据集中：代码、发布权限、飞书身份、登录态 Chrome 都在本地 Mac；一台失守就是合集失守。
  • 审查非独立：Codex 审 Claude 的代码，仍是模型审模型；同源盲点与 3 轮上限都可能漏问题。
  • 自建平台成本：中台、规则、去重、CI、虚拟机、监控都要维护；小团队很容易被运维反噬。
  • 规则/去重会漂移：事件类型增加、来源变化、重复键设计不当，都会导致漏处理或重复执行。
  • 注意力仍会被刷屏：作者自己承认曾一天几十条；升级清单是人工经验，不是完备分类。
  • 合规与隐私：用户反馈、聊天记录、浏览器账号进入 Agent 流程，数据保留与删除策略原文未展开。

结论这是一份高价值的“系统设计经验”，不是可直接照搬的“生产架构”。最值得学的是事件、规则、去重、门禁、升级清单这几个机制；最不该无脑复制的是两台 Mac + 自建 CI + 全自治 Agent这套重资产组合。

10

对 Agent 工作台的启示

分析如果把这篇复盘放回“Agent 工作台”的语境，它其实给了五条设计约束，而不是五个功能：

约束对工作台的含义
Router / Worker 分离一个负责人类交互、全局上下文和分派；多个 Worker 在隔离上下文里执行。不要让一个主会话又聊天又干活。
事件是入口工作台不只接受“人打开窗口输入”；还要能接 webhook、cron、IM、GitHub、告警。
Skill 是 SOP把流程从 prompt 里拿出来，做成可版本化、可审查的 Skill；工作台要能管理/加载/共享 Skill。
CI 是门禁“Agent 说做完了”不算完成；要有只读审查、测试、合并规则、发布后核实。
注意力预算把“当前活跃会话数、Needs You 数、review lag”当一等指标；超过阈值就停止加窗口。
与 100+ 窗口教程的关系：这篇复盘说人通常只能同时跟进 3–5 个活跃会话；这不否定 100+ worktree，而是给它划了边界——100+ 是总量，3–5 是同时占用注意力的活跃面。Orca 的 100+ 方案必须靠事件、看板、批处理把“需要人看”的窗口压到个位数，否则只是把 100 个未读堆在一起。参见 Orca · 100+ 会话窗口实战教程。

该抄的

  • 统一事件 schema + 规则表 + 去重键
  • 单一通知出口 + 明确的升级清单
  • Skill 化 SOP，流程与 Agent 解耦
  • 只读审查 + 测试/构建 + 合并门禁 + 发布后核实
  • “定过的事 / 定了不做的事”决策记忆
  • 任务日志与可追溯的数据沉淀

别照搬的

  • 两台 Mac + 自建 CI + 自建中台的重资产组合
  • 把登录态、发布权限、身份都放在同一台机器
  • 用模型审查替代人工最终验收
  • “3 轮审查”当成通用质量上限
  • 把作者 2026 年的模型路由表当成选型结论
  • 在没有指标前就追求 100 个并发窗口

建议对 OpenCode × Pi 这类工作台，优先级不是再加一个 agent，而是补上事件层、路由层、CI 门禁层、决策记录层。这四层决定它是“更好用的终端”还是“可托付的工作系统”。参见 Agent 工作台设计方案。

11

简化落地方案

分析不需要一上来就自建中台。按下面的顺序，每一步都能独立产生价值；任何一步跑不通，就先停在上一阶段。

层最小版本进阶版本
事件入口Cron + 一个 Webhook，先接一类事件统一事件总线 + 数据库 + 重放
路由一个 rules.json：来源/类型 → Agent/Skill规则 UI + 灰度 + 权限
执行一台机器 + 长轮询 worker + 一个 Skill多机/远程 + 隔离环境 + 并发配额
门禁测试 + 只读审查 + 合并规则五步 CI + 临时 VM + 发布后核实
人飞书/Slack 卡片 + 7 类升级清单决策日志 + 指标 + 审批审计
观测每个任务一条记录：来源、Agent、结论、耗时看板 + 成本/失败率/积压分析

30 天最小闭环

  1. 第 1 周：选一个高频、低风险流程
    例如“每周清理一次无用分支/文档”或“每天汇总一次告警”。只接一个事件源，写一个 Skill。
  2. 第 2 周：加规则与去重
    把“什么事件、交给谁、用什么 Skill、并行多少、何时通知”写成一份 rules 文件；给事件加稳定 id，重复事件只处理一次。
  3. 第 3 周：加门禁
    让 Agent 只能提交，不能直接上线；测试/构建/只读审查通过才合并；记录发布后核实结果。
  4. 第 4 周：加人的入口
    只把不可逆/花钱/对外/权限类决策推到一张卡片；建立“定过的事 / 定了不做的事”两份记录；开始记活跃会话数与 review lag。

一条可运行的工作流（以每天 18:00 开源巡检为例）

落地把原文的机制压成一条可执行链路；每一步都能单独观测、单独失败、单独重试。

步骤输入 / 动作输出失败时
1. 触发18:00 Cron 产生 github.sweep 事件，带 repo、日期、目标清单一条统一 schema 的事件错过就补跑；事件记录可重放
2. 路由中台鉴权 → 去重（github.sweep:日期）→ 匹配规则 → 指派 M5-Claude、Skill review-prs、parallel 3、tell needed一个待执行任务规则不匹配则只记录；重复事件丢弃并计数
3. 接单M5 上的 worker 长轮询领活；读 PR/issue/评论，分类为“可自动修 / 需人决策 / 忽略”分类结果与执行计划worker 掉线：租约超时后重派；连续失败 3 次通知人
4. 执行自动修：改代码 → 开草稿 PR → CI 只读审查（最多 3 轮）→ 检查 → 合并 → 发布 → 线上核实PR 链接、CI 结果、上线确认审查/检查失败：退回修改；超过上限升级给人
5. 决策需要人定：飞书卡片给出“发生了什么 / 影响 / 建议 A/B”点击结果 + 决定记录超时默认不合并、不对外发送；卡片可重发
6. 收尾运行记录、结论、耗时、token、是否需留意写入中台可追溯的记录与摘要记录失败不阻断主流程，但必须告警

故障与回退

故障处理
同一事件重复到达稳定 id + 去重键 + TTL；重复只计数，不再叫醒 Agent
Worker 离线/卡死租约 + 心跳 + 超时重派；连续失败进入人工队列
CI 反复失败带日志退回 Agent，限制重试次数；超过阈值转人工
审查超过 3 轮停止自动循环，升级给人；避免“无限审查”
人未及时处理默认安全动作：不合并、不对外、不删数据；卡片可重发
凭据/权限泄露立即吊销/轮换、隔离机器、审计该 worker 的全部任务

复盘每周花 15 分钟看六个指标：事件量、去重命中、活跃会话/Needs You、审查轮数、人被打扰次数、每个合并 PR 的 token。指标恶化时先减并发，而不是加机器。

上线前检查

这份清单是本文基于原文机制的重构，不是作者原文；具体实现可用现成队列、CI、聊天机器人，不必复刻作者的自建服务。
