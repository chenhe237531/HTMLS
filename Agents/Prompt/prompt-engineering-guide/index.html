01

它是什么

一句话：一份系统性的提示工程学习资料库。它把概念、技巧、论文、示例、Notebook 和模型说明组织成一本可在线阅读、也可本地运行的书。

适合谁

想系统学习提示工程的人；需要查技巧出处与论文的开发者；想给团队做培训的人。

不是什么

不是「1000 条万能提示词」合集，也不是可直接调用的 SDK 或评测框架。

怎么用最值

按路线读概念 → 跑 Notebook → 选一个技巧用在自己的任务上 → 做评测。

02

仓库结构

看懂目录，就知道该去哪里找内容、去哪里改。

dair-ai/Prompt-Engineering-Guide
Prompt-Engineering-Guide/
├── pages/                 # 主要内容（MDX），按主题分目录
│   ├── introduction.en.mdx
│   ├── techniques/        # zero-shot / few-shot / CoT / RAG / ReAct …
│   ├── applications/      # function calling / RAG / coding …
│   ├── prompts/           # Prompt Hub：按任务分类的示例
│   ├── models/            # GPT / Gemini / LLaMA / Mistral …
│   ├── risks/             # 对抗、事实性、偏见
│   ├── agents/            # Agent 相关内容
│   ├── papers/            # 论文索引
│   └── _meta.*.json       # 各语言的导航配置
├── notebooks/             # 可运行笔记（含 pe-lecture.ipynb）
├── lecture/               # 讲座幻灯片 PDF
├── guides/                # 补充指南
├── components/            # 站点组件
├── public/                # 静态资源
├── infographic-review.html
├── package.json           # pnpm / next / nextra 依赖
└── README.md

为什么是 MDX

每篇文章是 Markdown + 可嵌入组件。你既能像读文档一样读，也能在页面里放提示示例、表格和交互组件。

多语言怎么组织

同一主题有 *.zh.mdx、*.fr.mdx 等版本；_meta.zh.json 控制中文导航。翻译就是改这些文件。

找内容的捷径 想查技巧 → pages/techniques/；想找示例 → pages/prompts/；想看来龙去脉 → pages/papers/；想跑代码 → notebooks/。
03

三种用法

方式适合怎么做代价
在线读学习、查资料打开 promptingguide.ai，按左侧导航读需要网络；内容更新以官网为准
本地跑离线阅读、改内容、做翻译clone → 安装依赖 → pnpm dev需要 Node 与 pnpm，首次安装较慢
只读源码找原始 MDX、论文链接、示例在 GitHub 直接浏览 pages/没有站点导航，长文阅读体验一般

大多数人只需要「在线读 + 偶尔看源码」。只有当你需要离线、批量改写、做翻译或给团队部署内部镜像时，才值得本地运行。

04

学习路线

不要从「技巧大全」开始读。先建立基础词汇，再挑一个技巧动手，最后补风险与论文。

30 分钟快速路径

  1. 读 Introduction 的 Settings、Basics、Elements、Tips 四页。
  2. 读 Zero-Shot 与 Few-Shot，理解「示例」的作用。
  3. 在 Prompt Hub 找两个与你任务相近的例子，改写一次。
  4. 停止。不要继续刷技巧，先去用。

四周系统路径

W1
基础与写法

Introduction（设置、基础、要素、技巧）→ Zero-Shot / Few-Shot → 示例页。产出：为你自己的任务写 10 条提示词，并记录失败案例。

W2
推理与分解

Chain-of-Thought → Self-Consistency → Prompt Chaining → Tree of Thoughts → ReAct。产出：选一个技巧，在同一批 10 个样本上与基线对比。

W3
应用与工具

Function Calling → RAG → 生成数据 / 代码 → Prompt Hub。产出：一个端到端小应用，至少包含检索或工具调用。

W4
风险与论文

Adversarial、Factuality、Biases → Papers 选读 → 建立自己的评测集。产出：评分 rubric + 10 条红队用例。

每周只做一件事 读完技巧不等于会用。每周留一个可验收的产出，比刷完 17 个技巧更有价值。
05

内容地图

按「你现在要解决什么」选章节，而不是从第一页读到最后一页。

章节包含什么时候读
IntroductionLLM 设置、提示基础、要素、通用技巧、示例刚开始，或提示总是「不稳定」时
TechniquesZero/Few-Shot、CoT、Self-Consistency、Chaining、ToT、RAG、ART、APE、ReAct、多模态 CoT、Graph Prompting需要提升推理、检索或工具使用能力时
ApplicationsFunction Calling、生成数据、合成 RAG 数据集、生成代码、岗位分类案例要把提示接进真实产品时
Prompt Hub分类、编程、创意、评估、信息抽取、数学、问答、推理、摘要、真实性、对抗需要现成示例与写法参考时
ModelsChatGPT、GPT-4、Gemini、LLaMA、Mistral、Mixtral、Phi-2、OLMo 等换模型、做兼容或选型时
Risks对抗提示、事实性、偏见上线前、处理用户输入时
Papers综述、方法、应用、合集要追源头、写报告或做研究时
Tools / Notebooks / Datasets工具列表、可运行笔记、数据集要动手实验时
AgentsAgent 相关章节与资源从单次提示走向多步任务时
注意「技巧」的适用边界 CoT、ToT、Self-Consistency 在推理题上有效，不代表在所有任务上都更好；它们会增加 token 与延迟。先测，再决定。
06

本地运行

仓库是一个 Next.js + Nextra 站点。本地跑起来只需要 Node 与 pnpm。

终端
git clone https://github.com/dair-ai/Prompt-Engineering-Guide.git
cd Prompt-Engineering-Guide

node -v          # 需要 >= 18
pnpm -v          # 没有就先装 pnpm

pnpm install
pnpm dev

# 打开 http://localhost:3000/

README 里也给出了显式安装命令：pnpm i next react react-dom nextra nextra-theme-docs。如果 pnpm install 因锁文件或版本报错，可以按 README 的命令重试。

常见问题

现象原因处理
pnpm: command not found未安装 pnpmcorepack enable 或 npm i -g pnpm
安装时报 Node 版本错误Node < 18升级 Node（建议 LTS）
端口 3000 被占用已有服务停掉旧进程，或改端口启动
页面 404 / 导航缺失内容或 _meta 文件未生效重启 pnpm dev；确认改的是对应语言文件
依赖安装很慢网络配置 npm/pnpm 镜像后重试

跑 Notebook

仓库的 notebooks/ 里有配套代码，包括讲座用的 pe-lecture.ipynb。用 Jupyter 打开前先准备模型 API Key，并注意不要把 Key 提交回仓库。

Notebook
pip install jupyter
jupyter notebook notebooks/pe-lecture.ipynb
07

把指南用在自己的任务上

阅读的终点不是「知道 CoT」，而是「知道什么时候该用、怎么验证它真的更好」。

你的任务先读可试技巧验收
分类 / 打标Prompt Hub → ClassificationFew-Shot + 明确标签集混淆矩阵与误判样本
信息抽取Applications → Function Calling结构化输出 + 校验重试字段完整率与准确率
知识问答Techniques → RAG检索 + 引用 + 拒答引用正确率与幻觉率
数学 / 推理Techniques → CoT / Self-Consistency / ToT分步推理 + 多次采样准确率 vs token 成本
工具 / 多步任务Techniques → ReAct；Agents思考-行动-观察循环任务成功率与越权率
内容创作Prompt Hub → Creativity约束 + 多版本 + 选优人工评分 rubric
上线前安全Risks → Adversarial / Factuality红队用例 + 拒答策略攻击成功率

一个改写示例：从 CoT 页到自己的提示词

基于 Chain-of-Thought 改写的任务模板
你是一位严谨的问题解决者。

问题：{{问题}}
约束：{{时限 / 可用工具 / 不允许的做法}}

请按步骤处理：
1. 用自己的话复述问题与约束，标出不确定的地方。
2. 列出已知条件、未知条件与可能需要的假设。
3. 给出 2–3 种解法，比较成本与风险。
4. 选择一种，写出完整推理过程。
5. 只输出：最终答案、关键步骤摘要、仍需确认的假设。

如果信息不足，先提问，不要编造。

这不是「官方模板」。它把 CoT 的思路（显式推理 + 多解比较）和工程约束（成本、假设、拒答）合在一起；使用前用你自己的 10–20 个样本测试。

不要直接复制指南里的示例 指南里的示例通常为了演示技巧而简化。真实任务需要补充：数据边界、输出格式、失败处理、权限与成本限制。
08

贡献与翻译

可以贡献什么

  • 修正错别字、失效链接与过时描述
  • 补充新的技巧、论文或应用案例
  • 翻译：仓库支持 13 种语言，按 *.zh.mdx 等命名
  • 改进 Notebook 与示例代码

提 PR 的注意点

  • 先开 issue 说明动机，避免大改被拒
  • 保持与现有 MDX 结构和导航文件一致
  • 只改对应语言文件，别动其他翻译
  • 代码与命令要能复现；不要提交密钥

09

局限与注意

局限说明应对
内容有「年代感」部分模型页与示例写于早期模型时代以官网最新页与当前模型文档为准
技巧不等于收益CoT / ToT 等会增加 token 与延迟用同一批任务做 A/B，算单位成本
示例偏简化演示用提示词缺少生产约束补边界、格式、权限、失败处理
不是提示词库Prompt Hub 是示例，不是生产模板把它当参考，不是复制粘贴的来源
安全内容有限对抗与注入的攻防在快速变化结合 OWASP LLM Top 10 等资料
仓库与官网可能不同步官网通常更新更快先读官网，再回仓库看源文件
不要把「提示工程」当万能药 很多问题不是提示词能解决的：知识缺失要靠检索，权限问题要靠系统设计，稳定性要靠评测与工程约束。提示词只是其中一层。
