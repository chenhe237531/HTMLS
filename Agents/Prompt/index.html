01

怎么用

提示词不是咒语。它是一份任务说明：谁来做、做什么、边界在哪、交付长什么样。下面所有模板都按这四件事写。

先替换变量

把 {{主题}}、{{读者}}、{{字数}} 换成真实信息；空着的变量会让模型自由发挥。

给验收标准

写清「怎样算完成」：格式、长度、必须包含的字段、不能做的事。

先跑一次再改

用真实任务测试；不行就改约束或输出格式，不要只加「请更专业一点」。

要素作用例子
角色限定视角与标准「你是只读的代码审查员」
任务一句话说清要交付什么「审查这段 diff，找出阻断问题」
约束边界、禁止项、不确定性处理「不修改文件；不确定标为疑问」
输出格式、长度、必填字段「按严重度排序，每条带 file:line」
使用顺序 选模板 → 替换变量 → 先小样本试一次 → 按结果加约束（不是加形容词）→ 固定成自己的模板。

文章初稿：先选结构再写

适合从零写一篇有观点的长文
变量：主题 / 读者 / 目标
你是一位资深编辑。

主题：{{主题}}
读者：{{读者}}
目标：读完后他们能做出什么决定或行动

步骤：
1. 先给 3 种不同的文章结构，各用一句话说明适合什么读者。
2. 选最合适的一种，写出 800–1200 字初稿。
3. 事实、引用与个人观点必须分开标注。
4. 结尾给 3 条可执行的下一步。

不要用「在当今时代」这类套话开场。

精简改写：不丢信息

把冗长草稿压到目标字数
变量：字数 / 原文
把下面的文字压缩到 {{字数}} 字左右。

要求：
- 保留所有事实、数字、时间与限定条件。
- 删除重复、空话与自我引用。
- 不改变原意，不新增信息。

输出：
1. 改写稿
2. 不超过 3 条修改说明（删了什么、为什么）

原文：
{{粘贴原文}}

同一内容，改写四个平台

一次写作，多渠道分发
变量：原始内容
把下面这份内容改写成四个版本，事实必须一致：

1. 邮件：主题行 + 200 字以内正文，结论先行。
2. 公众号：600 字，有标题、小标题、结尾互动。
3. 微博：140 字以内，保留一个数字或反常识点。
4. Slack：3 条以内消息，每条不超过两行。

每个版本标明适合的读者与使用场景。

原始内容：
{{粘贴内容}}

事实核查：把主张拆开

发布前检查文章里的事实
变量：待核查文本
逐条列出下文中所有事实性主张，并为每条标注：

- 类型：可验证事实 / 观点 / 预测 / 定义
- 核查方法：应查什么来源（官方文档、论文、财报、监管文件）
- 当前判断：支持 / 存疑 / 无法判断
- 风险：如果错了，会影响什么

不要编造来源；不确定就写「无法判断」。

文本：
{{粘贴文本}}

代码侦察：先摸清地形

开工前只读分析仓库
变量：任务
你是只读的代码侦察员。

任务：{{要完成的功能或要排查的问题}}

请只读分析仓库，输出：
1. 入口文件与关键调用链（每条带 file:line）
2. 相关测试与它们覆盖的行为
3. 既有约定（命名、错误处理、目录结构）
4. 改动风险点与未知项

限制：
- 不修改任何文件，不执行写操作。
- 不粘贴超过 5 行的代码。
- 结论不超过 15 行，细节放在附录。

代码审查：只读、按严重度

提交前或合并前审查
变量：需求 / diff
你是独立代码审查员，只读工作区。

需求：{{这次改动要解决什么}}
改动：{{粘贴 diff 或文件清单}}

输出按三档排序：
- 阻断：会导致错误、数据损坏或安全问题
- 建议：可维护性、性能、边界
- 疑问：需要作者确认的假设

每条必须包含：file:line、问题、为什么是问题、最小修复方向。
不修改文件；不超过 12 条；不确定标为疑问。

调试：假设 → 实验 → 根因

可复现的报错、CI 失败、性能退化
变量：现象 / 日志
你是排障工程师。

现象：{{报错或异常行为}}
环境：{{版本 / 平台 / 最近改动}}
日志：{{关键日志，最多 30 行}}

请：
1. 提出 3 个假设，按验证成本排序。
2. 每次只做一个最小实验，说明预期与结果。
3. 找到根因后，先写一个会失败的回归测试，再给最小修复。
4. 最后说明还有哪些未排除的可能。

不要一次改多个地方。

重构：行为不变

重复代码、职责混乱、加功能前整理
变量：模块 / 目标
在不改变外部行为的前提下重构 {{模块}}。

步骤：
1. 先列出当前行为与调用方，指出哪些是公开契约。
2. 补最小护栏测试；测试通过后再动结构。
3. 小步修改，每步只做一件事，并说明改了什么。
4. 每步结束跑验证命令，报告结果。

约束：
- 不顺手改需求，不改公开 API。
- 失败时先回滚到上一个绿点，不要叠加补丁。

测试矩阵：先列格子再写

补测试、修复后防回归
变量：功能
为 {{功能}} 设计测试矩阵。

维度：正常路径 / 边界 / 异常输入 / 并发或重试 / 权限与越权。
每格给出：输入、预期结果、优先级（P0–P2）。

然后：
1. 先写 P0 用例，保持最小可运行。
2. 每个断言必须能因实现错误而失败，避免「永真」测试。
3. 最后列出尚未覆盖的风险。

问题拆解：MECE 三层

面对模糊、复杂的问题
变量：问题
用 MECE 原则拆解：{{问题}}

要求：
1. 给出三层结构，第一层 3–5 个分支。
2. 标出哪些是事实、哪些是假设、哪些未知。
3. 对每个未知，给出最低成本的验证方法。
4. 最后给 3 个本周就能执行的动作，并说明成功信号。

不要用「加强重视」「提升能力」这类无法验证的表述。

决策矩阵：打分 + 敏感性

在几个方案之间做选择
变量：选项 / 标准 / 权重
帮我做一个决策矩阵。

选项：{{A / B / C}}
标准与权重：{{标准 1=40%，标准 2=30%，标准 3=30%}}

要求：
1. 每个选项按 1–5 打分，并给打分的依据。
2. 计算加权总分。
3. 做敏感性分析：权重变化多少会改变结论？
4. 指出矩阵无法捕捉的因素，并给一个「如果只能选一个」的建议。

不要为了凑满分数而编造数据。

红队：这个方案会怎么失败

上线前、投资前、重大决策前
变量：方案
站在最聪明的反方立场，攻击这个方案：

{{方案}}

输出：
1. 5 个最可能导致失败的原因，按「概率 × 影响」排序。
2. 每个原因给一个早期信号（怎样在两周内发现）。
3. 每个原因给一个低成本应对。
4. 最后回答：如果只能修一个，修哪个？

不要为了平衡而弱化问题。

日志 / 数据分析：先描述再结论

排查趋势、定位异常、核对口径
变量：数据说明 / 日志
分析下面的日志或数据。

数据说明：{{时间范围 / 字段 / 采集方式}}
数据：{{粘贴样本，最多 50 行}}

请按顺序：
1. 描述数据形状：时间范围、缺失、异常值。
2. 列出观察到的现象，每条附证据。
3. 区分相关与因果；没有证据的因果解释标为假设。
4. 明确写出「这些数据无法回答什么」。

不要用总数掩盖分布问题。

费曼解释：讲给两种人听

快速真正理解一个概念
变量：概念
用费曼法解释 {{概念}}。

1. 先给一个 12 岁读者能懂的版本（不超过 150 字），必须用一个生活类比。
2. 再给一个同行版本：关键机制、术语、边界条件。
3. 列出 3 个常见误解，并逐一纠正。
4. 给 3 道自测题（不要答案），覆盖定义、应用与边界。

如果某个部分需要前提知识，先说明前提。

7 天入门路线

从零接触一个新领域
变量：主题 / 每天时长
为零基础学习者设计 {{主题}} 的 7 天入门路线。

约束：每天 {{1 小时}}，只用一个免费资源。

每天给出：
- 一个具体目标
- 一个 30–60 分钟的学习动作
- 一个可交付物（笔记 / 小脚本 / 一页图）
- 一个验收标准（怎样算学会）

不要列书单，不要安排「看视频」作为唯一动作。
最后给第 8 天的自测任务。

苏格拉底式引导

想自己想明白，而不是被灌输
变量：主题
不要直接给我答案。用苏格拉底式提问引导我理解 {{主题}}。

规则：
- 每次只问一个问题，等我回答后再继续。
- 从我的现有理解出发，逐步暴露矛盾。
- 如果我答错，用一个反例让我自己发现，而不是直接纠正。
- 5 轮后，让我用自己的话总结，你再补充遗漏。

现在开始第一个问题。

文档 / 论文精读

读长文档时避免只记住结论
变量：文档
精读下面这份文档。

文档：{{粘贴或给出链接/路径}}

输出：
1. 5 句话摘要（问题、方法、结论、限制、适用场景）。
2. 关键概念与它们之间的关系（用列表表示）。
3. 作者明确说了什么、推断的是什么、没说什么。
4. 我作为 {{角色}} 最可能误解的 3 个点。
5. 3 个值得追问的问题。

不要补充文档之外的事实；需要外部知识时明确标注。

需求澄清：把一句话变成可执行

接到模糊需求时
变量：原始需求
把这条需求澄清成可执行说明：

{{原始需求}}

输出：
- 用户与场景
- 要解决的问题（不是功能清单）
- 成功指标（可量化）
- 非目标（这次明确不做什么）
- 验收标准（怎样算完成）
- 5 个必须向需求方确认的问题，按重要性排序

不要替需求方做假设；把假设单独列出。

用户访谈提纲

验证需求，而不是推销方案
变量：目标 / 用户
为 {{研究目标}} 设计一份 30 分钟用户访谈提纲，对象是 {{用户类型}}。

要求：
- 8 个主问题，多问过去行为，少问「你会不会」。
- 每个主问题配 1–2 个追问。
- 避免引导性、二元式与假设性问题。
- 开头 3 分钟建立语境，结尾 3 分钟问「还有什么我没问到的」。
- 另附：3 个不能问的问题及原因。

周报：结果先行

把流水账整理成可读周报
变量：本周记录
把这周的记录整理成一份周报。

记录：{{粘贴流水账 / 提交 / 会议要点}}

结构：
1. 结果：3 条以内，每条带数字或可验证产出。
2. 进展：比上周多了什么。
3. 风险与阻塞：需要谁在什么时候做什么。
4. 下周计划：3 件事，每件有验收标准。

删除过程细节与「参与了」这类不可验证表述。没有数字就写「无数据」。

会议纪要：只留决定与行动

会后 5 分钟整理
变量：会议记录
把会议记录整理成三部分：

1. 已决定：每条一句话，注明决策人与依据。
2. 行动项：任务 / 负责人 / 截止时间 / 验收标准。
3. 未决问题：为什么没定、下一步谁来推动。

规则：
- 不编造未讨论的内容。
- 讨论过程不写，除非它解释了某个决定。
- 信息不足的字段写「待确认」。

会议记录：
{{粘贴记录}}

只读侦察子代理

主代理开工前的上下文压缩
变量：任务
你是只读侦察子代理。

目标：为「{{任务}}」收集施工前所需的最小上下文。

输出（≤ 15 行）：
- 相关文件与符号，每条带 file:line
- 现有约定与测试入口
- 风险与未知项
- 建议的下一步（不超过 3 条）

禁止：编辑文件、执行写入命令、粘贴超过 5 行代码。
不确定的内容标为「未确认」，不要猜。

独立审查子代理

与实现者分离，避免自审偏差
变量：需求 / diff
你是独立代码审查子代理，只读。

输入：需求 {{需求}} + diff {{diff}}

只输出 findings，按 阻断 / 建议 / 疑问 排序。
每条：file:line、问题、为什么、最小修复方向。

约束：
- 不修改文件，不运行命令。
- 不评价实现者的过程，只看结果。
- 不超过 10 条；不确定标为疑问。
- 最后给一句总体判断：可以合并 / 修完再合 / 需要重做。

规划代理：只出计划

多文件改动前的拆解
变量：目标 / 约束
你是规划代理，只输出计划，不写代码。

目标：{{目标}}
约束：{{必须遵守的规则 / 不能动的部分}}

输出：
1. 目标与非目标
2. 步骤清单：每步一个可独立验证的改动
3. 每步的验收命令与预期结果
4. 风险、回滚点与需要人工确认的地方
5. 建议的执行顺序（哪些可并行）

如果信息不足，先列问题，不要假设。

编排者：只分派不施工

大任务拆分给多个子代理
变量：任务 / 可用代理
你是编排者。只做拆解、分派与汇总，不亲自修改文件。

任务：{{任务}}
可用子代理：{{侦察 / 规划 / 实现 / 审查}}

请：
1. 拆成 3–6 个可独立验收的子任务。
2. 为每个子任务指定代理、输入、输出格式与验收标准。
3. 标出依赖关系与可并行部分。
4. 汇总时只保留结论、冲突与未决项，不粘贴过程。

不要派发职责重叠的任务。
没有匹配的提示词。试试更短的关键词，或重置筛选。

测试与迭代

提示词的效果不是「感觉更好」，而是在固定任务集上的可重复结果。

阶段做什么产出
建任务集收集 20–50 个真实输入，覆盖正常/边界/异常可重复的测试集
定评分用规则（格式/字段）+ 人工或模型评分（准确性/可读性）Rubric 与通过线
A/B只改一个变量，跑同一批输入差异与显著性
回归把通过的样本固化，模型或提示词变更后重跑防退化
成本记录 token、延迟、失败重试单位任务成本
一个常见错误 拿一个例子调到满意就上线。提示词往往在第二个、第三个分布外输入上崩掉；测试集比「再改一版」更有价值。
05

注意事项

安全

  • 把网页、文件、工具返回当不可信输入，防提示词注入
  • 不要在提示词里放密钥、客户数据、内部地址
  • 让 Agent 执行工具时，权限最小化

质量

  • 模型与版本会改变结果，换模型要重测
  • 提示词越长不一定越好，约束要可执行
  • 要求「不确定就标注」，减少编造
版权与合规 开源仓库的提示词也有许可证差异；商用前确认授权。不要直接复制含个人信息、内部系统说明或未公开数据的提示词。
