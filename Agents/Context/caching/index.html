缓存：同一段前缀，第二次为什么更便宜

从 GPU 里的 KV cache，到 API 层的前缀缓存，再到语义缓存与工具结果缓存——它们都叫「缓存」，但缓存的东西、失效条件、省钱方式完全不同。搞混了，就会出现「明明开了缓存，账单没降、延迟没变」。

01

先分清四层缓存

「缓存」在不同层解决不同问题。越靠前越省钱，也越容易出错。

层缓存什么命中条件省什么主要风险
精确响应缓存完整响应请求字节完全一致全部计算与 token个性化/时效性内容被错误复用
语义缓存问题 → 答案embedding 相似度超阈值全部计算假命中、跨用户泄露
前缀缓存前缀的 K/V 或计算结果从 token 0 起完全一致输入费、prefill 时间前缀一变全失效
KV cache每层 K/V 张量同一序列持续 decode重复计算显存占用、被驱逐
关键区别：KV cache 是「推理过程中不重复算」，前缀缓存是「跨请求不重复算」，语义缓存是「跨问题不重复答」。它们不是同一个东西，也不能互相替代。
02

KV cache：模型内部到底缓存了什么

要理解前缀缓存为什么快，先要理解 Transformer 生成时重复计算了什么。

2.1 一次生成的两个阶段

阶段做什么并行性主要成本
Prefill把整段输入一次性算完，得到每层、每个 token 的 K/V高，整段并行算力；与输入长度近似线性/二次相关
Decode每次生成 1 个 token，读取历史 K/V，算注意力串行，逐 token显存带宽；与已生成长度相关

没有 KV cache 时，每生成一个新 token 都要把前面所有 token 的 K/V 重算一遍，复杂度会爆炸。KV cache 把已算过的 K/V 存下来，decode 时直接读。

KV 显存 ≈ 2 × 层数 × KV 头数 × head_dim × 序列长度 × 每元素字节数

2 代表 K 和 V。GQA/MQA 通过减少 KV 头数来降低显存；量化则降低每元素字节数。具体数值取决于模型结构，不是「每个 token 固定多少 KB」。

2.2 为什么还会「分块」

早期实现要求 KV 连续存放，长序列会碎片化、浪费显存。PagedAttention 把 KV 切成固定大小的 block，用 block table 做逻辑到物理的映射，类似操作系统的分页：

  • 按需分配：生成到哪分到哪，不必预占最大长度；
  • 共享前缀：多个请求的相同前缀可以指向同一批物理 block，写时复制；
  • 可驱逐：显存紧张时按 LRU 回收，后续命中再重算。

这也是 vLLM 的 prefix caching 与 SGLang 的 RadixAttention 的基础：把「相同前缀」的 KV 复用起来，而不是每个请求都从零 prefill。

2.3 KV cache 救不了什么

它不减少输入 token 的计费。在按 token 计费的 API 里，KV cache 是厂商内部的事；你能看到的是「缓存读取 token」这一项。它也不加速 decode：输出仍然要一个 token 一个 token 生成，长输出的时间省不掉。

所以判断收益时要看瓶颈：如果 TTFT（首 token 延迟）占主导、输入很长，缓存有效；如果输出很长、decode 占主导，缓存对总延迟的帮助有限。

2.4 自托管时的三个开关

  • Prefix caching：vLLM 的 --enable-prefix-caching（新版本默认开启），按 block hash 复用。
  • 显存比例：--gpu-memory-utilization 决定能给 KV cache 多少空间；开太大影响其他进程，太小频繁驱逐。
  • 块大小与调度：block size、最大并发序列数、chunked prefill 都会影响命中率与尾延迟。

自托管还要考虑「缓存感知路由」：同一个前缀尽量落到同一个副本，否则每个副本都冷启动。网关层的 consistent hashing 或 prefix-aware routing 就是干这个的。

03

Prompt caching：API 层的前缀缓存

厂商把「前缀的 KV」或「前缀的计算结果」存起来，下一次同样前缀直接复用。你看到的是更低的输入价和更短的 TTFT。

3.1 命中要求：从第一个 token 开始完全一致

缓存不是「相似就命中」，而是按块做哈希，并且后一块的哈希包含前一块：

3.2 三种接入方式

方式代表怎么用控制粒度
显式断点Anthropic在消息块上加 cache_control，标记可缓存前缀的结束位置高：自己决定缓存到哪
自动前缀OpenAI、DeepSeek前缀超过最小长度自动缓存，无需改请求中：结构决定命中
显式缓存对象Google Gemini创建 CachedContent，设置 TTL，请求时引用高：可跨请求复用大段材料
自托管vLLM、SGLang开启 prefix caching / RadixAttention高：可调块大小、显存、路由

3.3 计费模型

以 Anthropic 的公开模型为例（数字会变，务必查当前文档）：

  • 缓存写入：5 分钟 TTL 约为基础输入价的 1.25×；1 小时 TTL 约为 2×。
  • 缓存读取：约为基础输入价的 0.1×。
  • TTL：默认 5 分钟，命中通常会刷新；也有 1 小时选项。
  • 最小长度：按模型有门槛（常见 1024 / 2048 / 4096 tokens），太短不缓存。
  • 断点数：一条请求最多若干个 cache_control 断点（当前为 4 个）。

事实 倍率与门槛来自 Anthropic 文档，具体数值随模型与时间变化。推断 其他厂商的「缓存折扣」逻辑类似，但计费单位与 TTL 不同，不能直接套用倍率。

写入不是免费的。如果同一前缀在 TTL 内只被用一次，缓存写入的 1.25× 会比不缓存更贵。盈亏平衡见第 6 节。
04

什么会让缓存失效

前缀缓存只有一条铁律：从第一个 token 到断点，必须逐字节、逐 token 完全一致。

4.1 失效原因清单

变更影响范围说明建议
系统提示改一个字全部块哈希从改动点起全变版本化发布，别做微调式热改
开头放时间戳 / 请求 ID / 用户名全部，且每次都写每个请求前缀都不同移到末尾或用工具查询
工具 schema 增删或改描述该块及之后工具定义通常在前缀里工具集冻结；变更走版本
JSON key 顺序不稳定包含该 JSON 的块序列化结果不同 → 哈希不同固定 key 顺序、稳定序列化
多轮对话追加新消息不影响旧前缀追加是缓存友好的保持只追加，不重写历史
编辑/删除早期消息从修改点起全部后续 token 位置与内容都变避免回改历史
压缩 / 摘要历史全部新摘要替换了旧前缀接受一次冷启动，之后重新积累
换模型或模型版本全部缓存按模型隔离固定版本；灰度时分开统计
换租户 / 组织全部厂商侧通常按组织隔离不要把租户信息拼进共享前缀
TTL 过期全部空闲超过 TTL 需重写按访问频率选 TTL；定时保活
自托管路由到别的副本该副本本地KV 缓存在各自 GPU 上前缀感知路由 / 会话粘性

4.2 多轮对话的缓存友好写法

友好

  • 只追加新的 user / assistant / tool 消息；
  • 系统提示、工具定义、示例保持稳定；
  • 把动态状态放在最后一条消息；
  • 断点放在「系统 + 工具 + 示例」之后。

不友好

  • 每轮重排消息、重写摘要；
  • 把「当前时间/剩余预算/用户名」塞进系统提示；
  • 按模型输出动态改工具列表；
  • 每轮都做一次全量压缩。
把缓存当成「前缀的指纹」：你改的不是一段文字，而是从那一刻起所有后续 block 的哈希。设计 prompt 时先问：哪些内容在多次请求间真的不变？把它们放前面。

4.3 断点放哪

  • 系统 + 工具定义 + 固定示例之后：这是最常见的稳定前缀；
  • 大段共享材料之后：比如同一份规范、同一份代码库说明，被多个请求复用；
  • 不要放在用户问题之后：那部分每次都变，缓存没有意义；
  • 断点数量有限（Anthropic 当前 4 个），优先覆盖「最长且最稳定」的段。
05

语义缓存与工具缓存：省得更多，也更容易错

这两类缓存不在模型内部，而在你的应用层。它们的收益更大，但正确性责任也完全在你。

5.1 精确响应缓存

对「完整请求」做哈希，命中就直接返回旧响应。适用条件很苛刻：

  • 输出确定（temperature=0，且模型/版本固定）；
  • 不含个性化、时间敏感、权限相关内容；
  • 请求 key 必须包含：模型版本、完整 prompt、工具定义、参数（temperature/top_p/max_tokens）、租户。

常见于：文档问答、固定分类、离线批处理。不要用于「我的订单」这类带身份的问题。

5.2 语义缓存

把用户问题做 embedding，在缓存里找相似问题；相似度超过阈值就复用答案。它解决的是「换了说法但意思一样」。

适合不适合必须做
FAQ、产品说明、稳定政策个性化、账户状态、实时价格按租户分区，禁止跨用户共享
高重复、低风险的问答多轮对话中的指代与上下文阈值 + 置信度 + 回退到模型
成本敏感的公开内容法律、医疗、财务建议TTL、版本号、审计抽样

最大的风险是「假命中」：问题相似但关键条件不同（不同地区、不同套餐、不同时间），复用了错误答案。缓解手段：

  • 把关键实体（地区、产品、版本）纳入 key 或过滤条件，而不是只靠向量相似；
  • 设置较高的相似度阈值，并对命中做抽样人工审计；
  • 命中后仍让模型做一次「是否适用」的校验（成本低于全量生成）；
  • 政策变更时按版本整体失效，不要等 TTL。

5.3 工具结果缓存

Agent 的大量 token 花在工具返回上。缓存工具结果通常比缓存模型响应更安全，因为结果是「事实」，只要 key 与时效正确。

key = tenant + tool_name + tool_version
    + normalized_args（排序后的 JSON）
    + 影响结果的环境（region / dataset / commit）

value = { result, fetched_at, ttl, source_version }
策略  = TTL + 负缓存 + single-flight（防击穿）
  • 只缓存幂等读：查询、文件读取、搜索可以；下单、发消息、改配置不要（除非有幂等键）。
  • 负缓存要短：404/空结果可以缓存，但 TTL 要远短于成功结果，避免「刚创建却一直查不到」。
  • 防击穿：同一 key 并发未命中时只放一个请求出去，其余等待结果。
  • 带版本：代码 commit、数据集版本、政策版本变化时主动失效。

5.4 检索缓存

缓存「查询 → 文档 ID/片段」而不是「查询 → 最终答案」。索引更新、权限变化、文档删除时按文档 ID 失效；权限必须作为 key 的一部分，否则会把无权文档带给用户。

5.5 一张表总结

缓存key典型 TTL主要风险推荐场景
精确响应完整请求 hash分钟–小时个性化/时效错配确定性批处理
语义embedding + 实体过滤 + 租户小时–天假命中、泄露FAQ、公开文档
工具结果工具 + 参数 + 版本 + 租户秒–小时脏读、权限查询、读文件、搜索

06

成本：什么时候缓存反而更贵

缓存写入要花钱，命中才省钱。复用次数不够，缓存就是负收益。

6.1 三个公式

不缓存：C₀ = N × T × p
缓存：C₁ = (W × T + (N − 1) × R × T) × p
盈亏平衡：N* = ceil( W / (1 − R) )

T = 前缀 token 数，N = 同一 TTL 内复用次数，p = 每 token 基础输入价，W = 写入倍率，R = 读取倍率。未计 TTL 过期后的重写、缓存存储费与输出费用。

代入 Anthropic 的 5 分钟档（W = 1.25，R = 0.1）：N* = ceil(1.25 / 0.9) = 2。也就是说，同一前缀在 TTL 内至少用 2 次才划算。1 小时档（W = 2）则要 3 次。

6.3 两个容易忽略的成本

  • 写入放大：如果前缀每个请求都变，你会在每个请求上付 W 倍写入，却没有一次命中。监控 cache_creation 与 cache_read 的比值，正常应远小于 1。
  • 过期重写：TTL 内没有请求，下一次又要付写入费。低频前缀不适合短 TTL；可以定时保活，或干脆不开缓存。
判断标准：同一条稳定前缀，在 TTL 窗口内的平均复用次数是否 ≥ N*。低于它，缓存只会让账单更贵。
07

提高命中率：结构比参数重要

缓存命中率不是调出来的，是 prompt 结构决定的。下面这些做法，比换模型或调 TTL 更有效。

7.1 把 prompt 分成「冷/热」两段

[稳定前缀 · 可缓存]
  系统角色与硬约束
  工具定义（顺序固定、描述稳定）
  固定示例（顺序固定）
  共享材料（规范/代码库说明/政策全文）
--- cache_control 断点 ---
[动态后缀 · 每次不同]
  当前时间、用户画像、会话状态
  检索结果、工具输出
  本轮用户问题
  输出格式要求

原则：越稳定越靠前，越动态越靠后。不要把「当前时间」放在第一行，也不要按用户拼接系统提示。

7.2 稳定序列化

  • 工具定义按固定顺序输出，不要依赖 map 的遍历顺序；
  • JSON 序列化固定 key 顺序（sort_keys 或 schema 顺序）；
  • 浮点数、空值、默认值的表示要一致；
  • 不要在工具描述里拼版本号、时间戳、环境名。

7.3 多租户与前缀隔离

如果每个租户有不同系统提示，最省的做法不是「拼一个大前缀」，而是按租户分前缀：每个租户的第一段稳定内容独立缓存。厂商侧通常按组织隔离；自托管要自己在 key 里加 tenant。

不要为了「共享缓存」把 A 租户的数据放进 B 租户也会用到的前缀。省下的钱远小于一次数据泄露的代价。

7.4 自托管：缓存感知路由

  • 同一个前缀尽量路由到同一个推理副本（consistent hashing / prefix-aware router）；
  • 会话粘性：多轮对话固定副本，避免每轮换机器导致本地 KV 失效；
  • 副本预热：部署后先用常见前缀打一遍，避免冷启动；
  • 监控每副本的 prefix hit rate，而不是全局平均。

7.5 开启顺序

  1. 先量：当前 cache_read / cache_creation / 输入 token 占比；
  2. 再改结构：稳定前缀、动态后置、固定序列化；
  3. 再设断点 / 开自动缓存；
  4. 最后调 TTL、路由、保活；
  5. 每次改动跑同一组请求，比较命中率、TTFT、单任务成本。
08

安全与多租户：缓存是共享内存，不是私有变量

缓存把「一次计算」复用给「多个请求」。只要 key 设计错一次，就可能把 A 的数据给到 B。

8.1 威胁与控制

威胁怎么发生控制
跨租户泄露语义缓存或响应缓存未按租户分区，key 只含问题文本key 强制包含 tenant / user scope；缓存层做命名空间隔离
缓存投毒攻击者诱导系统缓存一段恶意内容，后续请求复用只缓存可信来源；外部内容不进入可复用前缀；写入前校验
过期政策政策/价格更新后，旧答案仍在 TTL 内内容版本号进 key；发布时主动 purge
敏感数据落盘把密钥、身份证、病历写进缓存缓存前脱敏；禁止缓存秘密；加密与访问审计
权限提升检索缓存未包含权限，复用了用户无权看的文档权限作为 key 或过滤条件；命中后再做一次授权检查
时序侧信道共享前缀的命中/未命中时间差，可能暴露某些内容是否存在敏感场景按租户隔离缓存；不要把秘密放进共享前缀
不可审计不知道某次回答来自缓存还是模型响应里带 cache_hit / source；记录 key 版本

时序侧信道在多数业务里不是首要风险，但只要缓存跨安全域共享，就值得在威胁模型里写一笔。推断

  "auth_scope": "role:support"     // 权限相关
}

少一个维度，就可能多一次错误命中。宁可多失效，也不要错复用。

8.3 清理与轮换

  • 政策发布、模型升级、工具变更时，按版本前缀批量 purge；
  • 语义缓存保留「原始问题 + 答案 + 来源 + 命中次数」，便于审计与回滚；
  • 定期抽样人工复核语义命中的正确率；
  • 缓存日志与模型调用日志使用同一个 trace ID，能追到「为什么返回了这个」。
不要把「缓存命中率」当成唯一 KPI。命中率 99% 但答案错，比命中率 0 更糟。正确性、时效性、隔离性要先于命中率。

度量与排障

缓存问题几乎都能从四个数字看出来：读了多少、写了多少、命中率、首 token 延迟。

9.2 排障顺序

现象先查常见原因处理
命中率 0前缀是否逐字节一致开头有时间戳/用户名；工具顺序变了；低于最小长度动态内容后置；固定序列化；加长稳定前缀
命中率突然下降最近一次发布系统提示、工具 schema、模型版本变了回滚或接受一次冷启动后重测
成本没降反升写入/读取比每个请求都写、TTL 太短、复用次数低于盈亏平衡延长稳定前缀；调 TTL；关掉无收益的缓存
TTFT 没变输出长度 / decode 占比瓶颈在 decode，不在 prefill别指望缓存；优化输出长度或流式
答案不一致语义缓存命中记录相似问题被错误复用；政策过期提高阈值；加实体过滤；版本失效
只有部分副本命中路由与副本指标自托管未做前缀亲和会话粘性 / 前缀感知路由

9.3 上线检查

  • 稳定前缀里没有时间戳、请求 ID、用户名；
  • 工具定义与 JSON 序列化顺序固定；
  • 断点覆盖了最长且最稳定的段；
  • TTL 与访问频率匹配，低频前缀不强行缓存；
  • 缓存 key 含租户、模型、提示词版本、工具版本；
  • 有 purge 流程与语义命中抽样审计；
  • 同时监控命中率、成本、TTFT 与正确性。

来源与口径

结构性事实与倍率来自以下公开材料，访问日期 2026-10-31：

  • Anthropic: Prompt caching：显式断点、TTL、写入/读取倍率、最小长度。
  • OpenAI: Prompt caching：自动前缀、最小长度与增量、prompt_cache_key、usage 字段。
  • Google Cloud: Context caching：隐式/显式缓存、TTL 与存储计费。
  • DeepSeek: Context caching：自动缓存与命中计价。
  • vLLM: Automatic prefix caching：块哈希、复用与驱逐。
  • SGLang: RadixAttention：用 radix tree 管理前缀复用。
  • PagedAttention / vLLM 论文：KV cache 分页与共享。

口径

  • 事实 倍率、TTL、最小 token 数等来自厂商文档；数值会调整，落地前请核对当前版本。
  • 推断 盈亏平衡、命中率目标、排障顺序是工程推导与经验，不是厂商承诺。
  • 不同厂商的「缓存」实现不同：有的缓存 KV，有的缓存前缀计算结果，有的只做请求级去重；不要假设行为一致。
  • 本文的成本模型只覆盖输入侧缓存，不含输出费用、网络、存储与向量检索成本。
