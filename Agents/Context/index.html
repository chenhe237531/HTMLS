上下文工程：把注意力当预算

同一个模型，喂 8 千 token 能稳定完成的任务，喂 8 万 token 反而开始忘事、跑偏、重复犯错。Agent 的能力上限，常常不是模型决定的，而是你每一步让它「看见什么、按什么顺序看见」决定的。

01

前提：上下文是预算，不是仓库

几乎所有上下文问题，都源于一个错误类比：把 context window 当成「可以随便塞的数据库」。

1.1 三个硬约束

  1. 注意力是有限的。模型不是均匀地读第 100 个和第 100,000 个 token。Anthropic 把它称为「attention budget」：每多一个 token，都在消耗预算，边际收益递减。
  2. 复杂度是 n²。Transformer 里每个 token 都要和其他 token 建立关系；上下文翻倍，关系数变四倍。窗口变大不等于理解变强。
  3. 训练分布偏短。模型见过的短序列远多于长序列，对「跨越很长距离的依赖」经验更少。
结论：「把窗口扩到 1M」只推迟了问题，没有消除问题。你要优化的是信噪比，不是召回率。

1.2 Context rot 不是玄学

Chroma 在 2025 年 7 月发布的 Context Rot 报告测试了 18 个模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3），结论不是「长上下文完全不能用」，而是更麻烦的一件事：

  • 即使任务难度不变、只增加无关内容，性能也会随输入变长而下降；
  • 加入一个干扰项就能拉低表现，四个干扰项进一步放大；
  • 问题与答案的语义相似度越低，长上下文下退化越明显；
  • 模型家族行为不同：有的倾向拒答，有的倾向编一个「听起来合理」的错答案。

这意味着：「相关信息在上下文里」是必要条件，不是充分条件。呈现方式、干扰项、位置，都会改变结果。Chroma 还发现，在他们的实验里打乱 haystack 的顺序反而提升了表现——这提醒我们不要凭直觉定「最佳排版」，要测。

更早的 Lost in the Middle 也观察到类似现象：关键信息在开头或结尾时利用得最好，被埋在大段中间时明显下降。所以「放进去」之后，还要问「放在哪」。

事实 报告与可复现实验：Context Rot（2025-07-14）。推断 具体任务上的最优排布必须自测，不能把论文结论当模板。

1.4 一个自检问题

如果你不能用一句话说清「这一步模型必须看到哪几条信息」，你就还没有做上下文设计，只是在堆输入。

下面所有的技巧，都是围绕这句话展开的：先决定「必须看到什么」，再决定「怎么放、放多少、放多久」。

02

解剖一次请求：钱和注意力花在哪

把一次 Agent 调用拆开，你会发现大部分 token 并不在「你写的 prompt」里。

2.1 八层结构

层内容典型占比失控信号
指令系统提示、角色、硬约束、输出格式1–3%越写越长，规则互相冲突
工具工具名、描述、JSON Schema3–10%工具几十个，模型选错或重复调用
任务当前目标、验收标准、上下文边界<1%目标模糊，模型自行发挥
证据检索文档、网页、日志、代码片段10–30%top-k 越来越大，引用率却下降
历史用户轮次、助手推理、工具调用与结果30–60%长会话后半段开始重复、遗忘
草稿计划、TODO、中间结论2–5%只存在模型脑子里，压缩后丢失
记忆跨会话事实、偏好、经验2–10%越积越多，过期信息不清理
输出预留回答、思考、工具参数的生成空间5–15%没预留，最后被硬截断

占比是经验区间，不是规范。推断 但它揭示了一个常被忽略的事实：历史 + 工具结果通常占一半以上，而它们恰恰是最容易清理的部分。

2.2 推荐顺序（以及为什么）

  1. 稳定前缀：系统指令 → 工具定义。放在最前，且不要插入时间戳、随机 ID、动态用户信息。
  2. 任务与约束：当前目标、验收标准、禁止事项。越靠近生成点，越容易被遵守。
  3. 证据：带来源、带时间、带适用范围；无关的先删，不要靠模型自己筛。
  4. 历史：从旧到新；旧轮次可摘要，最近 3–5 轮保留原文。
  5. 草稿 / 记忆：只放「这一步会用到的」，不要把整个 NOTES.md 灌进去。
  6. 输出指令：格式、长度、停止条件。放在最后，紧贴生成。
缓存视角：prompt caching 命中依赖前缀完全一致。把动态内容放前面，会让整段缓存失效——这既是性能问题，也是成本问题。

2.3 一个 200k 窗口的预算示例

指令 3k 工具 8k 证据 20k 历史 60k 草稿 5k 输出预留 16k 空闲 88k
不要把空闲吃满。Agent 的下一步往往要调用工具、读文件、看报错。没有余量，第一次工具返回就会触发截断或强制压缩。
03

六种操作：所有技巧都能归到这六类

Anthropic 的实践覆盖四类核心动作：外置、检索、压缩、隔离。工程上再加两个：排序与清除。

01外置 Write

把状态写到上下文之外：文件、对象存储、数据库、任务队列。上下文里只留「句柄」——路径、ID、URL、查询。

何时：内容超过一屏、需要跨轮/跨会话、可被重新读取。
代价：多一次工具调用；要保证句柄可解析。

02检索 Select

按需取回最小片段：RAG、grep/glob、SQL、工具搜索、网页抓取。关键是先给索引，再给内容。

何时：语料大于窗口、答案稀疏、需要引用。
代价：检索质量决定上限；top-k 过大会稀释。

03压缩 Compress

摘要、去重、结构化、只留结论与引用。压缩不是「写短」，而是「保留可继续工作的最小状态」。

何时：接近窗口上限、历史重复、工具输出冗长。
代价：有损；过度压缩会丢掉后来才显现的关键细节。

04隔离 Isolate

让子任务在独立上下文里完成，只回传结论、证据与失败原因。子 Agent、代码执行、独立工具进程都属于此类。

何时：多源调研、探索性搜索、大日志分析、并行子任务。
代价：协调成本；回传契约设计不好会丢信息。

05排序 Order

把目标、硬约束、当前状态放在开头和结尾；把参考材料放中间并分段。利用首因与近因，而不是平均铺开。

何时：长上下文、多个约束、需要精确遵守格式。
代价：没有通用最优解，需要按任务评测。

06清除 Evict

删掉过期、可重取、低价值的内容：旧工具结果、已解决的报错、重复轮次、失效记忆。保留「调用发生过」的记录。

何时：工具密集、长会话、上下文接近阈值。
代价：模型可能重复调用；需要可重取保证。

3.1 操作之间的关系

你想解决的问题优先操作不要先做
窗口要爆了清除旧工具结果 → 压缩历史 → 外置直接换更大窗口的模型
模型找不到重点减少证据 → 重排 → 明确任务加更多「请注意」
长任务丢状态外置计划文件 → 结构化笔记让模型「记住」
多源信息打架隔离子 Agent → 证据表 → 来源分级把所有原文塞进主上下文
工具调用太贵精简工具集 → 懒加载 schema → 输出契约给每个工具都加详细说明

3.2 一条判断规则

能重新取到的，就不要常驻；能算出来的，就不要复述；能交给子上下文做的，就不要放进主上下文。

这三句话覆盖了 80% 的优化空间。剩下的 20% 是排序、格式和评测。

04

场景配方：不同 Agent，不同的上下文结构

没有通用最优解。但每个场景都有一条「常驻什么、按需取什么、什么时候清」的主线。

编码 Agent：索引 + 局部读取 + 计划文件

常驻：仓库约定（构建/测试/风格）、当前任务与验收标准、最近编辑过的文件路径、当前失败测试的尾部输出。

按需：符号表/文件树（只给名字和大小）、grep 结果、按行号读取的片段。不要预加载整个仓库，也不要把 embedding 索引当唯一入口——grep 往往更快更准。

外置：PLAN.md（目标、步骤、已完成、卡点）、NOTES.md（踩过的坑）、补丁文件。压缩后至少保留计划与最近 5 个文件。

清除：成功命令的完整输出只留摘要；失败的测试只留首个错误与堆栈关键行；重复的 ls/cat 结果。

失败信号：反复读同一个文件、重复同一处修改、忘记已通过的测试、把旧报错当新问题。

客服 / 业务 Agent：短历史 + 政策片段 + 结构化档案

常驻：角色与语气、可执行动作清单、禁止承诺、当前工单状态、用户身份与套餐（摘要，不是全量档案）。

按需：政策条款的精确片段（带版本号与生效日期）、订单/账单的字段级查询结果、历史工单的结论。

清除：已解决的中间查询、重复的身份校验、超过 N 轮的寒暄；工具返回只留字段与状态码。

触发：当轮次超过 8–10 轮或工具结果累计超过预算 30% 时，把「用户诉求 + 已确认事实 + 待办」压成结构化卡片。

失败信号：引用过期政策、重复问用户已提供的信息、承诺了没有权限的动作。

深度研究：子 Agent + 证据表 + 写作分离

结构：主 Agent 只维护「问题树 + 证据表 + 结论草稿」；每个来源或子问题交给子 Agent，回传「结论 + 3 条证据 + 来源 + 置信度」。

证据表字段：主张、来源链接、原文摘录（≤ 2 句）、日期、支持/反驳、可信度。原文留在文件里，上下文只放摘录与链接。

清除：抓取失败的页面、重复转载、与问题无关的段落；子 Agent 的完整推理轨迹不回传。

失败信号：结论没有引用、同一来源被重复计入、把摘要当原文、越写越像综述而没有回答原问题。

长时运维 / 自动化：状态机 + 时间线 + 运行手册

常驻：当前事件状态（正常/降级/故障）、SLO、值班约束、最近一次变更、下一步动作与回滚方案。

外置：事件时间线（时间、观察、动作、结果）、运行手册链接、仪表盘查询语句。上下文里只放最近 10 条与未解决项。

压缩：把「已排除的假设」单独列出，避免多轮后重复排查；保留每个动作的前置条件与影响范围。

失败信号：重复执行同一检查、忘记回滚、把历史告警当当前状态、在没有审批的情况下扩大影响面。

多工具助手：少而清晰的工具 + 惰性 schema

原则：同时暴露的工具控制在 5–7 个；名字动词化、边界互斥；工具描述写「什么时候用」，不是「它做了什么」。

按需：工具多时用工具搜索/分组加载，先给目录，再加载 schema；MCP 服务器按域拆分。

输出：统一返回 summary + items + truncated + total + artifact_path + next_cursor，让模型能决定「继续取」还是「够了」。

失败信号：选错工具、参数幻觉、同一工具反复调用、忽略 truncated 直接下结论。

多 Agent 协作：契约式回传，不共享轨迹

主线：主 Agent 持有目标与最终决策；子 Agent 只拿到「任务 + 输入句柄 + 输出契约」，不继承完整对话。

回传：结论、证据、未决问题、产物路径、失败原因。禁止回传「我思考了 30 步」的流水账。

共享：共享只读事实库（带版本），不共享各自的工作草稿；写操作通过主 Agent 串行化。

失败信号：子 Agent 重复主 Agent 的工作、回传内容互相矛盾、主上下文被多个子轨迹撑爆。

05

压缩与记忆：最容易被做坏的两件事

压缩不是「让模型写短一点」，记忆也不是「把聊天记录存起来」。它们是两种不同的状态管理。

5.1 三种手段，别混用

手段作用范围解决什么不解决什么
Compaction整段对话（含工具调用、旧摘要）历史整体膨胀工具结果占比过高、跨会话记忆
Tool-result clearing只替换旧 tool_result 块工具输出堆积，且大多可重取对话本身冗长、推理重复
Memory上下文之外的文件/库跨会话、跨任务的状态当前窗口内的注意力稀释

顺序很重要：先清工具结果（无损、可重取），再压缩历史（有损），最后才考虑加记忆（引入长期维护成本）。反过来做，往往会用记忆去弥补本该清理的垃圾。

5.2 压缩保留什么、丢弃什么

必须保留

  • 目标、验收标准、硬约束
  • 已做的决策与理由
  • 失败过的尝试（避免重跑）
  • 未解决的问题与下一步
  • 关键文件路径、命令、ID、URL
  • 用户明确表达的偏好与禁止项

可以丢弃

  • 寒暄、确认、重复复述
  • 完整的工具输出（保留路径/摘要）
  • 已解决的报错全文
  • 重复的推理与自我纠正
  • 与当前目标无关的旁支讨论
  • 过期的中间结论
有损是必然的。Anthropic 的建议是：先在复杂 trace 上把压缩提示词调到「高召回」，确保不漏关键信息，再逐步提高精度、删冗余。不要一上来就追求短。

5.3 一个可用的压缩提示词

把下面的工作记录压缩成一份“可继续工作”的状态摘要。

必须保留：
- 当前目标与验收标准
- 硬约束、用户偏好、禁止事项
- 已做出的决策及理由
- 失败过的尝试及失败原因（避免重复）
- 未解决的问题、风险、待确认项
- 关键文件路径 / 命令 / ID / URL
- 下一步的具体动作

可以丢弃：
- 寒暄与重复内容
- 完整工具输出（改为：一句话摘要 + 产物路径）
- 已经解决的报错细节

输出格式（Markdown，≤ 800 tokens）：
## 目标
## 约束
## 已完成
## 失败与原因
## 未决
## 关键引用
## 下一步

把「≤ 800 tokens」换成你预算的比例，但不要只写「尽量简短」——那会触发下面的问题。

5.4 上下文坍塌：越摘要越笨

ACE（Agentic Context Engineering，2025）记录了一个典型故障：让模型反复「整体重写」累积上下文，它会不断压缩，直到把知识压没。论文里的例子是：第 60 步还有 18,282 tokens、准确率 66.7；下一步被压成 122 tokens，准确率掉到 57.1，比不 adapt 的基线 63.7 还差。

两个根因：

  • 简洁偏置（brevity bias）：优化目标奖励短而通用的表述，丢掉了领域细节、工具用法、失败模式。
  • 上下文坍塌（context collapse）：每次都整体重写，信息在多次有损变换中单调流失。

ACE 的做法值得借鉴：把上下文当成不断演进的 playbook，用「生成 → 反思 → 策展」分离角色，并且做增量 delta 更新，而不是每次重写全文。论文报告在 agent 类基准上 +10.6%，金融类 +8.6%，且适配延迟与 rollout 成本下降。

事实 数据与机制见 Agentic Context Engineering（arXiv:2510.04618）。推断 对多数团队，先做到「增量更新 + 保留引用」就能避开大部分坍塌，不必完整实现三角色架构。

5.5 什么时候压：别等到 100%

水位（占可用窗口）动作原因
50–60%开始整理：去重、清旧工具结果、把结论写进笔记此时还有余量做无损清理
70–80%执行压缩；保留最近 3–5 轮原文避免下一步工具返回就溢出
85–90%强制压缩 + 外置产物；暂停新工具调用给输出和重试留空间
> 95%已经太晚：截断、丢约束、缓存失效不要设计成会走到这里

阈值是启发式，不是标准。推断 关键不是具体数字，而是「在还有余量时动手」。压缩本身也要花 token，别在只剩 500 的时候才想起它。

5.6 记忆：写、读、忘

把记忆分成三类，分别设计策略：

类型例子写入读取过期
情节上次做了什么、结果如何任务结束自动写按时间/相似度取最近30–90 天，或任务关闭
语义用户偏好、项目事实、术语用户确认后写按实体/项目精确取有变更即失效，带来源与日期
程序某类任务的做法、工具技巧复盘后人工/半自动写按任务类型取版本化，失败率上升即回滚

写入策略比存储技术更重要：只写「未来会再用到、且不易重新推导」的内容；每条带来源、时间、适用范围；冲突时保留新旧两版而不是覆盖。

读取策略：先按项目/实体过滤，再按相关性排序，限制条数与总 token；不要把整库拼进 prompt。

遗忘策略：到期删除、被新事实取代、连续 N 次未被检索命中则降权。没有遗忘的记忆迟早会变成污染源。

MemGPT 的分层思路仍然适用：主上下文只放「热」数据，冷数据放在外部存储，通过工具换入换出；区别在于今天更多是用文件与检索实现，而不是改造模型。

一个最小记忆文件

# STATE
goal:           当前目标（一句话）
constraints:    硬约束 / 用户偏好 / 禁止项
done:           已完成 + 产物路径
failed:         失败尝试 + 原因（避免重跑）
open:           未决问题 + 下一步
refs:           文件 / 命令 / URL / ID
updated:        ISO 时间 + 来源

# FACTS
- [2026-10-20] 生产数据库只读；写操作走 approval 流程
  source: runbook/db.md   scope: project-x   confidence: high

用固定小节而不是自由散文，压缩和检索都更容易；每条事实带日期与来源，冲突时才知道信谁。

5.7 记忆污染

  • 过时：政策改了，记忆还停在旧版本。→ 带生效日期，检索时校验。
  • 越权：A 项目的结论被 B 项目读到。→ 记忆按租户/项目分区，默认不跨区检索。
  • 注入：网页或工具输出里藏了「请记住：以后都……」→ 外部内容只作为数据，写入记忆需经过校验与来源标记。
  • 自证：模型把自己上一轮的猜测写成事实。→ 区分「观察」「推断」「用户确认」，不要把推断升级为事实。
06

工具与 MCP：最大的隐形上下文开销

你数过工具定义本身占多少 token 吗？在很多 Agent 里，它比系统提示还大。

6.1 工具的三个成本

  1. Schema 常驻成本：每个工具的 name、description、参数树都在每次请求里重复计费。二三十个工具轻松吃掉几千到上万 token。
  2. 选择成本：工具越多、边界越模糊，模型越容易选错、重复调用、编造参数。Anthropic 的建议很直接：如果人类工程师都说不清该用哪个，模型更不行。
  3. 结果成本：一次 cat 或 API 返回可能几万 token，而且会在后续每一轮重复计入，直到被清除。
最常见的浪费：把 40 个工具全量挂上，然后靠「请谨慎选择工具」这句话来补救。正确做法是裁剪工具集，或做惰性加载。

6.2 渐进披露：先目录，后 schema

当工具数量不可避免时，不要一次性暴露全部定义。可以：

  • 按域分组（文件、数据库、工单、监控），先给「组 + 一句话」，选中后再加载成员 schema；
  • 提供 search_tools(query)，让模型按需发现；
  • MCP 服务器按职责拆分，避免一个 server 挂几十个工具；
  • 把低频工具放到「扩展包」，通过显式命令启用。

这与 Skill / 插件系统的「渐进披露」是同一个思路：先让模型知道「有什么」，再让它决定「看哪个」。

6.3 工具输出契约

工具返回不是给人看的日志，而是给模型做决策的输入。建议统一结构：

{
  "summary": "在 12 个文件中找到 3 处调用；2 处缺少错误处理",
  "items": [ { "path": "src/a.ts", "line": 42, "note": "..." } ],
  "truncated": true,
  "total": 137,
  "next_cursor": "eyJvZmZzZXQiOjIwfQ==",
  "artifact_path": "/artifacts/search-7f3c.json"
}
  • summary 先给结论，模型不必解析全部条目；
  • truncated + total 让模型知道「不完整」，避免基于残缺结果下结论；
  • next_cursor 支持继续取，而不是一次全量；
  • artifact_path 把大结果外置，需要细节时再读。

坏输出 vs 好输出

坏：原样回灌

... 8,000 行构建日志 ...
（模型不知道哪里重要，
  也不知道有没有截断）

好：摘要 + 定位 + 句柄

summary: 构建失败，首个错误在
  src/api.ts:118，类型不匹配
first_error: TS2322 ...
tail: 最后 20 行
total_lines: 8123
artifact: /logs/build-7f3c.txt

6.4 工具结果清除策略

结果类型保留清除条件
文件内容摘要 + 路径 + 读取范围超过 2–3 轮，且文件可重读
搜索结果前 10 条 + 总数已选定目标后
命令输出退出码 + 首错 + 尾 20 行下一步不再依赖
API 响应关键字段 + 状态码 + 请求 ID已提取所需字段
报错堆栈错误类型 + 首个业务帧已修复或已定位

清除时保留 tool_use 记录（「调用发生过」），只替换 tool_result 的内容为占位符。这样模型知道「我查过」，需要时可以再查，而不是以为自己没查过。

07

多 Agent：上下文隔离，而不是上下文复制

多 Agent 最大的价值不是「更多智能」，而是「更干净的上下文」。如果每个子 Agent 都继承完整对话，你只是把成本乘了几倍。

7.1 为什么隔离有效

  • 注意力：子 Agent 只面对一个子问题，信噪比高；
  • 并行：多个来源可以同时处理；
  • 失败隔离：一个子任务跑偏，不会污染主上下文；
  • 成本：子上下文可以便宜模型、短提示、用完即弃。

但代价是：信息在边界上会丢。所以真正的设计重点是「回传契约」，而不是「怎么拆」。不要用多 Agent 去做一件单文件修改——拆分的协调成本会大于收益。

7.2 回传契约

字段内容反例
answer对子问题的直接回答（1–3 句）「我经过了仔细分析……」
evidence≤ 5 条，带来源与原文摘录整页复制
artifacts产物路径 / ID / 查询语句把产物内容贴回来
open未决问题、冲突、需要主 Agent 决策的点隐藏不确定性
failed试过但失败的方法及原因只报成功
confidencehigh / medium / low + 依据一律 high

7.3 Handoff 模板

## TASK
给子 Agent 的唯一目标（一句话）+ 验收标准

## INPUT
只给必要的句柄：文件路径、查询、URL、范围
不要给完整对话历史

## CONTRACT
返回：answer / evidence(≤5) / artifacts / open / failed / confidence
不要返回：推理轨迹、完整工具输出、与任务无关的背景

## BOUNDARY
允许访问的资源、禁止的动作、时间/成本上限

7.4 共享什么，不共享什么

共享

  • 只读事实库（带版本与来源）
  • 任务 ID、产物目录、术语表
  • 全局约束与安全策略

不共享

  • 各自的完整对话与推理轨迹
  • 未验证的中间猜测
  • 各自的工作草稿（除非显式发布）

写操作要让主 Agent 串行化或加锁，否则两个子 Agent 会各自基于旧状态修改，最后互相覆盖。

08

度量与成本：别用「感觉变好了」验收

上下文优化最容易自欺： prompt 变短了，但任务成功率也掉了。必须同时看效果与成本。

8.1 六个指标

指标定义为什么重要粗略目标
tokens / 成功任务总输入输出 token ÷ 成功任务数把「便宜」与「有效」绑在一起持续下降，成功率不降
上下文利用率已用 ÷ 可用（扣除输出预留）过高会触发退化与截断决策点 40–70%
工具输出占比tool_result token ÷ 总输入最大的可清理项< 25%
压缩频率 / 压缩比每任务压缩次数；压缩前后 token 比过频说明结构有问题；过狠会丢信息按任务类型设基线
缓存读取占比cache_read ÷ 总输入直接反映前缀稳定性与成本稳定负载下越高越好
长会话漂移同一问题在第 1 轮 vs 第 N 轮的答案一致性捕捉「越聊越忘」关键约束不丢

目标值是经验区间，不是行业标准。推断 先建立自己的基线，再谈优化幅度。

8.2 让缓存站在你这边

  • 稳定前缀：system → tools → 固定示例。不要在前面插时间戳、请求 ID、用户名。
  • 动态内容后置：把用户输入、检索结果、当前状态放在稳定前缀之后。
  • 少改动：每次请求都改一个空格，也会让缓存失效；模板变更要按版本发布。
  • 长 TTL 要匹配访问模式：低频任务开长缓存可能只付写入费不命中。
反直觉但常见：为了「更个性化」把用户画像放在系统提示最前面，结果每个用户都缓存不中，成本翻倍。把个性化放到后缀，或做成工具查询。

展开阅读：缓存机制——KV cache、前缀缓存、语义缓存与盈亏平衡的计算。

8.4 做一次像样的 A/B

  1. 固定任务集：30–50 个代表性任务，含长会话、工具密集、多源冲突三类。
  2. 固定预算：比较「同一 token 预算下谁做得更好」，而不是「谁用的 token 更多」。
  3. 扫上下文长度：把历史/证据从 25% 扫到 100%，画成功率曲线，找拐点。
  4. 记录失败类型：忘约束、引用错、重复调用、过早结论、格式错。不要只看总分。
  5. 看成本：tokens / 成功任务、缓存命中、压缩次数。
  6. 回归：每次改提示词、工具、压缩策略，都重跑同一套。
最小可行评测：20 个任务 × 3 种上下文配置 × 2 次重复。一个下午能跑完，足以发现「塞得越多越差」的拐点。
09

反模式与上线清单

9.1 十二个反模式

  1. 窗口大就全塞把「能放下」当成「该放下」，用长度换确定性。
  2. 历史无限保留每轮都带全部对话，成本和稀释一起涨。
  3. 摘要套摘要反复整体重写，信息单调流失，最后比不压缩还差。
  4. 工具输出原样回灌几万行日志进入后续每一轮，且大多可重取。
  5. top-k 越大越好召回上去了，精度和引用率下来，干扰项变多。
  6. system prompt 写成手册规则互相冲突，模型抓不住重点。
  7. 所有工具都挂上schema 常驻、选择困难、参数幻觉。
  8. 多 Agent 传全量轨迹隔离失效，成本乘倍数，信息反而更乱。
  9. 记忆只写不清过期事实越积越多，最终污染所有回答。
  10. 动态内容放前缀缓存全失效，延迟和成本双输。
  11. 靠自然语言让模型记住没有外部状态，压缩或重启就丢。
  12. 只测单轮不测长会话漂移，上线后才发现越聊越差。

9.2 上线前清单

清单可打印；勾选状态不会保存，刷新后重置。

9.3 一页决策树

如果你的任务是…先做什么再做什么
单轮、可一次完成直接做，别建记忆只保留必要证据与输出格式
多轮、同一会话计划文件 + 最近 3–5 轮原文清理旧工具结果；到阈值再压缩
超出窗口外置产物 + 压缩历史把「可重取」的内容全部改成句柄
多来源、需交叉验证子 Agent 隔离 + 证据表主 Agent 只做整合与决策
跨会话、长期外部记忆 + 检索写入校验、分区、过期与冲突处理
低延迟 / 低成本稳定前缀 + 小工具集缓存友好排序；按需加载 schema
最后一条建议：先把「清理」做好，再谈「记忆」；先把「句柄」做好，再谈「压缩」；先把「回传契约」做好，再谈「多 Agent」。顺序反了，复杂度和成本都会先于效果到来。
