怎么选 MCP

MCP 的数量不是问题，问题是你用「排行榜」代替了「试用」。这套方法只做一件事：把「感觉不错」变成可复现的判断——一个真实任务、一张打分卡、48 小时。

适用 Trae / OpenCode / Pi 耗时 每次 1–2 小时 产出 保留 / 观察 / 淘汰

01

先问三个问题

不要从目录开始，从你的任务开始。装之前先回答这三问，能挡掉一半「装了但不用」的 MCP。

问题怎么判断结论
1 · 频率
一周会用几次？		低于每周 1 次 → 临时用一次就够，别常驻低频：写进笔记，需要时再装
高频：值得进入候选
2 · 读写
只读够不够？		查询、检索、看图、读日志 → 只读足够只读：直接试
需要写：先过权限与回滚
3 · 敏感度
数据能不能出本机？		代码、客户数据、密钥、生产库敏感：本地或容器
公开：可接受托管
最常见的错误 因为「这个 MCP 很火」而安装，而不是因为「我明天要做的事需要它」。判断标准永远是：没有它，我的哪个具体任务会变慢？

三个入口，三种用途

发现

Glama / PulseMCP / mcp.so：先收集 3–5 个候选，不要只看第一名。

核对

官方 Registry / GitHub：确认发布者、仓库、最近更新。

安装

Trae 市场 / Docker Catalog：走客户端或容器，配置可回滚。

候选池规则 一次最多保留 3 个候选。超过 3 个说明需求还没想清楚，先回到第 01 节。
03

五个红灯

下面任意一条命中，直接淘汰或降级为「临时用」。它们比评分更省时间，因为是否定项，不是加减分。

1 · 没有源码或发布者不明

你无法判断它会把数据发到哪。只给一个安装命令、没有仓库的，先跳过。

2 · 半年没更新，issue 堆着

MCP 协议与客户端都在变，旧实现很容易在权限或传输上出问题。

3 · 默认要全局密钥、权限过大

「一个 token 访问你所有仓库」这种设计，出事时无法收敛。

4 · 一次暴露几十个工具

工具列表会长期占上下文，还会让模型选错工具；没有裁剪能力的慎用。

5 · 文档只有截图，没有配置与限制

说明它自己也没想清楚边界；出问题时你只能猜。

灰色地带：需要关闭安全设置

要求忽略 TLS、关闭沙箱、给 root 的，一律不进入常驻清单。

04

打分卡

给候选打分，权重可以按你的偏好理解；0 = 很差，5 = 很好。低于 60 分就别花时间试用了。

需求匹配权重 30% · 它是否直接解决你的任务
3
维护活跃权重 20% · 最近提交、issue 响应、版本发布
3
权限可控权重 20% · 能只读吗？能限 scope 吗？
3
来源可信权重 15% · 发布者、源码、签名、社区口碑
3
上下文成本权重 10% · 工具数量与返回体积，越轻越高
3
可替代性权重 5% · 换掉它的成本，越低越好
3
60
限场景试用 只在明确任务里开，别常驻

默认值都是 3 分，所以是 60。把每个维度按真实情况调一遍再看结论。

每个维度怎么打分

维度0–1 分3 分5 分
需求匹配只是「可能有用」能覆盖任务的一半正好解决，且比手做快
维护活跃半年无提交几个月内有更新近期有版本与 changelog
权限可控只能全权限能选 scope只读可用，能按工具裁剪
来源可信无仓库个人仓库、有 issue官方/组织维护，有签名或审计
上下文成本几十个工具全开十来个工具少量精准工具，返回结构化
可替代性深度绑定有同类可换换掉只是改一行配置
分数只是过滤器 80 分也可能在你的任务上失败，60 分也可能刚好够用。打分只决定「值不值得花 30 分钟试用」，不替代试用。
05

48 小时试用

用真实任务，不用 demo。给自己一个硬性窗口，到点必须做决定，避免「装了再说」变成长期负担。

  1. 选一个真实任务

    最好是你这周本来就要做的事，例如「查这个库的最新 API」「定位这个报错」「读这张表的结构」。

    不要用「你好世界」式验证
  2. 限时 30 分钟装好并跑通

    从安装到第一次成功调用，超过 30 分钟就先记为失败，不要熬夜调配置。

    记录：耗时、卡在哪一步
  3. 第一轮只用只读

    能只读就只读；需要写时单独开一次，并确认可回滚。

    记录：是否有不可逆操作
  4. 记录五个指标

    见下表。指标比「感觉」可靠。

    产出：一行试用记录
  5. 48 小时后决定

    保留（常驻）/ 观察（按需开）/ 淘汰（卸载并记下原因）。

    避免无限期「再看看」

五个指标

指标怎么量通过线
首次成功耗时从点安装到第一次有效结果≤ 30 分钟
失败次数安装/调用失败并重试的次数≤ 1 次
上下文增量工具列表长度 + 单次返回体积不挤掉原有任务上下文
输出可验证性能否用文件、行号、URL 或查询结果核对可核对，不是「看起来对」
卸载成本删配置、撤权限、清凭证要多久≤ 5 分钟
A/B 测试更可靠 同类候选（例如 Chrome DevTools 与 Playwright）用同一个任务各跑一次，比较「首次成功耗时」和「输出可验证性」。差异往往比宣传页更明显。
出现这些就停 要求把生产库写权限、要求上传整份代码、要求关闭校验、或者失败后无法回滚——立刻卸载，不要「先用着看」。
06

好不好用，看什么

不要看 star 数，也不要看宣传页。看它在你的任务上，是否降低了「从想到做」的摩擦。

客观信号（可观察）

  • 一次安装成功，不需要改系统设置
  • 工具名与描述能让你猜出该传什么参数
  • 报错会指向具体原因，而不是只有堆栈
  • 返回结构化内容（JSON / 列表 / 带行号），而不是整页 HTML
  • 权限可缩小，只读模式真的能用

主观信号（诚实记录）

  • 第二次遇到同类任务，你愿意再打开它
  • 不用回头翻文档就知道怎么用
  • 出错时你敢让它重试，而不是自己接管

如果三条都做不到，它对你就是「不好用」，与它在别人那里多受欢迎无关。

一个实用判断 如果它需要你在 prompt 里额外解释「怎么用这个工具」，说明工具本身没设计好；好的 MCP 应该让模型自己就能选对。

场景速查

下面是常见场景的起点，不是结论。每个都配了一个「验证任务」，装完直接照着跑。

场景首选备选验证任务

别一次装一排 同一个场景先只留一个。两个浏览器 MCP 同时开，工具列表会重复、模型会犹豫，最后你想关掉一个却发现配置找不到了。
