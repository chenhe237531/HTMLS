x402 Protocol2026-10-31

x402：把付款变成一次请求

它把闲置了三十年的 HTTP 402 Payment Required 真正用起来：客户端请求 → 服务器报价 → 客户端签名付款 → 重试 → 拿到资源。没有账号，没有 API Key，没有月度账单。

01

它是什么

一句话：x402 是“按请求付费”的开放支付标准。它不发明新传输，而是把支付谈判塞进标准 HTTP 请求里；钱主要用稳定币在链上结算。

对买家

Agent 或程序遇到 402，读报价、签名付款、重试请求。不需要注册账号，也不需要预存余额（取决于钱包）。

对卖家

在路由上声明价格与收款地址；验证签名后交付资源。可以把链上验证与结算交给 facilitator。

对生态

协议中立、无协议费；任何链、任何资产、任何实现都能接入，只要双方接受同一组支付要求。

从 Coinbase 到基金会

  1. 2025-05 · Coinbase 提出 x402

    把 HTTP 402 与稳定币支付结合，面向 API、内容与 AI Agent 的按次付费。

  2. 2025-09 · 与 Cloudflare 发起基金会

    宣布共建 x402 Foundation，并把它接入 Agents SDK 与 MCP Server。

  3. 2026-04 · 协议捐给 Linux Foundation

    Coinbase 完成贡献，x402 进入厂商中立治理。

  4. 2026-07 · 基金会正式运营

    40 家成员，包括 AWS、Google、Visa、Mastercard、Stripe、Shopify、Cloudflare、Solana Foundation 等。

它不是「另一个 AP2」 AP2 解决的是「用户授权 Agent 花钱」的凭证与举证；x402 解决的是「这笔钱怎么在 HTTP 请求里付掉」。两者可以叠：用 AP2 授权，用 x402 结算。
02

为什么需要它

现有 API 商业化假设「有人注册、有人管密钥、有人月底付款」。当调用方是 Agent 时，这三件事都不成立。

传统方式对 Agent 的问题x402 的做法
注册账号 + API KeyAgent 无法完成注册、验证码、邮件确认无账号；钱包签名即身份
订阅 / 预充值低频调用不划算，余额管理复杂按次付费，用多少付多少
月度发票 / 对公转账延迟高，无法完成「这一次调用」请求内完成支付，秒级到分钟级结算
信用卡扣款需要人、需要卡、拒付与风控稳定币转账，无拒付

典型场景

  • 付费 API / 数据接口，按调用计费
  • 内容与文档付费墙
  • Agent 调用付费工具（搜索、抓取、推理、存储）
  • MCP Server 按工具调用收费
  • 算力 / 模型推理转售

它真正改变的事

把「商务流程」压缩进「协议交互」：过去要销售、合同、开票、对账，现在是一次 HTTP 往返。对机器来说，这是唯一可行的节奏。

先泼一盆冷水 x402 让「收钱」变简单，但没有让「合规、退款、对账、税务」消失。它适合高频小额、可自动化的场景，不适合所有交易。
03

一次支付的全过程

核心只有五步。注意一个关键顺序：默认是「先验证、后干活、再结算」，不是先扣钱。

STEP 1请求资源 STEP 2402 + 报价 STEP 3签名付款 STEP 4验证 STEP 5结算交付

点击任一步跳到详细说明；五步全部在下方展开。

Client Resource Server Facilitator │ │ │ │── GET /paid ─────────────────────▶│ │ │◀─ 402 + PAYMENT-REQUIRED ─────────│ (scheme / network / amount) │ │ │ │ │── GET /paid + PAYMENT-SIGNATURE ─▶│── POST /verify ──────────────▶│ │ │◀─ valid ──────────────────────│ │ │ （执行业务逻辑 / 生成内容） │ │ │── POST /settle ──────────────▶│ │ │◀─ tx hash ────────────────────│ │◀─ 200 + resource + PAYMENT-RESPONSE│ │

Step 1 · 请求资源

客户端就是一个普通 HTTP 请求，可能是浏览器、脚本，也可能是一个 Agent 的工具调用。没有任何预注册。

请求
GET /api/weather?city=shanghai HTTP/1.1
Host: api.example.com

Step 2 · 402 报价

服务器返回 402 Payment Required，把「怎么付」放在 PAYMENT-REQUIRED 头（Base64 编码的 JSON）。v2 的核心字段如下。

PAYMENT-REQUIRED（解码后）
{
  "x402Version": 2,
  "accepts": [{
    "scheme": "exact",
    "network": "eip155:8453",
    "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
    "amount": "10000",
    "payTo": "0xSeller...",
    "maxTimeoutSeconds": 60,
    "extra": { "name": "USDC", "version": "2" }
  }]
}

amount 是代币最小单位，10000 = 0.01 USDC（6 位小数）；network 用 CAIP-2 标识链。

Step 3 · 签名付款

客户端按 accepts 选一种，构造支付载荷并用钱包签名。以 EVM 的 exact 为例，签名的是 EIP-3009 的 transferWithAuthorization——此时钱还没有动，只是一个可验证的授权。

关键设计：签名 ≠ 转账 授权里包含金额、收款方、有效期与一次性 nonce。facilitator 不能把钱转去别处，也不能重复使用同一笔授权——这是「trust minimizing」的核心。

Step 4 · 验证

服务器可以本地验证，也可以把载荷与自己的支付要求 POST 到 facilitator 的 /verify。验证检查：签名有效、金额足够、收款方匹配、未过期、未重复。

验证通过后才执行业务逻辑。如果业务失败，默认流程下尚未结算，不会扣钱；但若启用「先结算」的 upfront 流程，失败就没有协议级退款。

Step 5 · 结算并交付

服务器调用 /settle（或自行上链），facilitator 提交交易、等待确认、返回交易哈希；服务器返回 200 与资源，并在 PAYMENT-RESPONSE 里附带结算回执。

超时 ≠ 失败 HTTP 超时或响应丢失，不能证明支付没发生。服务端要做幂等与去重；客户端重试前应检查回执，否则可能重复付款。这是 x402 落地最容易踩的坑之一。
04

技术拆解

三个头，v1 与 v2 不同名

用途x402 v2x402 v1（旧）方向
报价 / 支付要求PAYMENT-REQUIREDX-PAYMENT（402 响应体）Server → Client
签名后的支付载荷PAYMENT-SIGNATUREX-PAYMENTClient → Server
结算回执PAYMENT-RESPONSEX-PAYMENT-RESPONSEServer → Client

两版头名容易混。新项目直接用 v2 SDK，不要手写 Base64 拼接。

核心字段

字段含义例子
scheme计价方式exact / upto / batch-settlement
network结算网络（CAIP-2）eip155:8453（Base）、solana:5eykt…
asset代币合约 / 资产Base 上的 USDC
amount最小单位金额"10000" = 0.01 USDC
payTo收款地址卖家钱包或合约
maxTimeoutSeconds报价有效期60

三种计价方式

scheme怎么用适合注意
exact固定金额，一次授权一次结算按请求、按文章、按次工具调用最常见；默认「验证→执行→结算」
upto授权一个上限，按实际用量结算推理 token、带宽、可变工时客户端需信任卖家不会顶格扣
batch-settlement多笔合并结算，降低链上开销高频微支付引入批次延迟与对账复杂度

Facilitator：可选的“验证 + 结算”层

facilitator 不托管资金，只验证签名并代发链上交易，因此卖家不需要自己跑节点、管 gas、处理 nonce。

  • POST /verify：只验证，不上链
  • POST /settle：验证通过后提交链上交易
  • GET /supported：声明支持的 scheme / network / asset 组合

它可以公共托管、自建，也可以「自facilitate」（在资源服务器里直接做）。协议本身不强制。

链与资产 Coinbase CDP facilitator 支持 Base、Polygon、Arbitrum、Monad、World、Solana 等；其他 facilitator 覆盖 Avalanche、Stellar、NEAR、XRPL、Algorand 等。资产以 USDC 为主，EVM 侧通过 EIP-3009 / Permit2 授权。

扩展点

x402 核心只管付款，周边能力用扩展：发现（把付费端点登记到 Bazaar / x402scan）、收据（在响应头附加签名凭证）、gas 代付（facilitator 赞助）、认证（与现有身份体系组合）。

06

优势与局限

优势

  • HTTP 原生：不需要新传输、新端口、新协议栈
  • 无账号：钱包签名即身份，Agent 可自主完成
  • 按次计价：微支付成本可控，不用预充值
  • 稳定币结算：跨境、秒级、可编程
  • facilitator 可选：卖家不必自己跑链上基础设施
  • 多链多资产：同一套流程接 EVM / Solana 等
  • 中立治理、零协议费：降低锁定风险

局限

  • 加密门槛：钱包、gas、USDC、链选择仍是门槛
  • 无拒付：链上转账不可撤销，纠纷处理靠链下
  • 合规与税务：KYC/AML、跨境、开票、审计不解决
  • 延迟：需等待链上确认，不适合极低延迟
  • facilitator 集中：默认路径依赖少数服务商
  • 波动与兑换：稳定币脱锚、法币出入金成本
  • 发现割裂：Bazaar / x402scan / 自定义目录并存

安全：论文指出的问题

2026 年的一篇测量论文（arXiv:2607.19545）对主流 facilitator 做了黑盒测试，指出验证与结算实现中的若干风险：重复结算、签名与请求绑定不足、facilitator 超时后的状态不一致。作者已负责任披露，部分问题被修复。

上线前必须做的四件事 ① 每笔支付做幂等键与去重；② 把支付证明绑定到具体请求（资源、金额、收款方）；③ 超时按「未知」处理，不要直接判失败；④ 不要手写头解析，使用官方 SDK。
07

与其它支付协议

x402 只占一层。把它和 AP2、UCP、ACP Commerce、MPP 放在一起看，关系就清楚了。

协议解决什么支付单位授权 / 凭证结算状态（2026-10）
x402请求级付款通道每次 HTTP 请求钱包签名（EIP-3009 等）稳定币，多链生产可用
AP2用户授权 Agent 花钱的凭证一次购物 / 支付Mandate（VDC），支付方式无关可接卡、x402 等v0.2，FIDO 标准化
UCP购物流程：发现、能力、结账一次结账依赖 AP2 等取决于支付层早期访问
ACP（Commerce）产品 feed + 对话内结账一次订单平台账号Stripe 等规范在，入口收缩
MPPHTTP 支付头（Cloudflare 支持）按请求WWW-Authenticate: Payment可插拔新兴

它们怎么组合

用户授权（AP2 Mandate） │ ▼ 购物流程（UCP：发现 → 结账） │ ▼ 支付通道（x402：402 → 签名 → 结算） │ ▼ 链上 USDC（Base / Solana / …）
一句话区分 AP2 问「谁允许花这笔钱」，x402 问「这笔钱怎么在请求里付掉」，UCP 问「买什么、怎么结账」。三者不是竞品。
08

场景与风险

适合

按次付费的 API

数据查询、抓取、翻译、OCR、地理编码。一次几分钱，用多少付多少。

Agent 工具与 MCP

让 Agent 自己为工具调用付费，不必由人预先充值或发 Key。

内容付费墙

单篇文章、报告、数据集；读者或 Agent 一次付费后取走。

算力与推理转售

代理上游模型 / GPU，按 token 或按秒计费（可用 upto）。

微服务与代理

聚合多个上游能力，按调用加价转售，结算自动完成。

跨境小额

没有本地支付通道、金额小、频率高的地区或场景。

不适合

  • 高客单、需要争议处理：链上转账不可撤销，退款与拒付要靠链下。
  • 只能用信用卡 / 对公转账：合规或财务流程不接受稳定币。
  • 极低延迟：等待链上确认会拖慢请求。
  • 强监管行业：KYC/AML、跨境、税务需要额外方案。
  • 免费为主的产品：为了 1% 的付费请求引入钱包与链，得不偿失。

风险清单

风险表现缓解
合规KYC/AML、跨境、税务、发票缺失与持牌服务商 / 法币出入金合作；保留链下票据
价格波动非稳定币贬值；稳定币脱锚只用主流稳定币；短报价有效期
密钥安全Agent 钱包被盗即资金被盗限额钱包、会话密钥、人工审批阈值
重复结算重试导致同一授权被多次提交幂等键、请求绑定、facilitator 去重
facilitator 停机无法验证或结算，服务不可用多 facilitator 备份 / 自建
退款协议不定义退款业务层补退款流程与凭证
链选择买家没有该链资产或 gas支持多链；gas 代付；清晰报价
别把它当「无摩擦收款」 x402 去掉的是账号与 API Key，不是合规与财务。上线前先问：谁承担退款？谁开发票？谁做制裁名单筛查？答不上来就先别接真钱。

上手与成本

最小路径：一个 Express 路由 + 一个付费客户端，跑在 Base Sepolia 测试网。

安装（v2 包名）
pnpm add @x402/core @x402/express @x402/fetch express
server.js（示意，字段以官方 quickstart 为准）
import express from "express";
import { paymentMiddleware } from "@x402/express";

const app = express();

app.use(paymentMiddleware({
  "GET /weather": {
    accepts: [{
      scheme: "exact",
      price: "$0.001",
      network: "eip155:84532",        // Base Sepolia
      payTo: process.env.PAY_TO
    }]
  }
}, {
  facilitatorUrl: "https://x402.org/facilitator"
}));

app.get("/weather", (req, res) =>
  res.json({ weather: "sunny", temperature: 21 })
);

app.listen(4021);
client.js（示意）
import { x402Client, wrapFetchWithPayment } from "@x402/fetch";

const api = wrapFetchWithPayment(fetch, x402Client);
const res = await api("http://127.0.0.1:4021/weather");
console.log(await res.json());
上线前 测试网用 x402.org facilitator 即可；主网不要默认用它，选生产 facilitator 或自建。先用 GET /supported 确认你要的 scheme + network + asset 三元组真的支持——「协议支持」不等于「这家实现支持」。

10

趋势判断

1 · 治理已中立，采用仍集中

协议进 Linux Foundation，但交易与 facilitator 高度集中。未来两年看「第二梯队 facilitator」能否起来。

2 · 多链，但会收敛

Solana 在 2026 年拿下多数月交易量，Base 仍是 EVM 默认。长期可能收敛到 2–3 条结算链。

3 · 与传统支付融合

Visa、Mastercard、Stripe、Adyen 都在基金会里。方向不是「取代卡」，而是让卡/银行账户也能作为 x402 的支付工具。

4 · 与 AP2 / UCP 组成栈

授权（AP2）+ 购物（UCP）+ 结算（x402）。单用 x402 适合 API 计费，进入零售则必须补授权与争议。

5 · 竞争来自「协议内建」

MPP 用 WWW-Authenticate: Payment 做类似的事；云厂商也可能把计费直接内建。x402 的优势是先发与生态。

6 · 安全会成为分水岭

重复结算、绑定不足、facilitator 信任问题已被论文点名。谁先补齐审计与凭证，谁拿到企业客户。

我的判断 短期（1 年）：x402 是「机器微支付」的事实标准，适合 API / 工具 / 内容的长尾计费。中期（2–3 年）：如果法币通道与合规补齐，它有机会成为 Agent 调用付费服务的默认结算层，但仍会与卡组织、AP2 授权层共存，而不是取代它们。
