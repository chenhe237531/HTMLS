AP2：让 Agent 代付可验证

AP2 不处理支付。它解决的是更难的那件事：当 Agent 替你买东西时，用什么凭证证明「你确实授权了这笔钱」，以及出事时谁能举证。

01

它是什么

一句话：AP2 是代理支付的“授权与问责层”。它定义一套签名的、可选择性披露的凭证（Mandate），把「用户同意买什么、花多少」变成商户和支付网络都能验证的证据。

它管

用户授权、代理边界、支付凭证、收据、争议证据。

它不管

商品目录、购物车、结账流程、清算与卡组织规则。

它依赖

商业协议（UCP）提供流程，A2A 提供消息，卡或 x402 提供资金轨道。

时间线

  1. 2025-09-16 · Google 发布 AP2

    与支付生态共同提出「Agent 代付」的授权模型，最初面向人在场的结账。

  2. 2026-04-28 · v0.2 发布

    补齐 Human Not Present（人不在场）流程，加入预算约束、Python SDK 与 Android 示例。

  3. 2026-04-28 · 捐赠给 FIDO Alliance

    规范开发转入 FIDO 的 Agentic Authentication 与 Payments 两个工作组；GitHub 仓库转为示例与 SDK。

  4. 2026-10 · 仍处早期

    没有已确认的生产部署，规范 v0.2 之后未再发版；采用取决于 FIDO 的标准化进度。

一句话区分 AP2 问「谁允许花这笔钱」；UCP 问「买什么、怎么结账」；x402 问「这笔钱怎么付掉」。三者是层，不是竞品。
02

三个问题

人点「购买」时，这些问题由界面、银行风控和卡组织规则共同回答。Agent 代付时，它们必须有新的答案。

问题传统支付Agent 代付的难点AP2 的答案
谁授权本人点击 + 3DS / 生物识别Agent 不是法律主体，无法“签字”用户签名的 Mandate，绑定到具体结账
买了什么商户页面 + 订单确认Agent 可能在过程中替换商品或金额Checkout Mandate 绑定商户签名的结账对象与哈希
出事谁举证卡组织拒付流程链上或代理交易缺少责任链Mandate + Receipt 形成可验证的审计链

AP2 的核心主张

不要相信 Agent，要验证它出示的凭证。每个动作都由上一环签名授权，任意一环被篡改都能被发现。

代价

商户、钱包、收单机构都要改流程；凭证格式、密钥管理、争议处理都需要行业共识——这也是它进展慢的原因。

03

角色

AP2 把「一笔代理支付」拆成六个角色。每个角色只验证自己该验证的部分，避免任何一方既当运动员又当裁判。

User
发起意图、设定边界、在可信界面上签名。可以全程在场，也可以只签一次「开放授权」后离开。
Shopping Agent
找商品、建购物车、与商户结账、组装并提交 Mandate。它是被授权方，不是授权方。
Merchant
生成商户签名的 Checkout（JWT），验证 Checkout Mandate 是否覆盖这笔结账，然后交付。
Credential Provider
钱包 / 发卡行。验证 Payment Mandate 与支付工具，签发支付 token。
Merchant Payment Processor
收单机构。验证支付 token 与 Payment Mandate，完成授权与清算。
Trusted Surface
用户设备上的可信界面（手机 / 钱包 App），负责展示结账内容并采集用户签名。

规范从「验证职责」角度概括为五类处理角色；User 与 Trusted Surface 是授权链的起点。

04

两种模式

Human Present · 人在场

用户看到最终订单与金额，直接在可信界面上签名。最接近今天的「确认支付」。

  • 用户签 closed Checkout / Payment Mandate
  • 商户验证后交付
  • 争议时凭证最直接

Human Not Present · 人不在场

用户先签一份带约束的 open Mandate（商户范围、商品、预算、有效期），Agent 在边界内自主完成，并自己签 closed Mandate。

  • 验证方同时拿到 closed 凭证与适用的 open 约束
  • 超出约束会失败，可升级为 Human Present
  • 适合抢票、补货、限时购买

Human Not Present 的流程

User Shopping Agent Merchant Credential Provider / MPP │ 设定任务与边界 │ │ │ │── open mandates ────▶│ │ │ │ （预算/商户/有效期） │── 浏览、加购、结账 ──────▶│ │ │ │◀─ 商户签名的 Checkout ───│ │ │ │ 在 open 约束内签 closed │ │ │ │── Checkout Mandate ─────▶│ 验证约束与金额 │ │ │── Payment Mandate ──────────────────────────────────────▶│ 验证并签发 token │ │◀─ Checkout Receipt ──────│ │ │ │◀─ Payment Receipt ───────────────────────────────────────│ │◀─ 结果与凭证 ────────│ │ │
最容易误解的一点 「人不在场」不是「没有授权」，而是「授权被提前参数化」。Agent 只能在用户签过的约束内行动；超出就失败。约束之外的自由，协议不背锅。
05

Mandates：核心抽象

Mandate 是签名过的授权凭证，用 SD-JWT 承载，可选择性地披露字段。两类 Mandate × 两种形态，构成四种组合。

类型open（约束）closed（具体交易）给谁
Checkout Mandate用户允许的商品范围、商户、预算、时间窗绑定某一笔商户签名的结账（含金额与商品哈希）商户
Payment Mandate允许的支付工具、单笔/总额上限、有效期绑定该笔结账的支付授权Credential Provider、网络、MPP

配套还有两类回执：Checkout Receipt（商户签发，证明交付了什么）与 Payment Receipt（支付方签发，证明付了多少）。它们与 Mandate 串成完整证据链。

开放 Checkout Mandate（示意，字段以规范为准）
{
  "type": "checkout_mandate",
  "mode": "open",
  "constraints": {
    "merchants": ["shop.example.com"],
    "max_total": { "currency": "USD", "value": "120.00" },
    "items": ["sku:12345"],
    "expires_at": "2026-11-01T00:00:00Z"
  },
  "nonce": "base64url...",
  "signature": "SD-JWT..."
}

为什么用 SD-JWT

用户只向验证方披露与本次交易相关的字段：商户不需要看到你的全部预算，支付方也不需要看到商品细节。这是「最小披露」与「可验证」的折中。

不可伪造的绑定 Checkout Mandate 绑定的是商户签名过的结账对象（含价格、商品、商户身份的哈希）。Agent 改一个字段，哈希就对不上，验证失败。
06

验证与举证

角色验证什么失败时
MerchantCheckout Mandate 是否覆盖这笔结账：商户、商品、金额、时间拒绝结账，返回未满足的约束
Credential ProviderPayment Mandate 与支付工具、预算、有效期拒绝签发支付 token
Merchant Payment Processortoken 与 Payment Mandate 的一致性拒绝授权 / 清算
Network按卡组织规则复核（如适用）按现有拒付流程处理

争议时能拿出什么

用户侧

自己签过的 open/closed Mandate、Trusted Surface 的签名记录、支付回执。

商户 / 支付侧

商户签名的 Checkout、Checkout Receipt、Payment Receipt、验证日志。

这套证据链的目标不是「保证不吵架」，而是让吵架时有可验证的事实：谁在什么时候、授权了哪一笔、金额是多少。

仍未定义的部分 Mandate 的选择与匹配（Agent 如何挑出适用的 open Mandate）在 v0.2 中仍由实现方自行决定；Human Present 的审批链也有未决 issue。接入前要读当期规范，不要假设「协议会替你决定」。
07

与其它协议

AP2 是授权层，必须挂在别的流程与资金轨道上。它官方提供 A2A 与 UCP 两种扩展。

协议层与 AP2 的关系
UCP商业流程UCP 管发现、购物车、结账；AP2 作为支付扩展提供授权与凭证。官方称「无缝集成」。
A2AAgent 通信AP2 的示例与 SDK 通过 A2A 在 Agent 与商户之间传递消息。
x402支付轨道AP2 授权，x402 结算。官方有 Human Present / Not Present 的 x402 示例。
卡片 / PSP支付轨道原有卡组织与收单流程；AP2 把 Mandate 作为授权证据交给它们。
ACP（Commerce）商业流程同层竞争：OpenAI/Stripe 的结账流程，目前不以 AP2 为授权层。
MCP工具无直接关系；Agent 可用 MCP 找商品，但授权仍走 AP2。
流程层 UCP（发现 / 购物车 / 结账） 授权层 AP2（Checkout / Payment Mandate） 通信层 A2A（Agent ↔ Merchant / Agent） 资金层 卡组织 / PSP / x402 / 稳定币 工具层 MCP（商品检索、比价、工具调用）
组合示例 用户在 UCP 商户结账 → Agent 出示 AP2 Checkout Mandate → 商户验证 → Credential Provider 验证 Payment Mandate → 通过 x402 或卡完成结算 → 双方各留回执。
08

现状与局限

优点

  • 把「代理授权」变成可验证凭证，而不是口头承诺
  • 支持人不在场的预授权，且有明确边界
  • 最小披露（SD-JWT），隐私与验证兼顾
  • 支付方式无关，卡与稳定币都能接
  • 与 UCP / A2A 的集成路径清晰
  • 治理已交给 FIDO，避免单一厂商控制

局限

  • 没有已确认的生产部署（2026-10）
  • v0.2 之后未再发版，规范开发转入 FIDO，节奏未知
  • GitHub 仓库自 2026-04 后基本停更，仍有未决 issue
  • 商户、钱包、收单机构都要改造，落地成本高
  • Mandate 选择与匹配仍留给实现方
  • 不解决退款、拒付与客服流程
最该记住的一句 AP2 目前是一份「设计严谨、生态未起」的规范。它值得理解与预研，但不适合作为近期唯一支付方案。

时间线视角

2025 年 9 月发布，2026 年 4 月补齐人不在场并捐给 FIDO，到 2026 年 10 月仍无生产案例。对比 x402 的链上交易量，AP2 的瓶颈不在技术，而在「支付行业的多方协调」。

谁该关注

角色该做什么优先级
钱包 / 发卡行 / PSP实现 Mandate 验证与支付 token 签发；参与 FIDO 工作组高
大型商户 / 电商平台通过 UCP 接入，验证 Checkout Mandate；准备争议证据链高
Agent 平台集成 SDK，设计 open Mandate 的约束与升级路径中
企业采购 / 财务关注预算约束与审计价值，暂缓生产依赖中
API / 工具计费不需要 AP2，直接用 x402 或按次计费低
如果只做一件事 先用 x402 解决「收钱」，用 AP2 的思路（预算、商户白名单、单笔上限、凭证留痕）设计你自己的 Agent 支付边界。等 FIDO 出稳定版，再替换为标准化 Mandate。
