缓存按前缀匹配，一个字节变了，后面全部作废。稳定在前，易变在后。

第 05 / 17 篇 stack ronny Context 与工具 工程笔记 05

01它治什么病

系统提示、环境信息、skill 列表、工具定义、每轮上下文块和提醒，全都塞进每次请求。其中只要有一项每轮都变（比如把当前时间写进环境块），它后面的一切都无法命中缓存，首 token 变慢、成本变高。

02机制

  1. 抓一次真实请求（调试日志、代理，或拼装请求的代码），把用户消息之外的部分全列出来：位置、变化频率、token 数。
  2. 新会话首轮和后面某一轮各看一次，两者常常不一样。
  3. 逐项写一句“没有它，模型会……”。写不出来，就是删除候选。
  4. 按前缀缓存判断位置：稳定内容放前面，易变内容往后移；只写入历史、不再编辑的内容付一次费然后一直可缓存；只挂在当前请求上的内容永远不进缓存。
  5. 跑 8 项清单：前缀意识、必要性、位置、频率、精度、历史改写、恢复路径、测量方式。

03规则要点

环境块
不要把当前时间写进 # Environment，放进每轮的上下文块。
历史
已经写进历史的提醒不要再改，只影响未来轮次。
精度
只用需要的精度。位置对了之后，秒级时间戳仍然保证每次副本都不同。
请求级提醒
它们本来就不进缓存，控制的是触发频率，不要把它当成“保护前缀”。
恢复路径
删掉的东西会不会在压缩、会话恢复、subagent 里彻底消失？谁负责补回来？
测量
改动前后看缓存命中率、每轮成本、任务质量，而不是只看 token 数降了。
原文关键句（English）
Caches match on prefix. One changed byte invalidates everything after it. Stable first, volatile last.

04落到你的场景

可以直接用

opencode 每轮都会注入环境块和全部 skill 描述。把日期、会话 id、随机量这类字段从稳定前缀里挪出去，是零风险的改动；再逐个问 skill 描述是否值得每轮都带。

05边界与反例

别用过头

只能审计你能抓到请求的那一层；provider 的缓存策略和寿命不一定公开，结论要标明是推断。
