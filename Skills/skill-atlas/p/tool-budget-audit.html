审计工具占用的 Context

工具定义常驻、工具结果回灌，还顺带让模型选错工具。先量，再做减法。

第 04 / 17 篇 stack ronny Context 与工具 工程笔记 02

01它治什么病

MCP 装了一排、skill 装了一堆。每次请求都带着全部工具的名字、描述和参数 schema，用不用都付费；一次任务的中间结果又整段回到对话里；名字相近的工具还让模型反复选错。

02机制

  1. 先量：列出所有暴露给模型的工具并按来源分组，用 tokenizer 估每个定义的大小并求和（说明用的是哪个 tokenizer，它是相对量）。
  2. 记录一到两个代表任务的调用次数、由此产生的模型请求数、工具结果大小，以及哪些工具几乎每轮都用。
  3. 第 0 步做减法：按用户意图合并工具（列表/按标签筛/按作者筛可以是一个带参数的工具）、让名字和描述可区分、按领域分组、核心工具常驻。
  4. 第 1 步考虑 tool search：核心常驻，低频可搜索。召回要在自己的工具集上实测，干净基准上的结果不迁移。
  5. 第 2 步考虑 programmatic tool calling：大量数据过滤聚合、三个以上依赖调用、可并行的批量操作时才上。

03规则要点

两类成本
定义常驻（每轮都付）与中间结果回灌（每次调用都付，且每次往返都是一次完整请求）。
分工
tool search 主要省定义，PTC 主要省结果——别指望一个手段解决两个问题。
PTC 的边界
与用户交互、改会话状态、需要先读结果再决定下一步的工具（tool search、加载 skill）、浏览器/发布、spawn subagent，都留在顶层。
PTC 的纪律
程序内调用要走同样的校验、hook、权限和 UI；工具失败返回 error 结果而不是 throw，免得一个失败丢掉整段程序。
隐性回归
搜一遍按工具名硬编码的逻辑（提醒、计数、埋点），工具搬进程序后这些会静默失效。
顺序
三个手段是叠的：先把目录做干净，tool search 才有效；tool search 有效，PTC 才值得上。每步前后跑端到端 eval。
原文关键句（English）
Tools cost context in two ways, plus one side effect: definitions sit in context whether or not they are used; every call puts its full output back; similar names and vague descriptions make the model choose wrong.

04落到你的场景

可以直接用

你现在装了 13 个 skill 加 1 个 MCP。先把每个 skill 的 description 长度加起来（它们全部常驻），再决定哪些领域 skill 该按需加载、哪些描述该缩短到一句。

05边界与反例

别用过头

没有 tokenizer 时只能给相对值，不要编绝对数字。PTC 需要 harness 支持，opencode 目前没有，这一层先停在“做减法 + 按需加载”。
