mcode-stack · long-session-check

长会话自查

Context window 是工作台，不是仓库。压缩和 memory 都有损，重要状态要早点写进文件。

第 06 / 17 篇 stack ronny 长会话与长命令 工程笔记 03

01它治什么病

会话越走越长，agent 开始忘记前面定过的约束、重复问已经回答过的问题、把早先排除的方案又提一遍。压缩几次之后，它甚至会把错误的尝试写进摘要，于是错误变成了“共识”。

02机制

  1. 把上下文里的东西分三桶：丢弃（能重新取的：大文件、测试日志、搜索结果、废弃尝试）、摘要（只属于本次的故事：现在在哪、下一步、未决 bug）、落盘（丢了会痛的：决策与理由、进度、验收标准、长期规则）。
  2. 先把第三桶写进项目的进度/设计文档，或者用 handoff-doc。
  3. 再选下一步：同一任务只是历史长 → 压缩，并说明保留什么、丢掉什么；换任务 → 开新会话；压缩多次仍在漂 → 先写交接再重开；走错路 → 回滚到出错之前，别让错误尝试进入摘要。

03规则要点

三桶
能重新取回的一律丢弃；只属于本会话的做摘要；跨会话要用的必须落盘。
压缩的定位
压缩回答“现在装不下”，memory 回答“下次还记得吗”。两者都不是唯一的安全网。
手动压缩
要能接受指令：保留什么、下一步是什么。
回滚优先
方向错了就回滚，不要用压缩把错误尝试“洗白”成摘要。
设计审查
审 agent 时看 12 项：旧工具结果是否先清、调用与结果是否成对、决策是否落文件、自动压缩是否留足输出空间、压缩失败能否继续、压缩请求能否复用缓存、压缩是否只改模型所见、是否告知模型上下文是自动管理的、项目 memory 是否只放稳定规则、memory 是否分作用域、截断是否可见、人能否关闭。
原文关键句（English）
The context window is a workbench, not a warehouse. Compaction answers "it does not fit right now"; memory answers "will we remember next time". Both are lossy.

04落到你的场景

可以直接用

你做那个跨天的 HTML 方案时就是这套：把“信息架构为什么这么定、排除了哪两种导航方案”写进 docs/，然后放心开新会话，而不是硬扛一个 200 轮的对话。

05边界与反例

别用过头

Mode B 是审 agent 的压缩/memory 设计，不是审你的会话内容；12 项里有一部分你在客户端观测不到，只能标 unknown。

06关联

handoff-doc写交接文档重要状态不该只活在 context window 里。一页纸让人（或新会话）接着干。 context-tax-audit审计每轮的上下文税缓存按前缀匹配，一个字节变了，后面全部作废。稳定在前，易变在后。 trajectory-review回看 Agent 的轨迹通过的结果可能藏着脆弱的过程。看它怎么走到那儿，不只看它到没到。
