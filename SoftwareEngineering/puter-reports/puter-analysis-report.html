01

它到底是什么：三个同心圆

Puter 同时讲三个故事。分开看，才知道每个故事的成本。

对用户

一个浏览器入口

窗口、文件管理器、应用商店，以及记事本、表格、相机等自带应用。官方托管在 puter.com，也可以自建。价值在“一个入口”，不是某个单点功能。

对开发者

把后端压进一个 script

引入 Puter.js 后，纯前端可以调用账号、文件、KV、AI、Workers、Peer。没有 API key，费用走 user-pays：由终端用户自己的 Puter 账户承担。

对运维

一套完整的单机栈

Docker Compose 带 Caddy、Puter、MariaDB、Valkey、DynamoDB-local、S3（RustFS）。得到的是“单机接近生产”，不是高可用集群。

一句话

Puter 卖的是“把后端压缩成一个前端库”；自托管送的，是同一套后端背后的运维作业。

02

技术架构：不是一个网盘加登录框

后端按 Controller → Driver → Service → Store → Client 分层，扩展可以插入任意一层。这个结构比“浏览器操作系统”的营销词更能说明它想做什么。

横向示意图，可左右滑动查看。

实线：文档描述的层间依赖虚线：可选服务事件与推送通道（doc/push-client.md）未展开
一个值得注意的设计

文档把 actor.app 与 actor.effectiveApp 分得很清楚：前者是请求直接携带的应用身份，后者是最终生效的身份。对访问令牌类型的 Actor，读 app 而不是 effectiveApp 会得到“没有应用”，权限门禁会放行。这说明它按多租户系统在做，而不是个人网盘加个登录框。

层与职责

层位置职责
Controllerssrc/backend/controllers解析与校验输入、执行每路由的鉴权/限流/子域门禁、调用 Service、组织响应。
Driverssrc/backend/drivers/drivers/* 上的 RPC 外壳，例如 puter-kvstore、puter-chat-completion。
Servicessrc/backend/services业务逻辑，默认调用方已通过鉴权，不再重复做门禁。
Storessrc/backend/stores把客户端包装成领域形态：行、实体、KV 命名空间。
Clientssrc/backend/clientsSQL、Redis、S3、DynamoDB、邮件等协议适配器。
Extensionsextensions/旁路注册，可插入任意层；也可挂事件与路由。

来源：doc/architecture.md。依赖从上层流向下层，由 PuterServer 按 clients → stores → services → drivers → controllers 顺序实例化并注入。

能力面：它不只管文件

能力形态要点
文件puter.fs + S3用户文件与应用数据共用一套账号与权限模型。
桌面与应用窗口管理、应用商店、私有应用托管按 api. / site. / app. 子域路由，因此自托管必须配通配符 DNS。
AIchat / vision / image / TTS / STT / OCR / video托管 AI Gateway；下一节单独讨论边界。
KV 与 Workersputer-kvstore + Serverless JS应用仓库里有邮件 worker 的部署脚本，可作为最小例子。
Peer 与 NetworkingWebRTC 会议；浏览器内 TCP/IPMeetings 应用完全基于 Peer API；Networking 是更激进的能力。
身份账号、应用 token、Actor应用可代用户行事，也可持有自己的 token，权限边界靠 Actor 约束。
03

自托管：一行命令背后的六件事

官方说一条命令。命令是真的，前提也是真的。

装 Docker 与 compose 插件

这是文档里唯一要求你自己装的东西。安装脚本会检查 docker compose version，不通过就停下，不会替你安装。

准备域名与通配符 DNS

*.your-domain.com 必须指向服务器 IP。Puter 用子域区分 API、静态站点与私有应用；只解析主域名，子域无法解析，应用与托管会不可用。

运行一行安装脚本

脚本生成 MariaDB、S3、JWT 等密钥，写 .env 与 puter/config/config.json，下载 compose 与 Caddyfile，然后 docker compose up -d。重复执行不会覆盖已有配置；强制轮换需 PUTER_FORCE=1。

curl -fsSL https://raw.githubusercontent.com/HeyPuter/puter/main/install.sh | sh
配 TLS 与反向代理

默认只开 80。生产环境要在 Caddy 配 443 与证书；文档给了 certbot 路线，但证书申请不在安装脚本里自动完成。

可选：本地模型与收信

compose 的 ai profile 会启动 Ollama 并拉 tinyllama；smtp profile 启动收信服务，把邮件投递到用户邮箱。两者都默认关闭。

备份与升级

文档说明状态在 ./puter/data/<service>/，另有 MariaDB 与对象存储。备份要同时覆盖数据库、对象存储与配置密钥；密钥漂移会导致数据库登录失败。

默认拉起什么

容器镜像作用
Caddycaddy:2.11-alpine80/443 反向代理与子域路由
Puterghcr.io/heyputer/puter应用本体
MariaDBmariadb:11SQL；首次启动自动建表
Valkeyvalkey/valkey:8-alpine缓存与限流
DynamoDB-localamazon/dynamodb-localKV 存储；自动建表
RustFSrustfs/rustfsS3 兼容对象存储
S3 initamazon/aws-cli一次性建桶后退出

可选服务：Ollama（CPU，GPU 需额外开启）与 SMTP 收信。前六行为常驻服务，S3 init 为一次性建桶。文档没有给最低配置或并发基准，容量需要按 MariaDB、对象存储与 Puter 本体自行压测。

“一行命令”的准确含义

一条命令可以完成安装，但它不是“零前置”。Docker、通配符 DNS、证书、备份策略仍然要人来准备。文档自己把 compose 描述为单机上最接近生产的部署，这不是 SLA 承诺。

04

AI 网关：500+ 模型，和它的边界

500+ 是真的，但它描述的是 Puter 的托管网关，不是自托管安装包的默认能力。

对独立开发者

没有 key，也没有后端

一个 script 标签就能调用文本、图像、语音与 OCR。模型切换是改参数；应用可以直接发布到 App Store 或自己的域名。

对自托管者

500+ 不会随 compose 到位

默认只拉起 Ollama 与 tinyllama。要用 GPT、Claude、Gemini，需要自己接供应商或扩展模型层；“500+”描述的是托管网关。

对终端用户

用的人付费

user-pays 把 AI 成本放到用户自己的 Puter 账户。开发者不承担账单，但也意味着用户必须先有账号、接受额度与数据路径。

托管网关与自托管默认栈

维度puter.com / Puter.js自托管默认
模型范围官方称 500+，含 GPT、Claude、Gemini、Grok、DeepSeek、FLUX 等Ollama + tinyllama；其余需自行接入
鉴权用户登录 Puter，无需 API key自己的账号体系；上游模型密钥自管
计费user-pays，用户承担自己的算力与供应商账单
数据路径请求经过 Puter 网关再到上游数据留在自己的服务器与模型上

“模型”包含对话、图像、语音、OCR、视频等，不等于 500 个通用大语言模型。

调用形态（示意，未在本报告执行）

<script src="https://js.puter.com/v2/"></script>
<script>
(async () => {
  const reply = await puter.ai.chat("用三句话解释云操作系统");
  await puter.fs.write("notes/hello.md", "hello");
  console.log(reply);
})();
</script>
把“500+ 模型”当成产品能力，不要当成部署属性

选型时先问：模型请求走谁的网络、谁付钱、出问题找谁。这三个答案在托管与自托管下完全不同。

事实核查：哪些说法要改

以下八条来自常见介绍与截图文案，逐条对照仓库、文档与产品页。

显示 8 / 8 条

说法判定核对结果
“Node.js 16 以上就能部署”需修正本地开发要求 Node >= 24.0.0（package.json 的 engines 字段）；Docker 路线不依赖本机 Node。Everything 的应用要求 22.12+。
证据：puter/package.json；everything/README
“49 个完整项目源码”需修正src/ 下是 51 个应用目录（2026-11-01 的 main 分支）。数量会变，引用时应写“截至某日”。
证据：git tree；README 表格
“复刻约 50 款商业软件”需限定目录有 51 个应用，但其中 5 个是棋牌/益智游戏；1 个（Assets）是占位。不能全部等同于商业软件替代品。
证据：README；src/assets 目录
“内置 500+ AI 模型”需限定官方 AI Gateway 页面确实写 500+，覆盖文本、图像、语音、OCR 等；但这是托管网关能力，自托管默认只带 Ollama 的 tinyllama。
证据：developer.puter.com/ai；self-hosting.md
“几行命令完成 Docker 部署”需限定一条安装命令确实能拉起；前置条件是 Docker + compose、通配符 DNS 与 TLS，默认 6 类常驻服务。
证据：install.sh；docker-compose.yml
“Dropbox / Google Drive 的开源替代”需限定文件、应用与身份有重叠，但 Puter 还包含 AI 网关、Serverless Workers 与桌面环境；定位比网盘大，成熟度比网盘小。
证据：README；doc/architecture.md
“隐私优先”需限定自托管时数据在自己机器上，这个说法成立；托管在 puter.com 时仍是第三方云服务，需要看条款与数据路径。
证据：产品定位；部署文档
“Everything 大部分应用接入 Puter.js”已核实抽查 5 个不同类别应用的 index.html，均直接加载 https://js.puter.com/v2/；文件与身份依赖 Puter。
证据：抽取 spreadsheet/documents/cad/teamchat/photo-studio

横向对比：它站在哪一格

不是“Puter 好不好”，而是“在你的场景里，它替代的是哪一层”。

方案定位部署AI许可主要代价
Puter云桌面 + 个人云 + 开发者 BaaS官方托管或单机 compose托管网关 500+；自托管需自接AGPL-3.0服务面大，运维与安全边界要自己扛
Nextcloud文件同步与协作套件自托管或托管商靠应用/外部集成AGPL-3.0不是浏览器桌面；AI 与 Workers 需另拼
Google / Microsoft 云办公托管生产力套件不可自托管内置闭源数据与费用锁定；无法改后端
自己拼 S3 + Auth + AI + 前端按需定制自建自选混合集成与维护成本最高，但边界最清楚

除 Puter 与 Nextcloud 的许可、部署形态外，本表为分析判断，不是基准测试。

07

风险与适用边界

把代价写在前面，比把功能列满更有用。

许可

AGPL 不是 MIT

修改后通过网络向用户提供服务，通常需要提供对应源码。闭源商用、二次分发、SaaS 封装都要先过法务。官方仓库是 AGPL-3.0-only。

运维

六个服务，一条链路

MariaDB、Valkey、DynamoDB、S3、Caddy、Puter 任一处配置漂移都会表现为登录或文件失败。文档面向单机 compose，多节点与故障转移需自行设计。

安全

攻击面比网盘大

身份、文件、Workers、浏览器内网络、邮件都在同一栈里。自托管意味着补丁、备份、审计都由你负责；本报告未做安全审计。

集中度

便利来自同一家

托管模式下，AI、应用分发、身份都指向 Puter。自托管能拿回数据，但也失去 500+ 模型的默认便利。

节奏

版本跑得快

日历式版本号（26.x），Node 24 起步，main 分支活跃。生产部署要锁镜像 tag、锁 Node 版本，并留回滚路径。

数据

出口不止一处

用户文件在 S3，元数据在 MariaDB，应用数据还有各自的 KV 与协作结构。迁移不是拷一个目录；要先定义导出格式，再做回读验证。

适合与不适合

适合

这些场景值得试

  • 给 AI 生成的前端应用找“无后端”后端
  • 需要文件、账号、KV、AI 一体的自托管个人云
  • 内部工具、教学、演示，能接受单机与手工运维
  • 愿意读 AGPL 并接受其义务
不适合

这些场景先别上

  • 要求 SLA、多活、等保/审计合规的生产系统
  • 没有 Docker、DNS、备份能力的团队
  • 要求模型完全不出内网，且不愿自接模型
  • 要把修改版闭源对外提供
落地前做三个验证

1）用 compose 起一遍，再按文档恢复一次备份；2）用一个真实应用走通登录、写入、分享、权限四条路径；3）让法务看 AGPL 与 user-pays 条款。三步都过，再谈迁移。
