商业管理类最多，办公与协作其次。这个组合说明它瞄准的不是消费级软件，而是中小企业的一长串付费 SaaS。

技术栈：没有框架，靠库和测试

51 个应用是 51 个独立 Vite 工程，靠 Puter.js 共享账号、存储与 AI。没有 UI 框架，也没有统一后端。

前端框架

51 个应用都没有 React / Vue / Svelte / Angular 运行时依赖。

Rust 源文件

.wasm 产物/夹具

测试文件
9,253

结构

51 个独立工程，不是 monorepo 工作区

  • 仓库没有根 package.json，也没有 workspaces；每个应用单独 npm install。
  • 每个应用各自带 Vite 配置，README 要求 Node.js 22.12+。
  • 抽查 5 个不同类别的 index.html，均直接加载 https://js.puter.com/v2/。
  • 4 个应用引入 Yjs：Documents、Whiteboard、Photo Studio、Wiki。
重依赖

重活交给成熟库，不自己造轮子

  • PDF：pdf.js、pdf-lib、Tesseract。
  • PSD：ag-psd；视频：mediabunny；3D：three.js；代码编辑：CodeMirror 6。
  • CAD 内核：replicad + OpenCascade WASM；音频编码：lamejs。
  • “从零重写”指应用层与交互，不是把渲染、解析、编解码全部重写。
测试多，不等于测试有效

Spreadsheet 有 3,436 个测试文件，Documents 有 1,973 个，Presentation 572 个。这个密度在同类开源应用里少见，但文件数不是覆盖率，也没有看到统一的 CI 覆盖率报告；复用前仍要自己跑 npm test 并读关键用例。

本报告没有启动任何一个应用，也没有做功能、性能或安全测试。把“深度实现”理解成“代码与测试体量更大、涉及更难的文件格式”，不是“可以直接替代 Photoshop/AutoCAD”。

根 README 写 MIT；打开应用自己的 package.json，会看到另一套答案。

读取各应用 package.json 的 license 字段；仓库根 LICENSE 与 README 声明 MIT。

“MIT”不是整仓统一答案

根 README 写“MIT unless explicitly stated otherwise”，而 9 个应用确实单独声明了 AGPL-3.0-only，35 个没有声明。也就是说，仓库级 MIT 与目录级 AGPL 同时存在。把某个应用嵌进产品前，先看那个目录的 package.json。

AGPL 的网络条款

如果你修改了 AGPL 应用并让它通过网络对外提供服务，通常需要向用户提供对应源码。闭源 SaaS、二次分发、白标封装都要先过法务。Puter 平台本身也是 AGPL-3.0-only，和 Everything 的 MIT 不是一回事。

06

复用它之前，先回答五个问题

这五个问题决定你是“参考实现”，还是把债务接进产品。

01

许可证允许你的分发方式吗？

9 个 AGPL、7 个 MIT、35 个未声明。先定位目标应用，再看目录级声明；不要用根 README 的 MIT 覆盖它。

02

数据层接在哪里？

应用的 index.html 默认加载官方 Puter.js，文件、账号、AI 都走 Puter。仓库里没有独立后端；少量应用带 Serverless Worker（如邮件处理），仍运行在 Puter 上。“完全自托管”需要替换 SDK 来源并自行验证。

03

文件能不能带走？

格式支持是这批应用的强项：xlsx、docx、pptx、psd、pdf、dxf、step、stl、gerber。协作数据用 Yjs，迁移要按具体应用的存储结构验证。

04

测试能不能信？

9,253 个测试文件是信号，不是保证。先跑 npm test，再看与你相关的路径：导入导出、权限、异常输入、协作冲突。

05

维护由谁来做？

51 个包各自独立，没有根工作区；Node 22.12+；上游 SDK 或格式库升级时要逐个跟进。把它当“源码参考库”比当“统一产品”更稳妥。

跑起来

git clone https://github.com/HeyPuter/everything.git
cd everything/src/spreadsheet
npm install
npm run dev

要求 Node.js 22.12+。每个应用单独安装、单独启动；运行时还需要网络访问 js.puter.com；存储与身份由 Puter 提供，通常需要一个账号。仓库没有统一的离线或自托管构建脚本。

时间也是证据

仓库创建于 2026-10-13，到数据快照日只有 19 天，已包含 51 个应用、34,458 个文件。这个速度很可能意味着高度自动化的开发流程（本报告无法核实具体工具）。这不是贬义，但意味着评估时要更依赖测试、代码审查与实际运行，而不是“项目年龄”。
