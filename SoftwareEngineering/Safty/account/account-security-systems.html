安全研究 · 账号与身份 · 2026

账号体系的攻防地图 Google、Apple、Microsoft、Meta、腾讯、阿里与企业 SSO 是怎么证明「你是你」的，攻击者又是怎么绕过这一步的。原理拆到协议字段，案例对到真实事件。

  • 协议基准 OAuth 2.0 / OIDC / SAML 2.0 / WebAuthn
  • 权威标准 RFC 9700 · NIST SP 800-63B
  • 覆盖体系 8 类
  • 攻击手法 20 种
  • 案例 2020–2025 · 14 起

三条结论

  1. MFA 普及之后，攻击重心已经从「偷密码」移到偷断言、偷会话：SolarWinds 偷的是 ADFS 签名证书，Storm-0558 用的是签名密钥加校验缺陷，infostealer 卖的是浏览器 Cookie。密码只是入口之一，不再是主战场。
  2. 六家账号体系的密码学基础几乎一样，差别在信任范围的收放：Apple 用中继邮箱把数据面压到最小；Google 与 Microsoft 用设备绑定把会话钉在硬件上；微信与支付宝把身份收敛到服务端、用 openid 与签名做信任锚。设计差异决定攻击面差异。
  3. 防御的有效顺序是：先缩短会话与令牌寿命，再换抗钓鱼认证，最后才是检测。只加一层可中继的 MFA，等于把攻击者从撞库赶到实时钓鱼——Twilio、Uber、Cisco 三起事件是同一条路径。

01 · 通用模型

先分清五件事，再看各家怎么实现

几乎所有账号体系都能拆成同一条链：证明你是谁（认证）、由谁替你作证（断言）、之后每次请求凭什么被相信（会话）、以及你能做什么（授权）。最后还要回答一个常被忽略的问题：账号丢了怎么找回（恢复）。

把一次登录摊开：四条泳道

下面这张时序图是 OAuth 2.0 授权码 + PKCE 的标准流程。八类体系的具体字段不同，但「谁把什么交给谁、谁验证什么」的结构基本相同——包括微信的 code 换 openid、支付宝的 auth_code 换 user_id。

认证 ≠ 授权

认证回答「你是谁」，授权回答「你能做什么」。大量真实漏洞属于后者：用户确实登录了，但接口没校验「这条数据是不是他的」。

协议规范 RFC 9700 把授权码流的安全边界写得很细，但对象级授权仍要业务自己实现。

断言是「别人替你作证」

OIDC 的 id_token、SAML 的 Assertion 都是 IdP 签名的声明。应用的信任对象不是用户，而是签名。

所以攻击者一旦拿到签名密钥或校验缺陷，就不需要再碰用户。

会话才是长期资产

MFA 只在建立会话的那一秒起作用。之后 30 天里，一个 Cookie 就能代表你——这也是 infostealer 与 AitM 钓鱼都盯着会话的原因。

会话寿命 × 绑定强度 = 攻击窗口。

AAL 的定义来自 NIST SP 800-63B（2025 年 8 月版）。其中 AAL3 明确不允许使用「可同步」的认证器（例如云同步 passkey），因为私钥必须可导出才能同步——这条限制直接决定了高价值系统该用什么。

一个反直觉的事实

在 2020 年之后的大型身份事件里，被攻破的几乎都不是「密码算法」，而是信任链上的实现细节：一个没校验的 issuer、一个客服流程、一个 HAR 文件里的 Cookie、一台没上 MFA 的远程桌面。协议本身很少是短板，落地方式才是。

02 · 各家体系

八类账号体系，同一道题的不同解法

下面每一家都按同一个模板拆：协议栈、一次登录的步骤、已知失效模式、防御要点、同类机制对照。切换标签看具体实现，重点不在 API 名字，而在「它把信任放在哪里」。

GoogleOIDC + 设备绑定会话

把「登录 Google」拆成三件事：OIDC 发断言、短命 access token 换数据、设备绑定的会话 Cookie。

  • OAuth 2.0
  • OpenID Connect
  • PKCE
  • JWT/JWKS
  • Session Cookie
  • DBSC
  • Passkey

一次登录发生了什么

  1. 应用生成 state（防 CSRF）、nonce（防 id_token 重放）和 PKCE 的 code_verifier，只把它的 SHA-256（code_challenge）放进跳转链接。
  2. accounts.google.com/o/oauth2/v2/auth，带 client_id、redirect_uri、response_type=code、scope=openid email profile、code_challenge。
  3. 密码、Passkey 或安全密钥在这一步；随后是授权同意页，用户看到的是「这个应用要读你的哪些数据」，这是整个链条里最容易被社工的一屏。
  4. 浏览器只拿到一次性 code；后端带 code_verifier 与 client_secret 调 /token，浏览器永远看不到 refresh token。
  5. 验签名（Google JWKS）、iss=accounts.google.com、aud=client_id、exp、nonce；用户主键用 sub，不要用 email。
  6. access token 默认 1 小时；refresh token 长期有效，靠 /revoke 与用户端的「第三方应用」页面撤销。

已知失效模式

  • 把 email 当主键：Workspace 域改名、邮箱回收、代理邮箱都会让 email 漂移；用 sub 才稳定。
  • 公共客户端不做 PKCE：原生 App、SPA 的 code 可被同设备恶意应用截获并抢先兑换。RFC 9700 已把隐式流与不带 PKCE 的授权码流列为不推荐。
  • redirect_uri 通配或可被开放重定向：code 被送到攻击者域名，等于把登录票据直接交出。
  • 前端解析 id_token 不验签：攻击者伪造 {"sub":"admin"} 即可；必须后端验签或走 /userinfo。
  • 同意钓鱼（consent phishing）：诱导用户给一个恶意 OAuth 应用授权 offline access，之后不需要密码也能长期读邮件。
  • 会话 Cookie 被窃取：MFA 只保护「建立会话」那一刻；infostealer 复制 Cookie 后可直接重放，这就是 pass-the-cookie。

防御要点

  • 设备绑定会话（DBSC）：Chrome 与 Google 账号把会话绑定到设备上的私钥——Cookie 被复制到另一台机器就失效。
  • Passkey 优先 + 高级保护：Advanced Protection Program 强制安全密钥/Passkey，直接掐掉 AitM 钓鱼与 OTP 中继。
  • scope 最小化与令牌审计：只申请必要 scope；定期拉取账号的第三方授权列表，清理离线访问。
同类机制对照

本文清单中没有 Google 侧的公开案例；机制对照：23andMe 撞库（a1）、同意钓鱼（a8）、会话 Cookie 重放（a10）。

Google 自己也是被攻击最密集的 IdP：2024 年后大量 infostealer 日志以「Google 会话 Cookie + 密码」组合打包出售。

Apple最小披露 + 密钥不出设备

Apple 的账号体系里，隐私设计本身就是安全设计：能不给的标识就不给，能给中继地址就不给真邮箱。

  • Sign in with Apple
  • OIDC 变体
  • ES256 client_secret
  • iCloud Keychain
  • Passkey
  • Private Relay

一次登录发生了什么

  1. appleid.apple.com/auth/authorize，response_mode=form_post，scope=name email，带 nonce 与 state。
  2. 开发者用 .p8 私钥签一个 ES256 的 JWT 当 client_secret，有效期最长 6 个月，不是写死在配置里的字符串。
  3. 选「隐藏邮箱」时返回 xxx@privaterelay.appleid.com，并带 is_private_email 标记；邮件由 Apple 转发。
  4. 验 Apple JWKS 签名、aud（Service ID）、nonce、exp；主键用 sub，它与开发者团队绑定。
  5. Safari/系统钥匙串保存 passkey，iCloud Keychain 端到端加密同步；App 内登录由系统生物识别解锁私钥。

已知失效模式

  • 不校验 nonce：id_token 可被重放到另一个会话；Apple 的 nonce 是防重放的主开关。
  • 把中继邮箱当真邮箱做账号合并：同一用户换一个 App 会得到不同的中继地址，按邮箱合并会造出重复账号或错误绑定。
  • client_secret 私钥泄露：拿到 .p8 的人可以为你的 Service ID 签任意 client_secret，冒充你的后端换 token。
  • 依赖「隐藏邮箱」当安全边界：它防的是数据面扩散，不防账号接管；用户侧被钓鱼仍然会丢号。
  • 同步 passkey 的单点风险：iCloud 账号被接管，等于拿到所有同步 passkey 的使用权（私钥不可导出，但可在攻击者设备上解锁使用）。

防御要点

  • 短周期轮换 .p8：把私钥放进 KMS，签发 client_secret 的服务最小权限化，定期轮换。
  • 中继邮箱只作通信通道：账号主键、风控、客服全部基于 sub；中继地址只用于发信。
  • AAL 分级：NIST 800-63B 明确同步类认证器不能用于 AAL3；高价值场景配硬件密钥或设备绑定。
同类机制对照

本文清单中没有 Apple 侧的公开案例；相关机制是 id_token 重放（a15）与「中继邮箱被当成主键」导致的账号合并错误。

Apple 把「隐藏邮箱 + 中继」做成默认选项，相当于把第三方应用的数据面压到最小——这是账号体系里少见的隐私即安全设计。

Microsoft企业身份 + 设备信任

Entra ID 的核心不是「验证密码」，而是「判断这台设备、这个位置、这个会话值不值得信任」。

  • Entra ID
  • OIDC / SAML / WS-Fed
  • PRT
  • Conditional Access
  • CAE
  • Token Protection

一次登录发生了什么

  1. login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize，或 SAML 的 AuthnRequest；租户 ID 决定信任哪个目录。
  2. 加入/注册设备会拿到设备证书与 PRT（Primary Refresh Token），条件访问基于「设备合规 + 用户 + 位置 + 应用敏感度」组合判定。
  3. Authenticator 推送（带数字匹配）、FIDO2 安全密钥、Windows Hello、临时访问通行证（TAP）。
  4. access token（JWT）+ refresh token + 浏览器会话 Cookie；PRT 由系统代理（WAM）持有，普通进程拿不到明文。
  5. CAE 让撤销在分钟级生效，不必等 token 过期；Defender for Cloud Apps 对异常令牌做「令牌窃取检测」。

已知失效模式

  • Golden SAML：ADFS 的 token 签名证书被拿走，攻击者可以自己签任意用户的 SAML 断言——签名是真的，身份是假的。
  • 签名密钥 + 校验逻辑双重失守：2023 年 Storm-0558：消费者密钥被用于伪造企业租户令牌，根因之一是接受端没有校验签发者。
  • 设备码钓鱼：诱导用户在真实微软页面上输入攻击者给的 device code，令牌就落到攻击者手里；MFA 全程有效。
  • 遗留协议与历史租户：SMTP AUTH、Basic 认证、多年前创建的非生产租户，往往没有条件访问覆盖，成为密码喷洒入口。
  • PRT 窃取（pass-the-PRT）：拿到设备上的 PRT 可换出该设备能拿的所有令牌，等同于拿到设备。

防御要点

  • 条件访问优先于密码策略：强制合规设备、封堵遗留认证、按应用分级；把「能登录」改成「在什么条件下能登录」。
  • 令牌保护与绑定：Token Protection 把令牌绑到设备密钥；关闭不需要的 device code 流，或对其单独加限制。
  • 监控断言签发面：ADFS/Entra 的签名证书、 federation 信任、企业应用授权变更都是高价值告警项。
同类机制对照

Microsoft 相关事件：SolarWinds / Golden SAML、Storm-0558、Midnight Blizzard。

微软自己统计过：密码攻击占入侵入口的绝大多数，而启用 MFA 能挡掉绝大部分自动化攻击——但挡不住钓鱼和令牌窃取，这两类要靠抗钓鱼认证与设备绑定。

Meta / Facebook社交图谱换登录

Facebook Login 卖的是「降低注册摩擦」，代价是长期令牌、复杂权限和一块持续被撞库的靶子。

  • Facebook Login
  • OAuth 2.0
  • Graph API
  • Long-lived token
  • appsecret_proof

一次登录发生了什么

  1. facebook.com/v19.0/dialog/oauth，scope=public_profile,email；用户已登录 Facebook 时往往一键通过。
  2. 用 app_id + app_secret 换短期 user token，再换长期 token（约 60 天）。
  3. 拿 id、name、email；appsecret_proof 防止 token 被挪到别的应用使用。
  4. 订阅 deauthorize / data deletion 回调，处理用户解绑与删除请求。

已知失效模式

  • 长期 token 泄露：60 天有效期意味着一次泄露可以长期调用；token 常出现在前端日志、第三方 SDK、崩溃上报里。
  • 恶意应用与权限滥用：用户授权后，应用可读取社交图谱；历史上多次出现大规模数据抓取（scraping）。
  • 撞库：邮箱 + 旧密码组合在暗网流通，社交账号是撞库最高频的目标之一。
  • 账号恢复流程被社工：客服/好友验证/信任联系人被用来重置 MFA，比破解密码便宜。

防御要点

  • token 不落前端：所有 Graph 调用在后端；前端只拿会话，不拿 user token。
  • 最小 scope + 定期清理：只申请必要权限，定期审查已授权应用。
  • 抗钓鱼 MFA 与恢复加固：安全密钥/Passkey 优先；恢复流程加延迟与人工复核，避免客服成为后门。
同类机制对照

机制对照：23andMe 撞库（a1）与 Snowflake 凭据复用（a2）。两者都不是 Meta 自身事故，但攻击路径相同。

Meta 的账号体系是「平台化」的典型：第三方应用越多，令牌与授权面越大，攻击者越不需要碰密码。

腾讯（微信 / QQ）openid / unionid 收敛身份

国内最主流的账号体系不是 OIDC，而是「code 换 openid」：身份在服务端收敛，前端只拿到一个跳转结果。

  • 微信网页授权
  • 扫码登录
  • 小程序 code2Session
  • QQ 互联
  • unionid
  • access_token

一次登录发生了什么

  1. 跳 open.weixin.qq.com/connect/oauth2/authorize，scope=snsapi_base（静默）或 snsapi_userinfo（要资料），必须带一次性 state。
  2. 服务端调 sns/oauth2/access_token（appid + secret + code），拿到 access_token、openid；需要资料再调 sns/userinfo。
  3. 同一用户在公众号、小程序、App 之间 openid 不同；只有绑定到同一个微信开放平台账号，才会返回同一 unionid。
  4. wx.login() 拿 code → 后端 code2Session 换 openid、session_key、unionid；session_key 用于解密加密数据。
  5. qrconnect 生成带 state 的二维码，手机扫码确认后，PC 端凭 code 换身份；二维码有效期通常 5 分钟。

已知失效模式

  • state 缺失或可预测：登录 CSRF——攻击者把自己的 code 塞进受害者的回调，受害者账号被绑到攻击者身份上。
  • 前端信任 openid：openid 由后端换得，任何前端传来的 openid/unionid 都必须视为不可信输入。
  • session_key / access_token 泄露：session_key 泄露可解密用户加密数据；access_token 出现在 URL、日志、前端缓存里是常见事故。
  • 二维码被替换或转发：钓鱼者用自己的登录二维码替换页面上的二维码，用户「扫码确认」等于把账号交给对方。
  • 回调域名与业务域名校验不严：开放重定向把 code 送到外部域名。

防御要点

  • 身份只在服务端解析：前端只接收「登录成功」与自建会话票据；openid/unionid 永不作为前端可信参数。
  • state 一次性 + 绑定会话：state 与浏览器会话绑定、5 分钟内有效、用后即焚。
  • 绑定前二次确认：手机号/微信绑定涉及账号合并时，要求已登录状态 + 二次验证，避免「一键绑定」被 CSRF。
同类机制对照

本文清单中没有腾讯侧的公开案例；同类机制是登录 CSRF 与账号绑定劫持（a9）、二维码劫持（a17）。

微信生态的攻防重点不在密码学，而在「账号绑定」与「身份映射」：openid、unionid、手机号三套标识之间的合并逻辑最容易出事。

阿里（支付宝 / 淘宝）签名信任 + 回调验签

支付账号体系的安全边界是「签名」而不是「密码」：每一笔通知都要能被商户用公钥验回。

  • 支付宝开放平台
  • RSA2 签名
  • auth_code
  • 异步通知
  • mTLS（部分场景）

一次登录发生了什么

  1. 商户跳到支付宝授权页，用户确认后回跳 auth_code；商户用它调 alipay.system.oauth.token 换 user_id/open_id。
  2. 商户用应用私钥对参数按字典序拼接后做 RSA2（SHA256withRSA）签名；支付宝用商户公钥验签。
  3. 支付宝的响应与异步通知 notify 带签名，商户必须用「支付宝公钥」验签，并校验 app_id、out_trade_no、金额、状态。
  4. 同一笔通知会重发；落库要幂等，最终以主动查询/对账为准。

已知失效模式

  • 回调不验签：攻击者伪造 notify 直接「支付成功」，是最经典的资损漏洞。
  • 验签但用错公钥：把应用公钥当支付宝公钥用，等于没验；密钥轮换后更常见。
  • 参数拼接与签名串不一致：中文编码、空值、排序差异导致验签失败，开发者图省事直接跳过验签。
  • 私钥泄露：应用私钥泄露后攻击者可伪造商户请求（退款、查询），必须用 KMS/HSM 托管。

防御要点

  • 验签封装成唯一入口：支付回调只允许通过一个验签函数，禁止业务代码直接信任 HTTP 参数。
  • 金额与订单双校验：验签之外再核对订单金额与状态机，防重放与改价。
  • 密钥托管与轮换：私钥不入代码库、不入镜像；按支付宝指引做密钥轮换与灰度。
同类机制对照

本文清单中没有支付宝侧的公开案例；同类风险是异步通知伪造——本质与 a19 一样，都是「把未经验证的外部输入当成授权结果」。

支付类账号体系的攻击目标通常不是「登录」而是「回调」：一次伪造的支付成功通知就够造成资损。

企业 SSO（SAML / CAS / Kerberos）一次登录，全公司通行

SSO 把几十个应用的信任集中到一个 IdP；这提高了可用性，也把「一个签名密钥」变成全公司的单点。

  • SAML 2.0
  • CAS
  • Kerberos / NTLM
  • LDAP
  • SCIM

一次登录发生了什么

  1. 应用（SP）生成 AuthnRequest（含 ID、ACS URL、Issuer），重定向到 IdP。
  2. 用户在 IdP 完成登录（可能已 SSO）；IdP 返回 Response，其中 Assertion 用 IdP 私钥签名。
  3. 验签名、Audience、InResponseTo（防重放）、NotOnOrAfter、Destination，再建本地会话。
  4. CAS 用一次性 ticket 校验；Kerberos 用 TGT/TGS 与 PAC；LDAP 直接 bind 查目录。

已知失效模式

  • XML 签名包装（XSW）：把签名节点挪到另一段断言上，解析器验签通过但取到的是攻击者伪造的身份。
  • 签名剥离 / 注释截断：把签名去掉后依赖「未签名也接受」的实现，或用 XML 注释截断身份字段。
  • 断言重放：不校验 InResponseTo 与有效期，截获的断言可以反复用。
  • Golden SAML：IdP 的 token 签名证书泄露后，攻击者可以离线签发任意身份，日志里看不出异常。
  • Kerberos / NTLM 旁路：委派配置不当、NTLM relay、Kerberoasting，都是「不碰密码拿身份」的路径。

防御要点

  • 严格按规范校验断言：签名必须覆盖断言本身；强制 InResponseTo、Audience、时间窗；用成熟库，别自写 XML 解析。
  • 签名证书与 DKM 分级保护：ADFS 签名证书、DKM 容器、 federation 元数据是最高等级机密，需 HSM + 双人审批。
  • 会话与权限解耦：SSO 只证明「你是谁」，授权仍按应用做最小权限，避免一个断言换到全部系统。
同类机制对照

企业 SSO 相关事件：SolarWinds（签名证书）、Storm-0558（签发者校验）、Okta 支持系统（旁路）。

SSO 的安全模型是「信任转移」：应用不再验证密码，而是验证 IdP 的签名。所以攻击者的最优路径也从应用转到了 IdP。

无密码与 MFA（Passkey / TOTP / 短信）认证器决定抗钓鱼能力

同样是「第二个因素」，短信、TOTP、推送、Passkey 的抗攻击能力差了一个数量级——差别在私钥有没有绑定源站。

  • WebAuthn / FIDO2
  • Passkey
  • TOTP (RFC 6238)
  • Push MFA
  • SMS OTP

一次登录发生了什么

  1. 服务端发 challenge 与 rp.id；认证器生成密钥对，返回 attestationObject 与 clientDataJSON；服务端存 credential ID、公钥、计数器。
  2. 服务端再发 challenge；认证器用私钥签 authenticatorData || SHA256(clientDataJSON)；服务端验签、验 rpIdHash、验 origin、比对计数器。
  3. 私钥在平台钥匙串（iCloud Keychain / Google 密码管理器）端到端加密同步，换设备可用；代价是恢复能力依赖平台账号。
  4. HMAC-SHA1(secret, floor(time/30)) 取 6 位，允许 ±1 个窗口；服务端与客户端共享种子。
  5. 推送靠用户点「批准」；短信 OTP 走 PSTN，受 SIM 交换与 SS7 影响。

已知失效模式

  • AitM 钓鱼：反向代理把真实登录页原样搬运，TOTP/短信/推送都能被实时中继；只有绑定源站的 WebAuthn 不行。
  • 推送疲劳：连续轰炸直到用户点错一次；NIST 800-63B 把「认证疲劳」列为正式威胁。
  • 短信 OTP：SIM 交换、运营商内部作案、SS7 拦截；NIST 对 PSTN 通道有明确限制。
  • 只校验签名不校验 origin：等于把 WebAuthn 降级成普通签名，钓鱼站可以转发 challenge。
  • 恢复流程绕过：再强的认证器也挡不住「打客服重置」；恢复通道往往是最弱的一环。

防御要点

  • 按 AAL 选认证器：AAL2 至少两种因素且必须提供抗钓鱼选项；AAL3 要求抗钓鱼 + 不可导出私钥，同步 passkey 不能用于 AAL3。
  • passkey 优先，短信兜底但加风控：高风险操作再叠加设备绑定或人工复核。
  • 恢复流程与认证同等强度：恢复要走同样的抗钓鱼与延迟机制，别让客服成为万能钥匙。
同类机制对照

MFA 相关事件：Twilio / 0ktapus（OTP 中继）、Uber 与 Cisco（推送疲劳）、MGM（客服重置）、设备码钓鱼。

判断一个 MFA 是否真的有用，只看一个问题：攻击者能不能在自己的域名上完整复刻登录流程并拿到可用的凭据。

03 · 攻击手法

20 种手法，落在五个环节上

按「被攻击的是哪一环」分类，比按「用了什么工具」分类更有用：同一种工具（比如反向代理）在认证环节是钓鱼，在会话环节就是令牌窃取。

原理与为什么有效 阻断与检测 案例
撞库 / 密码喷洒凭据凭证填充用别的站点泄露的邮箱+密码批量试；密码喷洒用少量常见密码横向试大量账号，规避锁定阈值。
为什么有效：大量用户复用密码；企业口令策略又鼓励「Summer2024!」这类可预测结构。
查泄露库（HIBP）、禁用已泄露口令、按 IP/设备/行为做速率与风险评分；对喷洒看「单 IP 多账号」而非「单账号多次」。c9

为什么有效：个人设备不受企业管控；Cookie 加密与浏览器账户绑定常可被同用户进程解密。

AitM 实时钓鱼认证反向代理（Evilginx、Tycoon2FA 等）把真实登录页镜像到攻击者域名，用户输入与 OTP 被实时转发，登录成功后会话 Cookie 被拿回。
为什么有效：用户只看页面外观；OTP 是一次性但对「实时中继」无效；很多站点没有 origin 绑定。
抗钓鱼认证（WebAuthn/Passkey）、设备绑定会话、品牌域名与证书监控、邮件侧隔离。c2
OTP 中继钓鱼认证钓鱼页收集账号密码后立刻在真实站点触发 OTP，并把验证码回填到钓鱼页，几秒内完成登录。
为什么有效：短信/OTP 与登录动作没有绑定关系；用户分不清「谁在要这个码」。
淘汰 SMS 作为唯一第二因素；改用 Passkey 或号码匹配推送；对异地新设备加强校验。c2
MFA 疲劳 / 推送轰炸认证反复发起推送认证，配合电话或聊天施压，等用户误点「批准」。
为什么有效：推送只显示「是否本人操作」，缺少上下文；用户被骚扰到妥协。
数字匹配、显示来源 IP/应用、限速与静默拒绝、异常推送告警；NIST 将认证疲劳列为正式威胁。c3
SIM 交换 / SS7认证收买运营商内部人员或伪造身份补卡，把受害者号码转到攻击者 SIM；短信与语音 OTP 全部落到攻击者手里。
为什么有效：PSTN 信任链在运营商侧，应用无法验证「谁真正持有号码」。
不要把手机号当唯一身份；号码变更加冷却期与通知；高价值操作改用抗钓鱼认证。c2
设备码钓鱼认证诱导用户在真实 IdP 页面输入攻击者生成的 device code，授权后令牌落到攻击者处——全程没有假页面，MFA 也照常完成。
为什么有效：设备码流为「输入受限设备」设计，缺少「这个 code 是给谁的」提示。
关闭或限制 device code 流；对 OAuth 授权做应用白名单与条件访问；监控异常授权。c14
OAuth 同意钓鱼授权诱导用户给恶意应用授权（如 offline_access + 读邮件），之后用 refresh token 长期访问，无需密码。
为什么有效：用户对「授权」的风险感知远低于「输入密码」；同意页信任链是 IdP 自己签的。
应用白名单/租户限制、用户授权可见与定期清理、检测异常第三方应用与高风险 scope。c6
redirect_uri / state 校验缺失授权回调地址允许通配或被开放重定向利用，code 被送到攻击者域名；state 缺失则导致登录 CSRF 与账号绑定劫持。
为什么有效：实现者常把 redirect_uri 当「跳转地址」而非「安全边界」；前端路由与 OAuth 回调混用。
精确匹配 redirect_uri、强制 PKCE、state 一次性并与会话绑定、禁止开放重定向。c2
会话 Cookie / 令牌窃取会话拿到浏览器 Cookie 或 refresh token 后直接重放，绕过登录与 MFA。
为什么有效：MFA 只保护建立会话；服务端默认信任 Cookie，Cookie 与设备无绑定。
HttpOnly/Secure/SameSite、绑定设备或 IP 风险评分、令牌轮换与重用检测、DBSC。c13
PRT / 刷新令牌滥用会话窃取设备上的 PRT 或长期 refresh token，换出该身份能访问的所有令牌（pass-the-PRT）。
为什么有效：长期令牌设计上就是为了「免登录」，天然是凭证；终端一旦被控就全丢。
令牌绑定设备密钥、缩短 refresh 寿命、条件访问要求合规设备、检测异常令牌使用。c11
JWT 算法与密钥混淆断言alg=none、HS256 与 RS256 混淆、把公钥当 HMAC 密钥、通过 jku/x5u 指向攻击者 JWKS。
为什么有效：验签库按 header 选算法；开发者信任 token 里的 kid/jku。
固定允许的算法、按 issuer 取 JWKS、拒绝 kid 内联密钥、校验 aud/iss/exp/nbf。c6
SAML XML 签名包装（XSW）断言构造多段断言，让签名验证的是 A 段、业务读取的是 B 段；或利用注释/命名空间差异绕过。
为什么有效：XML 解析器与签名校验器对「哪一段被签名」理解不一致。
用成熟 SAML 库、签名必须覆盖断言本体、拒绝多断言、做 XSW 测试用例。c1
Golden SAML断言窃取 IdP 的 token 签名证书后，攻击者离线签发任意用户的 SAML 断言，像 IdP 一样「合法」登录。
为什么有效：所有 SP 只验证「是不是 IdP 签的」；签名有效即身份有效。
签名密钥进 HSM、最小权限与双人审批、审计断言签发异常（同一 IdP 大量新设备/新地理位置）。c1
断言重放 / 受众校验缺失断言截获未过期断言或 id_token，在另一个会话/另一个应用重放。
为什么有效：未校验 InResponseTo、nonce、Audience、时间窗。
一次性 nonce、InResponseTo 绑定、严格 Audience、短有效期。c1
账号恢复滥用恢复打客服热线冒充员工，要求重置 MFA 或改绑手机；或利用找回密码逻辑（安全问题、好友验证）绕过。
为什么有效：恢复流程为了体验牺牲验证强度；客服权限过大且缺乏审计。
恢复走强身份核验（视频+证件+经理审批）、延迟生效、通知原设备、把恢复事件当高危告警。c7
二维码登录劫持认证替换/转发登录二维码，让受害者在自己的手机上「确认登录」攻击者的会话。
为什么有效：扫码确认页缺少「登录设备/位置」提示，用户默认二维码可信。
确认页显示设备与地理位置、二维码短时效且一次性、非同设备登录二次确认。c3
开放重定向 / 子域接管授权借可被控制的重定向参数把 code 或 token 送到外部；被接管的子域可托管钓鱼页或读取同域 Cookie。
为什么有效：重定向白名单用前缀/正则匹配；遗留子域 CNAME 指向已释放的云资源。
严格白名单、清理悬挂 DNS、CSP 与 HSTS、子域接管监控。c4
对象级越权（IDOR）授权已登录用户改一个 ID 就读到别人的数据；认证没问题，授权没做对象级校验。
为什么有效：把「已登录」当成「有权限」；接口按前端传参取数据。
服务端强制对象级授权、统一鉴权中间件、按租户隔离查询、越权测试进 CI。c5
支持系统 / 运营后台旁路恢复不打 IdP，改打 IdP 的客服或支持工单系统，用「帮忙查一下」拿到重置链接或临时密码。
为什么有效：支持系统常是 IdP 的高权限客户端，日志与 MFA 覆盖反而更弱。
支持系统纳入同等认证强度、最小权限、全量审计、敏感操作双人复核。c8

攻击者的选择题

这 20 种里，成本最低、回报最高的永远是「不需要 0day、只需要一个电话或一封邮件」的那几种：客服重置（a16）、OTP 中继（a4）、同意钓鱼（a8）。它们不依赖技术漏洞，所以补丁管不到，只能靠流程与认证强度。

04 · 案例

2020–2025：身份体系是怎么被绕过去的

这 14 起事件覆盖了五个环节里的每一个。看的时候注意一件事：几乎没有一起是「密码学被攻破」，全部是信任链某一环的实现或流程出了问题。

14 / 14 起可见。

  • 2020-12

    SolarWinds 供应链事件（UNC2452）

    入口：篡改 Orion 更新包，落地后横向移动到 ADFS 服务器

    被利用的机制：导出 ADFS 的 token 签名证书，离线伪造任意用户的 SAML 断言（Golden SAML），直接访问 Microsoft 365 / Azure，不需要密码也不需要 MFA。

    影响：多个美国联邦机构与数千家客户被访问；事件推动「签名密钥 = 最高等级机密」的行业共识。

    教训：当断言由 IdP 签名时，签名密钥就是全公司的万能钥匙；它的保护等级必须高于任何单个应用。

    断言
  • 2022-08

    Twilio / Cloudflare / 约 130 家组织（0ktapus）

    入口：短信钓鱼冒充 IT 通知，把员工引到仿冒 Okta 登录页

    被利用的机制：AitM + OTP 实时中继：钓鱼页把账号密码与一次性验证码即时转发到真实 Okta，完成登录后窃取会话。

    影响：约 9,900 组凭据被收集；Twilio 确认约 125 家客户数据被访问；攻击者随后转向新目标。

    教训：OTP 只能证明「此刻有人能收到码」，不能证明「对面是真实站点」；抗钓鱼认证是唯一的结构性解法。

    认证
  • 2022-09

    Uber

    入口：承包商个人设备被入侵，凭据在暗网购入

    被利用的机制：MFA 疲劳（连续推送 + WhatsApp 冒充 IT 施压）拿到一次批准；随后在内网共享脚本里发现硬编码的管理员凭据，横向到 G-Suite、Slack、AWS 控制台。

    影响：内部工具与部分代码仓库被访问；公司确认无客户数据泄露，但暴露了「MFA + 硬编码凭据」的组合风险。

    教训：MFA 疲劳是人的问题，硬编码凭据是工程的问题；两者叠加时，第二个因素形同虚设。

    认证
  • 2022-09

    Cisco

    入口：员工个人 Google 账号被控，进而社工其企业账号

    被利用的机制：语音钓鱼 + Duo 推送轰炸，最终拿到 VPN 与内网访问；攻击者自称 Yanluowang，声称窃取大量文件。

    影响：公司承认部分数据被访问，事件与同期多起「vishing + MFA 疲劳」 campaigns 同源。

    教训：员工的个人账号也是攻击面；推送认证必须带上下文与限速，否则就是可被疲劳攻破的确认框。

    认证
  • 2022-12

    LastPass

    入口：2022 年 8 月开发环境泄露的凭据，加上一名 DevOps 工程师家用电脑被入侵

    被利用的机制：用前期侦察得到的信息进入云存储，导出客户保险库备份（含站点 URL、加密字段与部分未加密元数据）。

    影响：加密保险库被带走；主密码未泄露，但弱主密码可被离线爆破，成为后续大量账号接管的源头。

    教训：密码管理器的威胁模型是「离线爆破」：KDF 强度、主密码强度与泄露范围披露同样重要。

    会话
  • 2023-07

    Microsoft / 约 25 家组织（Storm-0558）

    入口：签名密钥从崩溃转储中被提取，配合令牌校验缺陷

    被利用的机制：攻击者用消费者账号的签名密钥伪造企业租户令牌；接受端未校验签发者，导致「签名有效但 issuer 不对」的令牌被接受，读取 OWA 邮件。

    影响：约 25 家组织邮箱被访问，含美国政府机构；微软更换密钥并修复校验逻辑。

    教训：密钥管理之外，校验逻辑同样是边界：签名有效 ≠ 令牌可信，iss/aud/scope 必须逐项对。

    断言
  • 2023-09

    MGM Resorts / Caesars（Scattered Spider）

    入口：打客服电话冒充员工，要求重置 MFA

    被利用的机制：十余名攻击者用 LinkedIn 收集的信息社工 IT 帮助台，重置多因素认证后进入 Okta 与内网；随后勒索。

    影响：MGM 称事件对季度业绩影响约 1 亿美元；Caesars 据报支付约 1,500 万美元赎金。

    教训：身份体系最脆弱的一环往往不是协议，而是「有人可以帮你重置」的那个流程。

    恢复
  • 2023-10

    Okta 支持系统泄露

    入口：攻击者拿到支持系统的服务账号凭据

    被利用的机制：在 Okta 的客服工单系统里读取客户上传的 HAR 文件，其中包含会话令牌；据此访问部分客户环境。

    影响：Okta 确认 134 家客户受影响；Cloudflare 等公司在数周内披露连带事件。

    教训：支持系统是高权限旁路：HAR、截图、日志里常带活令牌，必须按生产凭证对待。

    恢复
  • 2023-10

    23andMe

    入口：撞库（用户在其他站点泄露的密码）

    被利用的机制：攻击者用凭证填充登录约 1.4 万个账号，再通过「DNA 亲属」功能横向拿到约 690 万用户的数据。

    影响：约 690 万用户信息泄露；公司面临集体诉讼与监管调查。

    教训：账号体系不是孤岛：一个「社交/亲属」功能可以把单账号失陷放大到整个关系图谱。

    凭据
  • 2023-11

    Cloudflare

    入口：Okta 事件连带：攻击者用此前窃取的服务账号令牌进入 Okta

    被利用的机制：在 Okta 中创建新的身份提供方与管理员账号，再据此生成 Cloudflare 的控制台 API 令牌，访问少量系统。

    影响：公司在感恩节期间自行发现并处置，称客户数据与生产系统未受影响。

    教训：IdP 被攻破后，攻击者会「再造一个 IdP」来持久化；对 IdP 配置变更本身要有独立监控。

    断言
  • 2024-01

    Microsoft（Midnight Blizzard）

    入口：对遗留的非生产租户做密码喷洒

    被利用的机制：拿到一个测试租户的账号后，创建 OAuth 应用并授予高权限，读取公司邮箱（少量高管与安全团队）。

    影响：微软披露被访问的邮件数量有限，但事件暴露「历史租户 + OAuth 应用」的组合风险。

    教训：退役租户、测试应用、遗留授权是身份体系里最容易被漏掉的资产。

    授权
  • 2024-02

    Change Healthcare

    入口：Citrix 远程访问入口未启用 MFA

    被利用的机制：攻击者用泄露的凭据登入远程桌面，横向到核心系统；ALPHV 勒索并要求赎金。

    影响：支付约 2,200 万美元赎金；约 1.9 亿人的健康数据受影响，成为医疗行业最大规模事件之一。

    教训：「一个没上 MFA 的远程入口」足以让整条业务停摆；身份覆盖要按资产清点，而不是按部门。

    认证
  • 2024-06

    Snowflake 客户群体（UNC5537）

    入口：从信息窃取木马日志中获得的账号密码

    被利用的机制：受害账号未启用 MFA，攻击者直接登录 Snowflake 实例，导出大量数据并勒索。

    影响：约 165 家组织被针对，Ticketmaster、Santander、AT&T 等相继披露大规模数据泄露。

    教训：凭据泄露是常态，MFA 与网络访问策略才是兜底；SaaS 的「默认安全」需要客户自己补齐。

    凭据
  • 2025

05 · 防御

优先级怎么排

  1. 先把没有 MFA 的入口全部关掉（VPN、远程桌面、管理后台、SaaS 管理台）。Change Healthcare 与 Snowflake 都属于这一类。
  2. 再把 MFA 换成抗钓鱼的（Passkey / 安全密钥），尤其是管理员、财务、HR、IT 服务台。
  3. 然后缩短会话与令牌寿命，并把高价值应用改成条件访问。
  4. 最后补恢复流程与支持系统——它们常是攻击者绕开前面三项的通道。

标准怎么说

协议规范 NIST SP 800-63B（2025-08）：AAL2 必须提供抗钓鱼认证选项；AAL3 要求抗钓鱼且私钥不可导出，同步类认证器不得用于 AAL3。同时把「认证疲劳」（反复推送直到用户误点）列为正式威胁。

协议规范 RFC 9700（2025-01）：弃用隐式流与不带 PKCE 的授权码流；要求精确匹配 redirect_uri、一次性 state、令牌绑定与受众校验。

给工程团队的 8 条落地细则
  • 身份主键用 sub，不用 email / 手机号。email 会变、手机号会回收，二者都不适合当主键。
  • 所有断言都做五项校验：签名、iss、aud、exp/nbf、nonce 或 InResponseTo。少一项就等于少一道门。
  • 授权码流必须带 PKCE，包括「有后端」的 Web 应用；移动端与 SPA 更是必须。
  • 会话 Cookie：HttpOnly + Secure + SameSite=Lax/Strict，登录成功后轮换会话 ID。
  • 令牌只存后端，前端拿不到 refresh token；日志里禁止出现 id_token、code、Cookie。
  • 登出与改密要吊销全部会话，并给出「我在哪些设备登录」的可见页面。
  • 对象级授权中间件统一处理「这条记录属于谁」，别让每个接口自己判断。
  • 把 IdP 配置变更当高危变更：federation、签名证书、企业应用授权、条件访问策略，每一项都要变更审计与告警。

06 · 三个专题

为什么这三件事值得单独说

前面是地图，这三节是地图上最容易被误读的三块地形。

一、Passkey 为什么能挡住实时钓鱼，又挡不住什么

WebAuthn

实时钓鱼（AitM）之所以有效，是因为它让用户在「看起来对、其实不对」的页面上完成认证，然后把结果中继到真实站点。TOTP、短信、推送都拦不住它——这些凭据本身不携带「我在哪个站点使用」的信息。

WebAuthn 的关键是把两件事绑死：私钥留在认证器里（钓鱼站拿不到可复制的秘密），签名覆盖源站信息（rpIdHash 与 clientDataJSON.origin）。钓鱼域名发出的 challenge，即使被转发到真实站点，签名也对不上——浏览器只会在 rp.id 匹配时交出凭据。

它挡不住的部分同样明确：账号恢复、会话 Cookie 窃取、IdP 侧被攻破、以及用户在自己设备上被骗授权。Passkey 保护的是「认证这一秒」，不是整条链。

二、Golden SAML 为什么难防：签名者就是身份源

案例 c1 / c6

普通伪造是「冒充用户」，Golden SAML 是「冒充 IdP」。攻击者拿到 ADFS 的 token 签名证书后，可以离线为任意用户、任意权限签发断言，所有 SP 都会验签通过——因为签名确实是真的。

这类攻击的检测几乎不可能靠单条日志：登录来自正常 IP、正常时间、MFA 已完成（因为不需要 MFA）。可用的信号只有行为层面的不一致：同一 IdP 突然出现大量新设备、断言签发量与登录量对不上、某个账号在极短时间内从不可能的两地登录。

所以防御重心在「事前」：签名证书与 DKM 进 HSM、双人审批、最小权限、把 ADFS 服务器当成域控级别资产。Storm-0558 是同一逻辑的变体——密钥泄露只是前半段，后半段是接受端没校验 issuer。

三、为什么「缩短会话」比「再加一层 MFA」更划算

算一笔账

假设 1 万个账号，定向钓鱼每次成功率为 3%，会话有效期为 30 天。攻击者只要在整个月里持续投放，命中期望是 300 个账号，而每个被钓中的会话在这 30 天里每天都能用——有效攻击面是 300 × 30 = 9,000 账号·天。

把会话缩到 12 小时、并加入设备绑定后，同样的 300 次命中只能在半天内有效，且换设备即失效：有效攻击面降到 300 × 0.5 ≈ 150 账号·天，相差 60 倍。再叠一层可中继的 MFA，只会把成功率从 3% 压到 2%，量级完全不能比。

这就是为什么 Google 做 DBSC、微软做 Token Protection 与 CAE：它们不是在提高「登录难度」，而是在压缩「登录之后」的价值。

07 · 落地

180 天：从「有 MFA」到「有身份边界」

不追求一次换完，按风险倒排。每一阶段都有可验收的产出，而不是「上线了某个产品」。

0–30 天摸清家底

  • 资产清单：所有 IdP、所有能登录的入口（含 VPN、堡垒机、SaaS 管理台、客服系统）。
  • 标出没有 MFA 的入口，按「能碰到多少数据」排序。
  • 导出全部长期令牌 / API key / OAuth 授权，标记无主与过期项。
  • 产出：一张「身份攻击面」表 + 前 10 个必须本周修的点。

31–90 天堵住大洞

  • 全量 MFA 覆盖远程入口与管理后台；关闭遗留协议（SMTP AUTH、Basic、NTLMv1）。
  • 管理员、财务、IT 服务台换成 Passkey 或硬件密钥。
  • 会话寿命统一收敛；登出与改密强制吊销。
  • 产出：无 MFA 入口数 = 0；高价值账号抗钓鱼覆盖率 ≥ 90%。

91–180 天加检测与恢复

  • 把 IdP 配置变更、federation、证书、企业应用授权纳入告警。
  • 恢复流程重做：冷却期 + 原设备通知 + 双人审批 + 全量审计。
  • 做一次「身份红队」：钓鱼中继、MFA 疲劳、客服社工、令牌重放各演练一次。
  • 产出：四类攻击的检测规则与演练报告。
验收标准

不要用「部署了 X」当里程碑。可验收的指标只有四个：无 MFA 入口数、抗钓鱼认证覆盖率、会话平均寿命、从发现异常到吊销会话的分钟数。最后一个尤其重要——它决定了前三个指标在真实攻击里还剩多少价值。
