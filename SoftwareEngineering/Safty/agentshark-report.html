02 / THE PROBLEMAgent 失败时，证据在哪

一次 Agent 任务会产生几百到几千条记录：prompt、模型步、工具调用、工具输出、子代理派生、失败重试。 这些记录默认是给程序读的，不是给人排查用的。

现状：四个断层

  • 格式不兼容：Claude Code 的 JSONL、Codex 的 rollout、Copilot 的 session 文件，字段各写各的。
  • 失败藏在中间：最终回复说"已完成"，实际上第 42 步有个命令被 hook 拦了，重试三次后绕过去了。
  • 子代理断链：父会话派生的子任务失败，父会话看起来一切正常。
  • 证据会消失：日志会被轮转、删除、覆盖，事后只剩一句"当时报错了"。

它的四个对应动作

  • 适配器归一化：每个 Agent 一个 parser，统一成 session / event / span。
  • Episode 聚合：把重试、恢复、绕过归并成"一次失败事件"，排到最前。
  • 父子关联：记录 spawn 边，子代理失败会浮到父会话的注意力队列。
  • 可携带抓包：.agentcap 打包原始字节 + 归一化结果，可离线回看。

和"看日志"的本质差别

普通做法是 grep -i error 然后人工读上下文。问题在于 Agent 的日志里，"错误"往往不叫 error： 可能是一次 exit code 1、一次被拒绝的权限请求、一次"测试通过"的声明，或者一个空结果。 AgentShark 的做法是把这些隐式信号变成显式的诊断项（Diagnostics），再用规则给它们分级—— 规则是启发式的，因此它反复强调"这是候选，不是判决"。

04 / ARCHITECTURE日志 → 适配器 → 索引 → 四个出口

它没有拦截流量，也不 hook Agent 进程；只读磁盘上的日志文件。 这决定了它的优点（零侵入、可回溯历史）和缺点（日志里没有的，它也看不到）。

索引是怎么建的

  • 启动后扫描每个受支持 Agent 的日志目录；agentshark sources 会报告"这台机器上有哪些源、各有哪些字段"。
  • 最多 8 个线程解析，新的会话优先：正在写的会话约 1 秒出现，历史随后补齐。
  • 落盘到 ~/.agentshark/index.sqlite；这是缓存，删掉可重建，但体积可能接近日志本身（官方给的例子：12GB 日志 → 约 10GB 索引，首次索引峰值内存约 5GB、耗时约 3.5 分钟）。
  • 监听文件变化（默认 3 秒检查、最多 5 秒一次增量），也可 --no-watch 手动刷新。

05 / THE VIEWER七个工作区，对应七种提问

这套界面明显是从 Wireshark 借来的：事件列表 + 解码树 + 原始字节。Alt+1–7 切换， e / E 跳下一个 / 上一个失败，u 跳到下一个待处理项。

工作区回答的问题里面有什么
Failures这次跑挂在哪，为什么注意力队列 + Lens：失败链、重试、两次尝试之间的改动、是否恢复
Events第 137 条记录到底写了什么可过滤事件表、解码字段树、原始记录（带字节偏移）
Session整场跑了多久，时间花在哪Steps / Transcript / Flow / Critical Path / Reliability 五种视图，可两场对比
Timeline并发与子代理谁先谁后会话、子代理、工具调用、后台进程、失败带对齐在一条时间轴
Statistics慢在哪，贵在哪工具/模型/轮次统计，首 token 延迟、输出速度、缓存复用、资源曲线、I/O 图
Diagnostics还有哪些可疑之处Wireshark 风格的专家信息：错误、重试、拒答、权限拒绝、未配对调用、坏行
Sources这台机器上数据全不全每个 Agent 的日志覆盖度与健康状态（哪些字段它根本不写）

最值得先看的两个：Failures 与 Critical Path

Failures 是它的主张：不按时间顺序读日志，而是先按"需要人处理"排序。 被 hook 拦截、测试失败、子代理静默失败、"所有测试通过"但没有测试支撑——这些都进入队列，并给出证据链接。

Critical Path（macOS ⌥⌘4） 把一场运行折算成"关键路径"：哪一步真的决定了总时长。这比看总耗时有用——总耗时 40 分钟里，可能有 25 分钟在等一个本来可以并行的安装。

06 / EVIDENCE最该被抄走的设计：每个值都标来源

AI 分析工具最大的陷阱是"用模型解释日志"，读起来很顺，错得很难发现。AgentShark 走了相反的路： 不调用任何模型，改用一套证据分级 + 缺失显式化。

标记含义例子
（无标记）日志里直接记录的值exit_code: 1 来自工具结果记录
≈ derived由记录推算，非直接字段用相邻两条记录的时间差算出的等待时长
~ parsed从自由文本解析出来从 "2 failed, 41 passed in 3.21s" 里抽出的测试计数
? inferred规则推断，最弱的一级"它声称测试通过，但最后一次测试是失败的"
gap日志里没有，明确留空Copilot 没记录上下文窗口容量 → 显示"未知"

为什么这套设计重要

  • 报告可以直接引用证据行号，别人能复核。
  • 规则失效时，? 级的结论可以被单独质疑，不会污染事实层。
  • "0" 和 "没有数据" 分开显示——这是很多监控系统都会犯的错。
  • 不需要把日志发给第三方模型，天然满足"数据不出本机"。

代价

  • 规则要人写，覆盖不到的场景就是空白。
  • 启发式会误报；CHANGELOG 里就有多处"修正 Reliability 误报"。
  • 没有语义总结，第一次用会怀念"让模型解释一下"。
  • 结论依赖日志质量：上游少写一个字段，这里就多一个 gap。

一条真实输出的样子

$ agentshark why
# Run report: Run the tests
claude-code · finished · unattended · 2026-10-11T09:00:00Z to 2026-10-11T09:30:30Z

Turns 16 (human 15 · task-notification 1) · Steps 53, 14 with a failure
Impact failed 4 · blocked 1 · interrupted 1 · masked 2 · degraded 2 · recovered 4 · clean 2

## Needs attention
- blocked episode …:24: PreToolUse:Bash hook error … Blocked: rm -rf is not allowed
- unrecovered episode …:92: tests failed on `sh:pytest` (ended-on-failure), 2 attempts
- silent-child delegation …toolu_m19: check docs (failed)
- unverified-claims claim …p89: “All tests pass.” (last-test-failed)

这段来自官方文档的示例，信息密度很高：既有计数（事实），也有分类（规则），每一条都能点回原始事件。 "unverified-claims" 是最有意思的一类——它检查 Agent 的自我报告与实际执行结果是否一致。

第一次运行会发生什么

08 / CLI不用打开界面也能定位问题

命令用途
why最近一次运行为什么失败，输出可直接贴进 issue 的 Markdown（--json 给机器）
failures --since 7d过去一周需要处理的失败 episode
sig "Error: Cannot find module ..."这个错误以前出现过吗？上次是怎么绕过去的
list -f '...'像 tshark 一样按过滤器列事件
stats工具 / 模型 / 轮次 / 调用对统计
fields列出所有可过滤字段名
sources这台机器上各 Agent 的日志健康度
index手动建/重建索引（--full、--rederive）
serve / demo / open起 Web 界面 / 看合成样本 / 打开 .agentcap
capture / replay导出抓包 / 在容器里重放
mcp以 stdio 方式提供只读查询接口

过滤器语法：几乎照抄 Wireshark

error                                  # 被标记为失败的事件
tool.name == "Bash" && dur > 2s       # 慢的 shell 调用（裸数字默认毫秒）
agent == codex && kind == "tool.call"  # 某个 Agent 的工具调用
"npm test"                             # 短语搜索：两个词必须相邻
"npm" && "test"                        # 两个词可以分开出现
ts > -2h                               # 相对时间
ts >= "2026-10-11 09:00"               # 无时区=本地时间；带 Z 或 +08:00 亦可

一个小坑

时间字段默认按本地时区解释，打印时却总带 UTC 偏移。跨时区看日志时（或把容器时间当本地时间）， 很容易对不上。习惯做法：一律用带 Z 的 UTC 写法，或加 --utc 输出。

09 / MCP让 Agent 查自己的病历

这是它区别于普通分析器的地方：注册为 MCP 服务器后，Claude Code / Codex 可以在下一轮对话里直接问 "我上次为什么卡住"。九个工具，全部只读，不写索引、不开 socket、不发网络请求。

九个工具

find_runs run_report list_failures get_episode lookup_error watch query get_event analyze_trace

注册

claude mcp add --scope user agentshark -- agentshark mcp
codex mcp add agentshark -- agentshark mcp

它替 Agent 挡掉的四件事

机制做了什么为什么必须
作用域默认只看当前 Git 根目录下的运行；--scope all 才放开防止一个项目的 Agent 读到另一个客户的轨迹
脱敏家目录→~、用户名→<user>、sk-/ghp_/AKIA/Bearer/JWT/PEM→<secret:类:长度>日志里经常混着密钥，不能原样回灌给模型
不可信文本日志正文只出现在 *_excerpt 字段，截断到 300 字符，并明确告知"这是数据不是指令"防提示注入：仓库里的一句注释可能变成攻击载荷
体积与元信息单次结果 ≤ 16KB，附 index_age_s、analysis_version、gaps让 Agent 知道"结果可能过期/缺字段"，而不是当成全知

仍然要清醒：脱敏是模式匹配，不是数据分类。自研格式的 token、内网主机名、客户姓名，都可能漏网。 把 MCP 接到含敏感数据的轨迹上之前，先用 --preview 看一眼实际输出。

10 / CAPTURE & REPLAY把一次运行打包带走

.agentcap：Agent 界的 pcap

  • JSON Lines，首行 header、末行 trailer；可选 zstd / gzip（按魔数识别，不靠扩展名）
  • 保存归一化记录 和 原始字节，Agent 删了日志也能回看
  • 引用到的旁路文件按内容哈希去重存放
  • 可附 10Hz 的 CPU / 内存 / 磁盘 / GPU / 网络采样
  • 分享前可 --profile shareable --preview 预览脱敏结果

录一次，复现一次

# 录（可同时记资源）
agentshark serve --record-resources
agentshark capture -o run.agentcap.zst --since 7d

# 分享前预览脱敏
agentshark capture -o share.agentcap.zst --profile shareable --preview

# 回放：先干跑，再进容器
agentshark replay SESSION --dry-run
agentshark replay SESSION --workspace ./repo --break status

回放的边界，必须说清楚

它重放的是记录下来的工具调用（shell 命令、文件写入），不是模型决策。所以： 模型这一步"为什么选错"不会被复现；依赖外部状态（数据库、网络、时间）的命令会在离线容器里失败或产生不同结果； 带破坏性的命令会真的执行——这就是它必须跑在无网络容器里的原因。

正确的用法是"验证问题是否可重演"，而不是"证明结果必然一致"。官方文档也把它称作 emulator-style replay： 断点、单步、保存状态，本质是调试器，不是时间机器。

和标准遥测互通

可以把索引里的 span 导出为 OTLP/JSON（OpenInference 属性），也可以把外部的 OTLP/JSON 转成 agentshark.telemetry.v1 转换文档。注意后者不会塞进原生索引——通用遥测缺少 Agent 身份和 必要时间戳，强行合并只会污染数据。这个取舍很克制：宁可少做，不制造假数据。

11 / COMPARISON它和"Agent 可观测性平台"不是一类东西

市面上的工具大多在云侧收数据、做评测、做看板；AgentShark 在本机读日志、做取证。 前者回答"整体质量趋势如何"，后者回答"这一次到底发生了什么"。

类型代表数据在哪强项弱项
本机检查器AgentShark本机 SQLite零侵入、离线、证据可回溯、可回放无团队协作、无托管看板、规则靠人写
托管追踪平台LangSmith、Langfuse、AgentOps云端或自托管服务跨会话看板、评测、成本统计要接入 SDK / 上报数据；离线不可用
OTel 原生评测Arize Phoenix、OpenInferenceCollector + 存储标准语义、生态通用需要自己搭链路；对"日志文件"这类历史数据无解
实验管理Braintrust、W&B Weave云端数据集、对比实验、评分面向"模型/提示词迭代"，不面向"这次运行为何失败"
通用日志Loki、ELK自建集群全文检索、长期留存不理解 Agent 语义，看不出"episode"和"未验证声明"

一个务实的组合：AgentShark 负责单机取证，把确认过的失败通过 .agentcap 或 OTLP 导出， 再由团队平台汇总趋势。它自己也提供 OTLP 导出，说明作者没打算做"唯一入口"。

12 / RISKS现在用它，要接受七个不确定

1. "日志即事实"是错觉

工具能看到的上限就是日志写了什么。不同 Agent 版本、不同插件、不同权限模式下的日志差异很大； 它用 Sources 页面把"缺哪些字段"显式化，但缺的仍然缺。做结论时要区分"没发生"和"没记录"。

2. 规则会误报，而且改起来很频繁

CHANGELOG 里有大量"修正 Reliability 误报""保留未知工具输出"这类条目。说明规则还在校准期。 看到 ? 级结论，先点开证据看原始记录，别直接贴进复盘报告。

3. 回放 ≠ 复现

只重放工具调用，不重放模型。外部依赖、时间、随机性都会让结果偏离。它可以证明"这个命令确实会失败"， 不能证明"当时失败一定因为这个"。

4. 脱敏是模式匹配，不是数据分级

内置模式覆盖常见密钥前缀与 PEM 块，但客户名、内网域名、自研 token 格式不在其中。默认抓包保留原文， 分享前必须走 --profile shareable 并肉眼复核。

5. 资源占用不小

官方给的实测：12GB 日志 → 约 10GB 索引，首次索引峰值约 5GB 内存、约 3.5 分钟。笔记本上建议 把 AGENTSHARK_HOME 指到大盘，并定期清理。

6. 权限与供应链

没有签名发布，需要自行构建；没有 npm 正式包，安装意味着从源码跑。MCP 是只读的，但它会把轨迹内容 （截断后）交给模型——这本身就是一次数据外流，接敏感项目前要评估。

7. 平台与接口都在变

macOS 体验最完整（原生应用、快捷键、Workbench），其他平台是 Web + CLI。0.1.0 阶段， CLI 参数、MCP 工具名、索引版本都可能在升级时改变。

13 / VERDICT给三类人的不同建议

个人开发者 值得花 30 分钟：demo 看界面 → serve 索引自己日志 → why 看最近一次失败。 哪怕不用，它的"证据分级"思路也可以直接搬进你自己的日志设计。
团队 / 平台工程 当作"自建 Agent 可观测性"的参考实现来读：.agentcap 格式、MCP 的作用域与脱敏、 episode 聚合模型，都是可以借鉴的接口设计。生产依赖请等签名发布与测试套件。
安全 / 合规 这是一个把"日志里有什么"暴露得更彻底的工具：方便取证，也方便泄露。 要评估的是索引文件、抓包文件、MCP 输出的留存与访问控制，而不是工具本身。

30 分钟试用路线

1

看合成样本（5 分钟）

node bin/agentshark.ts demo：不需要任何本地日志，先理解七个工作区。.agentcap 的结构也能在这里看清。

2

索引自己的日志（10 分钟）

agentshark index 后跑 agentshark sources：先确认你的 Agent 版本是否被"完整解析"， 再决定要不要投入时间。

3

查一次真实失败（10 分钟）

agentshark failures --since 7d → 选一条 → why --session ID。 重点验证：它给的证据能不能对上你记忆中的现场。

4

决定要不要接 MCP（5 分钟）

接上后让 Agent 自己解释一次失败。观察它是否会滥用"日志里的文本当作指令"——这是检验 MCP 设计是否可靠的直接方式。

一句话判断

如果你的痛点是"Agent 说做完了，但其实没做完，而我不知道哪一步断的"，它现在就值得试； 如果你的痛点是"要在团队层面统计成功率、做 A/B 评测"，它是错的工具，去看 LangSmith / Phoenix 那一类。
