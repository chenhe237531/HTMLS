摘要：它改了问题，不是改了工具

Cairn 不是“更强的渗透工具集”，而是把渗透测试重新表述为：已知起点、已知终点、路径未知的图搜索。它把这条搜索的每一步都写成图上的节点和边，让多个无角色 LLM Worker 并发推进。

真正的工程内核只有三条不变量：Agent 不写 API、Dispatcher 独占写回、事实只增不改。剩下全是围绕这三条做的调度与容错。

0

处 MCP / RAG / 角色模板（作者明确如此设计）

三个判断

  1. 架构值得抄，战绩需要打折。协议与调度设计有真东西（双阶段收尾、单写者、lease 租约）；但“54/54 AK、第三名”是单次比赛自述，没有公开基准与复现脚本。
  2. “通用”目前是结构上的通用，不是证据上的通用。把问题抽象成图搜索确实不限于渗透，但公开验证只有渗透这一个域——“零 MCP、零 RAG、零角色”在渗透里成立，不代表换域也成立。
  3. 默认配置很危险。Agent 以 --dangerously-skip-permissions 级别运行、容器挂宿主 Docker socket、local 模式无沙箱。它假设你在一台可丢弃的隔离机器上跑。
怎么读这份报告：第 01–06 节讲机制（含可点的图生长演示与并发计算器），第 07–09 节是可证伪的部分——数字、优点、风险，每条都标了依据出处。
01

它是什么：一张只生长不修改的事实图

官方定位：“Cairn 是一个通用问题求解引擎。它不定义角色，不定义工作流。给定起点和目标，它在未知状态空间里搜索一条路径。” 渗透只是第一个被验证的域。

FACT

事实 = 节点

已确认的客观结论，写进黑板。只有描述文本，没有状态字段，只增不改、永久保留。

例：f002 布尔盲注确认，参数 user
INTENT

意图 = 边

从若干事实出发的探索方向。未结论时 to=null，被某 Worker 认领后 worker 非空。

例：i003 from f002「时间盲注 dump users 表」
HINT

提示 = 旁注

人随时注入的判断，不在图里、不参与因果推理，Worker 下一轮读图时吸收。也可用来做“态势压缩”。

例：h001 WAF 只拦 union，改用时间盲注

设计血缘（这是它最有意思的部分）

  • 黑板架构（Hearsay-II，CMU 1970s）：多个专家读写同一块黑板，无中央调度。Cairn 的差别是把“行动记录”也留在图上——于是图同时是知识库和审计日志。
  • 共识主动性 / 信息素（stigmergy）：个体不直接通信，只通过改变共享环境间接协调。Worker 之间确实没有任何消息通道。
  • OODA 循环：每个 Worker 执行 观察图 → 定位态势 → 决定意图 → 执行探索。
  • 任务式指挥（Mission Command）：只下发目标，各单位按态势自主决策，Hint 扮演“指挥官意图”。

所以它和主流“多 Agent 框架”的差别是可量化的：没有角色表、没有节点/边编排、没有消息总线。任务不是预先声明的，而是从图的当前状态即时生成的——图里没有可认领 intent 时，就会自然产生一个 reason 任务来制造 intent。

一个容易误读的点：README 说“不定义工作流”，但代码里确实有三个硬编码任务类型（bootstrap / reason / explore）。准确说法是“不定义领域工作流”：渗透步骤没有一条写死在代码里，但“如何推进搜索”这个元流程是固定的。
02

架构解剖：四层，三种人写不同东西

Cairn 的分层不是为了微服务好看，而是为了把“谁能写协议”收窄成一个点。

层实现职责不做什么
Cairn Server FastAPI + SQLite（server/，257 行 services + 358 行 projects 路由） 协议真相源：保存 Project / Fact / Intent / Hint，维护 claim-heartbeat-conclude 生命周期与 reason 租约 不做任何推理、不做调度、不调用 LLM
Dispatcher Python 线程池（scheduler/loop.py 935 行，最大单文件） 读图 → 选任务类型 → 选 Worker → 认领 → 起进程 → 解析 JSON → 写回；管容器、超时、健康检查 不直接执行渗透动作；它是唯一的协议写入者
项目容器 Kali rolling 镜像（container/Dockerfile） 提供工具链与网络环境；每个项目一个容器，多个 Worker 进程共享 不持有状态，容器可 stop / remove 后重建
Worker / Agent CLI driver：claudecode / codex / pi / mock 收 prompt、在容器内干活、输出结构化 JSON 不认领 intent、不发心跳、不调 API——它连 Cairn 的存在都不知道

为什么“Agent 不碰 API”是关键设计

在一次真实渗透里，模型的输出经常是烂 JSON、跑偏的 shell、半截日志。如果把写协议的能力交给模型，图会被污染，而且你没法区分“图错了”还是“模型错了”。Cairn 的做法是：模型只负责产出结论，Dispatcher 负责判断这份结论配不配进图（schema 校验、`accepted` 检查、写回失败即丢弃）。

代价是 Dispatcher 变成了单点，也是它代码量最大的原因（935 行循环 + 481 行 bootstrap 任务 + 424 行配置校验）。

执行主链路（一次 explore 的完整往返）

  1. 读图结构化接口用于调度判断；GET /projects/{id}/export?format=yaml 单独取一份 YAML 快照给 prompt 用。
  2. 选任务 + 选 Worker按任务类型、并发余量、优先级、健康状态筛；explore 还要先成功 claim 到 intent。
  3. 认领POST /intents/{id}/heartbeat 抢占；失败就换下一个，抢不到就不启动进程。
  4. 起进程在项目容器里 exec claude --session-id ... -p -- "{prompt}"，stdout 全文作为模型正文。
  5. 解析从 stdout 抽取 JSON，逐字段做 schema 校验；accepted:false、非法 JSON、字段缺失都直接作废。
  6. 写回POST /intents/{id}/conclude 落 Fact 并关边；失败则 release，不写任何图数据。
顺手记一个漂亮实现：“完成项目”不是一个独立状态位，而是一次 complete 调用插入的 to='goal' 的 Intent（见 server/routers/projects.py）。也就是说完成本身也是一条边，图里能看到“是谁、从哪些事实、判定达成”的完整证据链。这个细节比多数 Agent 框架的 “done = true” 认真得多。

04

任务与契约：三类任务，两种收尾

整套系统只有三类任务，全部由同一个 Worker 执行——Worker 没有“角色”，只有当前被派的活。

任务什么时候派输入必须输出失败怎么算
bootstrap 项目初始态：facts 恰好只有 origin+goal，且没有普通 intent origin / goal / hints（不读图） 成功时必须同时给 fact 和 complete 超时 → 同 session 进 bootstrap_conclude，只产 fact；两阶段都失败才 release
reason 无未认领 intent，且出现“新态势”（Fact 或 Hint 变多，或有 intent 全部收口） 整图 YAML + 合法 fact id 列表 + 未结论 intent 列表 complete ／ intents[] ／ 空对象 超时或非法输出直接作废，不写图
explore 存在可认领的未结论 intent 整图 YAML + intent id + intent 描述 一条客观事实 description 超时 / 解析失败 → 同 session 进 explore_conclude；仍失败则 release

双阶段收尾：这套设计里最实用的一手

LLM 跑到 300 秒还没输出合法 JSON 时，常见做法是“任务失败、白干”。Cairn 的做法是：杀掉进程、保留 session id、在同一 session 里补一个“别继续探索，只总结到目前为止确认了什么”的收尾 prompt，用剩余的 conclude_timeout（示例 90 秒）产出一条 Fact。

这解决的是一个真实痛点：探索过程本身往往已经挖到东西，只是没跑到“收尾”就开始写总结或超时。把已发生的探索捞回来，比重新派一次任务便宜得多。

状态机

active
接受写入，正常调度
stopped
硬停止：取消本地任务、停容器、不再落 Fact；可恢复
completed
不再接受写入；判断错了可 reopen 回 active
deleted
orphan 容器直接删除（不是仅停止）

两条不被允许的偷懒

  • 模型不能返回“我拒绝协助渗透”当结论——explore 的 description 必须是客观事实。
  • 模型不能只给结论不给证据链：complete.from 必须是图上真实存在的 fact id。
看 explore 的输出契约（服务端会逐字段校验）

{"accepted": true, "data": {"description": "确认 /search 的 q 参数存在报错型注入，DB 为 MySQL 5.7"}}

// 没打出漏洞也要给客观结论，不能空手

// reason 的两条出路

05

调度与并发：四个旋钮，一个真正的瓶颈

调度逻辑维持在一个刻意的低复杂度：一个 tick，按顺序试 bootstrap → reason → explore，试不到就启动新项目。

# scheduler/loop.py 的核心形状（伪代码）
for project in running_projects_round_robin:
    if has_dispatchable_bootstrap(project): dispatch(...); continue
    if has_dispatchable_reason(project):    dispatch(...); continue
    if has_dispatchable_explore(project):   dispatch(...); continue

if running_project_count < runtime.max_running_projects:
    maybe_start_one_new_project()

四层限额，谁先卡住

runtime.max_workers 看着是“并行 8”，但示例配置里两个 worker 各 max_running: 2，Σ=4——所以真实并行上限是 4。这个差别在调优时很要命：加项目不会更并行，只有加 worker 配额才会。下面这个计算器可以自己试（数字可以改）。

瓶颈：Σ workers[].max_running —— 加项目不会更并行，只有加 worker 配额才会。
注意：单项目内同一时刻最多 1 个 reason，它会占用 max_project_workers 的一个名额。

reason 的触发去重：防的是“自己吵自己”

朴素的实现会让 reason 刚创建的 intent 立刻触发下一次 reason，形成风暴。Cairn 的做法是把“重触发条件”限定为三种可观测的变化：

  • Fact 数量增加
  • Hint 数量增加
  • 项目从“还有 open intent”变成“没有 open intent”

“intent 数量增加”被刻意排除在外——因为那通常正是上一次 reason 的产物。这个判断很小但很关键，多数多 Agent 系统就是在这类“事件回环”上烧掉预算的。

心跳与 lease：把耦合做成显式不变量

runtime.interval（默认 3s）被同时用作主循环节拍和 claim 任务的 heartbeat 周期。这本来是个危险耦合，Cairn 的补法是启动时校验服务端的 intent_timeout / reason_timeout（默认 15s）必须大于 interval，小于 2 倍时还要告警——心跳余量不足会先被说出来，而不是等线上出现“自己的 intent 被别人抢走”。

仍有的隐患：超时清空 worker 只发生在一轮 tick 之后，若某任务恰好在心跳与过期之间完成，理论上可能出现“同一 intent 被两个 Worker 同时探索”的窗口（后写的那次 conclude 会失败并被丢弃，不会污染图，但会白烧 token）。
06

协议面：16 个端点，一套租约语义

服务端刻意不做推理，只维护一致性——所以 API 很小，全部围绕“图的生长”和“谁在占用什么”。

端点作用谁调
GET/PUT /settings全局 intent / reason 超时（最小 5s，默认 15s）前端、运维
GET /projects项目摘要：fact / intent / hint 计数、可认领数、当前 reason 租约Dispatcher 每 tick
POST /projects建项目，同时写入 origin 与 goal 两个特殊 Fact人 / 前端
GET /projects/{id}完整图（facts / intents / hints）前端、Dispatcher
PUT /projects/{id}/statusactive ↔ stopped，硬停止会取消任务并停容器人
POST /intents声明一条意图（可同时认领，worker 必须等于 creator）Dispatcher（代 reason 写）
POST /intents/{id}/heartbeat认领 + 续租；首次心跳即 claimDispatcher
POST /intents/{id}/conclude落 Fact 并闭合这条边（to 只写一次）Dispatcher
POST /intents/{id}/release放弃本次尝试，intent 回到可认领状态Dispatcher
POST /projects/{id}/reason/claim项目级 reason 互斥租约（保证单项目只有一个 reason）Dispatcher
POST /projects/{id}/reason/heartbeat续租，状态对前端可见Dispatcher
POST /projects/{id}/hints注入人工提示；stopped / completed 状态下仍可写人
POST /projects/{id}/complete插入一条 to=goal 的 Intent 并置 completedDispatcher（代 reason 写）
POST /projects/{id}/reopen撤销完成态，回到 active 继续探索人
GET /export?format=yaml给 prompt 用的图快照Dispatcher
GET /export?format=timeline时间线导出，用于复盘前端、人

三个值得注意的语义细节

  • Fact 只增不改。“shell 掉了”不是修改旧事实，而是新增一条 f025 host-A shell 已断开。时序本身就是状态信息，读图的人自己判断可达性。
  • Intent 可以是超边。from 收多个 fact id，保留“多个已知事实共同支撑一次探索”的因果，而不是被迫选一个主事实丢掉上下文。
  • Hint 不受状态限制。项目 stopped 甚至 completed 时仍可继续写 Hint——它是一个旁路输入，用于在 reopen 之后把人的判断补进去。

前端是仓库自带的单文件 server/static/index.html（3,406 行，Alpine + Cytoscape，依赖全部 vendor 在本地），能直接看图、注入 Hint、导出 YAML / timeline。它不走 CDN，离线可用。

反过来，仓库本身的活跃度是真实的：4,746 星、918 fork（fork/star ≈ 19%，偏高，通常是“拿来改”的比例大）、70 次提交、3 个版本、18 个未关闭 issue。

做对了什么：七条可以直接抄的设计

  1. 协议只有三原语，没有 DSL没有角色表、没有节点编排、没有 YAML 工作流。换域时改的是 prompt 和容器，不是引擎——这是“通用”说法的唯一硬支撑。
  2. Agent 不写 API，Dispatcher 独占写回模型只产结论，协议由代码写。图被污染和被模型骗这两种故障，在这里被物理隔离了。
  3. 双阶段 conclude超时或解析失败时保留 session 做“只总结、不继续”的收尾，把已发生的探索捞成 Fact。省钱且显著提高单次任务的有效产出率。
  4. 完成即一条指向 goal 的边不留“done 标志位”，完成判定是谁、基于哪些事实，全部在图上可查。
  5. reason 用“新态势”去重只认 Fact / Hint 增加与 open→empty 转变，避免“提案→立刻再提案”的预算黑洞。
  6. 把隐藏耦合变成启动期不变量心跳周期复用主循环节拍是危险设计，但代码在启动时校验 server 超时 > interval，余量不足 2× 还告警。承认耦合并加护栏，比假装解耦现实。
  7. 可观测性优先稳定轮询不打日志、状态变化必打；容器 stop 而不是 remove，留现场给复盘；mock driver 能注入延迟与失败概率，让“超时 / 非法 JSON / 拒绝”这些路径可以在没有 LLM 的情况下测——13 个测试文件、2,603 行测试就是这么来的。
09

风险清单：先看高危三条

按“会不会真出事”排序，每条给出依据出处。授权与合规责任在 README 里被明确交给使用者，工程上没有任何 scope 强制。

级别问题依据建议
高 Agent 被赋予无审批执行权：claude --dangerously-skip-permissions、codex exec --dangerously-bypass-approvals-and-sandbox 设计文档「CLI 接入约定」；容器内是 Kali 全家桶 + network_mode: host 只跑在一次性 VM / 隔离网段；跑完销毁环境
高 docker-compose 把宿主 /var/run/docker.sock 挂进 dispatcher（它要建/删容器） docker-compose.yaml 等价宿主 root：不要在多人共享或生产宿主机上跑
高 local 模式无沙箱，Agent 以你的用户权限直接在宿主机执行 README「no sandbox」「runs with your user's permissions」 专用账户 + 专用机器；不要在你的日常工作站上用
中 单 Dispatcher、SQLite 单机、无 HA；作者明确不支持多实例共管同一服务端 设计文档「已知限制」第 10 条 当作单机工具，不要当平台底座
中 上下文随图线性膨胀：每次 reason/explore 都把整图 YAML 铺进 prompt prompt 契约 {graph_yaml}；作者自述零 RAG 长项目用 Hint 做态势压缩；限制 fact 描述长度，把原始数据放文件引用
中 成本与时长不可控点：3s tick、单任务 300s、示例 4 并发满打满算，且每次派发前先做一次 healthcheck ping dispatch.example.yaml、UNHEALTHY_RETRY_AFTER_SECONDS=5 先 1–2 并发、把 explore.timeout 降到 120 观察曲线
中 双轨许可：AGPL-3.0 + 商业授权。做成 SaaS 或嵌进闭源产品会触发 AGPL 义务 README「License」段落 商用前先谈授权，别事后补救
中 文档与实现漂移：设计文档写 reason 返回单数 intent，实际 prompt 用 intents[]（contracts 兼容单数）；驱动文档列 3 种，代码里有 4 种（含 pi） contracts.py 的 backward compat 注释；workers/registry.py 以代码为准；规范滞后说明迭代快于文档
低 图只增不改、没有失效标记，长任务会产生大量“已失效”的历史事实 协议文档「状态变化的表达」 靠 Hint 做人工压缩；前端按时间线阅读
低 战绩是自述，没有基准与复现脚本 README「Results」，仅一段文字 当作工程案例，不要当性能承诺
低 前端 3,406 行单文件 + 依赖直接 vendor，无构建链 server/static/index.html 改 UI 成本偏高，别指望二开体验好
最重要的一句：这套系统的默认形态是“把一台装了 Kali 的机器、以及一整个攻击面，交给一个不受审批约束的模型”。风险不在代码质量，在授权边界。README 的免责声明把责任完全交给使用者——它不是形式条款，是真的会发生。

部署与成本：两条路，先走轻的那条

路径 A：容器模式（完整）

docker pull --platform=linux/amd64 \
  ghcr.io/oritera/cairn-worker-container:latest
docker pull ghcr.io/astral-sh/uv:python3.13-trixie
cp dispatch.example.yaml dispatch.yaml   # 填 LLM 端点与 key
docker compose up --build

server 在 8000 端口，dispatcher 等健康检查通过后启动；每个项目一个 Kali 容器；数据落在 ./datas/cairn/。

路径 B：local 模式（推荐先试）

cp dispatch.local.example.yaml dispatch.yaml

# 终端 1：起服务端
uv run --project cairn cairn serve

# 终端 2：起调度器
uv run --project cairn cairn dispatch \
  --config dispatch.yaml

复用本机已登录的 claude / codex / pi，不需要 Docker、不需要在配置里放 key；代价是无沙箱、以你的权限运行。

上线前的三件小事

  • 先跑离线测试：uv run --project cairn --group dev pytest，不碰 Docker、不碰真实模型端点。mock driver 能复现超时、非法 JSON、拒绝等路径。
  • 把并发调到 1–2：示例配置 Σ max_running=4 已经能长时间占满一个 key；观察单任务耗时与 token 再放大。
  • 先确认心跳余量：启动日志会打印 server setting validated intent_timeout=15s interval=3s；如果看到 tight warning，先调大服务端超时。

成本怎么估：这套系统没有内置 token 计量。粗算式是「有效并行数 × 单任务时长 × 每任务输入 token（整图 YAML + 系统提示）+ 输出 token」，再乘模型单价。变量里最不直观的是输入 token 随图增长——同一道题跑到第 20 条事实时，每次 reason 的输入会比第 2 条事实时大一个量级。

横向对比：它到底比谁强，强在哪

方案协调机制状态表示需要预设角色/流程审计能力适合什么
Cairn 共享事实图 + 租约（无消息通道） DAG：事实节点 + 意图边 否（任务运行时生成） 强：图即日志，含失败与负结果 长链条、需要规划与多步验证的目标搜索
单 Agent + 工具 无（单线程会话） 上下文窗口 否 弱：只有 transcript 短任务、单点突破、人机协作
MCP 直连工具 无 无 否 弱 给现有 Agent 加一个工具能力（如 GhidraMCP）
多 Agent 框架
（LangGraph / AutoGen / CrewAI）		 消息传递 / 编排图 代码里的 state 对象 是：角色、节点、边 中：取决于是否自己记 trace 流程已知、要工程化落地的业务任务
传统扫描器
（nuclei / naabu）		 无 无 是（模板） 有扫描日志 已知模式的匹配与覆盖，不解决多步推理

一句话定位：Cairn 补的是“多步探索的记账”这块空白。扫描器给你覆盖面，单 Agent 给你单点突破，Cairn 给的是“谁在什么时候基于哪条事实走了哪一步、失败的那些步留下了什么”。

12

结论：分三类人给建议

想用它打靶 / 做授权测试

值得跑。先 local 模式 + 单 worker + 隔离 VM，一道小题观察 2–3 轮图生长，再决定是否上容器与多并发。别指望开箱即用——README 里的“开赛 4 点才跑通”就是真实上手曲线。

想抄架构做自己的系统

三件可直接搬：单写者 Dispatcher、双阶段 conclude、完成即指向 goal 的边。第四件是 reason 的“新态势”去重——如果你的多 Agent 系统有事件回环问题，这条最省预算。

想商用 / 集成进产品

先解决两个硬门槛：AGPL 授权、单 Dispatcher + 无沙箱的形态。这两条不解决，技术上再顺手也不能进生产；它不是平台底座，是单机引擎。

最后一句评价：它最值钱的不是“AI 自动渗透”，而是把“探索过程本身”变成了可审计的一等公民——失败的方向、被排除的路径、人插的一句话，都在图里。这件事做得比它的战绩更值得被记住。
