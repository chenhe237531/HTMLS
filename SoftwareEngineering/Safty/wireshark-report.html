Wireshark：把"网线里发生了什么"
变成一棵可以点的树

Wireshark 是网络协议分析器的事实标准：抓包、解码、过滤、还原四件事做成一条流水线。 这份报告讲清三件事：GitHub 上的仓库为什么只是镜像、1700 多个解析器是怎么组织的、 以及哪些问题适合用它、哪些问题它根本不该上场。

01 / BOTTOM LINE三句话说完，再决定要不要读完

它的护城河是"解析"

抓包这件事 tcpdump 也能做，真正难的是把 1700 多个协议解析器组织成同一套字段树， 再让你用 http.response.code >= 500 这种表达式直接问问题。换工具容易，换这套字段体系很难。

命令行才是它能自动化的那一半

GUI 适合人看，tshark 适合机器看。把 -Y 过滤器和 -T fields 拼起来，等于给任何脚本加了一个"能读协议"的函数——这是它被集成进流水线的真正原因。

它是显微镜，不是监控系统

没有告警、没有长期留存、没有资产画像。连续抓一周的流量该交给 Zeek / Arkime / Suricata， Wireshark 负责"这条流为什么慢"这种需要人盯着看的时刻。

解析器就是攻击面

每个 dissector 都在处理不可信输入。项目自己把"解析器崩溃或死循环"列为安全漏洞， 并持续做 fuzzing。打开来源不明的 pcap，最稳的做法是放进虚拟机。

适合 / 不适合

任务用 Wireshark更好的选择
某接口 500ms 延迟从哪来是，首选—
TLS 握手失败、证书链问题是，前提是有密钥或 keylogopenssl s_client
还原一次 HTTP 上传 / 抓明文口令是NetworkMiner（更省事）
7×24 流量留存与检索否Arkime、Zeek + 对象存储
入侵检测与告警否Suricata、Zeek、NDR 产品
CI 里对 pcap 做断言是（tshark + 脚本）scapy（写逻辑更自由）
审计加密流量内容不适用端点侧 eBPF / 应用日志

02 / THE REPO两个仓库，分工很清楚

Wireshark 2006 年从 Ethereal 改名而来，2014 年在 GitHub 建立镜像。镜像存在的意义是"可搜索、可引用"， 不是"可协作"。理解这一点，能省掉很多"为什么我的 PR 没人理"的困惑。

GitHub 镜像GitLab 主仓库
地址wireshark/wiresharkgitlab.com/wireshark/wireshark
性质只读镜像，README 明确写了 "Read-only mirror"开发主库：合并请求、CI、issue 都在这里
提交与上游同步，有延迟唯一入口，走 Merge Request + 代码评审
Issue镜像上仅 2 个，基本不用缺陷与需求在这里跟踪
Star（抓取时）约 10.1k约 1.7k
适合做什么读源码、grep、给文章做引用提交补丁、跟进开发进度

仓库规模（本次统计）

  • epan/dissectors/：3,560 个文件，其中 1,874 个 .c 解析器
  • wiretap/：198 个文件，负责 90+ 种抓包文件格式
  • ui/qt/：848 个文件，Qt 界面层
  • test/：927 个文件，pytest + 抓包样本
  • extcap/：26 个文件，15 个外接采集器
  • 仓库体积约 1.5 GB，C 为主

版本节奏（抓取时）

  • 当前稳定：4.6.9；旧稳定：4.4.19（仍在维护）
  • 开发分支：4.7.x，master 已进入 5.0 的 RC 阶段
  • 发布说明里写着 "experimental release intended to test new features for Wireshark 5.0"
  • 同树还有 Stratoshark（系统调用 / 日志分析器，`ssv` 版本号）

给贡献者的两个信号

仓库根目录有 AGENTS.md，专门写给 AI 编程助手：提交必须用 Assisted-by: Claude 这类 trailer 声明 AI 参与，摘要行要用组件名前缀（如 TLS: Fix ...）， 并且要求"每个 MR 的 commit 原样落地，修订请 amend + force-push"。 这不是形式主义——它意味着合并历史保持线性，git log 能当变更日志读。

另一条是 doc/README.developer 的健壮性规则：解析器遇到畸形数据只能报 expert info， 不能 assert、不能无限递归。DISSECTOR_ASSERT() 只用于"代码有 bug"，不是"包有问题"。

03 / ARCHITECTURE一条包从网卡到字段树的路径

分层很干净：采集、落盘、解析、呈现四段各自独立， 中间用 pcap/pcapng 文件格式解耦。这也是为什么 dumpcap、tshark、GUI 能共享同一套解析代码。

四个模块各管什么

模块职责你会直接碰到的部分
capture / dumpcap通过 libpcap/Npcap 抓包；环形缓冲；权限分离（GUI 不用 root）抓包选项、-b 轮转、网卡列表
wiretap读写抓包文件格式，不关心协议打开 pcapng、导出成别的格式、editcap
epan真正的解析引擎：dissector、字段、显示过滤器、统计 tap、专家信息过滤表达式、列、统计菜单、-z
ui / 前端Qt 界面、tshark 命令、sharkd 服务快捷键、profile、导出 JSON/CSV

04 / TOOLCHAIN别只认识那个蓝色图标

发行包里其实有十几个可执行文件，man 手册也是按工具分开的。GUI 只是最显眼的一个， 真正能进脚本、进 CI、进事故复盘的是后面这几个。

命令干什么典型用途
wiresharkQt 图形界面人工逐个包看、画时序、跟流
tshark命令行解析器，功能≈GUI 的解析部分批量提取字段、CI 断言、统计
dumpcap专职抓包，权限最小化长时间抓包、环形缓冲、多文件轮转
editcap按条件裁剪 / 切分 / 改时间戳把 20GB 拆成可分析的小块、去重
mergecap按时间合并多个抓包多网卡、多段同时抓的包合成一条时间线
capinfos输出文件元信息先看时长、包数、接口，再决定怎么分析
text2pcap十六进制 / ASCII 转 pcap把日志里的报文片段变成可解析的包
rawshark对原始字段做过滤输出字段级处理，比 tshark 更底层
sharkd解析守护进程（socket 接口）给别的程序提供解析能力
randpkt / captype / reordercap造随机包、判类型、重排序压测解析器、修乱序抓包
stratoshark / strato系统调用与日志分析前端把 syscall 当"包"来过滤（结合 Falco 采集）
sshdump / ciscodump / androiddump / sdjournal / etwdumpextcap 外接采集器远程抓、交换机抓、安卓抓、读 systemd/ETW 日志

一个经常被忽略的组合：dumpcap 抓 + tshark 判 + editcap 切

事故现场先用 dumpcap 低开销抓 10 分钟（带环形缓冲，防止写满磁盘）， 回办公室用 capinfos 看规模，editcap -A/-B 截出问题时段， 再用 tshark 出统计，最后才打开 GUI 精看。整条链路不需要图形界面，也不需要 sudo 跑 GUI。

05 / GETTING STARTED装好、拿到权限、抓第一个包

安装

# Debian / Ubuntu / Kali
sudo apt install wireshark tshark

# macOS
brew install --cask wireshark

# Windows：装官方包，会一并安装 Npcap
winget install WiresharkFoundation.Wireshark

权限：不要用 root 开 GUI

# Linux：让普通用户能用 dumpcap 抓包
sudo dpkg-reconfigure wireshark-common   # 选 Yes
sudo usermod -aG wireshark "$USER"
newgrp wireshark

# macOS：安装包里的 ChmodBPF 会处理 BPF 权限

# 验证
dumpcap -D

三种抓包姿势，按场景选

# 1) 临时看一眼：只留 DNS 和 HTTP，避免抓一堆无关流量
sudo dumpcap -i eth0 -f 'port 53 or port 80' -w /tmp/look.pcapng

# 2) 长时间抓：每 200MB 或每 5 分钟切一个，最多留 20 个（约 4GB 上限）
sudo dumpcap -i eth0 -b duration:300 -b filesize:204800 -b files:20 -w /var/tmp/cap.pcapng

# 3) 远程机器：sshdump 免装 Wireshark，直接抓远端接口
#    GUI: Capture ▸ Options ▸ SSH remote capture

捕获过滤器和显示过滤器不是一回事

捕获过滤器是 BPF，在抓之前就把包丢掉，写错就等于没抓到；显示过滤器是 Wireshark 自己的语法， 作用于已经落盘的数据，可以随时改。常见错误是在 -f 里写 http.request—— BPF 不认识这个字段，只会静默抓到空文件。

六个够用的显示过滤器

目的过滤器
只看某主机的 HTTP 请求ip.addr == 10.0.0.5 && http.request
5xx 响应http.response.code >= 500
TCP 层异常（重传、乱序、零窗口）tcp.analysis.flags
TLS 握手失败tls.alert_message
DNS 返回错误dns.flags.rcode != 0
只看到致命错误（专家信息）_ws.expert.severity == error

记不住字段名时：tshark -G fields | grep -i tls 列出所有字段，tshark -G protocols 列协议。 这比背文档可靠——字段名随版本变，-G 永远和当前二进制一致。

tshark：把包变成表格

# 一条 TCP 流里，谁在哪一刻重传了
tshark -r cap.pcapng -Y 'tcp.analysis.retransmission' \
  -T fields -e frame.number -e frame.time_relative -e ip.src -e tcp.srcport -e tcp.seq

# HTTP 请求清单（含耗时）
tshark -r cap.pcapng -Y 'http.request' -T fields \
  -e frame.time_relative -e ip.src -e http.host -e http.request.method -e http.request.uri -e http.time

# 协议分层统计 + 会话统计
tshark -r cap.pcapng -q -z io,phs -z conv,tcp

# 导出为 JSON 再交给 jq
tshark -r cap.pcapng -Y 'dns' -T json | jq '.[]._source.layers.dns'

06 / FIELD NOTES五个真实场景，过滤器 + 怎么读

这一节不是"功能列表"，而是拿包的人实际会遇到的判断顺序。每条都给过滤器和判读要点—— 后者才是新手和熟手的差距。

1. 接口慢：先分清"网络慢"还是"服务慢"

过滤器：tcp.analysis.flags、tcp.window_size == 0、frame.time_delta > 0.2

读法：先看 Statistics ▸ TCP Stream Graphs ▸ Time/Sequence。曲线出现平台说明等待（零窗口=接收端处理不过来； 没有 ACK=链路丢包）。再看 tcp.analysis.retransmission 的比例：偶发重传是常态， 成片重传才是链路问题。最后对齐服务端日志的时间戳——如果请求到达服务端时已经晚了 300ms，问题在网络上，不在应用里。

常见误判：把"客户端渲染慢"当成网络慢。Wireshark 只看到 TCP 层，看不到浏览器解析和 JS 执行。

2. TLS 握手失败：证书、协议版本还是 SNI

过滤器：tls.handshake.type == 1 || tls.handshake.type == 2、tls.alert_message

读法：先展开 Client Hello，看 supported_versions、server_name、密码套件； 再看 Server Hello 选了什么；最后看 Alert 的 description（40=handshake_failure，112=unrecognized_name，70=protocol_version）。 现代排查还要注意：中间设备（防火墙、CDN、零信任网关）会替服务端回 RST 或伪造证书，此时握手看起来"失败得很干净"， 但 ip.ttl 和证书签发者会露馅。

3. HTTP 500：到底是哪一跳返回的

过滤器：http.response.code >= 500，然后 Follow ▸ HTTP Stream

读法：看响应头里的 Server、X-Powered-By、Via，判断是源站还是网关； 对比 http.time 与 tcp.time_delta——前者是服务端处理时间，后者包含排队与网络。 如果响应体是 HTML 错误页而不是 JSON，多半是网关/反代生成的，先把责任边界划清再找研发。

4. DNS 慢：是解析慢，还是每次都重新解析

过滤器：dns.flags.rcode != 0、dns.time > 0.5

读法：Statistics ▸ DNS 能直接看响应时间分布；看 dns.flags.response == 0 的请求是否有对应的响应，没有就是超时重试。NXDOMAIN 大量出现时，先怀疑拼写错误或搜索域后缀被滥用， 而不是"DNS 服务器坏了"。

注意：加密 DNS（DoH/DoT）下看不到域名，只能看到 443/853 的连接行为，这是协议设计，不是工具缺陷。

5. 广播风暴 / ARP 冲突：二层问题不要在三层找

过滤器：arp.duplicate-address-detected、arp.opcode == 1、broadcast

读法：先看 Statistics ▸ Endpoints 里广播包的占比，再按 MAC 统计发包量找出"话最多"的那台。 一个 IP 对应两个 MAC 且频繁切换，通常不是攻击，是有人在手动改 IP 或双网卡同时上线。 ARP 欺骗的特征是"网关 MAC 突然变了"，此时对比 arp.src.hw_mac 的历史值即可。

加一条：找明文凭据

# 只在授权范围内使用：找 Basic 认证头、FTP/Telnet 明文口令
tshark -r cap.pcapng -Y 'http.authorization || ftp.request.command == "PASS" || telnet' \
  -T fields -e ip.src -e http.authorization -e ftp.request.arg -e telnet.data

这条命令本身就是"pcap 为什么不能随手外发"的最好证明：一个抓包文件里可能有别人的口令、Cookie 和会话令牌。

07 / SCALE大文件不是不能开，是别用错方式

采集端就该做的

  • 先加捕获过滤器，别"先全抓再筛"
  • 用环形缓冲 -b filesize/files/duration，别让磁盘写满
  • 按需改 snaplen（-s 128 只看头），能显著降体积
  • 关名字解析（-n），否则每个包都可能触发一次 DNS 查询

分析端该做的

  • capinfos 先看规模和时长，再决定是否切分
  • editcap -A "2026-11-01 10:00:00" -B "2026-11-01 10:05:00" 截时段
  • 用 tshark -Y 做统计，而不是打开 GUI 加载整包
  • 确实要看树时，先 editcap -c 50000 切块

两个性能陷阱

1）-V 是奢侈品。它会把每个包的完整协议树都渲染出来，几十万包就会让 tshark 慢到不可用。 先用 -T fields 提取你真正需要的字段。

2）GUI 的内存和包数近似线性。千万级包的 pcapng 不要直接双击打开；先切分，或者用 tshark + tcp.stream 定位到具体流，再把那一小段导出来看。

08 / RISK三个必须提前想清楚的风险

1. 解析器是攻击面

项目自己的安全策略把"dissector 崩溃或死循环""文件解析器崩溃""本地/远程代码执行"都算安全漏洞。 这意味着：别人给你的 pcap 和网上的样本包，等于可执行输入。 分析来源不明的包，用虚拟机或容器，别在办公机上直接双击。

2. 抓包即收集个人数据

抓包里可能有账号、Cookie、聊天内容、内网拓扑。在中国法域下，这同时涉及《网络安全法》《数据安全法》 与《个人信息保护法》：没有授权不能抓他人流量，抓到了也要最小化留存、限期销毁、控制访问。 pcap 不应进公开仓库、不应发到群里求助。

3. 远程抓包不是"开个端口"

历史上的 rpcapd 远程捕获缺少认证与加密，直接暴露在网络上等于把网卡交出去。 需要远程抓包时，优先用 sshdump（走 SSH）或在目标机上抓完再拉文件， 不要为了省事把 rpcapd 暴露到公网。

GPL-2.0 的边界

Wireshark 是 GPL-2.0。把它的代码链接进闭源产品会触发开源义务；用 Lua 写插件、 通过 tshark 子进程调用、或用 sharkd 做进程隔离，通常风险更低， 但"通常"不等于"一定"——商用前让法务看，不要靠博客文章下结论。

TLS 解密的现实边界

你手上有什么能解吗说明
浏览器/客户端的 SSLKEYLOGFILE能Wireshark 里设置 tls.keylog_file 即可；TLS 1.3 也适用
RSA 密钥交换 + 服务器私钥能（仅旧套件）TLS 1.2 的 RSA 密钥交换已基本淘汰
ECDHE 会话 + 服务器私钥不能前向保密的意义就在于此
只有中间人证书（企业代理）取决于客户端是否信任客户端不信任就是握手失败，不是"解不开"

09 / LIMITS它明确不解决的问题

  • 不做检测与告警。没有规则引擎、没有基线、没有值班通知。需要这些，上 Suricata / Zeek / NDR。
  • 不做长期留存与检索。没有索引、没有冷热分层。需要"三个月前那次连接"，上 Arkime 或自建 pcap 归档。
  • 不看应用内部。它看到的是协议，不是业务逻辑；"为什么这个请求算失败"只有应用日志知道。
  • 不重建加密内容。端到端加密、证书固定（pinning）、QUIC 加密握手，都会让可见性骤降。
  • 不做统计建模。内置统计够用，但异常检测、聚类、时序预测不是它的职责。

替代与搭配

工具定位和 Wireshark 的关系
tcpdump最小化抓包服务器上通常只装它；抓完拉回 Wireshark 看
Zeek流量转结构化日志长期留存用 Zeek，细节回查用 pcap
Arkime大规模 pcap 索引与检索"先搜后看"，搜到会话再导出给 Wireshark
SuricataIDS/IPS告警触发后，用 Wireshark 复盘那一段
scapy用 Python 造包/解包需要写逻辑和批量处理时比 tshark 更自由
Stratoshark系统调用 / 日志分析同一套引擎换了数据源，思路可以直接迁移

10 / ECOSYSTEM怎么持续跟上它

值得投入的三件事

  1. 熟练 tshark + 字段名：这是从"会用"到"能自动化"的分水岭。
  2. 读几个 dissector 源码：packet-http.c 看状态机，packet-tls.c 看握手解析。
  3. 自己写一个 Lua 解析器：内部协议、私有二进制格式，比等官方支持快得多。
