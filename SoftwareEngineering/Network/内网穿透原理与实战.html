NETWORK · FIELD GUIDE

内网穿透原理、常用方式与实战案例

内网穿透不是某一种协议，而是一类方法的统称：让位于 NAT 或防火墙之后的服务，能够被外部按需访问。理解“连接由谁发起”，就能看懂绝大多数方案。

  • 更新于 2026-10
  • 阅读约 25 分钟
  • 家庭 / 中小企业 / 开发调试
本质

先由内向外建立并保持一条连接，外部请求再复用这条连接回到内网。

三条路线

有公网 IP 做端口映射；没有就做隧道或中继；多设备互访做覆盖组网。

安全顺序

身份认证 → 加密 → 最小暴露 → 审计。能不开公网入站端口就不开。

01问题：为什么内网访问不到

家里的 NAS、公司的测试服务器、你笔记本上的开发服务，通常都拿不到独立的公网 IPv4 地址。它们处在路由器或运营商 NAT 之后，只拥有 192.168.x.x、10.x.x.x 这类私网地址。私网地址在互联网上不可路由，外部设备即使知道 IP 也发不过去。

NAT 设备内部维护一张映射表：内网机器主动访问外网时，NAT 把源地址改写为公网地址并记录“谁对应哪个端口”，回包才能被正确送回。但这张表是由内向外建立的。没有表项时，来自外部的第一个数据包会被直接丢弃。

一句话理解

NAT 像公司总机：外线不能直接拨到某个分机，但分机可以打出去；打出去并保持通话后，总机才知道后续声音该转给谁。

常见阻碍不止 NAT 一种：

  • 运营商级 NAT（CGNAT）：多个用户共享一个公网 IPv4，路由器 WAN 口拿到的可能是 100.64.0.0/10 地址，做端口映射没有意义。
  • 动态公网 IP：地址会变，需要 DDNS 把域名指向新地址。
  • 防火墙默认拒绝入站：即使有公网 IPv6，未经放行的入站连接依然会被拦截。
  • 公司网络只放行出站：多数办公网允许访问 80/443，不允许外部主动连入。
先判断你处于哪种网络环境，再谈方案
环境典型特征可用的入口方式
公网 IPv4路由器 WAN 地址与外部查到的公网 IP 一致端口映射 + DDNS；或任意隧道方案
公网 IPv6设备有 2000::/3 地址，但入站被防火墙拦截放行指定端口；AAAA 记录 + 证书
CGNAT / 仅内网WAN 地址是私网或运营商共享地址只能由内向外建连：隧道、组网、托管服务
严格办公网只允许出站 80/443，禁止安装服务出站隧道（需符合公司规定）

02原理：三条主线

所有内网穿透方案，最终都落在三种基本机制上：反向连接、中继转发、NAT 打洞。产品只是把这些机制组合起来，再加上认证、多路复用和运维界面。

2.1 反向连接：方向反了，问题就解了

内网客户端主动向公网服务器发起一条长连接。因为方向是“内 → 外”，NAT 会正常建立映射，防火墙也通常放行。连接建立后，外部用户访问公网服务器，服务器把请求通过这条已存在的连接送回内网客户端，客户端再访问本机的真实服务。

关键点是：连接的发起方向，不等于数据的流动方向。隧道一旦建立，数据可以双向流动。SSH 反向隧道、frp、nps、Cloudflare Tunnel 都建立在这个机制上。

2.2 中继：让公网服务器替双方转发

中继（relay）是最通用的做法。内网客户端和外部用户都连接到公网节点，由节点把字节流对接起来。它不要求 NAT 类型，也不要求双方能直连，因此几乎总能工作。

代价也很直接：所有流量都经过中转服务器，带宽受它限制，延迟增加一跳，数据对中转方可见（除非在隧道内部再做端到端加密）。免费或低配套餐的“速度慢”，通常就是中转带宽和线路造成的。

2.3 打洞：先让双方“认识”，再尝试直连

NAT 打洞（hole punching）的目标是让两端建立直接连接，绕开中继。典型流程：

  1. 双方分别向 STUN 服务器发一个 UDP 包，得知自己在公网上的“IP:端口”映射。
  2. 通过信令服务器交换这个公网地址。
  3. 双方几乎同时向对方的公网地址发包。第一个包可能被丢弃，但发出去的动作会在各自 NAT 上建立允许回包的规则。
  4. 后续包就能双向通过，形成直连；再用保活包维持映射。

如果双方都是“锥型 NAT”，打洞成功率很高；如果一方是对称 NAT（每个目标地址分配不同映射），预测对方端口很困难，通常会回退到中继。TCP 打洞比 UDP 更不可靠，所以很多组网产品优先用 UDP，并在失败时使用中继（如 TURN、DERP）。

2.4 隧道封装：为什么很多工具偏爱 443

隧道工具会把内网服务的字节流包进另一层协议里传输，常见做法包括 TLS、HTTP/2、QUIC、WebSocket。这样做有三个好处：

  • 穿透出站策略：443 端口通常被允许，看起来像普通 HTTPS。
  • 多路复用：一条连接上并发跑很多请求，减少握手和端口占用（如 yamux、HTTP/2 流）。
  • 加密与认证：TLS 同时解决机密性和服务端身份校验。

注意，“封装”不等于“安全”。隧道只保护到隧道端点为止，端点之后是否加密、服务本身是否有认证，仍要单独设计。

03NAT 类型与可行性

NAT 的分类没有想象中那么重要，但它能解释“为什么同一款工具在公司和家里表现不同”。下面是最常见的四种模型：

NAT 行为与打洞可行性（实际设备常混合多种行为）
类型映射行为过滤行为UDP 打洞
完全锥型 Full Cone同一内网地址固定映射到一个公网端口任何外部地址都可发入容易
受限锥型 Restricted映射固定只接受曾通信过的 IP较容易
端口受限锥型映射固定只接受曾通信过的 IP + 端口需要精确信令
对称型 Symmetric每访问一个目标就换一个公网端口按目标严格过滤困难，通常中继
实践提醒

“NAT 类型”只是模型。真实的运营商设备、企业防火墙、云安全组可能按应用层策略丢包，也会对 UDP 限速或直接封禁。判断能否直连，最可靠的办法是用目标工具自带的探测（例如 tailscale netcheck、ZeroTier 的路径状态）实测。

04常见方式

下面按“依赖什么入口”分组。每组给出原理、适用场景和最小可用示例；示例中的域名、IP、端口都需要替换成你自己的值。

4.1 端口映射与直连

路由器端口映射 / UPnP / DMZ

最传统的做法：在路由器上把“公网 IP:端口”静态转发到“内网 IP:端口”。它严格来说不属于穿透，而是让入口存在。前提是你真的有可用的公网 IPv4，并且运营商没有封禁入站端口（不少家庭宽带封 80/443）。

优点
链路最短、延迟最低、不依赖第三方；配置一次即可。
缺点
暴露的端口会被全网扫描；动态 IP 需要 DDNS；CGNAT 下完全不可用。
注意
UPnP 能让程序自动开端口，但也让恶意软件更容易开洞，建议关闭或按需开启。DMZ 主机等于把某台设备全部端口暴露，不建议长期使用。
路由器管理界面（示意）
外部端口 8443  →  192.168.1.10:443   TCP
外部端口 2222  →  192.168.1.10:22    TCP
建议：只映射必要端口，源地址尽量限制为固定 IP

4.2 IPv6 直连

公网 IPv6 + 防火墙放行

IPv6 没有 NAT，设备通常直接拥有公网地址。真正的障碍变成防火墙：家用路由器默认拒绝入站。为某台设备放行指定端口，再配置 AAAA 记录和证书，就能从支持 IPv6 的网络直接访问。

优点
无 NAT、无中转、性能好；适合家庭 NAS、自建网站。
缺点
客户端必须支持 IPv6；地址会变，需要 DDNS；暴露后同样会被扫描。
注意
只放行需要的端口；不要放行管理面；用 ping6 或在线检测确认入站确实可达。

4.3 SSH 反向隧道

ssh -R：一条命令的临时穿透

借助一台有公网地址的服务器，把内网端口反向映射到服务器上。它只转发 TCP，配置最少，适合临时运维和救急。

在内网机器上执行
ssh -N -R 0.0.0.0:2222:127.0.0.1:22 \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  ops@203.0.113.10

服务器端需要允许远程端口绑定：在 /etc/ssh/sshd_config 中设置 GatewayPorts clientspecified（或 yes），并在防火墙/安全组放行 2222。之后访问 203.0.113.10:2222 就等于访问内网的 22 端口。

断线自动重连（autossh）
autossh -M 0 -N \
  -R 0.0.0.0:2222:127.0.0.1:22 \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -o ExitOnForwardFailure=yes \
  ops@203.0.113.10
优点
零额外软件（客户端通常自带 SSH）、全程加密、几秒完成。
缺点
需要一台公网服务器；只适合少量 TCP 端口；公网服务器是信任端点。
注意
服务器上使用专用低权限账号、仅密钥登录；给端口加访问限制；长期方案建议用 systemd 托管或改用组网。

4.4 自建隧道：frp / nps / rathole / gost

frp：最常用的自建反向代理

frp 由服务端 frps 和客户端 frpc 组成。frpc 主动连接 frps，按配置把本地端口暴露到服务端；支持 TCP、UDP、HTTP、HTTPS、STCP、XTCP 等代理类型，并用多路复用承载多条隧道。

frps.toml（公网服务器）
bindPort = 7000
auth.method = "token"
auth.token = "替换为足够长的随机字符串"

# 需要 HTTP/HTTPS 虚拟主机时再启用
vhostHTTPPort = 80
vhostHTTPSPort = 443
frpc.toml（内网机器）
serverAddr = "203.0.113.10"
serverPort = 7000
auth.token = "替换为足够长的随机字符串"

[[proxies]]
name = "nas-web"
type = "tcp"
localIP = "127.0.0.1"
localPort = 5000
remotePort = 15000

启动后，访问 203.0.113.10:15000 即到达内网的 5000 端口。生产环境建议：frps 只开放必要端口；启用 TLS；限制 allowPorts；给 dashboard 设置强密码并限制来源；用 systemd 或容器托管。

同类选择
nps 带 Web 管理界面，适合多客户端统一管理；rathole 用 Rust 编写，配置更轻；gost 偏代理与转发编排，能串接多种协议。
注意
自建意味着你要负责服务器安全、证书续期、升级和监控；“免费”只是省了软件订阅费。

4.5 托管隧道：Cloudflare Tunnel / ngrok / localtunnel

Cloudflare Tunnel

在内网运行 cloudflared，它主动向 Cloudflare 边缘建立出站连接（QUIC 或 HTTP/2），不需要开放任何入站端口。把域名解析到隧道后，外部访问由 Cloudflare 边缘转进来。配合 Cloudflare Access 可以做 SSO、邮箱验证码或一次性 PIN，把“能访问”升级为“授权的人才能访问”。

最小流程
cloudflared tunnel login
cloudflared tunnel create home-nas
cloudflared tunnel route dns home-nas nas.example.com
cloudflared tunnel run home-nas
config.yml（示意）
tunnel: <TUNNEL_ID>
credentials-file: /etc/cloudflared/<TUNNEL_ID>.json
ingress:
  - hostname: nas.example.com
    service: http://127.0.0.1:5000
  - service: http_status:404
优点
免公网 IP、免开入站端口、自动 TLS、可接 SSO；对 Web 服务和 SSH 都友好。
缺点
流量经过第三方；可用性依赖服务商；高级能力与用量受套餐约束。
注意
边缘会终止 TLS，Cloudflare 能看到明文 HTTP；敏感服务应叠加应用层加密或端到端方案。

ngrok / localtunnel

适合“现在就要一个公网 HTTPS 地址”的演示场景。ngrok 一条命令即可把本地端口映射到随机域名，并提供请求查看器；localtunnel 更轻量但稳定性一般。免费地址通常会变化，生产用途需要付费固定域名与更高配额。

ngrok
ngrok http 8080
ngrok tcp 22

临时地址不要长期挂在生产环境；演示结束后及时关闭；Webhook 调试时注意校验签名，避免把真实密钥写进日志。

4.6 覆盖组网：Tailscale / ZeroTier / WireGuard

Tailscale

基于 WireGuard 的覆盖网络。每台设备安装客户端并登录同一账号后，会得到一个稳定的 100.x 地址；客户端自动尝试 NAT 打洞直连，失败时通过 DERP 中继。开启子网路由后，可以把整个家庭或办公室网段共享给其他设备。

把内网网段共享出去
# 在作为网关的设备上
tailscale up --advertise-routes=192.168.1.0/24 --accept-routes

# 到管理台批准该子网路由，然后查看状态
tailscale status
优点
配置极少、跨平台、默认加密、ACL 可精细控制谁能访问哪个端口；个人免费额度通常够用。
缺点
依赖协调服务器（可自建 Headscale）；企业合规需评估；直连失败时速度受中继影响。
注意
用 ACL 限制访问范围，不要“登录即全通”；定期清理失效设备密钥。

ZeroTier

二层覆盖网络，设备加入同一个虚拟网络后像接在同一台交换机上，支持广播，适合局域网联机、老旧软件和需要二层发现的场景。它有自己的根服务器与中继，也可以自建 Moon 节点改善路径。

优点
二层体验、跨平台、配置直观；对游戏联机和发现协议友好。
缺点
免费网络规模与功能有限；路径质量依赖运营商与根节点；二层广播会带来额外流量。

WireGuard：自建 VPN 的基线

内核态、配置简单、性能高。它本身不负责 NAT 穿透：需要至少一端有可访问的 UDP 端口（公网 IP 或已映射端口）。适合有云服务器、需要长期稳定站点互联的人。

服务端 wg0.conf（示意）
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <server-private-key>

[Peer]
PublicKey = <client-public-key>
AllowedIPs = 10.8.0.2/32
客户端（示意）
[Interface]
Address = 10.8.0.2/32
PrivateKey = <client-private-key>

[Peer]
PublicKey = <server-public-key>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.8.0.0/24, 192.168.1.0/24
PersistentKeepalive = 25

云服务器需在安全组放行 UDP 51820；开启 IP 转发并配置 NAT，客户端才能访问服务器背后的内网。密钥用 wg genkey 生成，不要把私钥提交到仓库。

4.7 商业服务与硬件盒子

花生壳、贝锐等国内服务提供“客户端 + 固定域名/端口”的打包方案，部分还附带硬件。优势是开箱即用、有客服和备案支持；代价是带宽按套餐限制、流量经过厂商、长期成本可能高于自建。选择前确认：是否支持所需协议、是否有固定入口、数据留存政策、以及能否满足单位的合规要求。

06实战案例

下面每个案例都给出目标、推荐路径、关键步骤和容易踩的坑。命令是示意，请按实际系统与域名替换。

A远程访问家里的 NAS

场景：NAS 在家庭宽带后面，没有固定公网 IPv4；希望在外面用手机和笔记本安全访问文件、相册和管理页。

推荐：优先 Tailscale（设备级访问，不暴露端口）；如果只想通过浏览器访问 Web 管理页，用 Cloudflare Tunnel + Access。

  1. 在 NAS 和手机、笔记本上安装 Tailscale 并登录同一账号。
  2. 用 tailscale status 确认在线，直接访问 NAS 的 100.x 地址；开启 MagicDNS 后可用设备名。
  3. 若使用 Cloudflare：运行 cloudflared 建隧道，把 nas.example.com 指向本地管理端口，再在 Access 里配置只允许自己的邮箱登录。
别这样做

不要把 SMB（445）、管理后台或数据库直接映射到公网；不要关闭 NAS 的自动更新与双因素认证。暴露在公网的服务几小时内就会遇到扫描和爆破。

B本地开发调试第三方 Webhook

场景：支付、IM、GitHub 等平台需要回调一个公网 HTTPS 地址，但代码跑在笔记本的 localhost:8080。

推荐：ngrok 或 Cloudflare Tunnel 的临时隧道；演示结束立即关闭。

两分钟拿到公网地址
ngrok http 8080

# 或使用 cloudflared 临时隧道
cloudflared tunnel --url http://localhost:8080
  • 把平台后台的回调地址改成生成的 HTTPS URL，并在本地日志确认收到请求。
  • 免费域名会变化，每次重启都要更新回调配置；需要固定地址时使用付费域名或自建 frp + 证书。
  • 回调内容可能包含签名和用户数据，不要在公网隧道上关闭签名校验，也不要把请求体原样打进生产日志。
C没有公网 IP 的服务器做 SSH 运维

场景：客户机房的一台 Linux 服务器只能出网，不能入站；你需要偶尔 SSH 上去排障。

推荐：用一台你自己的公网服务器做跳板，配置 SSH 反向隧道 + autossh + systemd。

systemd 单元（示意）
[Unit]
Description=Reverse SSH tunnel
After=network-online.target

[Service]
User=tunnel
ExecStart=/usr/bin/autossh -M 0 -N -R 0.0.0.0:2222:127.0.0.1:22 -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes ops@203.0.113.10
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
  • 跳板机上创建专用账号，仅允许密钥登录，并限制该账号的 authorized_keys 命令。
  • 只开放一个高位端口，配合防火墙白名单；不要使用弱密码。
  • 若需要长期、多端口、图形化访问，改用 Tailscale 子网路由或 WireGuard，维护成本更低。
D异地办公室访问总部数据库

场景：总部数据库只监听内网地址，分公司需要让开发人员访问，但不能把 5432/3306 暴露到公网。

推荐：Tailscale 子网路由 + ACL；或总部防火墙上的 WireGuard，只允许分公司网段访问数据库端口。

  1. 在总部放一台常开设备作为子网路由器，执行 tailscale up --advertise-routes=192.168.10.0/24。
  2. 在管理台批准路由，并写 ACL：只允许 group:dev 访问 192.168.10.20:5432。
  3. 分公司设备登录后直接使用内网地址连接；用 tailscale ping 观察是否直连。
关键点

数据库自身仍要强密码、按用户授权、开启审计。覆盖网络解决“可达”，不替代数据库权限设计。

E给客户临时演示测试环境

场景：测试环境在你公司内网，客户在外网，需要一周内可访问，且不能让无关的人看到。

推荐：Cloudflare Tunnel + Access（邮箱一次性验证码）最省心；或者 frp + HTTPS 虚拟主机 + 应用层登录。

  • 为演示单独建子域，例如 demo.example.com，不要复用生产入口。
  • 访问策略设置有效期和允许的邮箱列表；演示结束立即停隧道、撤销策略。
  • 测试数据脱敏；关闭调试接口和详细错误页；确认日志里没有客户敏感信息。
  • 若客户要求数据不经第三方，改用自建 frp/WireGuard，并在合同中说明数据路径。
FIPv6 家庭宽带直连自建服务

场景：家庭宽带已下发公网 IPv6，希望不经过任何中转，直接访问家里的服务。

  1. 确认设备拿到 2000::/3 地址，且路由器没有启用 IPv6 防火墙的全拒绝策略。
  2. 为服务器配置固定后缀或 DHCPv6 保留地址；在防火墙上只放行 443。
  3. 用 DDNS 更新 AAAA 记录；证书用 DNS-01 方式签发，避免依赖 80 端口。
  4. 用手机 5G 网络（通常有 IPv6）测试；再到只有 IPv4 的网络测试，确认是否需要双栈回退。

坑：公司网络可能没有 IPv6；部分路由器重启后后缀变化；放行后同样会被扫描，别把管理端口一起打开。

09排错与 FAQ

有公网 IP 还需要“穿透”吗？

严格说不需要，你只需要端口映射或 IPv6 防火墙放行。但“有公网 IP”不等于“能入站”：运营商可能封端口，路由器可能开防火墙，云服务器还有安全组。逐层确认后再判断。

怎么判断自己是不是 CGNAT？

比较路由器 WAN 口地址和外部网站显示的公网 IP。如果不一致，或者 WAN 地址落在 100.64.0.0/10、10.0.0.0/8 等私网段，基本就是 CGNAT。此时端口映射无效，应选择隧道或组网。

隧道通了，但访问显示 502 / 连接被拒绝？

按顺序检查：

  • 本地服务是否真的在监听，端口是否写错，是否只绑定了 127.0.0.1 而客户端在别处。
  • frp 的 localIP 是否应为 127.0.0.1；远程端口是否被 allowPorts 拒绝。
  • 公网服务器安全组/防火墙是否放行入口端口。
  • HTTP 场景下 Host 头、WebSocket Upgrade、HTTPS 证书是否匹配。
WebSocket 或长连接总是断？

确认反向代理保留了 Upgrade 与 Connection 头；调大空闲超时；在客户端和隧道两端都开启心跳/保活；QUIC 或 UDP 被限速时改用 TCP/TLS。还要排查 NAT 映射老化时间，保活间隔应小于它。

为什么连接速度很慢？

看流量路径：如果是中继，速度受中转服务器带宽和线路影响；如果是打洞失败后的回退，也会走中继。用工具自带的状态命令确认是直连还是中继（例如 Tailscale 的 tailscale ping 会显示 via DERP 或 direct）。家庭宽带上行通常远小于下行，也是常见瓶颈。

HTTPS 证书怎么处理？

三种常见做法：隧道服务商自动签发（Cloudflare Tunnel）；在公网服务器上终止 TLS 并申请证书（frp + Nginx/Caddy）；或者在内网服务上直接申请。证书续期要纳入监控，避免过期导致整条入口不可用。内网自签证书只适合临时测试。

免费方案能用于生产吗？

可以用于低风险、可中断的场景，但要接受三个限制：地址或端口可能变化、带宽与并发受限、没有 SLA。生产环境至少要有固定入口、监控告警、备份路径和明确的数据合规结论。

内网穿透是否违法？

工具本身中立，关键在于用途和授权。未经允许访问他人系统、绕过单位安全策略、规避监管或传播违法内容都可能违法。企业环境中先走 IT/安全审批，并遵守数据出境与网络安全相关规定。

10术语与延伸

NAT
网络地址转换。把私网地址改写为公网地址并维护映射，使多台内网设备共享一个公网地址。
SNAT / DNAT
源地址转换 / 目的地址转换。出站改写源地址是 SNAT，端口映射改写目的地址是 DNAT。
CGNAT
运营商级 NAT。多个用户共享公网 IPv4，用户侧通常无法做有效端口映射。
STUN
帮助客户端发现自己在 NAT 后的公网 IP 与端口，用于打洞前的地址探测。
TURN
当直连失败时提供中继转发，保证连通性，代价是带宽与延迟。
ICE
综合 STUN、TURN 与直连候选的协商框架，WebRTC 用它选择可用路径。
Hole Punching
NAT 打洞。双方同时向对方公网地址发包，借 NAT 放行规则建立直连。
Relay
中继。所有流量经过公网节点转发，通用但消耗中转带宽。
Tunnel
隧道。把一种协议的流量封装进另一种连接中传输，常见于反向代理与 VPN。
Overlay Network
覆盖网络。在现有互联网之上构建的虚拟网络，如 Tailscale、ZeroTier。
DDNS
动态 DNS。把域名自动指向变化的公网地址。
UPnP / NAT-PMP
让程序自动请求路由器开放端口的协议，方便但扩大攻击面。
mTLS
双向 TLS。客户端与服务端都出示证书，常用于服务间认证。
ZTNA
零信任网络访问。以身份和策略为中心，而不是以网络位置为中心。
