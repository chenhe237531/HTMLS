01

结论先行：它到底在主张什么

如果只记一句话：好的 Agent 不是“给模型一个目标，让它自己循环到完成”，而是“确定性的软件流程 + 在关键节点让 LLM 做判断”。

THESIS 1

问题不在模型不够强

把整张 DAG 交给 LLM，会让步数、上下文和分支爆炸；10–20 轮后模型开始迷路、重复错误，70–80% 的质量墙很难靠“再调调 prompt”突破。

THESIS 2

答案是把 Agent 缩小

把 Agent 做成 DAG 里的一个节点：只处理 3–10 步的窄任务，负责解析自然语言、选择下一步、生成结构化参数；流程、权限、重试、审计仍由代码掌握。

THESIS 3

四个部件，而不是一个框架

prompt（怎么问）、switch（怎么处理意图）、context（给模型看什么）、loop（何时继续/暂停）。四者都由你拥有。

THESIS 4

12 条是“原则”，不是 SDK

它不提供运行时，也不保证效果；它是一套可逐条落地的工程约束，适合嵌进已有产品，而不是 greenfield 重写。

“Agents, at least the good ones, don’t follow the ‘here’s your prompt, here’s a bag of tools, loop until you hit the goal’ pattern. Rather, they are comprised of mostly just software.”
— 原文 README

一句话版本：LLM 负责“下一步做什么”，代码负责“怎么做、什么时候停、出了事谁负责”。12 条原则几乎都在服务这个分工。
02

它要解决什么问题：从“扔掉 DAG”到“回到 DAG”

这份指南的起点不是技术炫技，而是一个很具体的产品困境：demo 很惊艳，但离“敢给客户用”总差最后 20%。

STEP 1

软件本来就是 DAG

流程图、Airflow / Prefect / Dagster 这类编排器，本质都是“节点 + 边 + 可观测性 + 重试”。确定性是工程可靠性的来源。

STEP 2

Agent 的承诺：扔掉 DAG

给模型一个目标 + 一组工具，让它实时决定路径。理论上少写代码、能恢复错误、还能发现新解法。

STEP 3

现实：循环会失焦

步数越多，上下文越长；模型开始重复同一种错误。作者观察到，超过 10–20 轮后，很多 Agent 就变成“看起来在干活”的混乱循环。

80% 质量墙：很多团队能靠框架快速到 70–80%，但客户面向的功能需要更高。继续往上走，往往要反向拆框架的 prompt、flow、状态管理——于是又回到自己写。

框架给了什么

快速起步、内置 prompt、工具抽象、社区示例。适合验证想法，但黑盒会隐藏真正送进模型的 token，调优和排障都变难。

框架拿走了什么

对 prompt、context、control flow 的精确控制；以及把 Agent 嵌进现有产品（而不是重写一个 Agent 产品）的路径。

“Most of the products out there billing themselves as ‘AI Agents’ are not all that agentic. A lot of them are mostly deterministic code, with LLM steps sprinkled in at just the right points to make the experience truly magical.”
— 原文 README

03

Agent 的四个部件：把“智能”拆成可测试的零件

作者把 Agent 还原成四个部件。理解这四个部件，比记住 12 条原则更重要，因为 12 条几乎都是它们的展开。

PART 1

Prompt

告诉模型怎么行为、有哪些“工具”。输出是描述下一步的 JSON。

PART 2

Switch

根据 JSON 的 intent 决定：执行、暂停、重试、升级人工。

PART 3

Context

累积的事件日志：用户消息、工具调用、结果、错误、人工响应。

PART 4

Loop

直到模型输出终止意图；但循环边界由你的代码控制。

python
initial_event = {"message": "..."}
thread = [initial_event]

while True:
    next_step = await llm.determine_next_step(thread)

    if next_step.intent == "done_for_now":
        return next_step.message

    if next_step.intent == "request_human_input":
        save(thread + [next_step])
        notify_human(next_step)
        return  # 暂停，等待 webhook 恢复

    result = await execute(next_step)   # 确定性代码
    thread.append(next_step)
    thread.append({"type": next_step.intent + "_result", "data": result})

从“循环”到“reducer”

如果把每个事件都写进日志，Agent 就可以看成一个 fold：

text
# 概念模型：Agent 是事件日志上的 fold
state_0 = initial_state()
state_1 = reduce(state_0, event_1)
state_2 = reduce(state_1, event_2)
...
state_n = reduce(state_{n-1}, event_n)

# 事件可以是：
#   user_message / llm_next_step / tool_result / error
#   human_input_requested / human_response / done

# 暂停 = 保存事件日志；恢复 = 从日志重建 state
# fork  = 复制前 k 个事件，得到一条新的分支
为什么这个视角有用：暂停 = 保存日志；恢复 = 重放日志；fork = 复制前缀；调试 = 看完整事件序列；UI = 把日志投影成人能读的界面。它把“Agent 状态”从框架内部拿出来，变成你自己的数据。
04

12 条原则：一张可筛选的工程清单

按“表示 / 上下文 / 运行时 / 协作 / 边界”分组。搜索匹配标题、英文名与正文；筛选只影响显示，不改变内容。

显示 12 / 12 条原则

01

自然语言 → 工具调用

Natural Language to Tool Calls

表示层

LLM 的职责是把模糊意图翻译成确定的 JSON 动作；执行交给代码。

原理

输入是自然语言，输出是 {intent, parameters} 这样的结构化对象；确定性代码用 switch 执行。模型不直接产生副作用，避免把“决策”和“执行”绑死。

反模式

让模型在自然语言里“顺便”执行；把 tool call 与内部函数一比一绑定；不校验参数就交给下游。

落地：定义窄 intent 联合类型；参数 schema 校验；未知 intent 走兜底；把执行结果写回事件流。
02

自己拥有提示词

Own your prompts

上下文层

不要把 prompt 外包给框架黑盒；prompt 是一等代码。

原理

Prompt 是应用逻辑与模型之间的主接口，应该像代码一样版本化、测试、评审、灰度。框架的 role / goal / personality 抽象方便起步，但会隐藏实际送进模型的 token。

反模式

Prompt 藏在框架内部；只改自然语言不改输出 schema；没有 prompt 版本与 eval。

落地：Prompt 与代码同仓；模板变量显式；记录 prompt hash；用 eval 驱动迭代。
03

自己拥有上下文窗口

Own your context window

上下文层

上下文不是“消息数组”，而是你为模型精心构造的工作集。

原理

LLM 是无状态函数；输入质量决定输出。上下文包括指令、RAG、历史、工具结果、记忆和输出格式。标准 chat 消息只是默认值，可以自定义 XML / YAML / 单条 user message 来提高信息密度。

反模式

无脑 append 全部历史；把原始错误、敏感数据全塞进去；指望模型自己忽略噪音。

落地：写事件→文本的序列化函数；按 token 预算裁剪；隐藏已解决的错误；过滤敏感字段；把“下一步”写进 prompt。
04

工具只是结构化输出

Tools are just structured outputs

表示层

工具调用不是魔法，就是模型输出一段可解析的 JSON。

原理

LLM 决定“做什么”，代码决定“怎么做”；同一个 intent 可以有同步、异步、审批、重试等不同执行策略。这层解耦让你能换执行器而不改模型。

反模式

认为模型“调用”了函数就必须执行同名函数；tool schema 与内部 API 一比一绑定；忽略 JSON mode / function calling / constrained decoding 的差异。

落地：用判别联合定义 next step；schema 校验；非法输出兜底；执行结果作为新事件。
05

统一执行状态与业务状态

Unify execution state and business state

运行时层

尽量让“走到哪一步”从事件日志里推导出来，而不是维护两套状态。

原理

Execution state（当前步、等待、重试）往往只是 business state（发生过什么）的元数据。统一成一份事件日志后，状态可序列化、可调试、可恢复、可 fork。

反模式

数据库一套状态、内存一套状态、框架一套状态；恢复时对不上；把 session id / 密钥塞进上下文。

落地：单一 thread / event log；事件类型显式；不能进上下文的东西放外部；用投影生成 UI。
06

用简单 API 启动 / 暂停 / 恢复

Launch/Pause/Resume with simple APIs

运行时层

Agent 是程序，就应该能启动、查询、暂停、恢复、停止。

原理

长任务、人工审批、外部事件都要求暂停；恢复不应依赖 orchestrator 深耦合。最关键的暂停点是在“工具选择”和“工具执行”之间。

反模式

用 while...sleep 阻塞等审批；进程重启就从头开始；暂停只存在内存里。

落地：start / status / pause / resume / stop API；持久化 thread；webhook 恢复；幂等键。
07

用工具调用联系人类

Contact humans with tool calls

协作层

把“问人”建模成一种结构化 intent，而不是特殊分支。

原理

模型默认要在“纯文本”与“结构化 JSON”之间做高 stakes 的首 token 选择。可以始终输出 JSON，用 request_human_input / done_for_now 表达意图，人类响应也是事件。

反模式

把人工审批写成 if/else 特例；不记录谁、何时、以什么方式批准；用自由文本解析审批结果。

落地：RequestHumanInput schema（问题、上下文、urgency、format、choices）；通知走 Slack / Email / SMS；响应写回 thread；权限与审计。
08

自己拥有控制流

Own your control flow

运行时层

不要让框架决定循环；用你自己的 switch / 状态机决定何时继续、暂停、升级。

原理

不同工具需要不同控制语义：同步继续、异步暂停、人工审批、重试、压缩、限流。拥有控制流才能插入这些策略，也才能在工具执行前拦截。

反模式

一个 while(true) 跑所有工具；把高风险操作和查询混在一个循环；没有最大步数 / 预算。

落地：按 intent 分支；同步 / 异步分离；最大步数、超时、预算；可中断；日志与 trace。
09

把错误压缩进上下文

Compact Errors into Context Window

上下文层

工具失败不是终点；把错误变成模型可读的事件，让它自我修复。

原理

好模型能读错误并调整下一次调用；但要限制连续错误次数，避免 spin。错误表示可以重构、裁剪、脱敏，不必把原始 stack trace 永久留在上下文里。

反模式

把完整 stack trace 永久塞进上下文；无限重试；错误后不重置计数器。

落地：error 事件 + 格式化；连续错误阈值（如 3）；超限升级人工；成功后折叠 / 清空错误；错误分类。
10

小而专注的 Agent

Small, Focused Agents

边界层

一个 Agent 只做一件事：3–10 步，最多约 20 步。

原理

任务越大 → 步数越多 → 上下文越长 → 越容易迷路。把 Agent 当作确定性 DAG 里的一个节点，而不是整个系统；LLM 只在需要判断的边界处出现。

反模式

一个 Agent 接管整个业务流程；用 prompt 让模型“记住所有规则”；把多 Agent 当规模化的默认答案。

落地：按职责拆；每个 Agent 有清晰输入 / 输出事件；用 DAG 编排；只在边界处用 LLM；监控步数与上下文。
11

从任何地方触发，去用户所在的地方

Trigger from anywhere, meet users where they are

协作层

让 Agent 从 Slack、Email、SMS、Webhook、Cron 触发，并回到同一渠道。

原理

用户不在你的 UI 里；Agent 要像数字同事一样出现在工作发生的地方。外部事件也是 thread 的输入，回复应走原渠道。

反模式

只做聊天框；要求用户登录你的后台；把触发渠道与 Agent 逻辑耦合。

落地：渠道适配器 → 统一事件；thread id 关联；回复走原渠道；身份 / 权限映射。
12

把 Agent 做成无状态 reducer

Make your agent a stateless reducer

运行时层

new_state = reduce(state, event)；Agent 是事件日志上的 fold。

原理

作者自己说这条“mostly just for fun”，是概念模型：把 LLM 调用、工具执行、人工响应都视为事件，状态由 reducer 计算。它让测试、回放、fork 变得自然。

反模式

把“无状态”理解成没有数据库；忽略工具副作用；不做幂等。

落地：事件溯源；纯 reducer + 副作用边界；幂等键；可回放；快照。
05

四个关键机制：这份指南真正的“原理”

12 条原则里，有四件事反复出现：上下文工程、暂停/恢复、事件溯源、Agent 边界。把它们吃透，剩下的都是组合。

5.1 上下文工程：不是“把历史拼起来”

原文的关键判断是：LLM 是无状态函数，上下文是输入；标准 chat 消息只是默认格式。你可以把整段历史压成 XML / YAML / 单条 user message，用更高的信息密度表达同一件事。

text
# 标准 chat 格式：每条消息一个 role，结构化信息被拆散
[
  {"role": "system", "content": "You are a deployment assistant..."},
  {"role": "user", "content": "Can you deploy the backend?"},
  {"role": "assistant", "tool_calls": [{"name": "list_git_tags", "arguments": "{}"}]},
  {"role": "tool", "name": "list_git_tags", "content": "{\"tags\": [...]}"}
]

# 自定义上下文：把“发生了什么”压成高密度的事件块
<slack_message>
  From: @alex  Channel: #deployments
  Text: Can you deploy the latest backend to production?
</slack_message>

<list_git_tags_result>
  tags:
    - {name: v1.2.3, commit: abc123}
    - {name: v1.2.2, commit: def456}
</list_git_tags_result>

what's the next step?

三个直接推论：信息密度（同样信息更少 token）、错误折叠（已解决的错误不必一直留在窗口里）、安全过滤（不该给模型的敏感字段在构造上下文时就删掉）。

5.2 暂停/恢复：最值钱的窗口在“选完工具、还没执行”

作者说这是他向所有 Agent 框架提的第一需求：能在工具选择和工具执行之间中断，恢复后继续。没有这个窗口，只有三种选择：阻塞 sleep、只让 Agent 做低风险研究、或者“yolo”直接执行。

python
# 工具选择与工具执行之间，是最有价值的暂停点
next_step = await llm.determine_next_step(thread)   # 模型说：deploy_backend(tag=v1.2.3)
thread.append(next_step)
save(thread)                                        # 持久化，进程可以退出

await request_human_approval(next_step)             # 发 Slack / Email
return                                              # 不执行，等 webhook

# 之后：webhook 带着 thread_id 回来
thread = load(thread_id)
thread.append({"type": "human_response", "data": {"approved": True, "by": "alex"}})
result = await execute(next_step)                   # 现在才真正执行
thread.append({"type": "deploy_backend_result", "data": result})

这也是 human-in-the-loop 能真正落地的前提：审批不是 UI 弹窗，而是事件日志里的一条 human_response；执行器在恢复后重新读取它，再决定是否产生副作用。

5.3 事件溯源：状态是日志的投影

Factor 5 与 12 的组合，本质是 event sourcing：不要同时维护“当前步骤”和“业务历史”两套状态；让 thread / event log 成为唯一事实来源。这样暂停、恢复、回放、fork、审计都变成同一套操作。

但要注意：“无状态 reducer”是概念模型，不是“没有副作用”。工具会发邮件、改数据库、部署服务；生产系统仍需要幂等键、去重、补偿事务和权限边界。作者自己也说 Factor 12 “mostly just for fun”。

5.4 Agent 边界：3–10 步，最多约 20 步

Factor 10 是整套方法的安全阀：任务越大，步数越多，上下文越长，模型越容易失焦。把 Agent 限制在窄领域，不是为了“架构好看”，而是为了让上下文可控、让 eval 可做、让失败可恢复。

原文也回答了“模型变强后还需要吗”：需要。模型变强可能让单个 Agent 处理更多步骤，但“有意识地控制范围、只在质量可维持的地方扩张”仍然是工程原则。

06

批判性评估：哪些是洞见，哪些是经验

这份指南的影响力很大，但它不是论文、不是 benchmark，也不是框架。读的时候要区分“可验证的机制”和“作者的经验判断”。

STRENGTHS

它说对了什么

  • 把 Agent 还原成软件：prompt / switch / context / loop 四部件，语言无关、框架无关。
  • 抓住生产化的真问题：暂停、审批、恢复、审计、错误恢复，而不是只追 benchmark。
  • 可增量落地：不必重写产品，可以把微 Agent 嵌进现有 DAG。
  • 与成熟工程范式对齐：事件溯源、工作流编排、幂等、可观测性都能直接复用。
LIMITS

它没有证明什么

  • 证据是经验性的：“100+ 创始人”和个人实践，不是对照实验；没有量化“用了 12 条就提升多少”。
  • 不是正式规范：12 条有重叠（5/6/8/12 都在讲状态与控制），边界并不正交。
  • 假设你能控制 prompt/context：托管 Agent API、闭源 Agent 产品未必给你这个权限。
  • 把复杂度转移了：微 Agent 让单个上下文变简单，但编排、持久化、幂等、权限会变复杂。
  • 人审有成本：审批延迟、审批疲劳、值班安排，都是产品问题，不是加个工具就能解决。
  • 时效性：仓库最近 push 在 2025-09；MCP、Agent SDK、托管运行时之后又演进了，例子会显得旧。

和常见方案对比

方案控制力上手速度最适合
全自主 loop低快demo、研究、低风险任务
Agent 框架中快快速原型、标准场景
12-Factor Agents高中生产级、需要审批/审计/恢复的产品
纯 DAG + LLM 节点最高慢流程稳定、强合规、强可观测
编辑判断：12-Factor Agents 最合适的定位不是“替代框架”，而是“框架之前/之后的设计检查表”。如果你已经有一个能跑的 Agent，它帮你找生产化缺口；如果你还没开始，它帮你避免把整个产品押在“无限循环”上。
07

落地路线：从一条窄流程开始

不要一次改造整个系统。选一个 5–10 步、有人审、可回放的流程，把 12 条原则压进去，再复制。

五步落地

  1. 选流程：找一条边界清晰、失败可恢复、确实需要 LLM 判断的流程（部署审批、工单分诊、内容审核）。
  2. 定事件：先把输入、intent、result、error、human response 定义成事件 schema。
  3. 拿回三件套：prompt 模板、context 构造器、switch/控制流，全部放进自己的代码。
  4. 加暂停与审批：在工具执行前落库、发通知、等 webhook；执行器要幂等。
  5. 加 eval 与回放：用完整 thread 做回归；记录步数、错误率、人工介入率、成本。

不建议的做法

  • 把 12 条当成“必须全上”的成熟度模型；先做 1/3/4/8 就能获得大部分收益。
  • 为了“agentic”而让模型做本可以确定性完成的事（见附录 13）。
  • 没有幂等和权限边界，就给 Agent 高风险写操作。
  • 用多 Agent 掩盖单个 Agent 的上下文问题。

附录：第 13 条——预取你确定需要的上下文

严格说它不是 12 条之一，而是“honorable mention”。但它很能体现整套方法的取向：能确定性做的，就别让模型多跑一轮。

原文的判断很直接：如果你已经知道模型大概率会调用工具 X，就直接把它需要的数据取好、放进上下文，让模型专注于“怎么用这些结果”，而不是先输出一个 list_git_tags 的 intent 再等一轮。

python
# 不要让模型先请求一个你几乎肯定需要的数据
git_tags = await fetch_git_tags()          # 确定性预取
thread.append({"type": "list_git_tags_result", "data": git_tags})

next_step = await determine_next_step(thread)
# prompt 里已经包含 tags，模型只需要决定 deploy 哪个 tag

“If you already know what tools you’ll want the model to call, just call them DETERMINISTICALLY and let the model do the hard part of figuring out how to use their outputs.”
— Appendix: Factor 13

边界：预取适合高频、只读、便宜的数据；如果数据贵、时效敏感、或模型不一定需要，保留工具调用更合适。它不是“把所有东西硬编码”，而是“别为了 agentic 而浪费一轮”。
