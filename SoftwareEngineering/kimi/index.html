01

怎么读这张图

43 个页面不是 43 个“模型”。把它们按职责分层，才能看出 Kimi 的开源策略；Mooncake 单列为组织外核心，避免与官方仓库统计混淆。

LAYER 1

模型权重

K3 / K2 / K2.5 / k1.5 / VL / Audio / Linear / Moonlight / Dev。决定能力上限，也决定部署门槛。

LAYER 2

架构与训练方法

MoBA、KDA、Attention Residuals、Muon。解释“为什么这一代更强/更便宜”。

LAYER 3

系统与工具

Mooncake、MoonEP、checkpoint-engine、FlashKDA、walle、batched-benchmark。把模型变成可服务、可训练的系统。

LAYER 4

Agent 产品

kimi-code、CLI、SDK、Rust 运行时、Zed/Zsh 集成。离用户最近的一层。

LAYER 5

评测与基准

PerceptionBench、WorldVQA、CombiBench、Kimina、Vendor Verifier。定义“什么叫好”。

LAYER 6

生态与组织

Cookbook、Koishi 插件、MoonPalace、Branding、Pages。降低接入与传播成本。

注意：本页把归档、迁移、纯元数据仓库也算进“全部”，因为问题问的是“所有项目”。如果你只关心可用的活跃项目，用下方筛选器看“活跃”，或直接读四条主线。
02

四条技术主线

把仓库按时间与依赖串起来，Kimi 的开源路线其实很集中。

LINE 1 · 稀疏 MoE 与长上下文

K2 → K2.5 → K3

1T/32B 的 K2 证明万亿 MoE 可训练；K2.5 加视觉与 256K；K3 用 KDA + AttnRes 把总参推到 2.8T、上下文推到 1M。配套是 MoBA（块稀疏）、Kimi Linear（KDA 验证）、FlashKDA（kernel）。

LINE 2 · Agent 产品化

kimi-cli → kimi-code

Python CLI 先跑通终端 Agent、MCP、ACP；kimi-code 用单二进制重做，加入视频输入、子 Agent、插件市场与 hooks；SDK / Rust / Zed / Zsh 把同一运行时铺到更多入口。

LINE 3 · 训练与推理系统

Moonlight → K2 MuonClip → Mooncake / MoonEP / checkpoint-engine

先解决优化器可扩展性，再解决万亿 MoE 的 serving、专家并行通信与权重热更新；FlashKDA、walle、batched-benchmark 补齐 kernel、结构化输出与压测。

LINE 4 · 评测与可信度

Vendor Verifier + 原子能力基准

K2VV/KimiVV 检查不同供应商的 toolcall 与精度；PerceptionBench/WorldVQA 把多模态能力拆成原子项；CombiBench/Kimina 覆盖形式化数学；Audio-Evalkit 统一音频评测。

05

方法与来源

数据

仓库清单、Stars、Forks、语言、许可证、创建/推送时间来自 GitHub REST API（orgs/MoonshotAI/repos），抓取于 2026-11-01。项目内容来自各仓库 README。

分类

6 个类别是编辑归类，依据仓库主职责，不是 GitHub topics。一个项目可能跨类（如 Kimi-Dev 既是模型也服务 Agent），这里取主要用途。

判断

“边界与注意”“生态关系”和主线叙述含编辑判断，已尽量与 README 事实分开。没有引用来源的数字不要当作官方承诺。

时效

Stars、榜单、许可证与模型版本都会变。归档/迁移状态以抓取日为准；使用前请回到仓库确认。

覆盖说明：MoonshotAI 组织显示 42 个公开仓库，本页覆盖全部 42 个，包括 1 个归档（kimi-cli）、2 个已迁移（kosong、pykaos）、3 个组织/站点类仓库。另加 1 个组织外核心项目 Mooncake（kvcache-ai），因为它的 README 明确写为 Kimi 的 serving platform。Mooncake 不计入 42 个官方仓库的统计，但单独有一页。其他外部依赖（Kimina Lean Server、flash-linear-attention）只在相关页面提及。
