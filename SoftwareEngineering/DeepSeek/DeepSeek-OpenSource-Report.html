04

十条观察

这一节是我对全量仓库的综合判断，不是对官方说法的复述。

  1. 开源的是“能跑得像”，不是“能训得像”

    权重 + 推理 demo 是常态，训练配方只以论文和拆散的 infra 仓库出现。真正被完整开源的是推理与系统能力，而不是预训练本身。

  2. 一条清晰的技术主线：MoE → MLA → MTP → DSA → Engram

    每一步都在压单位 token 的显存或算力，而且每一步都配了对应 kernel。架构和工程是同步发布的，这是 DeepSeek 最难被复制的地方。

  3. 开源周是分水岭

    2025-02 五天放出 FlashMLA、DeepEP、DeepGEMM、DualPipe/EPLB、3FS/smallpond，把训练系统拆成可复用积木；open-infra-index 解释了每块积木在生产里怎么用。

  4. 2026 年重心明显转向 Agent 与运行时

    harness、DeepInfer、recipe 三者合起来是“模型 → 可执行系统”的转向。权重不再是唯一的竞争面，协议、工具调用与运行稳定性变得同样重要。

  5. 国产硬件是第二条主线

    Ascend 版本覆盖 GEMM、EP、TopK、TileKernels、clangd、DeepInfer，已经不是“移植一个 demo”，而是完整栈。这在国内是差异化优势。

  6. 许可证总体友好，但边界要分清

    代码多为 MIT，infra 有 Apache-2.0，文档清单用 CC0；模型权重另有 Model License。Prover-V2、clangd-ascend、DeepEP-Ascend 等“Other / 未标注”的仓库，商用前必须单独确认。

  7. 成熟度差异极大，README 自己会说

    3FS / DeepGEMM / DeepEP / FlashMLA 是生产级；LPLB、Engram demo、dsh-superagent 是研究原型；harness 明说 developer preview。按仓库自述判断，别按 star 数判断。

  8. 停更也是信息

    V2 停在 2024-09、Janus 停在 2025-02、Coder 系停在 2025-11，对应的是架构或产品线的世代更替，不是项目失败。读旧仓库要看它被谁取代。

  9. 最能“拿走去用”的五块

    recipe（协议适配）、DeepJIT（JIT 缓存）、DeepSelect（TopK）、EPLB/LPLB（负载均衡）、DeepSpec（投机解码）。它们不绑定 DeepSeek 模型，迁移成本最低。

  10. 三条阅读路径，对应三种目的

    理解模型：V2 / V3 论文 + V3.2-Exp；理解系统：open-infra-index 再按图索骥；做产品：DeepInfer + recipe + harness。不要混着读。

DeepSeek-LLM

67B 稠密中英双语模型，2023 年 11 月发布，口号是 “Let there be answers”。

我的分析

  • 它确立了 DeepSeek 后来的发布范式：技术报告讲训练方法，仓库给权重和推理示例，训练代码不开源。
  • 数据侧值得看的是中英配比与去重策略；模型本身已经被 V2 之后的 MoE 路线取代。
  • 作为起点，它证明小团队用较少算力也能做出可用的 67B 基座，这个定位比架构细节更有史料价值。

风险 / 局限没有训练代码，无法复现训练过程；2024 年后基本停更。

DeepSeek-Math-V2

自验证数学推理模型，基于 V3.2-Exp-Base；在 IMO 2025、CMO 2024 达到金牌水平，Putnam 2024 为 118/120（scaled test-time compute）。

我的分析

  • 路线从“奖励最终答案”转向“验证推理过程”：先训一个可信 verifier，再用它当 reward model 训证明生成器。
  • 生成器变强后验证差距会拉大，所以它用更多验证算力自动标注难验证证明，反过来继续训 verifier。
  • 这是 test-time compute 的一个具体工程解，而不是又一个刷分模型。

风险 / 局限成绩依赖大规模测试时计算与未公开数据；仓库只给权重和评测产物。

Engram

Conditional Memory via Scalable Lookup：用 N-gram 查表给 LLM 增加一条稀疏轴；Engram-27B 在等参等 FLOPs 下优于 MoE 基线。

我的分析

  • 它把经典 N-gram embedding 现代化成 O(1) 查表，并给出神经计算与静态记忆之间的 U 型最优配比。
  • 确定性寻址让巨大的 embedding 表可以 offload 到 host memory，推理开销很小，这是工程上最值钱的一点。
  • TileKernels 里已经有 Engram 的融合 kernel，说明它不是纯论文，已经进了内部训练与推理。

风险 / 局限仓库 demo 把 attention / MoE 都 mock 了，只能看数据流，不能直接训练。

ICLR 2024，层次化 3D 生成 + bootstrapped diffusion prior，从单图生成 3D 资产。

我的分析

  • 它不是 LLM 主线，是团队早期在 3D 生成上的独立探索，说明 DeepSeek 的研究面比现在看到的宽。

DualPipe

双向流水线并行算法，用于 V3 / R1 训练中的计算-通信重叠。

我的分析

  • 把流水线做成双向调度，用反方向微批填掉 bubble，再和 EP / DP 组合成多维并行。
  • 仓库给的是调度算法与示意，不是可直接接入的训练框架。
  • 它和 profile-data 配套看，才能理解论文里 overlap 的数字怎么来的。

风险 / 局限强依赖集群拓扑与自研训练栈，通用性有限。

EPLB

专家并行负载均衡器，为 V3 / R1 的 MoE 训练与服务做专家复制与重排。

我的分析

  • 解决专家负载随 batch 漂移：先统计、再复制热点专家、最后重排到 GPU。
  • 纯 Python、层次化估计 + 贪心打包，代码短到可以一下午读完，是理解 EP 负载均衡的好入口。
  • 它的静态重排是 LPLB 动态优化的基线。

风险 / 局限只做静态 / 离线规划，不处理单 batch 内的瞬时不均。

LPLB

基于线性规划的 MoE 动态负载均衡器，单 SM 内点法 + cuSolverDx / cuBLASDx，早期研究阶段。

我的分析

  • 在 EPLB 的静态重排之上，对每个 batch 解一次 LP，把 token 沿冗余专家形成的边重新分配。
  • 它把“边容量 = 冗余专家本批承载量”讲得很清楚，是少见的把优化模型写明白的 infra 仓库。
  • 作者也承认：只平衡 token 数、不看 grouped GEMM 的非线性，极端情况下可能不如 EPLB。

风险 / 局限solver 约 100µs 开销；性能仍在评估，非生产组件。

ESFT

Expert-Specialized Fine-Tuning：只微调与任务相关的专家（EMNLP 2024）。

我的分析

  • 先用校准集给每个专家打任务相关性分数，再选 top-p 专家训练，省显存也少灾难性遗忘。
  • 这是 MoE 微调的高性价比做法，尤其适合多任务分别出 adapter 的场景。
  • 前提是你能观测路由；黑盒 API 模型用不了这套。

风险 / 局限任务分布漂移时专家选择会失效；依赖 DeepSeekMoE 结构。

DeepSpec

投机解码草稿模型全栈：数据准备、Draft 模型（Eagle3 / DFlash / DSpark）、训练与评测。

我的分析

  • 把草稿模型当独立模型认真训，而不是随手拿小模型凑；DSpark 还用置信度来调度验证长度。
  • 开源了 Qwen3-4B / 8B / 14B 与 Gemma-4-12B 的 checkpoint，复现路径清晰。
  • 代价是默认配置需要约 38TB target cache 和 8 卡单机，个人开发者只能缩小规模。

风险 / 局限数据管线重、存储需求大；换目标模型需重新训练。

DeepInfer

支撑 DeepSeek 线上服务的高性能推理框架，本次开源离线推理；支持 V4.1-Flash，NVIDIA SM100 与 Ascend 950。

我的分析

  • 基于 vLLM 改造，但把自家模型特性做进去了：DSpark 验证调度、SWA 有界重放、batch-invariant、确定性采样。

FlashMLA

Hopper GPU 上的 MLA 解码 kernel，支持变长序列与分页 KV（block 64）；H800 上 3000 GB/s、BF16 580 TFLOPS。

我的分析

  • MLA 的 KV 是压缩 latent，解码时既要算对又要吃满带宽，这个 kernel 把两件事同时做了。
  • 后续 PR 加入了 DSA 稀疏注意力 kernel，说明它已从单一 kernel 长成注意力 kernel 集。
  • 它是“模型架构创新必须配套 kernel”的最佳例证。

风险 / 局限绑定 Hopper 架构，API 随模型版本变动。

算子与推理引擎 生产级

DeepEP

首个开源 EP 通信库，支持 NVLink / RDMA、FP8 dispatch、训练与预填充高吞吐、解码低延迟。

我的分析

  • 把 MoE 的 all-to-all 拆成 dispatch / combine 两段，并针对训练、预填充、解码给三套 kernel。
  • FP8 原生 dispatch 让通信量和显存一起降，是 V3 / R1 能大规模 EP 的前提。
  • LPLB 可以直接从 DeepEP buffer 取实时负载，生态是打通的。

风险 / 局限需要 NVLink / RDMA 集群；版本与 CUDA / NVSHMEM 强绑定。

DeepGEMM

干净的 FP8 GEMM 库，支持 dense 与两种 MoE 布局，全 JIT，核心约 300 行。

我的分析

  • 用 JIT 在运行时按 shape 生成调度，少写模板也能在多数矩阵尺寸上超过手工调优。
  • “核心 300 行”是刻意的工程美学：可读、可改、可审计。
  • 后续承接了 DSA indexer 的 logit kernel，说明它在向模型专用算子集合演化。

风险 / 局限依赖 Hopper 与较新 CUDA；极端 shape 仍需自己调。

算子与推理引擎 生产级

DeepSelect

DSA 与 sampler 的 TopK 算子，支持 CUDA 与 Ascend，较 torch.topk 快 2–20 倍。

我的分析

  • 把 top-k 当带宽问题而不是浮点问题来优化，指标也用有效带宽，思路很正。
  • 针对 topk=512、vocab 128K 这类真实负载特化，支持变长行、stride 对齐与 NaN trap。
  • 它是 V3.2 / V4 / V4.1 稀疏注意力与采样器的共同底座。

风险 / 局限topk 上限 4096；Ascend 版只支持 bf16。

算子与推理引擎 基础设施库

DeepJIT

header-only C++20 JIT 运行时，面向 CUDA 与 Ascend，提供内存 / 磁盘 kernel 缓存。

我的分析

  • 把每个 kernel 库都要重写一遍的“编译-缓存-加载-启动”抽成公共层，减少重复造轮子。
  • 缓存键覆盖源码、include 树、编译器版本、编译选项、post-hook 哈希，设计比多数 JIT 工具严谨。
  • 它也暴露了一个真实问题：JIT 的正确性取决于你显式声明了多少隐式依赖。

风险 / 局限环境变量、传递头文件等隐式输入不会被自动发现；缓存目录必须可信。

TileKernels

用 TileLang 写的数十个 kernel：MoE 路由、Engram、量化、流形超连接（mHC）。

我的分析

  • 用 DSL 换可读性和跨后端：同一套 Python API 在 NVIDIA 与 Ascend 上自动选后端。

  • 它和 DeepGEMM 是两种哲学：一个是极致手写，一个是可维护的 DSL。

3FS

Fire-Flyer File System，面向 AI 训练 / 推理的分离式并行文件系统；180 节点 6.6 TiB/s，GraySort 3.66 TiB/min，单客户端 KVCache 40+ GiB/s。

口径与可信度

数据来源

仓库清单、star、许可证与最后更新时间来自 GitHub 组织仓库页（抓取于 2026-10-31）；“官方定位”是对各仓库 README 与 open-infra-index 的转述；论文链接指向各仓库给出的 arXiv 编号。

哪些是事实，哪些是判断

每张卡片的“官方定位”尽量贴事实；“我的分析”和“风险 / 局限”是我的推断与评价；成熟度分级（生产级 / 研究原型 / 内部组件…）也是我的判断，不是官方声明。

没有做什么
